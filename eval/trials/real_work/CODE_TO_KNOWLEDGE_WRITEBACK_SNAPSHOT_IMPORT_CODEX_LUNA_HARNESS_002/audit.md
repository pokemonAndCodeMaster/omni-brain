# 本地快照导入代码回写：第二轮 Luna 审计

## 当前结论

第二轮证明 `f29328b` 的通用修正确实改变了弱模型行为，而不是只改变检查结果。Luna 主动核验 `c51e232` 是 `ea10860` 的祖先，不再把固定报告误判为冲突；它完整保留 11 列 CSV 外部契约、18 列快照返回契约、13 键指标状态和导入模型，并真正更新了既有软件结构页。按同一套 24 个冻结问题评分，本轮从首轮 **17/24 提升到 20/24**。

候选仍不能发布。C01、C02、I02、S02 四项关键问题未通过：来源页残留了与当前 commit 冲突的旧句子；用户看不到可复制执行的 CLI 命令；数据库公共能力没有吸收新消费者；固定日期锚定没有与产品能力分开。工作台的 `publish_ready` 和四个 `check-unit` 通过没有发现这些语义问题。

本轮状态为 **materially improved but content not certified**。同一用例到此停止调优，避免把 Skill 拟合成快照导入专用提示词；剩余通用原则应在 Harness 中收束，并由相邻新用例验证。

## 仍未达到的内容能力

### 1. 来源页存在直接自相矛盾

来源页已经固定到 `ea10860`，并在后文说该提交包含 CSV 导入；但第 23 行仍保留父版本的句子：

> SQL 性能优化与 CSV 导入位于其他实验分支，不能从本 commit 推断已经合入。

这与同页第 35、44 行和系统页的当前事实冲突。模型更新了版本字段和新增段落，却没有逐句复核父页面中与旧 commit 绑定的状态声明。C01 因此失败。

### 2. 用户无法从知识中直接运行命令

候选反复出现 `snapshot-import preview/apply`，但没有保留可执行入口：

```bash
.venv/bin/python -m src.cli snapshot-import preview <file.csv>
.venv/bin/python -m src.cli snapshot-import apply <file.csv> --confirm-token '<token>'
```

也没有把 preview 与 apply 的完整返回结构放在命令旁。读者知道“有两个动作”，仍不能从项目根立即使用，C02 失败。

### 3. 数据库公共能力没有吸收新的真实消费者

模型在软件页解释了 `PGConnector.transaction`，但 `knowledge/capabilities/database-access.md` 相对父知识完全未改。用户要求新事实进入公共数据库能力，冻结问题 I02 也明确要求；本轮没有登记“现有页已充分、无需修改”的依据，更没有增加导入如何消费事务、锁和 schema 的实例。I02 失败。

### 4. 固定验证准备被省略

报告明确把动态 14 天种子窗口平移到 `2026-07-13..2026-07-26`，并说明日期锚定 SQL 只是重放准备。候选只写“14 天固定数据”，没有说明日期移动，更没有排除它是产品能力。S02 失败。

## 本轮后的工程判断

当前 `ingest-knowledge` 已从“能生成结构正确的候选”推进到“弱模型通常能形成高价值代码知识”，但尚未稳定到可无人审查发布。成熟度应保持：

- 工作区隔离与父知识保护：`verified@multiple-slices`；
- 固定证据发现与提交关系：`verified@snapshot-import-slice`；
- 外部契约与软件职责内化：`verified@snapshot-import-slice`；
- 既有知识语义融合：`implemented`，仍会遗漏旧状态矛盾与公共能力影响；
- 可运行操作知识：`implemented`，尚未稳定保留 copy-paste 入口；
- 完整代码变化回写：`implemented / human review required`，尚未达到 `verified@slice`。

下一版只应收束三条一般完成标准：用户要执行时保留完整可运行入口；更新已有页面时复核所有与旧版本绑定的当前态句子；用户点名或代码变化真实影响的既有公共能力必须更新或明确证明无需改。固定报告中的夹具/日期/环境变换也应作为证据边界逐项处理。不要再运行同一快照题；在相邻真实代码变化中验证这些原则是否泛化。
