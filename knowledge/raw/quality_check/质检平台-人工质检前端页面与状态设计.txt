# 质检平台人工质检前端页面与状态设计

← 总入口：[[质检一站式平台人工质检模块整体架构]]。API 契约：[[质检平台-API契约与前端交互设计]]。权限：[[质检平台SSO鉴权接入方案]]。

## ① 组件概述

人工质检前端（Vue3）承担"选择范围—预览—确认—执行—回查"完整状态闭环的页面与交互职责，位于质检平台整体架构的**前端层**，通过 HTTP 调用 [[质检平台-API契约与前端交互设计]] 定义的端点，并依据 [[质检平台SSO鉴权接入方案]] 的模块等级控制按钮可见性。

## ② 架构结构

### 前端目录结构（计划目标）

```text
src/frontend/src/
├── features/manual-qc/
│   ├── api/
│   │   ├── acceptance.ts       # 验收相关 API 调用（preview/execute/stats）
│   │   ├── personnel.ts        # 人力相关 API 调用
│   │   └── client.ts           # axios 实例与拦截器（feature 内单例）
│   ├── components/
│   │   ├── AssignView.vue      # 验收分配页（含 preview→execute 状态机）
│   │   ├── StatsView.vue       # 验收统计页（筛选+概览+趋势+明细）
│   │   ├── ExecuteView.vue     # 通过/打回页（PENDING→确认→执行→回查）
│   │   ├── PersonnelOverview.vue
│   │   ├── AnnotatorProfile.vue
│   │   ├── AcceptorList.vue
│   │   └── GroupManager.vue
│   ├── stores/                  # Pinia store（跨页面共享筛选态）
│   │   └── acceptanceFilter.ts
│   ├── types/                   # 与 OpenAPI 对齐的 TS 类型
│   │   └── schema.d.ts
│   └── routes.ts               # feature 路由声明
└── shared/                      # 至少两个独立 feature 复用后才上提
    └── ...
```

模块内部组件先留在 feature 内；只有至少两个独立 feature 复用后才上提到 `shared/`。


组件树说明：路由根 `/manual-qc` 下分 `acceptance/` 与 `personnel/` 两大分支；所有 API 调用集中在 feature `api/` 目录，Vue 组件不直接创建 axios 实例，统一通过 `client.ts` 单例与后端通信。

### 分配页状态机时序图（Mermaid sequenceDiagram）

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant V as AssignView.vue
    participant API as api/acceptance.ts
    participant BE as Backend

    U->>V: 编辑筛选与策略
    V->>V: state = idle
    U->>V: 点击 Preview
    V->>V: state = previewing（锁定表单）
    V->>API: POST /acceptance/assignment/preview
    API->>BE: 请求配额与 task_ids
    BE-->>API: summary + task_ids + warnings
    API-->>V: preview 响应
    V->>V: state = preview_ready（展示 Good/Bad、scene、人员分布、警告）

    U->>V: 修改筛选或策略
    V->>V: 旧 preview 失效，回到 idle

    U->>V: 点击 Execute
    V->>V: state = executing（锁定表单，提交 preview task_ids）
    V->>API: POST /acceptance/assignment/execute
    API->>BE: 按 task_ids 执行分配
    BE-->>API: success_count/skipped_count/failed_count
    API-->>V: 执行结果
    V->>V: state = executed（展示请求/成功/跳过/失败数量）

    U->>V: 点击 Refresh
    V->>V: state = refreshing
    V->>API: POST /acceptance/stats/refresh + GET /acceptance/stats
    API-->>V: 实际 acceptance_allocated
    V->>V: state = preview_ready（更新实际状态）
```

时序图说明：分配页共 6 个状态（idle → previewing → preview_ready → executing → executed → refreshing）。关键约束：修改筛选或策略后必须使旧 preview 失效，防止用户看着旧表格执行新参数；execute 原样携带 preview 的 task_ids，不重新随机采样。

## ⑤ 详细设计展开

### 初衷

前端不是把旧脚本按钮搬到网页，而是让用户看清"选择范围—预览—确认—执行—回查"的完整状态。由于外部 Delta 操作可能部分失败或延迟，页面不能只显示一个同步成功弹窗。

### 页面结构

```text
/manual-qc
├── acceptance
│   ├── assign       验收分配
│   ├── stats        验收统计
│   └── execute      通过/打回
└── personnel
    ├── overview     人力概览
    ├── annotators   标注员画像
    ├── acceptors    验收员列表/抽检统计
    └── groups       分组管理
```

### 页面结构（2026-07-05 新版，合并自源仓库 A3）

> 业务主线演进为"以数据集交付任务为主线"：交付中心负责完整进度、风险和行动项；验收中心负责验收分配、监控、分析、结论和返修；人力页面负责人员与分组。新版页面结构如下：

```text
/manual-qc
├── overview                     人工质检总览（模块根路由默认落点）
├── deliveries                   交付中心
│   └── :deliveryId              单交付任务详情
├── annotation                   标注中心
│   └── :deliveryId              单需求标注工作区
├── acceptance                   验收中心总览
│   └── :deliveryId              单需求验收工作区
└── personnel                    人力与分组
    ├── overview                 人力概览
    ├── annotators               标注员画像
    ├── acceptors                验收员列表/抽检统计
    └── groups                   分组管理
```

总览详细设计见 [[人工质检总览信息架构]]；交付中心见 [[质检平台-人工质检交付中心前端设计]]；标注中心见 [[质检平台-人工质检标注中心前端设计]]；验收中心见 [[质检平台-人工质检验收中心前端设计]]。

### 页面组织原则（2026-07-05 新版，合并自源仓库 A3）

- 交付中心默认展示表格，时间轴是同一集合的第二视图。
- 所有人使用同一 OneTrack 页面，不显式切换"管理者/日常运营"身份。登录权限自动决定路由、面板、按钮和数据范围；"全部/我的/我关注的/保存视图"只是业务筛选，不是角色模拟器。
- 点击一级"人工质检"先进入总览，用需求接纳、近期交付倒排、标注健康、验收健康和完成盖戳帮助团队抓主要矛盾；完整字段在交付中心维护。
- 交付详情沿阶段组织内容，不用一个巨型表单承载需求、规则、生产、标注和验收。
- 验收中心默认按数据集交付任务聚合，task 明细按需下钻。
- 行内只突出一个下一动作，减少同一行堆叠大量按钮。
- 页面切换必须保留筛选、列配置、分页、展开和滚动位置。

### 分配页状态

1. `idle`：编辑筛选与策略。
2. `previewing`：请求配额和 task_ids。
3. `preview_ready`：展示 Good/Bad、scene、人员分布和警告。
4. `executing`：锁定表单，提交 preview task_ids。
5. `executed`：展示请求/成功/跳过/失败数量。
6. `refreshing`：回查实际状态，更新 `acceptance_allocated`。

修改筛选或策略后必须使旧 preview 失效，防止用户看着旧表格执行新参数。

### 统计页

- 筛选：日期、项目、scene、组、标注员、题型。
- 概览：提交量、实际验收分配量、完成量、Good/Bad/整体通过率。
- 趋势：按日期聚合个人最小行。
- 明细：默认个人最小行，用户切换后端聚合的组级/scene 级视图。
- 刷新：明确显示 `computed_at`，避免把延迟数据误认成实时数据。

统计页只读用户也可访问；触发刷新需要 OPERATE。

### 通过/打回页

- 先显示验收完成度，未满足前置条件时结论为 PENDING，不展示可执行按钮。
- 展示规则名称、阈值、Good/Bad/整体通过率和自然语言原因。
- 执行前二次确认操作范围和 task 数量。
- 执行后展示即时结果，并允许回查最终状态。

通过/打回属于最高业务权限，仅 EXECUTE 可操作。

### 人力页面

- 概览：项目、供应商、角色和未进组人数。
- 标注员：项目、组、等级、单价、提交量、通过率、风格标签。
- 验收员：供应商、当前状态和后续抽检一致率。
- 分组：调组前后值、操作者和未进组预警。

人员只能属于一个当前项目；修改项目或组必须刷新相关列表并写操作日志。

### 权限展示

| 等级 | 前端行为 |
|---|---|
| NONE | 不显示模块入口 |
| VIEW | 可看筛选、统计、preview，不显示写按钮 |
| OPERATE | 可刷新统计、执行验收分配 |
| EXECUTE | 在 OPERATE 基础上可通过/打回 |
| MANAGE | 可编辑人员和分组 |

前端权限只用于交互；安全边界仍在后端。

### 状态放置原则

- 页面筛选、弹窗、当前 preview 用组件本地状态。
- 跨验收三个页面共享的日期/scene 筛选在确有复用后放 Pinia。
- API 调用集中在 feature `api.ts`，Vue 组件不直接创建 axios 实例。
- TypeScript 类型与 OpenAPI 对齐，禁止直接照抄数据库列形成第二套隐式契约。
