# 读者优先的知识表达

本参考只在形成或重构**用户可见的知识入口、领域全貌、规范知识页和产品视图**时读取。它规定判断方法，不要求所有页面长成同一种模板。

## 1. 先确定页面在阅读链中的责任

写作前用一句话回答：读者从哪里进入本页，读完能理解或完成什么，下一步会去哪里。一个页面只承担一个主要责任：

- **总入口**：展示知识范围、层级、默认阅读顺序、任务快捷入口和覆盖边界；
- **领域全貌**：说明领域为什么存在、有哪些业务模块、模块怎样衔接和当前知识覆盖；
- **专题总览**：说明专题在上级流程中的位置、完整主线、内部知识结构和深入顺序；
- **专题正文**：完整解释一个可独立维护的业务、数据、规则或软件主题；
- **产品视图**：为一种稳定用户目标选择和排序规范页，不复制规范事实；
- **来源记录**：保存依据、版本和定位，不作为第一次学习的默认路线。

如果两个章节都在回答同一个问题，合并它们；如果一个章节同时承担全貌、专题细节和来源审计，拆分责任。

## 2. 使用自顶向下的页面主线

用户可见页面默认使用下面的认知顺序，只有读者任务确实不同才调整：

1. **本页导航**：长页面先给可点击大纲，短页面可以省略；
2. **概览**：明确主题是什么、本页包含什么、按什么逻辑展开、当前适用边界；
3. **全貌或主线**：先呈现完整结构、流程或核心关系；
4. **分层细节**：沿业务过程、对象关系、数据变化或软件调用逐层展开；
5. **覆盖与未知**：按相同维度并列已经覆盖、仍需补充和缺口影响；
6. **继续阅读或行动**：说明下一篇、直接事实源或责任动作；
7. **引用**：最后提供追溯入口。

章节标题使用稳定、专业、可预测的名词短语，例如“验收业务流程”“数据状态变化”“当前实现边界”。不要把正文第一句话、提问句或“图怎么读”“先看什么”等口语直接当标题。

每个一级到三级章节开头先说明以下内容中的必要部分：本节作用、核心判断、展开维度、与上一节的关系。不要无缘无故抛出一句事实。

## 3. 让段落的作用和重点可见

- 一段只完成一个表达任务。较长章节用 `**概述：**`、`**业务含义：**`、`**输入：**`、`**处理：**`、`**输出：**`、`**边界：**`、`**结论：**` 等贴合内容的标签标明段落作用；标签后使用冒号。
- 标签不是固定字段清单。短段落语义已经明确时不强加标签，同一章节也不要机械重复“概述”。
- 只加粗决定理解或行动的**关键词、关系、限制和短结论**，不只加粗标签，也不把整句、整段全部加粗。
- 多项并列内容使用列表；有先后关系时使用编号；有相同比较维度时使用表格。不要把本可扫读的并列信息压成一个长段落。
- 开头先给概览，再展开细节，结尾只在需要收束判断或过渡时增加结论，不机械为每段补一句总结。

## 4. 让表达形式匹配信息关系

| 信息关系 | 优先形式 | 必须补足的信息 |
|---|---|---|
| 同类对象按相同维度比较 | 表格 | 维度一致；未知直接标明；单元格内容多时用 `<br>` 分点 |
| 有明确先后、分支或返工 | 流程图 + 说明表 | 每步输入、输出、处理、异常和下一步 |
| 上下级、包含或知识层级 | 树或分层图 + 导航表 | 每层职责、粒度和下钻入口 |
| 跨对象调用或消息顺序 | 时序图 + 调用表 | 调用主体、数据变化、副作用和失败边界 |
| 对象、状态或类之间的关系 | 关系图/类图 + 解释表 | 对象职责、关键字段、关系含义和现实范围 |
| 单一结论或边界 | 短段落或列表 | 依据、适用范围和不能推出什么 |

图只回答一个主要问题。邻近内容补充图中难以直接表达的输入输出、职责、数据变化、规则、异常和现实边界；不要把图上的节点换成句子再复述一次。

标准 Markdown 表格不保证列宽。优先通过合理列数、精炼但完整的单元格和结构化分点提高可读性；不要为固定列宽引入 HTML/CSS，也不要仅为视觉宽度拆散本应内聚的表格。

## 5. 知识入口和领域页的特殊要求

### 总入口

- 大纲、知识地图和默认阅读顺序合并为一套主线，不再分别维护“第一次学习”“按主题浏览”等近义路线；
- 任务快捷入口只是缩短查找路径，不创建第二套分类；按用户目标分组，指向最小充分的规范页；
- 已覆盖与待补内容按领域或知识层级并列，说明缺口影响；
- 来源、变更日志和后台状态放在维护区，不混入默认学习路线；
- 不向普通读者暴露批次号、候选代号、父版本、摄入状态字段等过程术语。

### 领域全貌与专题总览

- 先说明所有直接业务模块及其职责，再说明它们怎样串成端到端过程；不要因为某个子模块材料更丰富就直接跳到它；
- 业务模块是能够独立承担业务结果的职责单元，不是流程步骤、角色、数据对象或软件层。先列全直接模块，再画流程；若材料只足以确认部分模块，应在同一位置显式标明覆盖缺口，不能用材料最丰富的子域替代全貌；
- 模块、角色、数据对象和技术层次不要混成同一层；
- 同类模块优先用一张同维度表格呈现职责、输入、输出、协作和知识深度；关系可在结构图及表格中表达，不为了“讲关系”硬造独立章节；
- 深入顺序要体现知识层次或业务依赖，例如“业务流程 → 规则与数据 → 软件实现 → 现实核验”，不要把粒度不同的页面平铺成列表。

## 6. 充分内化而不丢失信息

- 引用只证明来源，不能替代正文。不能把关键机制压缩成一两句话后让读者自行回原料寻找；
- 保留会改变理解、决策、实现或验证的对象、字段、步骤、算法、条件、异常、责任和边界；
- 删除的只能是重复叙述、摄入过程噪声和不会改变理解的枝节，不能为了“更易读”静默缩短事实；
- 区分当前实现、当前业务决定、目标设计、历史做法、冲突和未知，并把这些状态写在相关结论附近；
- 同一核心定义只在一个规范页维护，入口和视图使用标准 Markdown 相对链接。链接文本应说明目的，不能只写“详见”。

## 7. 把未知变成可处理的问题

未知和冲突不要平铺成长清单。按业务模块或知识维度分组，并尽量说明：

| 问题 | 当前已知 | 缺少的直接证据 | 影响 | 责任方或下一动作 |
|---|---|---|---|---|

只在这些维度确实适用于同组问题时使用表格。问题很多时先给分类和优先级，再下钻细节；已经被新证据解决的问题从“当前未知”移除或改为带时间范围的历史记录。

未知与冲突较多时，页面先给一张总览，至少让读者看出**问题类别、优先级、影响范围和责任动作**；随后按业务、数据、软件运行、人员或公共能力等真实维度展开。每个问题要么在总览中拥有完整处理信息，要么在下钻章节中说明当前已知、冲突/缺口、影响、所需证据和责任方；不能只平铺问句或把所有证据集中到文末。

## 8. 用业务主线解释软件，而不是展示方法名

- 软件页以一个真实业务动作开篇，先写用户目的、输入、成功输出、失败结果和副作用，再进入对象、代码、调用和数据转换；
- “逻辑视图、开发视图、进程视图、物理视图”以及设计模式名称只在它们本身是读者目标时出现。默认把章节命名为“核心对象与职责”“代码结构与依赖”“一次调用过程”“运行边界”等业务可理解的结果；
- 结构图、类图和时序图是解释手段，不是章节主线。每种图都要由邻近内容回答模块为什么这样协作、数据怎样变化、失败在哪里，以及一次真实修改会影响哪里；
- 评价软件设计时，说明当前组织让哪类业务变化更容易、哪里会形成耦合，以及源码依据。不要用“用了某模式”“符合 4+1”代替设计判断。

## 9. 完成前的读者检查

从实际入口开始，不依赖摄入聊天和原始材料，逐项确认：

1. 第一次进入能否在一分钟内说出页面主题、结构、重点和适用边界；
2. 章节顺序是否形成一条主线，标题与正文是否回答同一个问题；
3. 图、表、列表和段落是否与信息关系匹配；
4. 同类内容是否按统一维度呈现，输入输出和上下游是否清楚；
5. 关键事实和技术细节是否已内化，链接是否只承担导航和追溯；
6. 过程黑话、版本噪声和重复导航是否已从用户视图移除；
7. 已知、未知、冲突、影响和下一动作是否能被直接识别；
8. 所有标准 Markdown 链接是否可从当前文件正常跳转。

未通过哪一项，就只修对应的内容、结构或视图层；不要为通过检查增加新的后台文件或复制知识。
