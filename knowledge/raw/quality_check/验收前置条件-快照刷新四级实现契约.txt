**时序图说明**：
- DAG 每 30 分钟触发，构造依赖链（PgConnector → LabelTaskRepository/SnapshotRepository/PersonnelRepository → SnapshotService）后调用 `refresh_snapshot`。
- 阶段一：`SnapshotService` 通过 `LabelTaskRepository.fetch_tasks_raw` **一次查全量**任务（含 behavior_status），`task_screener=None` 不加单人过滤（快照需全量）。**直连原始表，不依赖中间表，也不依赖 t_text_label_task 中间层**。
- 阶段二：`_aggregate_by_min_unit` **单遍历双累加**，每行同时累加标注指标（每行）和验收指标（仅 `task_status IN (67,68,69,70)`，验收是标注的子集）。`_prepare_row_context` 提取公共上下文并缓存。
- 阶段三：`_enrich_with_personnel` 将 task_screener（工号）**直接写入** employee_id（无需映射 t_personnel.id），并从 t_personnel 查当前组（`WHERE leave_date IS NULL`，SCD Type2）写入 group_name。`project_name` 从 `task_name`（含前缀）推断，**非 scene_name 短名**（见 [[PF-Scene短名误匹配项目前缀]]）。
- 阶段四：`upsert_many` 批量 UPSERT，UPDATE SET **仅含统计列**，严禁含 execution/confirmed_*/executed_*/good_conclusion/bad_conclusion 字段（边界情况1）。
- 范式细节详见 [[SYN-SQL精简与快照单遍历双累加范式]]。

## ⑤ 详细设计展开

### 1. 核心目标与复用策略

**核心目标**：实现统计快照表 `t_qc_daily_snapshot` 的定时刷新机制——每 30 分钟从 Delta 原始表聚合标注进度与验收结果，UPSERT 写入快照表，同时匹配 `t_personnel` 当前组别信息冗余写入 `group_name`。

**复用与熵减策略**：
- 复用 Airflow DAG 调度模式（`src/data_check/dags/` 既有模式：PythonOperator + max_active_runs=1 + dagrun_timeout + wrapper_failure_callback）
- 复用 `PgServer` 数据库连接（统一 psycopg2 路径，弃用 HiveConnector 双轨）
- 复用 `AppGy1Model.get_pass_rate_info()` 的聚合 SQL 业务逻辑（迁移到 Repository 层重新实现，参数化）
- 复用 `t_personnel` 人力管理表（migration 依赖已设计）
- **避免过度设计**：不引入 ORM（遵守 Repository 设计规范），不引入中间表，不引入异步任务队列

**全局约束**：
- 性能：单次刷新覆盖最近 4 天数据（参照旧版分片策略），UPSERT 批量执行
- 并发安全：DAG `max_active_runs=1`，`dagrun_timeout=28min`
- 时区：所有时间按 `Asia/Shanghai` 处理
- DDL 兼容基线：PostgreSQL 10+（禁 identity/generated column/NULLS NOT DISTINCT）
- migration 顺序：`V20260630_01__create_personnel_and_permission_tables.sql` 必须先于 `V20260630_02__create_qc_daily_snapshot_table.sql` 执行

### 2. 数据流详图

```
Airflow DAG (每30min)
  └→ SnapshotService.refresh_snapshot(stat_date_range)
       ├→ Step1: _fetch_all_tasks
       │    └→ LabelTaskRepository.fetch_tasks_raw(start, end, task_screener=None)
       │         └→ SELECT FROM delta.ods_t_label_screening_task_datalake + sdobject(分批查)
       │              WHERE task_creator ANY + task_name LIKE OR + to_review_time 范围 + del_flag=0
       │              无 task_status 过滤（Python 层做），无 LATERAL
       ├→ Step2: _aggregate_by_min_unit (单遍历双累加)
       │    └→ 1 个 for 循环遍历 List[TaskRawRow]
       │         每行: _prepare_row_context 提取公共上下文 (stat_date/employee_id/scene_name/project_name/is_good/behavior_status) + 缓存
       │         标注分支: 每行累加 annotation_total/submitted + good/bad/option
       │         验收分支: if task_status IN (67,68,69,70): 累加 acceptance_completed + good/bad_completed + good/bad_passed
       ├→ Step3: _build_raw_rows (从 agg dict 构造 raw_rows)
       ├→ Step4: _enrich_with_personnel
       │    └→ PersonnelRepository.get_current_groups(employee_ids)
       │         └→ SELECT employee_id, current_group, project_name FROM t_personnel
       │              WHERE employee_id IN (...) AND leave_date IS NULL  -- SCD Type2 当前有效行
       │    └→ task_screener(工号) 直接写入 employee_id（无需映射 t_personnel.id）
       │       group_name 从 t_personnel 查当前组冗余写入
       │       project_name 从 task_name（含前缀）推断，非 scene_name 短名（见 [[PF-Scene短名误匹配项目前缀]]）
       └→ Step5: _persist
            └→ SnapshotRepository.upsert_many(merged_rows)
                 └→ INSERT INTO t_qc_daily_snapshot ... ON CONFLICT (stat_date, scene_name, group_name, employee_id)
                    DO UPDATE SET 仅统计列（含 project_name/option_annotation/good_completed/bad_completed），
                    严禁含 execution/confirmed_*/executed_*/good_conclusion/bad_conclusion
```

> 🔄 **范式重构（TAG 20260711_160000）**：`refresh_snapshot` 由 150 行超大函数拆为 5 个步骤函数（body ≤ 30 行）；双查询 + 双遍历改为单查询 + 单遍历双累加；`__init__` 改为无参数内部自建依赖。详见 [[SYN-SQL精简与快照单遍历双累加范式]] 范式二/三/四。

* **目标文件**：`src/manual_qc/snapshot/snapshot_service.py`、`src/manual_qc/snapshot/factory.py`
* **接口签名**：

```python
@dataclass
class SnapshotRow:
    stat_date: date
    scene_name: str
    group_name: str
    employee_id: str          # VARCHAR(64)，原 annotator_id: int 改为工号字符串
    project_name: str         # 由 task_name 前缀映射（非 scene_name 短名，见 [[PF-Scene短名误匹配项目前缀]]）

    annotation_submitted: int
    option_annotation: dict   # 各选项标注数量
    acceptance_allocated: int
    acceptance_completed: int # 原 acceptance_submitted 改名
    good_allocated: int
    good_completed: int       # 新增
    good_passed: int
    bad_allocated: int
    bad_completed: int        # 新增
    bad_passed: int
    option_acceptance: dict   # 结构增强，含 allocated/completed/passed/conclusion

class SnapshotService:
    def __init__(self):
        """无参数，内部自建 LabelTaskRepository / SnapshotRepository / PersonnelRepository。"""
        ...

    def refresh_snapshot(self, stat_date_range: tuple[date, date]) -> int:
        """编排 5 个步骤函数，返回 UPSERT 影响行数。"""
        tasks = self._fetch_all_tasks(stat_date_range)      # Step 1: 查全量任务
        agg = self._aggregate_by_min_unit(tasks)             # Step 2: 单遍历双累加
        raw_rows = self._build_raw_rows(agg)                 # Step 3: 构造 raw_rows
        rows = self._enrich_with_personnel(raw_rows)         # Step 4: 人员合并
        return self._persist(rows)                           # Step 5: 持久化
```

| 步骤函数 | 职责 | 关键约束 |
|---------|------|---------|
| `_fetch_all_tasks` | Step 1：调用 `fetch_tasks_raw(start, end)` 查全量任务 | 不传 task_screener（快照需全量） |
| `_aggregate_by_min_unit` | Step 2：单遍历聚合标注+验收指标 | 1 个 for 循环；`_prepare_row_context` 提取公共上下文并缓存；标注分支每行累加，验收分支仅 `task_status IN (67,68,69,70)` 累加 |
| `_build_raw_rows` | Step 3：从 agg dict 构造 raw_rows dict 列表 | 字段对齐 UPSERT 模板 |
| `_enrich_with_personnel` | Step 4：人员合并，task_screener→employee_id + group_name 查当前组 | PersonnelRepository 查询含 `WHERE leave_date IS NULL`（SCD Type2） |
| `_persist` | Step 5：`upsert_many` 持久化 | UPDATE SET 仅统计列，严禁含 execution/confirmed_*/executed_*/good_conclusion/bad_conclusion |

* **契约定义**：
  * **输入前置条件**：`stat_date_range` 的 start_date <= end_date，日期范围不超过 7 天
  * **输出后置条件**：返回实际 UPSERT 的行数；`t_qc_daily_snapshot` 中该日期范围的统计列已刷新，执行字段（execution/confirmed_*/executed_*/good_conclusion/bad_conclusion）未被动
  * **副作用**：通过 Repository 写入 `t_qc_daily_snapshot`
  * **验证规格**：
    - **验证目标**：单遍历双累加正确性、project 映射正确性、人员匹配正确性、空数据处理、`refresh_snapshot` body ≤ 30 行
    - **验证入口**：`tests/manual_qc/test_refresh_snapshot_e2e.py`、`tests/manual_qc/test_snapshot_jsonb_refresh.py`
    - **预期结果**：raw 数据正确聚合为 SnapshotRow；task_name 正确映射 project_name（**非 scene_name**）；task_screener 直接写入 employee_id；无提交的标注员不产生快照行
* **实现约束**：
  - **禁止**在 Service 层拼接 SQL（全部通过 Repository）
  - `__init__` **无参数**，内部自建 `LabelTaskRepository` / `SnapshotRepository` / `PersonnelRepository`；`factory.py` 的 `build_snapshot_service` 不传参调用 `SnapshotService()`
  - `_aggregate_by_min_unit` **单遍历双累加**：1 个 for 循环，每行同时累加标注指标（每行）和验收指标（仅 `task_status IN (67,68,69,70)`，验收是标注的子集）
  - `_prepare_row_context` 提取 `stat_date / employee_id / scene_name / project_name / is_good / behavior_status` 公共上下文，结果缓存到 agg dict，避免重复调用 `_map_project_name` / `is_good_behavior` 等纯函数

  - DAG 内**禁止**业务逻辑，仅组装依赖并调用 `StatService.refresh_snapshot()`
  - 依赖注入：DAG 内构造 `PgConnector` → `SnapshotRepository` / `PersonnelRepository` → `StatService`
