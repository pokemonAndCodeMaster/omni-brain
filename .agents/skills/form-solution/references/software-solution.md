# 复杂软件方案的审查结构

本参考只用于跨模块、跨层或公共能力的软件方案。目标是让审查者先理解需求，再理解系统中的变化；不是提前写实现报告。

## 顶部入口

标题下说明：

- **审查对象：** 这次要形成什么方案；
- **当前状态：** R1 待审、R1 已通过/R2 待审，或 R2 已通过；
- **怎样审查：** 从当前开放的 R 开始，回复编号和意见；前序不通过时后续暂停；
- **内容导航：** 背景、需求、方案和当前开放的审查点。

不要在顶部写模型、评分、门禁或实验术语。

## R1：需求

推荐顺序：

1. 背景与主要问题；
2. 目标与用户使用结果；
3. 日常使用流程；
4. 功能范围与业务规则；
5. 保持不变的行为和边界；
6. 完成标准；
7. 需要确认的问题；
8. R1 反馈区。

“日常使用流程”按用户动作组织；“功能范围与完成标准”可合成一张表，避免先平铺功能、后面再重复一次验收。复杂范围可按用户入口、公共组件、数据与后端能力分组，但同一张表中的行应保持同一粒度。

R1 反馈区包含：审查目的、当前待审内容、可选决定、不同决定如何处理、用户反馈占位。只开放 R1；不要提前让用户审方案。

## R2：方案

### 系统位置

先用普通名称说明产品、业务模块、页面/入口以及涉及的前端、后端和数据层。随后用 Mermaid 图表示关系，例如：

```mermaid
flowchart LR
    U[用户入口] --> F[页面与交互]
    F --> S[对应业务服务]
    S --> R[领域数据访问]
    R --> D[(当前数据源)]
```

图只保留理解本次方案所需节点。图后补充每个节点的职责、本次是否改变以及箭头承载的数据或动作；不要用文字重复图形外观。

### 总体方案

先用一段话说清“现状能力 → 本次改变 → 用户结果”。如变化跨层，再用前后对比图或主流程图标出新增、修改和继续复用的节点。

### 模块方案

使用同粒度表格：

| 所在位置 | 当前职责与现状 | 本次改变 | 改变后的作用 | 上下游 |
|---|---|---|---|---|

从产品入口到前端公共能力、领域前端、后端业务服务、数据访问与数据源逐层展开。只有大型模块内部确实存在多个独立责任时才再分一级。

### 关键流程与数据

选择真正会影响实现的内容说明：

- 默认使用路径与可调整路径；
- 筛选、聚合、展开、选择、下钻等交互怎样组合；
- 一份数据怎样被不同视图复用，何时才重新查询；
- 指标、状态或业务规则由谁计算；
- 完整结果、错误和大数据量怎样处理；
- 公共组件提供什么稳定能力，领域模块提供什么业务配置。

适合时使用时序图、状态图或伪代码。不要为了齐全机械加入所有图。

### 接口与代码组织

接口按一个清晰业务动作命名并保持高内聚。目录先按领域和业务模块归属，再在模块内放路由、Schema、Service、Repository 或前端组件；这些技术角色不能替代业务边界。

方案只写职责、输入输出、复用关系和必要算法，不罗列尚不存在的文件清单冒充设计已经落地。

### 验证方案

把每项重要用户结果对应到一个真实证据：页面操作、API 输入输出、数据库/固定数据对账、关键边界和必要回归。性能或规模结论必须有当前数据量与运行观察；没有证据时保留为待验证，不先定任意阈值。

### R2 反馈区

说明审查目的、待审方案、用户可批准/修订/驳回的内容、反馈将影响哪些模块，以及用户反馈占位。R2 通过前不得进入实施。

## 裁剪原则

- 单页面、单模块且无公共影响：系统位置、一段总体方案、模块表和验证即可；
- 跨前后端或共享能力：保留系统图、数据/交互流程和模块责任；
- 有真实技术选择时比较选项；没有选择时直接说明方案，不制造“关键取舍”；
- 需求尚未确认时只写 R1，不加载本参考来提前完成 R2。
