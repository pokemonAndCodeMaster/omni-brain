## ① 组件概述

**一句话职责**：定义人工质检模块的核心数据底座 `t_qc_daily_snapshot`——每行记录一名标注员在某日、某 scene、当日组别下的最小统计单元（含 project_name 冗余维度），既服务统计看板，也为采样配额计算和通过/打回判断提供计数依据，并通过/打回结论（good_conclusion/bad_conclusion）与执行计数（execution JSONB）同行记录，无需跨表 JOIN。

**在整体架构中的位置**：数据层。位于 Repository 层之下、Delta 原始表之上的聚合产物；由 [[质检平台-Repository与数据库访问设计]] 的 `SnapshotRepository` 读写，由 [[验收前置条件-快照刷新四级实现契约]] 的 `StatService` + Airflow DAG 每 30 分钟从 Delta 原始表聚合刷新；向上为 [[质检平台-验收采样配额与任务选择设计]] 的 Sampler 和 [[质检平台-通过打回规则与执行设计]] 的 PassRule 提供计数依据。

**数据流说明**：
- Airflow DAG 每 30 分钟触发 `SnapshotService.refresh_snapshot(stat_date_range)`，覆盖最近 4 天分片（幂等可重复刷新）。
- `SnapshotService` 通过 `LabelTaskRepository.fetch_tasks_raw` 从 Delta 原始表**一次查全量**（**直连原始表，不依赖中间表，也不依赖 t_text_label_task 中间层**，架构决策人类反馈1）。`task_screener=None` 时不加该过滤（快照需全量）。
- `_aggregate_by_min_unit` **单遍历双累加**：每行同时累加标注指标（每行都累加）和验收指标（仅 `task_status IN (67,68,69,70)` 累加，验收是标注的子集）。`_prepare_row_context` 提取 `stat_date/employee_id/scene_name/project_name/is_good/behavior_status` 公共上下文并缓存。
- `_enrich_with_personnel` 将 `task_screener`（工号）**直接写入** `employee_id`（无需映射 t_data_check_screeners.id），并从 `t_data_check_screeners` 查当前组（`WHERE end_time IS NULL`，**group_name 来源字段为 team_leader**）写入 group_name 冗余字段。
- `upsert_many` 批量 UPSERT 写入快照表，UPDATE SET **仅含统计列**，严禁含 execution/confirmed_*/executed_* 字段（边界情况1）。
- 范式细节详见 [[SYN-SQL精简与快照单遍历双累加范式]]。

## ⑤ 详细设计展开

### 1. 设计原则

| 原则 | 说明 |
|------|------|
| **一行 = 一个最小统计单元** | `(stat_date × scene_name × group_name × employee_id)` + project_name 冗余；employee_id 必须有值 |
| **标注+验收合一** | 同一行承载该维度下标注进度、标注结果分布、验收分配、验收结果 |
| **执行确认同行** | good_conclusion/bad_conclusion 记录分类结论，execution JSONB 记录各维度执行计数，confirmed_*/executed_* 记录人工确认与执行，无需跨表 JOIN |
| **采样计算依据** | sampler 从本表计算每个最小单元的配额；执行前再查 Delta 原始表取得 task_id/clip_id（**本表不记录 clip_id 列表**，反查走 Delta 原始表） |
| **JSONB 无 schema 扩展** | 选项分布和验收明细用 JSONB，新增选项/题型无需加列 |
| **good/bad 独立列 + 选项 JSONB 混合** | 固定高频维度（good/bad 的 allocated/completed/passed/conclusion）用独立列（可索引、SQL 简洁），可变维度用 JSONB（灵活扩展） |

### 2. 维度设计

```
stat_date       DATE         -- 标注提交日期（以标注工作日为主轴）
scene_name      VARCHAR(256) -- 任务组/场景名（见 scene_name 概念卡片）
group_name      VARCHAR(128) -- 冗余存储的标注员组名（不做 FK，便于 GROUP BY）
employee_id     VARCHAR(64)  -- 必填，最小统计单元对应的标注员工号（逻辑引用 t_data_check_screeners.employee_id）
project_name    VARCHAR(64)  -- 冗余项目名，由 scene_name 前缀经 Python 字典映射
```

本表只保存个人最小行，不额外保存组级汇总行。`group_name` 是历史维度快照：记录该标注员当天所属组，后续调组不回写历史。组级、scene 级、project 级和日期级结果通过 `GROUP BY` 直接聚合。

**project 维度映射**：`project_name` 由 `scene_name` 前缀经 StatService 中的 Python 字典硬编码映射（仅 2 个项目，无需建表避免过度设计）：

```python
PROJECT_MAP = {
    "vpd质检标注_v4": "vpd",
    "驾驶行为质检": "城区and高速",
}
```

**反查 clip_id 策略**：本表**不记录 clip_id 列表**。执行阶段需具体 clip/task 时，反查走 Delta 原始表（`ods_t_label_screening_task_datalake` + `ods_t_label_sdobject_datalake_new`），按 (stat_date, scene_name, employee_id) 维度回查 task_id/clip_id。

**唯一性保证**：`UNIQUE (stat_date, scene_name, group_name, employee_id)`，只使用 PostgreSQL 10+ 支持的普通列唯一约束。分布键 = UK 全列 `(stat_date, scene_name, group_name, employee_id)`，满足 GaussDB/DWS 分布键⊆唯一约束要求（V20260706_01 修复 cn_5001 后）。id 为 SERIAL 自增逻辑主键，无 DB 层 PRIMARY KEY 约束。

### 3. 字段分组设计

#### 3.1 标注进度字段

```sql
annotation_total     INT   -- 该维度下分配的总标注任务数
annotation_submitted INT   -- 已提交/完成标注数
-- annotation_pending 去掉（运行时派生 = total - submitted）
option_annotation    JSONB -- {"A": 120, "B": 30, "C": 15}  各选项标注数量（新增）
```

#### 3.2 验收分配+进度字段

```sql
acceptance_allocated   INT  -- 状态回查后确认实际成功分配到验收员的数量（总验收条数）
```

### 6. 核心业务流程与数据流

```
① 标注完成 → StatService.compute_annotation_stats()
   → 读 Delta 原始表，按维度聚合标注数据
   → UPSERT t_qc_daily_snapshot（刷新 annotation_* 和 option_annotation 列）

② 验收分配 → AssignmentService.execute_assignment()
   → 执行采样（sampler 从本表读 option_annotation 做比例判断）
   → 根据配额反查 Delta 原始表取得具体 task_ids（本表不记录 clip_id）
   → 调用 Delta API batch_assign()/batch_review_pass()
   → 回查任务状态后 UPSERT acceptance_allocated（实际成功量）

③ 验收进行中 → StatService.refresh_acceptance_stats()（定时或手动触发）
   → 读 Delta 原始表，获取最新验收状态
   → UPSERT t_qc_daily_snapshot（刷新 good_*/bad_*/option_acceptance/acceptance_completed 列）

④ 结论确认 → ExecutionService.confirm_conclusion()
   → 调用 PassRuleStrategy.evaluate(snapshot_row) 计算通过率（分母用 good_completed/bad_completed）
   → UPDATE good_conclusion / bad_conclusion / confirmed_by / confirmed_at

⑤ 结论执行 → ExecutionService.execute()
   → 调用 Delta API（batch_acceptance_pass 或 task_rollback×2）
   → UPDATE execution（JSONB 写入各维度 passed/rejected/total）/ executed_by / executed_at
```

#### Delta 原始表查询算法（1 个统一查询方法 + Python 层过滤）

> 🔄 **范式重构（TAG 20260711_160000）**：原 3 个 fetch 方法（`fetch_annotation_raw` / `fetch_acceptance_raw` / `fetch_task_ids_by_dimension`）已合并为 1 个统一查询方法 `fetch_tasks_raw`。核心理由：三者查同一张表、SELECT 字段完全一致、仅 WHERE 不同，且验收是标注的子集（`task_status IN 67,68,69,70` ⊂ 全量）。详见 [[SYN-SQL精简与快照单遍历双累加范式]] 范式一。

上述业务流程中"读 Delta 原始表"的具体实现由 `LabelTaskRepository.fetch_tasks_raw` 统一承担，它是快照刷新链路与 Delta ODS 层之间的数据桥梁。调用链与查询逻辑如下：

```mermaid
sequenceDiagram
    participant SS as StatService / ExecutionService
    participant LTR as LabelTaskRepository
    participant Delta as Delta ODS 原始表

    SS->>LTR: fetch_tasks_raw(start, end, task_screener=None)
    Note over LTR: task_screener=None → 不加该过滤（快照路径需全量）<br/>task_screener=xxx → 动态追加（执行路径）
    LTR->>Delta: SELECT task 字段 + behavior_status<br/>WHERE task_creator ANY + task_name LIKE OR<br/>+ to_review_time 范围 + del_flag=0<br/>(可选 task_screener=%s)<br/>无 LATERAL，分批查 sdobject BATCH_SIZE=5000
    Delta-->>LTR: List[TaskRawRow] (含 behavior_status，空串=无 sdobject)
    LTR-->>SS: List[TaskRawRow]
    Note over SS: 快照路径: 单遍历双累加（标注每行累加，验收仅 status IN 67,68,69,70 累加）<br/>执行路径: Python 层提取 (task_id, behavior_status)，过滤掉空 behavior_status
```

**源码出处**：`src/manual_qc/label_task_repository.py` `fetch_tasks_raw` + `_STEP1_TASKS_SQL_TEMPLATE`

| 路径 | 调用方 | task_screener 参数 | Python 层过滤 |
|------|--------|------------------|--------------|
| 快照路径 | `SnapshotService._fetch_all_tasks` | `None`（全量） | 单遍历内按 `task_status` 分支累加标注/验收指标 |
| 执行路径 | `ExecutionService._fetch_task_ids_by_category` | 具体值（单人） | 提取 `(task_id, behavior_status)`，过滤掉 `behavior_status` 为空的行 |

**关键设计**：
- good/bad 判定**不在 SQL 层进行**，`behavior_status` 原样返回供 Python 层 `gt_parser.is_good_behavior()` 解析（判定算法详见 [[质检平台-ods_t_label_sdobject_datalake_new表结构]] good/bad 判定算法段）。
- `scene_name` **不在 SQL 层提取**，`task_name` 原样返回，由 Python 层 `_extract_scene_name_from_task_name` 按 `SPLIT_PART(task_name, '_', 2)`（e2e）/ `SPLIT_PART(task_name, '_', 3)`（vpd）提取（提取逻辑详见 [[质检平台-ods_t_label_screening_task_datalake表结构]] scene_name 提取逻辑段）。
- `task_status` / `scene_name` 过滤全部在 Python 层完成，SQL 只做 `task_creator` / `task_name` 前缀 / `to_review_time` 范围 / `del_flag` / 可选 `task_screener` 过滤。
- **无 LATERAL**（GaussDB/DWS 不支持），sdobject 取最新行用分批查 + Python 层去重（BATCH_SIZE=5000）。

#### 两表关联关系

上述拓扑图中 ① 的两张 Delta 原始表通过 `task_id` 构成 1:N 关联，是快照刷新 SQL 的 JOIN 基础。关联结构如下：

```
delta.ods_t_label_screening_task_datalake (task)
  │  PK: id
  │  索引: task_name / task_status / task_screener / task_acceptor / task_reviewer / to_review_time
  │
  │  1:N (id = task_id)
  │
  ▼
delta.ods_t_label_sdobject_datalake_new (sdobj)
  PK: (id, task_finished_time)
  索引: (sds_id, del_flag) / task_id
```

**去重策略**：一个 task_id 可对应多条 sdobject 记录，使用 `LEFT JOIN LATERAL` + `ORDER BY task_finished_time DESC LIMIT 1` 取最新行，避免笛卡尔积膨胀：

```sql
LEFT JOIN LATERAL (
    SELECT behavior_status
    FROM delta.ods_t_label_sdobject_datalake_new
    WHERE task_id = task.id AND del_flag = 0
    ORDER BY task_finished_time DESC
    LIMIT 1
) AS sdobj ON TRUE
```

**源码出处**：`src/manual_qc/label_task_repository.py` `fetch_annotation_raw` / `fetch_acceptance_raw`（原查询逻辑卡 §1）。两张表的完整字段清单与索引设计详见 [[质检平台-ods_t_label_screening_task_datalake表结构]] 和 [[质检平台-ods_t_label_sdobject_datalake_new表结构]]。

**聚合 SQL 来源原型**（来自存量代码 `AppGy1Model.get_pass_rate_info()`，新架构中由 Repository 层重新实现）：
- 按 `(DATE(submit_time), screener, company)` 聚合
- `COUNT(DISTINCT CASE WHEN status != 'UNLABELED' THEN task_id END)` → 提交数
- `COUNT(DISTINCT CASE WHEN status = 'HUMAN_PASS' THEN task_id END)` → 通过数
- good/bad 分类依据 `result->>'驾驶问题分类' = 'good'` 判定

| 通过率计算 + 规则判定 `PassRuleStrategy` | `good_passed/good_completed` 计算通过率，判定 good_conclusion/bad_conclusion | 查询单行 |
| 看板/统计查询 API | 按组/场景/项目/日期汇总，通过率必须先 SUM 再相除 | `GROUP BY stat_date, scene_name, group_name, project_name` |
| 待执行看板 | `good_conclusion IS NOT NULL OR bad_conclusion IS NOT NULL` | 部分索引扫描 |

### 12. 定时刷新机制

| 维度 | 配置 |
|------|------|
| 刷新周期 | 每 30 分钟（与旧版状态刷新一致） |
| 调度方式 | Airflow DAG（PythonOperator + max_active_runs=1 + dagrun_timeout） |
| 覆盖范围 | 最近 4 天分片（`date.today() - timedelta(days=4)` 至 `date.today()`），幂等可重复刷新 |

| 时区 | 所有时间按 `Asia/Shanghai` 处理 |
| 失败回调 | 复用 `dags.common_fun.wrapper_failure_callback` |

### 13. 边界情况与典型工况

| # | 边界情况 | 处理策略 |
|---|---------|---------|
| 1 | **UPSERT 不得误清空已确认执行字段** | 刷新只更新统计列（annotation_*/acceptance_*/good_*/bad_*/option_*），`execution/confirmed_*/executed_*/good_conclusion/bad_conclusion` 列在 UPSERT 的 UPDATE SET 中**不出现** |
| 2 | **人员调组后历史快照** | `group_name` 写入即冻结，调组不回写历史行（架构护栏2） |
| 3 | **人员尚未进组** | `team_leader=''` 时快照行 group_name 记录空串，后续调组无法修正（已知取舍） |
| 4 | **跨天分片** | 聚合按 `DATE(submit_time)`（上海时区）分组，DAG 每次刷新覆盖最近 N 天（参照旧版过去4天分片） |
| 5 | **空数据** | 某日某标注员无提交时，不产生快照行（非 UPSERT 空值） |
| 6 | **Delta 平台同步延迟** | 刷新周期 30min，容忍 ODS 层分钟级延迟 |
| 7 | **标注员离职** | `t_data_check_screeners.status=0`（int2，0=离职）的人员，其历史快照行保留不删（SCD Type2 旧行 end_time 已设） |
| 8 | **Good/Bad 判定** | 依据 `ods_t_label_sdobject_datalake_new.behavior_status` JSONB 中的 `驾驶问题分类` 字段，`='good'` 为 good，其余为 bad |
| 9 | **并发刷新** | DAG `max_active_runs=1` 避免并发 |
| 10 | **临时表污染** | 新架构用 `execute_values` 批量 UPSERT，**禁止**再用临时表模式 |

### 16. 分布键修复记录（V20260706_01，修复 cn_5001）

**问题**：原建表 `DISTRIBUTE BY HASH(id)`，但 UNIQUE 约束 `uk_qc_daily_snapshot_dim (stat_date, scene_name, group_name, employee_id)` 不含 `id` → 触发 GaussDB/DWS cn_5001（`PrimaryKey/UniqueIndex of distribute table must contain hash distribution column`）。

**根因**：分布键 `HASH(id)` ∉ UK 列集合，违反 NORM-GAUSSDB-001 §3.1（分布键必须是 PK/UK 的子集）；同时 `id SERIAL PRIMARY KEY` 作为 PK 也不含目标复合分布键 → 改分布键后 PK 同样违规。

**修复手法（方案B：复合分布键保留 UK）**：
1. 去 PK 约束：`id SERIAL PRIMARY KEY` → `id SERIAL`（id 保留 SERIAL 自增逻辑主键，无 DB 层 PK 约束）
2. 改分布键：`DISTRIBUTE BY HASH(id)` → `DISTRIBUTE BY HASH(stat_date, scene_name, group_name, employee_id)`（全部 UK 列作为复合分布键）
3. UK 约束原样保留，Repository UPSERT `ON CONFLICT (stat_date, scene_name, group_name, employee_id)` 逻辑零改动

**迁移脚本**：[`V20260706_01__fix_qc_daily_snapshot_distribute_key.sql`](../../../data_schemas/migrations/V20260706_01__fix_qc_daily_snapshot_distribute_key.sql)，幂等。pnc_simulation（正式表 UK 已存在）直接去 PK + 改分布键；data_common_4（测试镜像原缺 UK）先补 UK 再去 PK 再改分布键。

**副作用**：执行后数据按新分布键在 DN 间重新散列（一次性操作，DBA 维护窗口执行）；id 列隐式唯一索引随 PK 删除而删除，按 id 查询将全表扫描（当前查询模式以维度键为主，影响可忽略）。

**关联避坑**：GaussDB/DWS 分布表设计必须确保分布键 ⊆ PK/UK 列集合，否则建表/迁移触发 cn_5001。优先以业务维度键（UK 全列）作为复合分布键，避免用自增 id 作分布键导致与 UK 不一致。
