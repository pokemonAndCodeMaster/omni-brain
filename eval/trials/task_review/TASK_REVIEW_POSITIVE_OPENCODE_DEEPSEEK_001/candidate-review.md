## R2 方案审查

**系统位置（本次改动节点用 ⬅ 标出）：**

```text
产品：人工质检平台
└─ 任务分析页（TaskAnalysisWorkspace）
   ├─ 任务分析表 TaskAnalysisTable.vue ⬅ 新增“验收未完成量”列（复用既有列定义能力）
   │   └─ 共享工作台 DataWorkbench.vue （未改，继续复用排序/筛选/列配置/下钻）
   ├─ 任务树 useTaskAnalysisTree.ts ⬅ 基础指标清单 + acceptance.pending
   ├─ 类型/转换 analysis.ts、utils.ts ⬅ 行字段 + 服务端值透传
   └─ 受控分析 API → AnalysisQueryService → AnalysisRepository（未改表达式）
        models.py ⬅ MAX_ANALYSIS_MEASURES 15→16（共享上限，保障 5 固定列）
```

**从什么改成什么：**

- 原来：任务表请求 10 个基础指标，仓库已有的 `acceptance.pending` 表达式未在表中消费，
  用户手工 `实际验收分配量 − 验收完成量`。
- 现在：基础指标增至 11，任务树每层（含下钻层）都请求 `acceptance.pending`；
  服务端在对应聚合层计算 `max(Σ分配 − Σ完成, 0)`，前端只读值并展示为新列。
- 保持不变：仓库唯一计算表达式、四级查询路径、DataWorkbench 全部表格能力、保存配置、
  “固定 5 个问题选项”前端上限（`setPinnedMetrics` slice(0,5) 与工作区 5 项守卫）。

**关键设计决策：**

- 上限 15→16：10 基础 + 5 固定 = 15；新增后 11 + 5 = 16，服务端 `_validate` 与 HTTP 422
  同源（`AnalysisValidationError → HTTPException(422)`，routers/analysis.py:101-104），
  属于必须同步放宽的共享契约。符合“不挤掉 5 个固定选项”的要求。
- 旧列顺序兼容：保存的 `columnVisibility` 未含新列时默认可见；`columnOrder` 未含新列时
  由 TanStack 表追加到末尾（DataWorkbench `applyState` 只应用已保存 id）。
- 未在前端复制公式：`utils.ts` 用 `count(row,'acceptance.pending')` 读取服务端值。

**用户可作的决定：** 认可总体与模块方案，或要求改口径/改位置。
**反馈会改哪里：** 修改方案或实现后再回到 R3 复检；方案被拒则下游停更。
