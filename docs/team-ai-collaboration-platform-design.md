## 1. 当前判断

现在应该开始设计这套平台。

原因不是“Agent 功能已经很多，需要做一个菜单”，而是当前已经出现了三个必须统一的真实对象：

1. 团队不断产生的灵感、问题、需求和人的判断；
2. 已经能够登记并由 OpenCode 执行的 Agent 能力与 Run；
3. 代码、评测、知识和运行证据形成的实际成果。

如果继续分别建设，后续会得到灵感列表、需求看板、Agent 目录、Run 页面、评测页面和知识页面等彼此无关的入口。用户仍然无法回答：一件事为什么开始、Agent 做过什么、人修正了什么、最后形成了什么、下一步由谁负责，以及这次经验有没有沉淀为更可靠的能力。

因此，产品目标暂定为：

> 让团队把一个尚不完整的想法，与人和 Agent 一起逐步变成可执行、可验证、可追溯的成果；同时把每次执行的反馈沉淀为知识、评测和能力改进候选。

它是团队工作的 AI 协作控制面，不是通用项目管理工具，也不是一个新的多 Agent 执行框架。

## 2. 一个真实用户工况

### 2.1 谁在什么情况下遇到什么问题

团队成员在讨论、使用系统或开发过程中产生一个想法，例如：

> 希望把团队的灵感讨论、正式需求和 Agent 开发过程连起来，以后平台本身的建设也通过这个过程完成。

今天这个想法通常散落在聊天、口头讨论或个人笔记中。即使后来启动了 Agent，也很难追溯它所依据的原始意图、人的后续纠正和最终决定。Agent Run 与需求、分支、验证和知识更新之间也没有稳定关系。

### 2.2 用户最终拿到什么

用户不只是拿到一段 Agent 回答，而是拿到一个持续可用的协作记录：

- 原始想法及来源没有丢失；
- 已有项目背景、未知和相关工作可以被补充；
- 人与 Agent 的讨论、修正和候选结论在同一条时间线上；
- 经人确认后形成独立、带版本的正式需求；
- 后续方案、开发、验证、审查 Run 均可回到该需求；
- 分支、Commit、MR、验证报告、知识提案和评测候选有明确关联；
- 当前负责人、待人处理事项和下一步动作清楚可见。

### 2.3 怎样证明有用

对于任意一个真实工作，另一名团队成员无需翻聊天记录，就能在平台中回答：

1. 最初为什么提出这件事；
2. Agent 查过和做过什么；
3. 人纠正、拒绝或批准了什么；
4. 当前正式需求和验收标准是哪一版；
5. 已经形成什么证据，下一步由谁做什么。

这五个问题能从一个对象页面直接回答，才算协作平台成立。页面、表和 Agent 数量本身不算产品结果。

## 3. 产品边界

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 团队 AI 协作工作台 | Idea、正式工作、讨论、负责人、人工决定、Run 关联和成果全景 | 不实现模型推理，不复制代码和知识全文 |
| Omni-Brain Harness | 获取知识、形成需求/方案、开发、验证、审查和知识回写的方法与能力 | 不承担团队业务记录和页面状态 |
| Agent Runtime | 统一启动能力、记录执行状态和规范事件 | 不决定业务优先级和是否接受成果 |
| OpenCode | 当前唯一执行器，执行一次具体 Agent 任务 | 不是协作历史或业务对象的事实源 |
| Git / PostgreSQL / 对象存储 | 分别保存代码、可查询业务状态和大体积原始产物 | 不相互复制成第二事实源 |

### 3.1 与现有质检平台的关系

首版继续以 `/home/yyh/project/quality-platform-lab` 的 Vue3、FastAPI 和 PostgreSQL 作为物理宿主，因为这里已经有可运行的 Agent 目录、OpenCode Run、规范事件和 worktree 能力。

但协作能力必须作为跨领域模块存在，不能放进 `manual_qc` 的业务模型。质检看板只是其中一个领域入口；以后知识管理、平台建设和其他项目也应能关联同一套 Idea、工作、讨论和 Run。

当跨团队规模或独立部署真实要求出现后，再决定是否从质检平台拆成独立产品。首版不为可能的拆分先建设微服务。

### 3.2 汇总入口与领域入口怎样分工

Agent 行为应尽量从工作发生的位置触发：

- 在 Idea 中触发“查背景”“梳理需求”；
- 在正式需求中触发“形成方案”“开始开发”“验证结果”；
- 在质检看板中触发与当前数据和异常强相关的 Agent；
- 在知识页面中触发问答、补知或知识变更提案。

全局入口不替代这些领域入口，主要负责：

- 查看我的待处理、团队进行中和阻塞事项；
- 发现和管理已发布的团队能力；
- 查看跨领域 Run、失败、等待人工和历史结果；
- 查看某项能力过去完成过什么、效果怎样；
- 管理评测、版本晋升和运行基础设施。

所以“在哪里使用 Agent”和“在哪里治理 Agent”是两个不同问题：前者靠领域内嵌入口，后者靠全局控制面。

## 4. 两条长期闭环

```text
价值闭环
Idea → 人机共创 → 正式需求 → 方案 → 开发 → 验证 → 审查/接受 → 知识与成果

能力闭环
真实 Run → 轨迹/结果 → 人的反馈 → 候选 EvalCase → 回归评测
→ Skill/Prompt/Tool/Harness 改进候选 → 人工批准 → 新版本 → 新 Run
```

第一条回答“事情有没有做成”，第二条回答“能力是否因此变得更可靠”。

外层阶段、输入输出和人工 Gate 必须确定；阶段内部由 Agent 自主规划。首版不会建设通用 Workflow DSL，而是在真实纵切中用明确的业务动作和状态迁移实现。至少有两条不同旅程稳定复用后，才抽取模板化工作流。

## 5. 用户看到的是能力，不是内部技术分类

普通用户无需区分 Harness、Agent、Skill、Preset 和执行器。前端统一称为“能力”，并显示：

- 它能帮助完成什么；
- 适用于哪些工作和阶段；
- 需要什么输入，会产生什么结果；
- 最近真实任务和评测效果；
- 当前发布版本和已知边界。

注册表内部仍然保留精确身份和版本。一次用户动作由某个已注册能力处理，再通过 OpenCode 执行。首版只支持 OpenCode，不出现执行器选择。

现有能力可直接映射到首批动作：

| 用户动作 | 当前能力 |
|---|---|
| 查已有背景、已知/未知和相关知识 | 知识问答 Agent |
| 把想法梳理为可审的需求 | 方案形成 Agent 的 R1 阶段 |
| 按批准方案实现 | 知识驱动开发 Agent |
| 对照需求和真实证据审查 | 工作审查 Agent |
| 形成知识更新候选 | 知识建设 Agent |

“开放式头脑风暴”可以先作为 Idea 上的协作动作验证，不预先注册一个没有任务证据的新 Agent 类型。

## 6. 产品信息架构

### 6.1 首版一级入口

```text
AI 协作
├── 工作台       我的待处理、进行中、最近成果、失败与等待人工
├── 灵感         快速记录、讨论、补背景、梳理和人工决定
├── 工作         正式需求与后续交付对象
├── 能力         团队能力目录、适用范围、历史效果和启动入口
└── Runs         跨领域执行状态、失败诊断和详细轨迹
```

工作站、评测与学习、知识提案在有真实功能前不占一级导航。它们先分别进入管理设置、能力详情和工作详情，内容足够稳定后再升级为独立入口。

### 6.2 工作台负责什么

工作台不是 KPI 大屏，首先帮助用户继续工作：

1. 等我判断：待补充、待批准、待验收；
2. Agent 正在做：进行中的 Run 和当前动作；
3. 需要处理：失败、超时、缺输入；
4. 最近形成：新需求、代码结果、验证、知识或评测候选；
5. 团队全景：按领域和阶段汇总，不默认加载对象详情与完整轨迹。

### 6.3 Idea 详情是首个核心页面

页面以协作为中心，而不是以字段表单为中心：

- 顶部：标题、领域、提出人、负责人和当前阶段；
- 主区：人的消息、Agent 候选、反馈、决定和 Run 结果组成的时间线；
- 右侧：当前摘要、已知/未知、关联对象和下一步；
- 就地动作：查背景、梳理需求、补充意见、接受为正式需求、延期、拒绝、合并。

Agent 原始 trace 只在具体 Run 详情加载。Idea 列表只读取摘要、阶段、负责人、最近活动和 Run 计数，不轮询详情。

## 7. 最小业务对象

```text
Idea ──promote──> Requirement ──later──> Work Item / Delivery
  │                    │
  └──── owns Thread ───┘
             │
             ├── human/agent entries
             └── launches Run ── produces Artifact/Evidence

Decision 指向被批准、拒绝或延期的具体对象与版本
Run 保存 OpenCode session 作为执行器关联，但 session 不是业务事实源
```

| 对象 | 责任 | 关键边界 |
|---|---|---|
| Idea | 保存未经整理也有价值的原始想法 | 不因梳理而覆盖原始输入，不代表团队承诺 |
| Requirement | 保存已经明确目标、范围和验收方式的正式工作意图 | 与 Idea 分离并保留来源关系；有版本，不等于已排期 |
| Work Item | 一次准备实际执行的工作及其负责人、输出和验收 | 在第二纵切引入，不用 Requirement 状态冒充 |
| Thread | 围绕一个 Idea 或工作对象持续的人机协作上下文 | 可以包含多次 Run，不等同于 OpenCode session |
| Run | 一次不可覆盖的 Agent 执行尝试 | 沿用当前 `t_agent_run`；失败重跑新建 Run |
| Run Event | 一次 Run 中的输入、工具、结果、状态和错误事件 | 追加写；保留鉴权、余额、模型不可用等原始信息 |
| Artifact / Evidence | Agent 结果、文件、Diff、Commit、验证报告等产物引用 | 大内容不重复塞入业务表 |
| Decision | 人对 Idea、需求版本或结果作出的接受、拒绝、延期等判断 | 是独立审计记录，不改写历史消息 |

### 7.1 三个容易混淆但必须分开的对象

```text
Thread = 人和 Agent 围绕一件事持续协作的产品上下文
Run    = 某个能力的一次执行尝试
OpenCode session = 执行器支持继续运行或定位原始会话的技术句柄
```

一个 Thread 可以先查背景，再梳理需求，再根据人的纠正重跑，因此会关联多个 Run；某次 Run 可以拥有一个 OpenCode session。即使 OpenCode 目录、进程或 API 不可用，平台仍应能从 PostgreSQL 中看到发生过什么、人的决定和结果摘要。

## 8. 简洁的生命周期与人工 Gate

首版不增加置信度、健康度或万能状态。

### Idea

```text
captured → shaping → decided
```

当进入 `decided` 时，单独记录决定：`promoted / deferred / rejected / merged`。

### Requirement

```text
draft → ready → in_progress → verifying → done
```

首个纵切只实现 `draft → ready`。后续状态必须由真实交付纵切实现，不能先做空看板。

### Run

继续沿用当前执行状态：排队、运行、成功、失败、取消。等真正出现 Agent 需要向人提问并恢复执行时，再增加 `waiting_human`，不以一开始的枚举代替能力实现。

### 首批人工 Gate

1. Idea 是否成为正式 Requirement；
2. 哪一版 Requirement 可以进入执行；
3. 实际结果是否接受；
4. 真实任务是否晋升为正式 EvalCase 或知识变更。

Agent 可以提出候选、运行验证和总结证据，不能替人作以上决定。

## 9. 事实源与存储边界

| 内容 | 权威事实源 | 当前策略 |
|---|---|---|
| Idea、需求、Thread、人的消息和决定 | PostgreSQL | 保存完整可查询业务记录 |
| Run 元数据与规范事件 | PostgreSQL | 沿用当前 `t_agent_run` / `t_agent_run_event` |
| OpenCode 原始会话 | OpenCode 工作目录/API | 保存 session ID 作为关联和补充读取入口，不在页面列表现场全量扫描 |
| 分支、Commit、MR 和代码 | Git / Git 托管平台 | PostgreSQL 只保存引用、摘要和同步状态 |
| 正式知识 | Git 管理的知识仓 | 平台保存提案、路径、版本和审查状态 |
| 大日志、附件和完整运行包 | 对象存储 | 当前本地结果足够时不强上；远程 Runner 或体积压力出现后接入 |

这意味着“以 OpenCode 会话存储比较方便”只适合作为执行器原始记录，不适合作为团队产品的唯一存储：一台工作站可能有多个目录、进程和端口，会话也可能被清理或无法被另一台服务访问。业务对象、责任人、人工决定和跨 Run 关系必须由 PostgreSQL 管理。

## 10. 首版系统边界

```text
Vue3 现有 AppShell
  ├── collaboration：Idea / Requirement / Thread / Decision
  ├── agent-runtime：能力目录 / Run / Event / OpenCodeExecutor
  └── manual-qc 等领域模块：嵌入关联动作和上下文

FastAPI
  ├── API → Service → Repository
  ├── Collaboration Service
  └── 现有 Agent Runtime Service

PostgreSQL
  ├── 协作业务表
  └── 现有 Run 与 Event 表

Git worktree + OpenCode
  └── 当前单服务、单执行并发；只提供文件隔离
```

首版不做：

- Codex 执行器；
- Docker；
- 远程工作站和自动调度；
- 通用 Workflow DSL；
- 多 Agent 集群；
- 模型置信度路由；
- 自动优先级、自动合并或自动发布知识；
- 为列表高频拉取完整会话、prompt、结果和 trace；
- 因为远期会用 OBS 就立即搬迁当前所有 Run 事件。

团队正式共用前，身份是必须补齐的边界：首版只需要可信用户身份、`member/admin` 两个系统角色，以及对象上的 owner/reviewer，不先建设按钮级 RBAC。当前平台尚无可信鉴权，因此在补齐前不能声称负责人和操作者已经适用于多人审计。

## 11. 首个数据切片候选

这是实现讨论的输入，不是已批准 Schema。建议最小涉及：

| 表 / 变化 | 保存什么 |
|---|---|
| `t_collab_idea` | 原始内容、当前摘要、领域、提出人、负责人和阶段 |
| `t_collab_requirement` | 正式需求身份、来源 Idea、负责人和当前版本 |
| `t_collab_requirement_revision` | 不可覆盖的需求正文、验收标准、来源 Run 和版本决定 |
| `t_collab_thread` | 关联 Idea 或 Requirement 的协作线程 |
| `t_collab_thread_entry` | 人的消息、Agent 结果引用和系统活动时间线 |
| `t_collab_decision` | Promote、接受、拒绝、延期、合并等人工决定 |
| `t_agent_run` 增量字段 | `subject_type`、`subject_id`、`thread_id`、`trigger_action` |

首版不创建万能 `object` 表，也不先拆 `WorkflowRun / StepRun / Attempt`。当需求到交付的多阶段聚合真实跑通后，再增加一个聚合多个 Run 的 Delivery/Process 对象；当前 Run 仍保持现有语义。

## 12. 两步完成自举

### S0：灵感到正式需求

真实输入就使用“建设团队 AI 协作与交付中枢”这条想法。

```text
录入 Idea
→ 在详情页调用知识问答 Agent 补已有项目背景
→ 调用方案形成 Agent 的 R1 阶段梳理目标、范围和验收
→ 人在时间线补充或纠正
→ 新 Run 基于显式选中的上下文修订
→ 人批准某一版
→ 创建并关联独立 Requirement
```

完成后，后续平台建设的需求讨论开始进入平台，而不是继续散落在聊天中。

### S1：第一个由平台管理的真实交付

使用 S0 形成的 Requirement，选择一个小而真实的平台功能：

```text
批准 Requirement
→ 形成方案
→ 创建 Work Item 和负责人
→ 启动 OpenCode 开发 Run
→ 回填 worktree / branch / Commit / 结果
→ 启动真实验证与审查 Run
→ 人接受或要求修改
→ 形成知识提案和 Candidate EvalCase
```

S1 跑通后，才可以说“平台自己的下一项开发和能力建设可以基于平台”。远程 Runner、OBS 和通用工作流都不应成为 S0/S1 的前置条件。

## 13. S0 的验收证据

S0 必须用真实浏览器、API 和 PostgreSQL 结果验证：

1. 用户一分钟内可以保存一条不完整 Idea，原文以后仍可查看；
2. Idea 列表只查询摘要、阶段、负责人、最近活动和 Run 计数；
3. 进入 Idea 后才加载 Thread，进入具体 Run 后才加载完整任务与增量事件；
4. “查背景”和“梳理需求”产生真实 OpenCode Run，并自动关联 Idea 和 Thread；
5. Agent 输出作为候选进入时间线，不自动覆盖人的原文或正式需求；
6. 人可以补充意见并产生下一次 Run，旧 Run 与旧结果不被覆盖；
7. Promote 会创建独立 Requirement 和首个不可覆盖 Revision，并记录操作者与决定；
8. 另一名用户能够仅凭 Idea/Requirement 页面回答第 2.3 节的五个问题；
9. 鉴权、模型不可用、余额不足和工具错误等失败原因保持原始信息量；
10. 列表不因 Run 数量增加而扫描本地全部 OpenCode session。

## 14. 最小评测与学习入口

首版不做复杂指标体系，也不使用多个不同置信度的 Judge。先围绕两个维度保存人的简单反馈和必要证据：

| 维度 | 首批问题 |
|---|---|
| 最终结果 | 是否忠实覆盖原始意图，是否形成可执行的需求和验收标准 |
| 中间轨迹 | 是否使用了正确背景、明确未知、响应人的纠正且没有无依据扩展 |

一次真实任务可以被标记为 Candidate EvalCase，但只有补齐固定输入、预期结果或 rubric、验证方式并经人确认后，才进入正式评测集。任何能力改进仍走“候选 → 回归 → 人工批准 → 发布/回滚”，不直接修改生产 Harness。

## 15. 需要用户确认的关键取舍

以下是本文的推荐方案，尚未升级为 `approved`：

1. **Idea 与 Requirement 分开。** Idea 保留原始思考，Promote 后创建关联的正式 Requirement，而不是只改一个状态。
2. **Thread、Run、OpenCode session 分开。** Thread 承载持续协作；Run 是一次尝试；session 只是执行器句柄。
3. **领域内使用、全局治理。** 具体 Agent 动作嵌入 Idea、需求、质检和知识页面；全局入口负责跨领域待办、能力、Run 与效果。
4. **先在现有质检平台宿主，逻辑上保持跨领域。** 不新建前端和数据库栈，也不把协作模型写进 `manual_qc`。
5. **先 S0、再 S1。** 先让灵感讨论真实进入平台，再用它管理平台自己的下一项完整开发；不先铺满全部阶段页面。
6. **PostgreSQL 是协作事实源。** OpenCode session 可用于补充查看，不能代替团队业务记录。
7. **暂不引入通用工作流、OBS 和远程 Runner。** 给它们保留清晰边界，等 S1 或多人真实运行暴露需要。

用户确认这些取舍后，下一份产物应是 S0 的可施工 R2：页面交互、API、PostgreSQL migration、与现有 `agent_runtime` 的接口、真实验收用例和回滚方式。确认前不继续增加页面或表。
