# <领域名称>

> 本页保存为领域目录的 `overview.md`，是领域正文的唯一规范落点。同目录 `index.md` 只链接本页和直接下级，不复制正文。

同时在 `draft/config/knowledge-domains.yaml` 登记领域。每项都必须包含 `id/title/parent/scope/excludes`；根领域的 `parent` 使用 `null`，不要用自造字段代替：

```yaml
schema_version: '0.1'
domains:
  - id: manual-qa
    title: 人工质检
    parent: null
    scope: 人工质检从任务准备到交付及其直接支撑能力
    excludes: 自动质检和跨领域公共基础设施的内部实现
```

有子领域时，子领域 ID 以父 ID 加 `.` 延伸，例如 `quality.manual`；必须先登记父领域。`overview.md` 路径由领域目录表达，不需要在领域地图里另造 `overview` 字段。

## 领域概览

**领域定位：** 说明本领域为什么存在、评价或处理什么对象、产生什么结果，以及它在上级范围中的位置。

**本页内容：** 先介绍全部直接业务模块，再说明模块怎样衔接，最后说明知识覆盖与未知。不要因为某个子模块材料更丰富就直接跳到它。

**当前知识范围：** 说明包含、排除、材料最深入处和不能据此推出的现实结论。

## 业务模块与协作方式

**呈现逻辑：** 先列出这个领域的全部直接业务模块，再按相同维度比较。业务模块是能够独立承担业务结果的职责单元，不是流程步骤、角色、数据对象或 API/Service/Repository 等软件层。先用结构图表达模块位置和共享支撑，再用表格说明职责、输入、输出、协作和知识深度；不为“关系”硬造独立章节。

| 业务模块 | 主要作用 | 主要输入 | 主要输出 | 与其他模块的协作方式 | 当前知识深度 |
|---|---|---|---|---|---|

需要解释端到端协作时，在模块表后增加一张流程图和说明表，补足起点、终点、并行、返工和下游。模块不能用角色、数据对象或代码分层名称代替。

若直接材料只能确认部分模块，不要让最详细的子域冒充领域全貌。在模块表中保留可确认范围，并在“知识覆盖与待补内容”写明还不能列全哪些模块及其影响。
