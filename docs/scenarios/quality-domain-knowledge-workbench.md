# 质检领域知识与方案设计工作台：真实场景定义 v0.1

> 状态：场景假设（provisional），已基于现有质检知识库做第一次实例分析，仍需用户校正。  
> 目的：作为 Omni-Brain 最小知识骨架、产品视图和任务上下文能力的首个真实验证场景。  
> 项目总图与当前路线：[Omni-Brain Blueprint](../blueprint.md)。  
> 原料：`knowledge/raw/conversations/2026-07-10-quality-domain-real-scenario.md`。

## 1. 核心判断

用户真正要解决的不是“质检文档太多”，而是：

> **在一个跨业务、跨系统、跨代码库且持续变化的质检领域中，怎样让人和 AI 获得足以理解现状、完成方案设计并安全推动实现的可信上下文，同时不把所有资料复制进一份越来越大的设计文档。**

这是一类**领域工程知识与决策支持**问题。知识管理只是底座；最终要支持的是业务理解、架构判断、方案设计、实现定位、影响分析和知识回写。

建议把所需产品暂称为：**质检领域工程知识与决策工作台**。它不是另一套质检业务平台，也不是单纯的 wiki/RAG，而是 Omni-Brain 在质检领域上的第一个产品实例。

## 2. 现有领域的客观复杂性

### 2.1 四块业务不是同一种模型

当前质检业务包含人工质检、自动化质检、大模型质检和专题数据质量，但它们的核心对象、流程和成熟度不同：

| 领域 | 当前核心对象/主线 | 典型事实源 | 当前成熟度特征 |
|---|---|---|---|
| 人工质检 | 数据集交付、标注、验收、返修、人力 | Delta、中间表、快照、业务脚本、平台代码 | 流程已有，正在门户化和纵切实现 |
| 自动化质检 | 质检项、配置、版本、产线执行与清理结果 | 代码版本、专题配置、产线结果 | 当前主要冻结边界，正式口径待补 |
| 大模型质检 | 实验、Benchmark、能力成熟度、数据/评测资产、生产任务 | 模型实验、评测集、六通道 Pipeline | POC 演进，不能套交付完成率模型 |
| 专题数据质量 | Golden 集、新增数据、抽检、清洗、质量趋势与风险 | 专题数据、质量指标、交付状态 | 各专题口径不同，部分仍待定义 |

证据入口：`/home/yyh/project/ai-knowledge-base/wiki/synthesis/质检业务总览信息架构.md`、`质检一站式平台顶层架构.md` 及四个模块 Hub。

现有资料已经显示出至少两条交叉轴：**质检能力/手段**与**数据需求/交付对象**。一条数据需求可能同时受到人工、自动化和专题质量能力的看护，因此不能只按四个业务目录组织全部知识。

### 2.2 人工质检验收本身就是跨层系统

人工质检现状包含从视频同步、任务创建、预标注、Delta 分配、标注审核、格式校验，到验收、GT 回写、预警、周报和审计的十五步链路。当前一站式平台并未重写全链，而是先门户化验收和人力模块。

仅“验收分配”这一条纵切就同时涉及：

- 业务对象和规则：交付任务、日期单元、Good/Bad 配额、通过/打回前置条件；
- 外部系统：Delta 接口、状态刷新链路、DMP；
- 数据事实：任务表、日快照、短期 preview、视图配置；
- 软件实现：Vue 工作台、FastAPI Router/Schema、Service、Repository、PostgreSQL；
- 安全约束：权限、预览过期、数据版本、执行前状态重查、部分失败与回查；
- 交付状态：只读查询与预览已部分落地，真实 Delta 执行和 SSO 尚未完成。

这说明“业务知识、平台方案、代码实现、运行事实”不能各自独立管理；但也不能被合并成一张巨型总览卡。

### 2.3 当前检索已经出现上下文爆炸

对外部图谱执行：

```bash
python scripts/query_graph.py \
  "质检业务 人工质检验收 知识组织 平台 架构 业务流程 数据事实源"
```

在 384 张卡片中召回 140 张：12 张 `full_read`、16 张 `summary_only`、112 张 `title_only`。结果横跨业务、页面、API、测试数据、代码模块、通用基建和前端规范。

这证明问题不只是“有没有知识”或“有没有关联”，而是系统能否围绕当前决策回答：**为什么需要这张卡、它属于现状还是目标、应该读到什么深度、哪些内容缺失或冲突。**

## 3. 用户的真实工作场景

当前推断用户承担或频繁切换以下职责：

1. **领域理解者**：需要掌握质检业务全貌及各专题差异；
2. **方案设计者**：需要为一站式平台或某个纵切设计业务和软件方案；
3. **工程协同者**：需要把方案定位到数据、接口、系统和代码，并理解上下游限制；
4. **知识维护者**：需要把新理解和新实现持续纳入体系，而不破坏既有结构。

典型触发不是“给我找一篇文档”，而是：

> 我要设计或修改某项质检能力，例如人工质检验收分配；请告诉我它解决什么业务问题、处于哪条流程、当前真实做法、依赖哪些系统和数据、现有平台与代码做到哪里、有哪些历史决策和未确认约束、这次改动可能影响什么。

## 4. 业务痛点

### 4.1 知识边界不是单一目录能表达

同一知识可能同时属于某个专题、质检手段、交付阶段、平台模块、数据对象和代码组件。强行选择唯一目录会丢失其他语义；全部复制到每个目录则必然不一致。

### 4.2 多种“真相状态”混在一起

现有卡片同时包含：上游旧系统快照、当前业务事实、长期产品北极星、阶段性方案、已实现纵切、待实现契约和开放问题。它们都可能有价值，但若只标记为 `active`，使用者很难知道哪一段可以直接作为当前设计依据。

### 4.3 方案设计缺少任务边界

一个“验收中心设计”会自然展开到页面、指标、表、采样、权限、API、代码、测试和公共组件。如果没有当前决策问题和阅读预算，追求面面俱到会制造几十张相互重叠的方案卡。

### 4.4 知识与代码只有链接，没有稳定的语义对齐

`related_code` 能说明可能相关的路径，却不足以回答：该路径实现了哪条业务能力、对应当前方案的哪一部分、代码变化使哪些结论失效、目标设计与已实现范围差多少。

### 4.5 更新传播不可控

业务规则、外部接口、表结构、平台方案和代码进度的变化速度不同。若每次变化都要求同步所有关联总览和分卡，维护成本会快速超过收益；若不更新，又会形成看似完整但不可信的知识。

### 4.6 有知识不等于能用于决策

当前检索能找到大量相关材料，但无法自动形成“本次方案的必要上下文、权威依据、冲突、缺口和影响范围”。这才是知识无法有效运用的核心。

## 5. 业务目标

### 5.1 北极星目标

> 当任何人需要理解、设计或修改一项质检能力时，系统能从业务目标出发，按需汇聚当前有效的流程、规则、数据、系统、代码、决策、上下游约束和开放问题，形成可核验、可下钻且不过载的任务上下文；任务产生的新结论能安全回写并触发必要复核。

### 5.2 具体收益

- 新人能够从质检业务全貌进入某个领域、流程和实现，不依赖口口相传；
- 方案设计能够显式覆盖业务目标、现状事实、上下游、数据和代码约束；
- 设计者不需要通读 140 张相关卡片或整个代码库才能开始工作；
- 任何关键结论都能看到来源、适用范围、事实状态和实现状态；
- 业务或代码变化只触发受影响知识的复核，而不是全库同步重写；
- 四块业务既可共享平台级能力，又不会被错误抽象成同一种流程和指标。

### 5.3 Omni-Brain 在本场景中的角色与双层目标

本场景的长期目标不是让 Omni-Brain 当前直接运行人工质检需求、任务和验收，而是检验它能否成为质检能力的建设与演进基座：从真实问题和分散事实出发，帮助建立知识、理顺流程、形成方案、建设平台/工具能力、验证结果并安全回收新增知识。质检一站式平台、规则体系和未来 Agent 是被逐步建设的领域能力。

采用双层牵引：

- **长期北极星**：借助 Omni-Brain 逐步贯通完整质检平台的能力建设闭环，并为规则资产复利、流程组合和 Agent 化建立基础；这不等于当前一次性建设整个平台。
- **短期目标**：选择一个边界明确的人工质检能力产物，完成“理解—设计—建设—验证—回写”闭环。首个候选是将依赖本地脚本的验收任务分配建设为可配置、可预览、可执行、可回查和可验证的平台能力，具体边界仍待确认。

短期实验同时评价两个结果：领域能力是否真实改善工作，以及 Omni-Brain 是否可靠完成上下文组装、缺口识别、产物建设辅助、验证和知识回收。

## 6. 候选承载模型：事实源、规范底座、派生结构与视图

“一个规范底座”不意味着把所有内容放进同一目录或同一种卡片。针对质检场景，建议先用以下物理/生命周期分工验证：

```text
① 事实源与原料
   代码 / 数据库 Schema / API 契约 / 运行平台 / 原始文档 / 访谈
                         ↓ 证据与稳定标识
② 规范语义底座
   业务对象 / 能力 / 流程 / 规则 / 数据资产 / 系统 / 决策 / 来源
                         ↓ 编译与对齐
③ 派生结构
   全文索引 / 关系图 / 代码符号图 / Schema 清单 / 数据血缘 / 新鲜度状态
                         ↓ 查询与投影
④ 受维护的产品视图定义      ⑤ 会话/任务投影
   浏览/学习/流程/设计/影响    本次上下文包、临时路线、方案证据集

治理控制面横切 ①—⑤：Schema、上下文边界、来源、状态、变更、评测、回滚
```

- ① 是外部事实，不复制成另一份实现真相；
- ② 只维护需要解释、关联、复用和影响分析的语义；
- ③ 尽可能由代码和确定性工具生成，不要求人手写每个符号、表字段和链路；
- ④ 维护选择/排序/下钻规则，不复制底座事实；
- ⑤ 默认不持久化，只在形成可复用的新知识或稳定视图需求时回写候选。

当前 Markdown + YAML 可以作为 ② 和 ④ 的初期载体，SQLite/JSON/图索引作为 ③；是否迁移 RDF、图数据库或其他存储，应由查询、关系约束和规模验证决定。

### 6.1 可靠性来自约束和可重建性，不来自图数据库

底座至少需要：稳定 ID、明确类型、上下文/所有权、来源、有效范围、事实时间、知识状态、语义关系和版本记录。尤其要拆开两个经常混淆的维度：

- **现实形态**：`as_is`（当前现状）/ `to_be`（目标方案）/ `historical`（历史）；
- **知识状态**：`draft` / `verified` / `stale` / `superseded`。

一张 `active` 卡不能同时替代这两个维度。结构约束必须可由检查器验证，来源和变更必须可追溯，派生图和视图输出必须能从规范来源重建。

### 6.2 图谱不是“所有句子都变节点”

规范图只保存对导航、复用、查询或影响分析有价值的稳定对象和有语义的关系。候选内容满足以下任一条件，才考虑成为独立节点：

1. 有稳定身份，需要被其他内容精确引用；
2. 有独立来源、所有者、生命周期或更新频率；
3. 会被两个以上真实任务/视图复用；
4. 变化后需要定位影响范围；
5. 独立呈现能显著改善理解或决策。

否则优先作为父节点的属性、正文小节、证据片段或派生索引项。代码函数、表字段、每次运行实例和每句话默认不建人工维护卡；需要时由代码图、Schema 索引或运行查询提供。

关系也必须通过门禁：有明确方向和语义、能回答一个真实问题、能回到来源。`related` 只能作为低权重临时关系，不能成为默认粘合剂；推导关系不重复存储，防止全连接膨胀。

### 6.3 小核心 + 领域模式包，而不是一个全能本体

当前候选核心语义保持小而稳定：

| 核心对象族 | 质检实例 |
|---|---|
| 业务对象 | 数据需求、交付任务、数据集、专题/场景、质量目标 |
| 能力 | 人工质检、自动化质检、大模型质检、数据存储、任务调度 |
| 流程/活动 | 生产、检查、标注、验收、返修、交付、监控 |
| 规则/指标 | 采样规则、通过阈值、Benchmark、质量指标 |
| 信息资产 | 数据表、数据契约、API、配置、数据集、报告 |
| 系统/实现 | 平台、服务、组件、代码模块、外部系统 |
| 决策 | 现状约束、目标方案、ADR、开放问题 |
| 来源/证据 | 原文、代码版本、运行结果、人工确认 |

人工质检、自动化质检、大模型质检、数据产线等各自使用**领域模式包（domain schema pack）**补充本领域的必填字段、合法关系和校验规则。不同包通过稳定 ID 和显式映射关联，不把一个领域的全部类型提升为全局核心。领域模式包描述“知识怎样合法组织”，不要与任务运行时生成的“上下文包”混为一谈。

例如人工质检可以规定“验收活动必须检查什么业务对象、产生什么结果”；数据平台包可以规定“数据资产必须指向物理载体和生产者/消费者”。核心模型只需要认识 Activity、BusinessObject、InformationAsset 及关系。

### 6.4 图遍历必须有边界和预算

当前外部图谱中，人工质检聚焦查询召回 140/384 张；加入公共基建词后召回 241/384 张。这说明两跳无差别扩展和宽泛 `related` 会让图失去任务价值。

任务检索默认应同时限制：

- 当前领域模式包/业务范围；
- 允许穿越的关系类型；
- 关系方向；
- 最大跳数和总节点预算；
- `as_is/to_be/historical` 与知识状态；
- 用户任务需要的抽象深度。

跨上下文扩展只沿 `depends_on`、`consumes/produces`、`implemented_by`、`governed_by`、`evidenced_by` 等明确关系进行；普通 `related` 不自动跨域扩图。

## 7. 产品视图：按用户任务稳定，按领域参数化

产品视图不应按“人工质检一个、自动化质检一个、数据库一个”无限新增。视图类型由跨领域稳定的用户任务决定，领域只提供范围、顺序和专属模块。

### 7.1 首批候选视图模板

| 视图模板 | 稳定问题 | 人工质检实例 | 扩展方式 |
|---|---|---|---|
| 领域/能力地图 | 这里有什么，边界和关系是什么 | 质检全景、人工质检边界 | 换 scope 和领域模式包 |
| 端到端流程/血缘 | 一件事怎样运作，输入输出是什么 | 十五步流程、验收纵切 | 选择流程、阶段和深度 |
| 学习路径 | 我应该按什么顺序理解 | 总览→交付→验收→实现 | 配置先修与角色目标 |
| 精确查询 | 某个规则、接口、对象是什么 | Good/Bad 配额、Delta 状态 | 按实体和事实状态检索 |
| 方案/决策上下文 | 设计这件事需要知道什么 | 验收分配变更上下文包 | 按任务类型组装章节 |
| 实现/影响视图 | 代码在哪里，改动影响什么 | Router→Service→Repo→表 | 沿 implemented_by/depends_on |
| 治理视图 | 哪里过期、冲突、缺失 | 目标方案与实现进度不一致 | 按质量信号和所有者聚合 |

视图定义可以持久化为模板/配置；某个领域的“人工质检学习路线”只是 `learning_path + scope=manual_qc + ordering` 的预设，不是新的视图类型。

### 7.2 新视图的晋升门禁

只有同时满足以下条件，临时投影才晋升为受维护产品视图：

1. 对应一个反复出现且明确的用户任务；
2. 现有模板无法通过 scope、过滤、排序或章节配置表达；
3. 有稳定入口、负责人和验证用例；
4. 输出结构在至少两个真实实例中有效；
5. 维护收益高于新增模板和迁移成本。

仅内容不同、领域不同或筛选不同，不创建新视图类型。若某领域需要专属章节，优先作为模板插槽或领域 pack 配置。

## 8. 跨领域公共基建：唯一能力节点 + 使用契约

公共基建不挂在每个质检子域下复制维护，也不全部堆入一个“common”目录。它们按照**能力所有权和事实源**拥有唯一规范落点，业务域只建立使用关系。

### 8.1 候选上下文边界

```text
质检业务上下文
├─ 人工质检
├─ 自动化质检
├─ 大模型质检
└─ 专题数据质量

质检共享平台上下文
├─ 权限与 SSO
├─ 数据工作台 / preview-execute-refresh
├─ 指标与视图配置
└─ 通用 API/交互契约

数据平台上下文
├─ 数据生产流程与调度
├─ 数据契约与物理载体
├─ 数据血缘
├─ PostgreSQL/其他数据库能力
└─ OBS 对象存储能力

代码与运行上下文
├─ 仓库 / 模块 / API / Schema
└─ 部署、配置、监控、测试
```

这些不是互斥目录，而是确定“谁维护定义、谁只能引用”的所有权边界。

### 8.2 具体对象怎样只维护一份

| 对象 | 规范落点 | 业务域保留什么 |
|---|---|---|
| PostgreSQL 连接/事务能力 | 数据或平台基础设施能力 | `manual_acceptance depends_on postgres`；特殊事务约束单独记录 |
| OBS 存储 | 对象存储能力与接口契约 | 某流程 `writes_to/reads_from OBS`，以及业务特有路径/保留策略 |
| 端到端数据物理载体 | 数据资产/数据契约节点 | 业务对象与该载体的语义映射、生产/消费关系 |
| 数据生产流程 | 跨域 Process/ValueStream | 各质检能力参与的阶段、输入、输出和责任 |
| 数据上下游链路 | 由 consumes/produces/derived_from 构成的血缘 | 业务特有解释和风险，不复制整条链 |
| 公共代码模块 | 唯一 CodeModule/符号索引 | 业务能力 `implemented_by/depends_on`，不重写模块说明 |

只有当某业务对公共能力增加了独立且稳定的语义约束，才创建“使用契约”节点。例如人工质检的“快照先求和再计算通过率”属于人工质检使用数据能力的业务约束，不应写进通用 PostgreSQL 定义；普通的连接池复用则只需要关系。

### 8.3 共享能力的晋升规则

能力先在最靠近真实用例的上下文中实现；出现第二个经过验证的消费者、或明确由平台团队负责时，再晋升为共享能力。晋升时保留稳定 ID、迁移引用并定义公共契约。不要因为“未来可能复用”提前创建庞大的全局基础设施本体。

## 9. 首个产品验证旅程

首个旅程调整为：**为人工质检建设一个真实能力产物，并走完理解—设计—建设—验证—回写闭环**。“验收任务分配闭环”是当前候选，尚未最终确认。

系统应能协助完成：

1. 明确变更针对交付任务、日期、scene、组、人员还是 task；
2. 还原现有验收流程、采样与 Good/Bad 规则；
3. 区分 Delta/中间表/快照/本地 preview 的事实职责；
4. 找到页面、API、Service、Repository、表和测试入口；
5. 标出真实已实现、目标设计和仍待确认的 Delta/权限契约；
6. 生成只包含本次必要背景的设计上下文；
7. 形成边界明确的领域能力产物及对应测试/运行证据；
8. 在产物验证后计算受影响知识和代码，提出安全回写候选。

### 9.1 起点尚未假定为完整需求或完备知识

首个实验必须假定使用者可能没有验收背景，知识库也可能没有验收规范知识，或只有零散边缘内容。实验起点可能是：

- 用户只想从零理解验收，再判断是否需要改进；
- 用户只反馈“验收不方便”，尚不能描述根因和目标；
- 用户已经掌握痛点和难点，希望重构具体能力。

因此当前不把“需求已经明确”或“知识库已有答案”写成统一前置条件。首轮先验证一个受控的任务知识准备循环：迭代维护任务框架、问题/缺口图和任务知识切片；盘点存量知识后，按缺口继续定位原始文档、代码、数据、脚本、运行事实或人工决定，完成候选摄入、关系编织、冲突/新鲜度检查，直到足以支持下一步决策。检索无结果只是补知分支的输入，不是由模型自由补写结论的许可。

该循环同时产生两类结果：本次使用的上下文投影，以及可进入规范底座的长期知识变更候选。后者必须说明稳定身份、来源、适用范围、与既有对象的关系和对人类浏览视图的影响；临时查询片段、一次运行明细和未验证推断不得为了当前任务批量建卡。反过来，具有复用与导航价值的稳定知识也不能只留在本次上下文中，否则下一项任务仍会重复调查。

“足以支持决策”与“长期可维护”构成双重门禁：关键问题和约束没有可靠答案时不能进入方案；新增知识无归属、无法下钻或使领域/流程视图更加混乱时，也不能把知识准备视为完成。具体字段、门槛和自动化程度仍由本实例发现，不在此提前冻结 Schema。

## 10. 验证标准

首轮总体目标为 [能力切片实验协议](../specs/capability-slice-experiment.md) 的 L2 可信最小闭环，不以一次路径跑通证明可复用或跨场景泛化。

第一阶段不以卡片数量衡量成功，而检查：

- 是否能清楚回答本次任务为什么做、当前怎么做、依据在哪里；
- 是否能区分业务现状、目标设计、当前实现和开放问题；
- 是否能从大量召回中压缩出有纳入理由的必要上下文；
- 是否能找到关键上下游、数据、权限、外部系统和代码入口；
- 是否能让人沿总览—流程—组件—实现逐层下钻而不迷路；
- 是否把任务投影与长期知识变更候选分开，稳定新增知识可由后续任务复用且不会破坏人类浏览层级；
- 是否能在换用能力较弱的模型时依据显式组件状态、缺口和门禁重放主要知识准备过程；
- 是否产出一个真实可运行或可任务验证的领域能力，而非只停留在方案；
- 领域能力是否降低手工查询、脚本依赖或重复确认等真实成本；
- 产物完成后是否只复核真正受影响的知识，并能回滚不理想的结构调整；
- 同一建设方法是否能迁移到下一项能力，而不是一次性项目协助。

## 11. 当前待用户校正

- 主要使用者是用户个人、质检研发团队，还是还包括业务运营/算法/数据团队；
- 当前最高频任务更偏业务平台方案、软件架构、具体开发，还是跨团队知识交接；
- “自动化质检、大模型质检、专题数据质量、人工质检”是稳定业务边界，还是当前组织方式；
- 外部 wiki 对应的代码仓、运行平台和真实业务资料分别有哪些，哪些是当前权威源；
- 首个真实能力产物是否选择“验收任务分配闭环”，以及本轮是否包含真实 execute/回查。
- 上述“核心对象族、领域模式包、视图模板、公共基建边界”哪些符合实际组织责任，哪些只是当前推断。
- “能力建设与验证”应扩展方案工作区，还是在首个实例稳定后成为独立产品组件。
