# 知识摄入

目标不是清点材料或通过检查，而是让不熟悉原料的读者建立正确心智模型并能继续工作。始终抓住三件事：用**问题主线**决定要学什么，用**逐层下钻**连接上级全貌与用户焦点，用**直接事实源**保住细节和现实状态。

来源是证据，`knowledge/` 是唯一发布面，`workspaces/knowledge-ingestion/<case-id>/` 是发布前工作台。工具只负责盘点、固定入口和结构约束；Agent 负责理解、取舍与编织；人负责关键语义和发布决定。

## 1. 定义读者结果并建立工作台

从请求中提取材料位置、目标读者、知识用途和用户真正关心的焦点。用户说“浏览、理解、学习、继续使用”且没有说明背景时，按零背景读者设计。

先读 `knowledge/index.md`、`config/knowledge-domains.yaml` 和直接相关入口，再初始化授权来源；初始化前不要自行递归枚举：

```bash
python scripts/ingestion_workspace.py init <case-id> \
  --goal '<用户读完后能够理解、判断或执行什么>' \
  --source <source-id>=<authorized-directory> [--source ...]
```

填写根 `brief.md`，先完成内容计划而不是文件计划。此时的来源和页面只是待查证假设，完成来源主题地图后必须修订，不能让最初搜索词永久决定知识范围：

1. 写出“上级定位 → 主题全貌 → 用户焦点”的逐层地图；上级定位必须说明所属领域与同级能力，只有直接证据表明主题确为根领域时才可没有上级；
2. 用生命周期、角色、核心对象与状态、平台/业务模块、上游下游与同级能力五个切面检查主题全貌；角色、对象、业务模块和代码分层不能互相代替；
3. 写出读者最终必须能回答的问题主线，并为每题标明回答深度、所需现实形态和候选直接来源；
4. 用户焦点是业务环节或工作台时，检查从进入、计划/分配、实际作业、监控、分析/决定、结果执行到返工/结束的完整运行闭环；按材料合并阶段，不机械套模板；
5. 规划候选规范页与产品视图，让每个问题都有落点；先按读者问题和稳定知识单元划分，不为少建文件把生命周期、数据、规则、软件或公共能力塞进一个总览；
6. 只有范围或关键语义必须由人选择时才追问；其余不确定项先作为待确认保留。

完成标准：读者结果清楚；焦点没有脱离上级领域和完整运作；每个核心问题已有预期答案深度、直接来源类型和候选知识落点；需要独立变化或核验的知识没有被总览页吞掉。

## 2. 沿问题主线阅读直接事实源

先读 `source-summary.md`，再围绕每个问题搜索最小充分来源。来源很多时用机器清单有界定位：

```bash
python scripts/ingestion_workspace.py files <case-id> <source-id> \
  [--glob '<pattern>'] [--limit 100]
```

先用文件名、标题、摘要、目录或代码符号在 `inventory.md` 建立**来源主题地图**，只做低成本定位：每份实质材料或可解释的小组分别记录主题、所属层次、现实形态、可能影响的问题和下一阅读动作。不要按目录从头读，也不要只读名字最像用户焦点的文件。标题或摘要明显涉及用户焦点、直接父级、直接上下游、完整生命周期、核心数据、规则、软件或公共能力时，默认进入定向阅读；只有能说明它不会改变知识地图、事实边界或读者答案时才排除。

实质内容按单文件读取。确定某份材料会影响问题、知识地图或现实边界后，用工作台有界展示，重复执行返回的 `next` 命令直到 `displayed_complete=true`：

```bash
python scripts/ingestion_workspace.py source-read <case-id> <source-id> \
  --path '<exact-relative-path>'
```

该命令每次只展示一个带行号的连续片段，并在现有 `coverage.yaml` 记录来源哈希和展示进度。`displayed_complete` 只证明脚本已把全文分块输出到会话，不证明 Agent 已理解；读完最后一块后仍要判断它支持什么问题、哪些细节改变结论、怎样进入知识地图。不得用 wildcard/循环把多份长文倾倒到一个工具输出；批量标题扫描只用于定位，不能替代正文阅读。

按以下方式匹配结论与事实源：

- 当前软件行为：源码、Schema、配置、测试和新鲜运行结果；
- 当前业务语义：明确的人工决定、业务原始记录和当前数据口径；
- 目标方案：设计稿、计划和待实施契约；
- 历史做法：历史脚本、旧规范和带时间边界的快照；
- 生成综合或旧知识页：用于定位和发现冲突，不能单独证明当前行为。

阅读时同步识别材料已经提供的上级领域、同级地图和公共实现。知识库当前为空不代表用户焦点就是根领域；owner、生产状态或完整契约未知，也不代表材料中的共享模块、公共依赖或占位边界可以从知识地图消失。

逐层下钻时控制深度：上级层讲清所属领域为什么存在、与同级能力怎样分工；主题全貌层覆盖生命周期、角色、核心对象与状态、平台/业务模块、上下游；用户焦点层再讲完整运行闭环、数据、软件、规则、算法和工程细节。上级不是一句背景，焦点也不能吞掉整个领域；当前代码纵切不能替代主题或焦点全貌。

若材料涉及软件或代码，且知识将用于理解、开发或维护，必须读取真实代码并至少追踪一个业务动作：

```text
用户目的与输入
→ 真实入口
→ 包、模块、类、函数与数据结构
→ 数据转换和状态变化
→ 数据库/外部系统
→ 返回结果与失败边界
→ 各层职责为什么这样划分、当前限制和一次具体修改路径
```

覆盖账本只在阅读过程中顺手维护，不用它决定内容范围。状态是 Agent 声明：标题或关键词扫描记 `screened`；精确段落/符号记 `read_targeted`；`source-read` 已显示 `displayed_complete=true` 且你已理解全文后才记 `read_full`。可以先批量把未处理文件标为 `screened`，但完成前必须重新处理来源主题地图中的相关材料；同一句泛化理由不能作为这些材料的最终排除说明。第一次登记前先运行 `python scripts/ingestion_workspace.py mark --help`；例如完整读完一个文件后可执行：

```bash
python scripts/ingestion_workspace.py mark <case-id> <source-id> \
  --status read_full --path '<exact-relative-path>' \
  --reason '<该文件支持什么问题>' --evidence '<exact-relative-path>#full-file'
```

禁止用 glob 写强阅读状态；命令失败时先根据帮助修正一次，不要连续猜参数。

在 `inventory.md` 按问题记录所用直接来源、能证明/不能证明、冲突和时效；无法安全回答的事项写入 `questions.md`，不以常识补齐。完成本步前回看来源主题地图：每个明显相关主题都应已定向阅读、转成可解释未知，或有具体排除理由，不能因为当前代码证据更容易验证就停止阅读业务全貌和目标/历史材料。

完成标准：每个核心问题都有直接证据、明确未知或人工待决；当前代码结论不依赖二手摘要；来源阅读范围由问题充分性而不是文件数量决定。

## 3. 先设计知识地图，再写正文

根据实际材料修订 `brief.md` 中的候选知识地图。用**独立变化**判断知识单元：一块内容若有不同事实源或现实形态、独立更新节奏、独立读者问题，或内部机制已复杂到会淹没父页，就建立独立规范页；只有确实一起维护和消费时才合并，并在地图中写明理由。这是页面边界判断，不是固定页面清单。

- 每个稳定主题只有一个规范落点；按领域主题组织，不按来源类型拆散同一件事；
- 先选择规范区域：`domains/` 保存业务领域的语义、流程、数据和领域规则；`capabilities/` 保存被多个领域或模块复用的能力与使用契约；`systems/` 保存具有独立实现和生命周期的具体系统/服务事实。来源登记和产品视图分别进入 `sources/`、`views/`。不得为了装公共内容新建 `shared`、`common` 等空泛根领域；
- 领域路径表达主要归属，从证据支持的现有上级逐层展开；新增领域在 `review.md` 展示名称、唯一上级、范围和排除项。读者定位需要且材料支持候选父级时，把父级及其现实形态写入领域地图和概览；不能只在正文提到上级，却把焦点提升成根领域；
- 领域目录的 `index.md` 是无 frontmatter 的导航页，只列直接下级和阅读入口；`overview.md` 是带 frontmatter 的领域规范正文。两者不能复制同一份解释，也不能把正文写进 `index.md` 后再制造一个空洞 `overview.md`；
- 公共能力只在 `capabilities/` 保留一个规范页，各消费者只写用途、输入输出、依赖保证、特有限制和失败影响。授权材料中的共享实现、两个真实消费者、明确公共 owner/复用契约或用户明确的团队公共能力，任一即可触发抽取审查，不要求等待第二个外部领域；
- 公共能力分别记录“已覆盖”“相关但未知或尚未抽取”“确实不适用”。已有共享实现时，owner 未知写入边界，不能作为不建立候选页的理由；只有占位、声明或目标依赖时，建立最小知识缺口页，说明预期用途和未知，不编造当前实现；
- 产品视图负责位置、阅读顺序、问题入口和下一跳，不复制规范事实；
- 当前实现、人工决定、目标设计、历史快照和开放问题可以互相连接，但不能混成一张“现状”。

在开始批量写页前检查：每个读者问题能落到一至三篇规范页或一个显式未知；每个候选页面都能说明服务哪个问题、进入哪个规范区域、为什么独立或与哪页合并、必须达到什么最低深度、用哪些直接来源证明完成。发现上级全貌或关键事实源缺失时回到第 2 步，不用窄主题摘要填空。

完成标准：知识地图覆盖问题主线且没有孤立焦点、重复事实或无来源页面；生命周期、数据、规则、软件和公共能力等不同更新面没有因为追求紧凑而失去独立落点。

## 4. 从全貌到细节编织候选

所有相对路径都以 `workspaces/knowledge-ingestion/<case-id>/` 为根；候选只写入该根下的 `draft/knowledge/` 和 `draft/config/`，不能在仓库根或相邻目录另建 `draft/`。

写领域内容时先写 `overview.md`，再让同目录 `index.md` 链接它和直接下级；不要反过来让导航页承担正文。

写每页前先判断读者打开它主要为了**学习主题、完成任务、精确查询、理解机制还是排查问题**。只选择一个主意图组织正文主线，其他信息作为下钻或关联内容；这个判断使用已有 `brief.md` 和知识地图，不新增文档工作流或必填文件。正文按读者需要信息的顺序组织，不能按来源顺序拼接摘要。

正文同时支持三遍阅读，但不套固定章节：

- **快速定位**：只看标题、开头、章节名、加粗重点和关键图表，就能知道本页回答什么、核心结论与适用范围；
- **理解主线**：顺着对象、因果、流程或实现关系，能够完成主要学习或工作；
- **深入核验**：继续下钻条件、证据、机制、实现、验证、例外、风险、未知和直接来源。

标题负责表达知识逻辑：H1 命名页面知识对象或总问题；H2 命名主要问题、任务阶段或稳定分析维度；H3 命名该维度下可独立理解的机制、阶段或组件。判断句、口语句、阅读指令以及“背景”“详细说明”“其他”等空泛词不能充当标题；只浏览标题应能复述页面主线。每个章节先用一至两句说明本节在父章节中的作用、范围或核心判断，再进入图、表、步骤和细节。

章节内部使用**语义路标**和**内容重点**两层导航。承担独立作用的正文块以 `**对象关系：** task 是**可执行的最小对象**。` 这种形式开头：冒号前的加粗标签准确命名本段作用；正文保持正常字重，只把决定理解或行动的关键词、关系、限制或结论片段加粗。不能只加粗标签而让真正结论淹没在正文，也不能整句或整段加粗后让读者重新寻找重点。每段只推进一个主要逻辑，通常只有一处内容重点；需要两个片段才能保留条件—结论、对象—边界等完整关系时才突出两处。只有真正承担概览或综合作用时才使用“概述”或“结论”，不能把每个换行机械套成同一组标签。仅用于引出列表或表格的短句可以只保留路标，由列表项名称或表头承担内容重点。

正文根据内容选用实际需要的递进关系，例如“定义或判断 → 机制与证据 → 限制或例外 → 必要时收束”。句子使用明确主语和具体动作，第一次出现的关键术语要能就地理解；不使用无解释的内部黑话，也不让名称代替结构、行为和理由。

按读者需要识别的关系选择表达形式：因果、机制和取舍用短段落；并列项用无序列表；步骤、阶段和优先级用有序列表；只有多个对象需要按相同维度比较时才用表格；层级、流程、状态变化、模块协作、时序、数据关系或算法结构确实比文字更清楚时才用相应图。一个图只回答一个主要问题；图前给出它支持的核心判断，邻近内容补充图中难以表达但会影响使用的输入输出、触发条件、数据变化、异常去向、约束和边界，不复述箭头，也不为了“图文并茂”强行画图。使用 Mermaid 时，代码块首个非空行必须是 `flowchart`、`sequenceDiagram`、`stateDiagram-v2`、`classDiagram`、`erDiagram` 等有效图类型声明；不会写成合法图时使用普通文本代码块，不得把文本箭头放进 `mermaid` fence。

引用只用于追溯和核验，不能替代知识内化。改变结论的细节必须进入正文；帮助验证结论的细节放在结论附近或验证章节；只供追溯的完整原料留在来源记录或附录。每个关键知识块按实际需要保留结论、成立条件、证据、机制或实现、例子或验证方法、例外、风险、来源、时间和版本，不机械凑齐全部字段，也不把充分消化替换为一两句摘要加链接。

不同内容的最低深度：

- 流程：起点、终点、角色、输入输出、并行、状态、异常、返工和下游去向；
- 模块：职责、上下游提供/消费什么、交接失败会怎样；
- 数据：核心对象、标识、关系、状态轴、统计口径、来源与新鲜度；
- 软件：使用 `assets/software-architecture.md` 按需组合代码地图、运行时序和核心类/数据关系，解释真实业务动作、职责划分、数据转换、当前限制、一次具体修改路径及基于代码的设计判断；不机械凑图；
- 规则/算法：用途、输入、输出、不变量、步骤、边界例子、容量/取整/失败行为和实际实现入口；
- 公共能力：唯一规范落点与本领域使用契约，不能把业务表字段语义吞进通用技术页。

拆出独立页不等于完成编织。逐页对照上面的最低深度和 `brief.md` 中的完成证据：若只是把父页的一段摘要搬到新文件，或授权直接来源中仍有会改变理解、实现或边界的机制尚未进入正文，回到第 2—4 步继续阅读和内化；不以页数或行数判断充分。

初稿形成后，在 `inventory.md` 完成一次**来源主题与知识落点复核**：逐项说明已定向阅读的主题进入哪篇规范页、只形成什么现实边界，或为什么明确排除。材料已经提供但正文没有落点、未知或排除说明时，不得进入内容消费；回到第 2—4 步补读、调整知识地图或编织正文。重复来源可以共同支持一个落点，不要求一份来源建一页。

同步建立领域位置视图和旅程/学习视图。视图首先回答“我在哪里、为什么先读这里、按什么问题下钻、哪些仍未知”，再链接规范页。

完成标准：零背景读者只浏览标题、章节开场、段落路标和正文中的短重点就能复述页面主线；继续阅读可以完成主要学习或工作；深入核验时能找到改变结论的条件、真实细节和直接来源。不存在连续多个作用不明的无名段落、只有标签而没有内容重点的实质段落、整句加粗后仍需重新找重点的段落、用链接替代知识内化的页面，未知也没有被完整叙事掩盖。

## 5. 先做内容消费，再做结构检查

从候选产品视图重新开始，假设自己没有读过原材料。在根 `reader-answers.md` 逐个回答 `brief.md` 的问题主线；每个有效问题必须恰好出现一次，答案要能独立理解，并且只依赖推荐视图和最多三篇规范页，精确核验时才进入来源记录。

先判断事实是否可信，再判断答案是否完整。完整性以问题原本询问的对象和范围为准：上级领域、主题全貌、完整生命周期或整个平台的问题，不能因为用户焦点中的一个当前代码纵切写得很深就升级为完整：

- `reliable` 表示题目主干和每个必要部分都已有直接证据，足以支持声明的用途；
- `partial` 表示已有可靠局部，但任一必要部分仍缺失、未展开、尚未抽取，或只能用历史/目标替代当前事实；
- `unknown` 表示现有授权材料不能形成安全答案；
- 清楚写出未知只会让答案更可信，不会把一个不完整答案升级为 `reliable`。若答案中的“未知、缺少、未实现、未展开”影响问题主干，整题必须是 `partial` 或 `unknown`；可以在正文中另说哪个局部已经可靠。

问题含多个部分时必须逐项核对：缺少平台模块、实际作业/监控/分析、核心数据或状态、公共能力落点、软件结构视图中的任何必要部分，都不能把已有局部声明成 `reliable`。

重点检查：

- 能否说清上级领域、主题全貌和焦点之间的关系；
- 能否画出主要流程、模块、对象或调用链；
- 能否从一个业务动作走到真实实现和结果；
- 能否区分当前、历史、目标、人工决定和未知；
- 能否找到算法细节、边界和来源，而不是只得到一句摘要。

回答不了时先补内容、调整知识地图或明确未知，不先围绕检查器修格式。如果 `partial` 来自已授权材料中本轮本应覆盖但尚未整理的内容，必须回到第 2—4 步；只有外部事实确实缺失时才保留责任人明确的未知。内容可用后再填写 `completion.yaml`：维度使用 `covered / unknown / not_applicable`；图表使用 `provided / not_applicable`；每项指向实际页面并说明边界。`not_applicable` 需要业务理由，不能表示“没有抽取”。这些仍是 Agent 的内容声明，人工审查前保持 `human_review_status: pending`。

完成标准：没有核心问题因为范围缺失、深度不足、错误事实源或导航断裂而不可回答；保留的未知明确由谁或什么系统补充。

## 6. 人工审查、发布与立即使用

在根 `review.md` 先链接 `reader-answers.md`，再展示推荐阅读路线、问题覆盖、核心内容差异和未知，并分为可以发布、需要选择、需要补充和建议忽略。最后运行结构检查：

```bash
python scripts/ingestion_workspace.py check <case-id>
```

它检查来源变化、工作台、Markdown、链接、视图、候选 Bundle 和正式知识零变化；`PASS` 只表示候选可交人工审查。正常摄入只使用 Skill、模板、命令帮助和错误输出，不读取检查器源码猜规则。

把最后一次检查的真实状态同步到 `review.md`；不能在最终交接中同时声称 `PASS`，却让用户入口仍显示 `PENDING_RUN` 或旧错误。声明图表 `provided` 前逐个确认 Mermaid fence 含有效图类型声明；结构检查不验证图是否能渲染。

最终只链接根 `review.md`，说明候选已形成、内容等待人工审查、正式知识未修改。用户批准后才更新正式知识、来源记录、产品视图、索引、日志和领域地图，并运行：

```bash
python scripts/knowledge_check.py
```

展示 `git diff -- knowledge config`。发布后从 `knowledge/index.md` 完成一次真实浏览或问题消费；记录实际读取页面、引用来源、未知和误解。只有人工批准、发布、结构检查和真实消费都完成，才报告摄入完成。
