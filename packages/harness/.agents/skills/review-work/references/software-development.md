# 软件开发工作审查

软件开发审查要让第一次接触任务的人快速理解完整工作，再按依赖顺序决定需求、方案、实现和证据是否成立。本文件规定复杂软件工作的报告骨架；局部简单修改可以压缩相邻章节，但不得打乱逻辑顺序或省掉决定所需事实。

## 报告骨架

按下面的顺序形成一张 `review.md`：

1. 顶部身份、使用说明与内容导航；
2. 完整工作全貌；
3. 需求审查与 `R1`；
4. 方案审查与 `R2`；
5. 修改内容、软件实现与 `R3`；
6. 运行演示、验证与 `R4`；
7. 总体决定 `R5`；
8. 报告体验 `D1`。

每一阶段先把事实讲清，再出现审查问题。后续章节可以预先呈现以便完整浏览，但只能开放第一个尚未确认的 `R`；其他审查点显示等待前序通过。

## 1. 顶部入口

标题下先给最少但完整的身份：报告版本或候选状态、审查对象、修改前后版本、任务性质和当前批准/发布状态。随后写：

- **怎样使用：** 说明从 R1 顺序审查，前序失败即可停止，并说明回复编号的方式；
- **内容导航：** 链接到完整全貌、需求、方案、实现、验证、总体决定和 D1。

顶部解决“这是什么、怎么审、从哪里开始”，不要在这里塞实现细节。

## 2. 完整工作全貌

使用四个小节建立完整故事：

### 2.1 背景与任务来源

说明业务背景、原始问题、任务由谁或哪份固定输入提出、是否为独立实验或更大诉求的合法切片，以及本任务真正要达成的目标。对齐的任务在这里说明关系，不另建重复的“任务对象核对”章节。

### 2.2 采用的方案

先用普通业务语言说清解决办法，再用一张简洁图表示“已有能力 → 本次接入或改变 → 用户结果”。图中只放理解全貌需要的节点。

### 2.3 完成的功能与结果

用紧凑表格列出用户功能、业务计算或规则、兼容性、重要共享契约、真实运行结果和回归。这里只给结论和入口，细节留在后文。

### 2.4 当前边界

明确未获批准或未发布事项、没有解决的业务含义、实验与生产边界、知识是否已更新。边界应帮助防止过度声明，不重复非目标清单。

完成标准：不看后文也能复述为什么做、采用什么办法、完成什么、证据到哪里以及不能证明什么。

## 3. 需求审查

### 3.1 原始问题

短引原始请求并链接完整任务。用户原话是事实；需求解释是分析，两者不要混写。

### 3.2 需求要做成什么

按阅读直觉说明：

1. **要解决的问题：** 用户当前为什么不方便、错误或低效；
2. **希望达到的使用效果：** 用户操作时应该得到什么变化；
3. **需要增加或改变的功能：** 为得到效果具体改变什么；
4. **做到什么算完成：** 用户路径、关键结果和必要回归；
5. **本次范围：** 只保留确实影响判断的规则、兼容、未知和不扩展内容。

不要使用“结构化需求理解”之类抽象分类，不在需求章节放实际交付结果，也不要把简单问题拆成十多个字段。

### R1：任务与需求是否成立

必须包含：

- **审查目的：** 为什么当前必须先判断需求；
- **当前待审内容：** 用一句到两句压缩本阶段判断对象；
- **请你决定：** 认可、修订、补信息或驳回的具体选项；
- **处理结果：** 不同答案会修改哪里，前序失败怎样阻断下游；
- **你的反馈：** 可直接填写的状态和意见占位。

## 4. 方案审查

### 4.1 功能位于系统的哪里

从用户和产品能理解的位置开始：

```text
产品 → 业务模块 → 页面/接口/用户入口 → 前端、后端、数据或外部系统
```

至少用一张 Mermaid 上下文或流程图标出本次主要修改节点、继续复用的节点和数据方向。图后用一两句解释颜色、箭头或边界；不能先罗列 Repository、Schema、Service、composable、类或函数。

### 4.2 总体方案

说明原来怎样工作、问题卡在哪里，以及修改后用户动作怎样经过各模块得到结果。跨层任务再用一张前后对比图或主流程图表示变化；简单单层任务可用短流程代替。

### 4.3 模块变更方案

用表格说明“所在位置、原来的情况、本次修改、修改后的作用”。模块粒度保持一致，从架构层到局部逐层展开。只有存在实质选项、风险或成本差异时才写设计取舍；正常复用和没有新增无关模块不单独包装成决策。

### R2：方案是否合理

沿用 R1 的五部分格式，审查系统位置、前后端通路、模块变化和真正的设计取舍。方案被否定时不批准现有实现。

完成标准：审查者不读源码也能指出改的是哪个产品模块、数据怎样流动、每一层为什么要改。

## 5. 修改内容与软件实现审查

### 5.1 版本与查看入口

列出修改前、修改后、相关知识或数据版本，并提供可直接执行的完整 Diff 命令或链接。不要用 Diff 行数代替实现说明。

### 5.2 按模块说明修改

用表格按架构层次说明文件、原职责、本次实现和影响。文件名应服从模块关系，而不是按 `git diff --name-only` 平铺。

### 5.3 关键实现流程

跨层调用、状态变化或数据转换使用 Mermaid 时序图、组件图或简短伪代码，展示用户动作怎样落到关键代码入口以及结果怎样返回。只放关键结构和算法，不复制大段源码。

### 5.4 核心算法与边界

说明本次新增或继续复用的业务规则、公式、数据转换、异常与边界。没有新增算法时明确 owner 在哪里以及本次只是怎样消费，不为了填章节编造复杂度。

### 5.5 批准关闭条件覆盖

任务有批准方案或明确完成条件时，用紧凑表格逐项说明：

| 批准条件或完成声明 | 实现落点 | 正向证据 | 最可能失败的反例 | 当前状态 |
|---|---|---|---|---|

反例随声明类型选择，不机械套用固定清单：

- “全部、任意、每个、完整”需要覆盖非默认分支、边界和至少一个反例；
- 筛选、选择、展开或范围切换需要追到承诺的导出、弹窗、图表、批量动作等下游结果；
- “公共复用”需要证明两个实际消费者共享同一 owner，而不只是出现一个公共命名的组件；
- “旧能力已迁移/不再使用”需要列出仍在运行的调用者，并证明旧 owner 没有活跃消费者；
- 删除旧实现或测试需要列出“旧行为 → 新 owner → 替代测试或真实证据”。剩余测试全绿不能替代这张映射。

未覆盖项写“未完成”或“未验证”，不能靠改写措辞、缩小批准条件或引用测试总数变成通过。
“实现落点”不能只写组件或函数名；每项用户能力还要能沿“触发入口 → 状态或作用域 → 全部承诺的
下游结果”走通。同一能力在主页面、详情、导出等多个位置出现时分别核对，不能用一个位置通过
概括其他位置。

### R3：实现是否符合方案

沿用 R1 的五部分格式，聚焦实际 Diff 是否落在方案边界、是否出现平行计算、无关重构、遗漏消费者或兼容问题。

完成标准：审查者能从模块图下钻到关键文件、数据流程和算法，并知道完整 Diff 在哪里。

## 6. 运行演示与验证审查

复杂施工若运行过独立交付复核，在本节列出复核上下文身份、逐条结果和它亲自执行的代表动作；
`fail` 或 `not_proven` 不能被开发者自己的测试数量覆盖。独立复核是 R4 的证据，不替代用户决定。

### 6.1 验证范围

先说明要证明的用户结果、真实输入、环境、数据范围和本轮没有执行的副作用。明确哪些是执行者已有记录、哪些是本轮新鲜观察、哪些只是代码推断。

### 6.2 真实结果

优先用结果表展示实际对象、输入、观察和结论。用户可见页面、API、数据库、CLI 或外部副作用优先于测试数量；跨层任务应能从同一范围串起关键结果。

页面任务先记录一次没有手动刷新或预热状态的首次进入结果，再记录其他交互。结构化文件、消息、
目录或规则表要展示解析后的字段/列、代表值和语义对账；文件存在、大小、返回成功或包含关键词
不能作为内容正确。目录或枚举指标至少用一个容易遗漏的合法状态与独立事实源对账。

### 6.3 回归与证据边界

列高价值回归、类型/构建结果和证据入口，并说明不能外推到生产、其他数据范围或未运行路径的内容。截图不能代替交互，测试数量不能代替用户结果。

同时检查报告内部是否自相矛盾：如果边界、遗留项或关闭条件覆盖表已经承认必需能力未完成，
“全部完成、完整交付、R3/R4 已满足”等总结必须同步收窄，总体决定保持关闭。测试文件被删除时，
还要检查它保护的行为是否已经迁移到新测试或真实用户路径；不能只比较通过数量。

### R4：验证是否足以支持当前结论

沿用 R1 的五部分格式，要求用户判断证据是否支持报告声明、是否要补真实路径。缺证据时补验证或收窄声明，不用改写措辞掩盖。

完成标准：每项完成声明都能回到真实结果或明确的已有记录，证据边界不会被误读为生产结论。

## 7. 总体决定

只有 R1—R4 均通过后才开放 R5。先用小表列出“认可/认证、修改后复审、驳回”分别怎样处理代码、报告、知识和发布状态，再形成 R5；R5 使用审查目的、决定选项、处理结果和反馈占位。

## 8. 报告体验

用 D1 单独评价报告是否让人快速理解和作决定。它与开发成果判断分开：工作被驳回不等于报告失败，工作正确也不等于报告好用。D1 询问缺背景、重点、顺序、信息量和待决点是否有效，并说明反馈先修改本报告/评价，跨第二类任务成立后才进入共享 Harness。

## 待决点优先级

优先呈现会改变接受结论的问题：

1. 任务和产物是否对齐，任务是不是更大诉求的合法切片；
2. 公共接口、Schema、指标上限、数据模型等共享契约是否被改变；
3. 业务含义、风险语义和用户看到的视觉表达是否需要决定；
4. 真实运行证据能证明什么，实验、生产和未验证路径的边界；
5. 代码、配置、知识和产品发布状态是否一致。

只有会影响上述判断时，才提升措辞、代码风格、测试粒度或其他局部问题。不要为了“发现问题”制造低价值待决点。
