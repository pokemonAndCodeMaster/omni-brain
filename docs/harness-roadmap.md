## 1. 一分钟看懂项目

### 1.1 最终要做成什么

Omni-Brain 最终交付的是一套可以复制到真实项目、由 Codex 或 OpenCode 直接使用的 **Agent Harness**。这里的 Harness 不是新的大模型运行平台，而是项目内的一组外部能力：项目规则、Skills、确定性工具、工作区、规范知识、验证方法和评测资产。

用户提出真实需求后，它应能完成下面的闭环：

```text
理解真实目标
→ 判断任务需要多少背景和设计
→ 取得最低充分的知识与当前事实
→ 形成方案并产生真实产物
→ 在项目真实环境中验证
→ 把稳定的新知识、规则、验证方法和失败经验变成长期候选
→ 人工审查后晋升
→ 后续任务直接复用
```

## 3. 一条统一复利闭环

知识、开发、验证、Skill、评测和系统演进不是六个平台，而是同一闭环中的六种责任：

```text
真实目标
  ↓
任务分级：直接执行 / 定向准备 / 完整准备
  ↓
知识与当前事实：已有、缺失、冲突、可信范围
  ↓
方案、开发或业务执行
  ↓
真实产物：知识、代码、SQL、配置、数据结果
  ↓
项目验证：数据库、API、页面、脚本和副作用
  ↓
候选沉淀：知识、规则、Skill、验证方法、评测样例
  ↓
审查、发布和回滚
  ↓
后续任务复用，并从重复失败中优化 Harness
```

一次非简单任务通常会涉及六类信息，但它们只是责任，不是强制创建六份文件：

1. 任务目标、非目标、风险和验收；
2. 本次需要的知识、事实、冲突和缺口；
3. 跨会话可恢复的工作状态；
4. 用户真正要用的产物；
5. 实际运行了什么、结果怎样、还没验证什么；
6. 哪些内容值得成为长期资产候选。

只有跨会话恢复、人工审查或重复复用确有需要时，才把相应信息持久化。

## 5. 五阶段时间线

下面的时间是**单主线、一个主要实现者、评测环境和用户审查能够正常获得**时的规划时间盒，不是固定交付承诺。阶段是否退出以真实结果为准，不能为了日期降低门槛。

| 阶段 | 预计时间盒 | 用户首次得到的能力 | 主要发布结果 |
|---|---:|---|---|
| **M1 知识整理与摄入** | **首个切片已完成** | 把混乱文档和代码变成可浏览、可追溯、可发布的知识 | 知识可用版 |
| **M2 可信查询与任务上下文** | 约 2—3 周 | 立即知道已有、缺失、冲突、可信范围和下一步 | 查询与上下文版 |
| **M3 知识驱动真实工作与验证** | 约 4—6 周 | 用知识完成真实开发/数据任务，并复用项目验证方法 | 真实工作版 |
| **M4 变化回写与资产复利** | 约 3—5 周 | 代码、规则和流程变化后，知识与可复用能力安全演进 | 持续演进版 |
| **M5 跨模型、领域与规模发布** | 约 4—6 周 | 换模型、宿主和领域后仍能开箱使用 | 可移植发布版 |

按照当前信息，从现在完成其余第一版可移植闭环约需 **13—20 个有效工作周**。时间盒仍按能力成熟度统计，但 M2 与 M3 不再机械串行：开发切片先交付日常价值，查询、知识和验证能力在其中逐步成熟；不需要等待 M5 才产生价值。

### 5.1 近期实际执行顺序

当前优先级由“哪个组件先完整”改为“哪条真实任务最快形成可用结果和可复用证据”：

1. **局部只读前端开发：** 验收配额可见性；验证取知、复用、Vue 交付、真实运行和知识候选；
2. **真实查询与调试：** 围绕首切片追问指标、零分母、代码入口和故障，抽取 M2 的最低充分上下文；
3. **隔离数据写入：** 本地表格入库；验证 Schema、映射、事务、幂等和副作用；
4. **只读 SQL 优化：** 从真实聚合中选取代表查询；验证执行计划、等价性和性能证据；
5. **跨层业务功能：** 验收分配缺口已经跑通 Catalog、Repository、HTTP、Vue 和真实页面；保留为开发回归；
6. **变化后回写：** 当前主线，使用配额和缺口的同一代码谱系更新正式知识和产品视图；
7. **跨模型/宿主/邻近模块：** 每个切片都做弱模型回归，M5 再做完整组合迁移。

知识摄入继续作为回归和缺口补全能力穿插其中，而不是暂停，也不再单独占据全部近期资源。质检资产的角色与用例覆盖见[质检真实工况与资产覆盖目录](experiments/quality-harness-fixture-catalog.md)。

附件提出的六次能力扩展没有被丢弃，只是合并进项目已经使用的五个阶段，避免再增加一套编号：

| 附件中的能力重点 | 本路线落点 |
|---|---|
| 先把知识生成—发布—消费闭环收口 | M1 |
| 可信查询与任务上下文 | M2 |
| 知识驱动真实开发 | M3 前半段 |
| 项目验证方法库 | M3 后半段 |
| 反馈、规则与 Skill 复利 | M4 |
| 统一项目验证/能力评测与受控优化 | M4，并在 M5 做跨模型和规模硬化 |

```text
M1：知识可发布、可消费（首个切片已完成）
  └─ 现在 → M2：知识可可信查询、可组装任务上下文
            └─ M3：知识进入真实开发，验证方法可复用
                 └─ M4：工作结果反向更新知识与 Harness
                      └─ M5：跨模型、领域和规模硬化
```

## 6. M1：知识整理与摄入

### 6.1 用户工况

用户给出一批质量不一、重复、过时、冲突、零散或结构混乱的文档和代码，希望得到能够长期维护、直接学习和继续工作的知识。

### 6.2 本阶段要实现的组件

| 组件 | 本阶段实现深度 |
|---|---|
| C1 | 固定文档、代码提交和非 Git 运行输入；说明能证明什么、不能证明什么 |
| C2 | Markdown/OKF 规范知识、唯一落点、现实状态和细节保真 |
| C4 | 轻量链接、关键词、符号、import 和接口路径选源 |
| C5 | 从目标到问题、小批来源、规范正文、缺口、审查、发布和回滚 |
| C7 | 领域位置视图与学习/调试旅程同步产出 |
| C9 | 正式/候选隔离、人工发布、Git 差异和回滚 |
| C10 | 认证参考、内容问题、真实运行、消费会话和跨模型 Trial |

C3 只记录公共能力候选；C6 只服务当前摄入问题；C8 不提前建设通用开发工作台。

### 6.3 技术方案

- 规范源：UTF-8 Markdown + OKF frontmatter；
- 版本与回滚：Git；
- 人类跳转：标准相对 Markdown 链接；
- 产品视图：领域位置 + 学习/工作旅程；
- 语义流程：一个知识摄入 Skill；
- 后台状态：单个 case 状态和来源清单，用户不手工维护；
- 确定性工具：来源冻结、候选选源、隔离运行、知识检查和审查页生成；
- 真实运行：临时 worktree/副本，复用项目自己的数据库、API、页面和测试入口；
- 当前不采用：数据库作为知识真相源、向量库、图数据库、Web UI、自研 Agent runtime。

### 6.4 用户最终拿到什么

1. 正式规范知识页；
2. 领域入口和学习/调试视图；
3. 来源、当前事实、历史、目标、冲突和未知边界；
4. 一份发布审查页；
5. 可复现的运行或核对路径；
6. Git 中可审查、可回滚的正式知识版本。

内部的 `case.json`、来源清单和运行记录只是支撑，不是用户主要产物。

### 6.5 用例和验证顺序

| 顺序 | 用例 | 验证目的 | 通过标准 |
|---:|---|---|---|
| 1 | 代码全链路摄入 | 证明中央源码、数据转换、运行环境和页面链能够进入知识 | 内容至少 `20/24`；固定 API、同范围 SQL、正常/边界对象和页面链可复现 |
| 2 | 基础文档摄入 | 防止代码工况优化后丢掉领域全貌、流程和复杂业务语义 | 内容至少 `20/24`，核心问题无 `0`，来源和正式知识不被候选污染 |
| 3 | 增量文档摄入 | 证明不是每次重建一套知识 | 正确新增、更新、合并、冲突、过时和视图变化；不产生平行知识 |
| 4 | 正式发布与新会话消费 | 证明候选真正成为可用知识 | 用户批准；新会话不读原料即可完成约定问题和一次真实核对 |
| 5 | 跨模型重放 | 证明不是当前模型临场能力 | 至少两种中等或偏弱模型保持内容、安全和运行下限 |

`18—19/24` 只允许一次有明确根因的定向修订；低于 `18/24` 回到工作流或组件层，不继续向 Prompt 写答案；达到 `20/24` 才进入发布审查。

## 7. M2：可信查询与任务上下文

### 7.1 用户工况

用户提出一个知识问题、调试问题或开发需求。Harness 不把整库塞进上下文，而是立即说明：已有知识是什么、当前源码或系统事实是什么、哪些内容缺失或冲突、还需要读什么、为什么读到这里就够了。

### 7.2 主要组件

| 组件 | 本阶段新增能力 |
|---|---|
| C4 | 从 Markdown、代码符号、Schema 和链接生成可重建查询索引 |
| C6 | 问题理解、可信状态、最低充分上下文、停止规则和补知闭环 |
| C7 | 问题直达、答案下钻和任务阅读路线 |
| C10 | 查询正确性、漏召回、无效阅读、成本和跨模型评测 |

复用 M1 的 C1/C2/C5；查询发现长期知识缺口时重新进入摄入，而不是把一次回答偷偷写成规范事实。

### 7.3 第一版产物

1. 一个自然语言查询/任务入口；
2. 直接答案与最短依据链；
3. 当前事实、历史、目标、推断、冲突和未知的明确区分；
4. 最低充分的任务上下文；
5. 缺口、责任来源和下一动作；
6. 一组真实查询与调试回归用例。

### 7.4 技术推进

第一版先使用 Markdown 导航、`rg`、代码符号和实时事实源。只有真实用例出现下面的失败，才升级技术：

| 可重复失败 | 最小候选技术 |
|---|---|
| 精确术语、字段或路径找不到 | SQLite FTS5 或等价全文索引 |
| 同义表达经常漏召回 | 向量召回或混合检索，并与基线成对比较 |
| 调用链和影响关系不完整 | 代码解析、符号图或关系索引 |
| 找到很多内容但方向错误 | 改任务规划、事实源顺序和停止规则，不先换数据库 |
| 旧知识压过当前实现 | 新鲜度、版本和事实源优先级 |

### 7.5 首批用例与退出标准

- 首先嵌入“验收配额可见性”开发切片，回答为什么复用既有指标、为何仍需把 9 + 5 查询上限最小调到 14、两个比率的分母、零分母、代码入口和验证路径；
- 再使用 M1 正式发布的代码知识回答并调试两个既有指标；
- 至少准备 10 个真实问题，覆盖直接事实、跨层追踪、缺失、冲突和当前源码下钻；
- 不读历史聊天即可得到正确答案；
- 不无界翻库，读源码范围与问题相关；
- 未知不编造，缺口能够进入补知并回到知识底座；
- 认证知识输入和真实候选知识输入都通过，避免只在完美种子上工作。

## 8. M3：知识驱动真实工作与验证

### 8.1 用户工况

用户提出真实开发、数据处理、SQL 优化或业务能力需求。Harness 根据影响和风险选择合适的设计深度，取得相关知识，完成修改，并在项目真实环境验证。

### 8.2 任务强度

| 模式 | 典型条件 | 必要产物 |
|---|---|---|
| 直接执行 | 局部、低风险、接口和验收明确、容易回滚 | 真实修改与直接验证 |
| 简要设计 | 两三个模块、存在局部接口选择 | 一页变更说明：改什么、为何、影响、不改什么、怎样验证 |
| 充分设计 | 跨前后端/数据库、公共契约、多个方案、高风险或知识冲突 | 现状、方案比较、影响、迁移、回滚和完整验证计划 |

### 8.3 主要组件

| 组件 | 本阶段新增能力 |
|---|---|
| C3 | 识别并复用数据库、公共组件、日志、存储等稳定能力 |
| C6 | 为真实任务组装业务—系统—代码—运行上下文 |
| C8 | 任务分级、方案、实现、调试、产物与交接 |
| C10 | 项目验证方法、真实运行记录和 Harness 能力评测 |

### 8.4 第一批真实任务

1. **验收配额可见性**：把已有预期分配量和分配达成率接入任务分析表，验证最低充分取知、既有能力复用、Vue 交付、真实运行和知识变化候选；
2. **本地表格安全写入数据库**：验证字段映射、人工确认、事务、重复执行和回滚；
3. **SQL 执行计划与性能优化**：验证真实参数、结果等价和性能前后证据；
4. **人工质检跨层业务能力**：验证业务语义、公共组件、数据库、API 和浏览器完整链。

任务必须解决真实问题，不为覆盖技术栈而造题。

### 8.5 验证方法库

M3 不建设抽象的“验证平台”，而是在真实任务中积累 **可重复验证方法**。每项方法至少说明：

- 适用于哪些代码或能力；
- 使用什么项目环境和服务；
- 正常、边界和失败输入；
- 执行哪些脚本、SQL、API 或页面步骤；
- 检查哪些不变量和副作用；
- 保存哪些结果；
- 怎样清理和回滚。

单任务验证回答“这次产物是否正确”；能力评测回答“模型、Skill 或 Harness 是否比基线更好”。二者复用环境、产物、运行记录和检查器，但隐藏参考与评测集保持隔离。

### 8.6 退出标准

- 三类真实任务至少各完成一个；
- 代码或数据副作用在项目真实环境跑通；
- 验证强度与风险匹配，不用大量无效单元测试代替用户路径；
- 形成首批 5—8 个可复用验证方法；
- 至少一个中等模型能够依靠 M1/M2 的知识完成任务；
- 任务完成后能够提出知识、规则、验证和评测候选，但不机械全部持久化。

## 9. M4：变化回写与资产复利

### 9.1 用户工况

代码、Schema、接口、业务规则或运行方式发生真实变化后，系统识别受影响知识，更新唯一规范落点和产品视图，并把多次任务中稳定出现的经验晋升为规则、Skill、工具或评测用例。

### 9.2 主要组件

| 组件 | 本阶段新增能力 |
|---|---|
| C1/C2 | 新旧事实、版本、历史和适用范围演进 |
| C4 | 从代码、Schema 和知识变化生成影响候选 |
| C9 | change set、人工审查、发布、回归和回滚 |
| C10 | 历史失败回归、Skill/Harness 对比和受控优化 |

### 9.3 任务结束时检查的四类资产

每次非简单真实任务结束时依次判断，而不是强制全部生成：

1. **可直接使用的产物**：代码、知识、SQL、配置或业务结果；
2. **可复用验证方法**：下次怎样在真实环境证明它仍然正确；
3. **值得回放的评测样例**：历史失败或容易回归的真实任务；
4. **长期候选**：知识、项目规则、Skill、工具或反例。

候选分流规则：

| 内容 | 默认去向 |
|---|---|
| 一次任务临时修正 | 任务记录，不进入长期底座 |
| 当前项目事实 | 规范知识候选 |
| 已批准架构选择 | 决策记录或规范知识 |
| 稳定项目规则 | `AGENTS.md` 或项目规范 |
| 可重复语义流程 | Skill |
| 确定性重复动作 | 工具或脚本 |
| 稳定验证步骤 | 验证方法 |
| 历史错误与反例 | 评测用例或避坑知识 |

### 9.4 Skill 分层

- 底层工具：搜索、worktree、运行、证据、diff、发布和回滚；
- 跨项目 Skill：现状调查、方案设计、有界实现、项目验证、任务复盘；
- 项目 Skill：质检平台特有的开发、指标追踪和运行方法；
- 模块级细节：先留在知识或验证方法，只有多次重复且接口稳定后才升级 Skill。

### 9.5 受控优化

第一版优化不是在线自改 Prompt 或强化学习，而是：

```text
多次真实失败
→ 聚合相似模式
→ 判断根因在知识、路由、Skill、工具、环境还是验证
→ 形成最小修改
→ 目标用例验证
→ 核心回归
→ 跨模型或留出用例
→ 人工批准、灰度和回滚
```

### 9.6 退出标准

- 使用 M3 的一次真实代码变化完成知识回写；
- 旧事实被正确更新或保留为历史，视图不复制第二份事实；
- 发布失败可以整组回滚；
- 至少形成一项经多任务证明的 Skill、规则或验证方法晋升；
- 调整 Harness 后目标用例改善且核心回归不退化；
- 单次反馈不会直接修改全局系统。

### 9.7 当前进度

首个代码回写用例使用已发布质检知识与 `qpl-gap-ref@35948ae`，已经具备固定输入、`24/24` 强参考、24 项内容题和四轮弱模型 Trial。第四轮候选达到工作台 `publish_ready`，正式知识与来源保持只读，独立内容审计为 `22/24`。这证明 M4 的最薄纵向能力已形成，但关键题未全过，尚未达到本阶段退出标准。

Trial 后的最小修正要求软件知识解释实际类型/行转换，固定验证报告进入正文时保留代表性结果；95 项 Harness 回归通过。下一次验证必须换相邻代码变化，若仍失败则回到内容取证与组织层，不扩建发布控制面。

## 10. M5：跨模型、领域与规模发布

### 10.1 用户工况

把已经验证的完整闭环交给另一模型、另一兼容助手、邻近业务领域或更大的材料/代码规模，结果仍可接受，失败能够安全停止并交给人。

### 10.2 主要工作

1. 固化可复制的发布目录、安装说明、升级和回滚方式；
2. 验证 Codex 与 OpenCode 的项目根发现、Skills 和命令兼容性；
3. 选择第二质检领域或邻近业务域，不复制第一领域答案；
4. 对比不同模型的内容质量、运行正确性、时间、成本和人工负担；
5. 增加材料规模、代码规模和并发协作，只修复真实暴露的问题；
6. 明确单项目文件模式何时需要 SQLite、服务化、权限或中央索引。

### 10.3 最终交付物

- 一个干净、可复制的 Harness Release；
- 项目接入、升级、回滚和兼容说明；
- 已验证 Skills、工具、知识结构和验证方法；
- 用例、参考、回归和跨模型结果；
- 适用范围、已知失败和人工接管边界；
- 第二领域的真实结果。

### 10.4 退出标准

- 至少两种模型、两个宿主组合和两个领域能够完成代表闭环；
- 结果质量、耗时和人工负担在批准范围；
- 不依赖设计仓私有参考或历史聊天；
- 新项目可以从根目录发现入口并完成首个任务；
- 升级、失败和回滚均有真实演练；
- 复杂存储或服务化只有在测量结果证明必要时引入。

## 13. 技术演进与复杂度准入

| 技术能力 | 当前决定 | 重新评估触发条件 |
|---|---|---|
| 模型运行 | 复用 Codex/OpenCode 原生会话 | 宿主无法提供必要状态、工具或权限边界 |
| 规范知识存储 | Markdown/OKF + Git | 人类审查、规模写入或复杂事务出现可测瓶颈 |
| 查询索引 | 文件导航、`rg`、轻量符号和链接 | M2 用例量化漏召回、延迟或上下文成本 |
| 向量检索 | 当前不引入 | 同义和语义召回持续失败，且基线对比证明有收益 |
| 代码关系图 | 当前只做可重建轻量关系 | 多个真实依赖/影响任务稳定失败 |
| 图数据库 | 不作为知识真相源 | 关系规模和多跳查询证明文件/派生索引不足 |
| 状态存储 | case-local 文件与 Git | 多用户并发、权限或查询量证明需要服务化 |
| Web 控制台 | 当前不建设 | Markdown 产品视图无法支撑已验证用户旅程 |
| 多 Agent 编排 | 当前不建设 | 单会话真实任务出现可重复的并行瓶颈和清晰隔离边界 |
| 自动晋升 | 不允许 | 即使后续自动提案，最终知识、规则和高风险动作仍需受控批准 |
| 在线自改/RL | 暂缓 | 证据、回归、失败归因、灰度和回滚都已成熟后再评估 |

原则只有一句：

> 当前薄实现 → 观测明确失败 → 证明现有方式不足 → 引入最小新能力 → 成对评测 → 保留或回滚。

## 14. 如何管理计划和进度

### 14.1 一个阶段怎样开始

开始前必须明确：

1. 谁在什么真实工况下使用；
2. 固定输入是什么；
3. 用户怎样从项目根触发；
4. 最终拿到什么、放在哪里；
5. 产物接下来怎样被真实消费；
6. 什么运行结果和人工判断证明通过；
7. 失败后优先修改哪一层。

缺少任一项，不开始实现。

### 14.2 一轮实验怎样结束

每轮至少冻结一种有价值结果：

- 可发布候选；
- 经验证的 Harness 修订；
- 新鲜运行证据；
- 能否定当前路线的明确结论。

只增加 Trial 目录、测试数、Prompt 规则或中间状态不算推进。

### 14.3 文档职责

| 文档 | 只负责什么 |
|---|---|
| [Blueprint](blueprint.md) | 稳定目标、架构、C1—C10 和设计原则 |
| **本 Master Roadmap** | 完整阶段计划、时间线、组件实施、用例、产物、验证和进度摘要 |
| [当前工作台](now.md) | 新会话恢复当前唯一动作 |
| [实验与评测总账](../eval/STATUS.md) | 精确 Trial、版本、分数和证据 |
| [真实工作场景](experiments/knowledge-driven-work-experiments.md) | 尚未实施场景的用户旅程和设计问题 |
| `docs/specs/` | 已确认阶段内某一具体能力怎样实现 |

本页应在阶段边界、时间盒、用例组合、组件计划或当前阶段结论变化时更新；单次 Trial 的细节只更新实验总账和审计，避免路线图被日志淹没。

只有出现以下情况才需要用户：

- 读后发现中的事实和机制出现来源无法解释的冲突，需要人类判断；

- 候选达到发布线，需要审查正式知识；
- 首个开发参考结果需要确认是否符合业务与交互预期；
