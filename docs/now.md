# 当前实验工作台

> 最近更新：2026-07-29。

## 当前状态

知识摄入已能在发布前隔离候选并形成局部业务—代码纵切。V10—V12 依次验证了长文有界输出、关键来源选择、三层知识定位和已读内容落页；同条件模型比较中 Kimi 与 GLM 5.1 均为 19/24，MiniMax M2.7 为 12/24，因此日常实验固定使用 GLM 5.1。V13.1 前向实验进一步验证了首读前完整内容计划、阶段化模板加载、21 个关键来源的串行直接展示和后置消费指令遵循，但内容仍为 19/24，且模型没有自行完成结构收尾。V13.2 只修现有接口：模板直接给出合法格式、相邻知识层允许合理共置、部分/未知答案必须说明责任与影响、占位和 stub 作为负面证据保留。当前状态是 `implemented_content_first_v13_2_awaiting_forward_test`；正式知识仍为空。

## 当前可用

- OpenCode 原生根路由；
- `ingest-knowledge` 的盘点、候选编织、人工门禁、发布与立即消费流程；
- 面向弱模型的内容主线：先定义读者问题和“上级定位 → 主题全貌 → 用户焦点”，再匹配直接事实源、设计知识地图、从全貌下钻到代码/算法，最后从产品视图实际回答问题；
- `reader-answers.md` 逐题消费页：每个核心问题都必须给出可靠答案、部分答案、明确未知或确实不适用，并限制到产品视图和最多三篇规范页；
- `ingestion_workspace.py` 的机器来源清单、`source-read` 有界连续展示、`source-select` 关键来源绑定、Agent 覆盖声明、固定根入口、内容声明契约和结构检查；
- `completion.yaml` 的 `parent → subject → focus` 知识主线：每个适用层必须关联已读直接来源和正文主落点；相邻层只有在同一稳定主题、共同维护且章节边界清楚时才能共置；
- `completion.yaml` 和内容消费均支持 `partial`：已有可用知识时保留证据页，同时明确已覆盖与仍缺范围，不再被迫在“完整”和“未知”之间二选一；
- Skill 模板按步骤渐进加载：内容计划、来源阅读、写作、产品视图、消费与审查不会在任务开始时一次性进入上下文；
- Skill 以单来源为原子推进单位：完成内容计划后，一次只读取一份实质来源，并在下一次阅读前把具体机制和落点写入可恢复工作台；
- `completion.yaml` 与 `review.md` 模板直接提供检查器所需的来源 mapping、相对路径、固定入口和分层标题，不要求模型读取源码猜格式；
- `reader-answers.md` 要求每个 partial/unknown 同时写明缺失事实、责任来源、工作影响和下一动作；
- 空目录、`.gitkeep`、stub 和占位接口作为负面证据保留，不能被写成已实现能力或简单筛成无关材料；
- `inventory.md` 的已读内容落点：关键来源中的机制、条件、边界、冲突和未知必须在继续阅读前关联到具体页面/章节、开放问题或具体排除；
- 候选产品视图唯一位于 `draft/knowledge/views/`：具名视图带 frontmatter，`index.md` 只导航；检查器拒绝旧 `draft/views/` 和重复 frontmatter 键；
- 空 OKF Bundle、领域地图和两类产品视图入口；
- 标准 Markdown 相对链接约定与只读链接/入链检查；
- 已有任务案和本地 Git 来源范围能力。

- 缺口责任和负面证据规则能否补齐完整交付、OBS、部署与人员责任，并让内容超过 19/24；

- 算法细节、现实形态、冲突和未知能否保持准确；
- 用户审查负担是否可接受。
