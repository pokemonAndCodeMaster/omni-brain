# 知识摄入

目标不是清点材料或通过检查，而是让不熟悉原料的读者建立正确心智模型并能继续工作。始终抓住三件事：用**问题主线**决定要学什么，用**逐层下钻**连接上级全貌与用户焦点，用**直接事实源**保住细节和现实状态。

来源是证据，`knowledge/` 是唯一发布面，`workspaces/knowledge-ingestion/<case-id>/` 是发布前工作台。工具只负责盘点、固定入口和结构约束；Agent 负责理解、取舍与编织；人负责关键语义和发布决定。

## 1. 定义读者结果并建立工作台

从请求中提取材料位置、目标读者、知识用途和用户真正关心的焦点。用户说“浏览、理解、学习、继续使用”且没有说明背景时，按零背景读者设计。

先读 `knowledge/index.md`、`config/knowledge-domains.yaml` 和直接相关入口，再初始化授权来源；初始化前不要自行递归枚举：

```bash
python scripts/ingestion_workspace.py init <case-id> \
  --goal '<用户读完后能够理解、判断或执行什么>' \
  --source <source-id>=<authorized-directory> [--source ...]
```

填写根 `brief.md`，先完成内容计划而不是文件计划：

1. 写出“上级定位 → 主题全貌 → 用户焦点”的逐层地图；上级定位必须说明所属领域与同级能力，只有直接证据表明主题确为根领域时才可没有上级；
2. 用生命周期、角色、核心对象与状态、平台/软件模块、上游下游与同级能力五个切面检查主题全貌，不能用一条流程代替全貌；
3. 写出读者最终必须能回答的问题主线，并为每题标明回答深度、所需现实形态和候选直接来源；
4. 规划候选规范页与产品视图，让每个问题都有落点；
5. 只有范围或关键语义必须由人选择时才追问；其余不确定项先作为待确认保留。

完成标准：读者结果清楚；焦点没有脱离上级领域和完整运作；每个核心问题已有预期答案深度、直接来源类型和候选知识落点。

## 2. 沿问题主线阅读直接事实源

先读 `source-summary.md`，再围绕每个问题搜索最小充分来源。来源很多时用机器清单有界定位：

```bash
python scripts/ingestion_workspace.py files <case-id> <source-id> \
  [--glob '<pattern>'] [--limit 100]
```

不要按目录从头读，也不要只读名字最像用户焦点的文件。按以下方式匹配结论与事实源：

- 当前软件行为：源码、Schema、配置、测试和新鲜运行结果；
- 当前业务语义：明确的人工决定、业务原始记录和当前数据口径；
- 目标方案：设计稿、计划和待实施契约；
- 历史做法：历史脚本、旧规范和带时间边界的快照；
- 生成综合或旧知识页：用于定位和发现冲突，不能单独证明当前行为。

逐层下钻时控制深度：上级层讲清所属领域为什么存在、与同级能力怎样分工；主题全貌层覆盖生命周期、角色、核心对象与状态、平台/软件模块、上下游；用户焦点层再讲业务、数据、软件、规则、算法和工程细节。上级不是一句背景，焦点也不能吞掉整个领域。

若材料涉及软件或代码，且知识将用于理解、开发或维护，必须读取真实代码并至少追踪一个业务动作：

```text
用户目的与输入
→ 真实入口
→ 包、模块、类、函数与数据结构
→ 数据转换和状态变化
→ 数据库/外部系统
→ 返回结果与失败边界
→ 各层职责为什么这样划分、当前限制和一次具体修改路径
```

覆盖账本只在阅读过程中顺手维护，不用它决定内容范围。状态是 Agent 声明：标题或关键词扫描记 `screened`；精确段落/符号记 `read_targeted`；确实完整读取单文件才记 `read_full`。第一次登记前先运行 `python scripts/ingestion_workspace.py mark --help`；例如完整读完一个文件后可执行：

```bash
python scripts/ingestion_workspace.py mark <case-id> <source-id> \
  --status read_full --path '<exact-relative-path>' \
  --reason '<该文件支持什么问题>' --evidence '<exact-relative-path>#full-file'
```

禁止用 glob 写强阅读状态；命令失败时先根据帮助修正一次，不要连续猜参数。

在 `inventory.md` 按问题记录所用直接来源、能证明/不能证明、冲突和时效；无法安全回答的事项写入 `questions.md`，不以常识补齐。

完成标准：每个核心问题都有直接证据、明确未知或人工待决；当前代码结论不依赖二手摘要；来源阅读范围由问题充分性而不是文件数量决定。

## 3. 先设计知识地图，再写正文

根据实际材料修订 `brief.md` 中的候选知识地图：

- 每个稳定主题只有一个规范落点；按领域主题组织，不按来源类型拆散同一件事；
- 领域路径表达主要归属，从现有上级逐层展开；新增领域在 `review.md` 展示名称、唯一上级、范围和排除项；
- 跨领域公共能力只保留一个规范页，各领域只写用途、输入输出、依赖保证、特有限制和失败影响；分别记录“已覆盖”“相关但未知或尚未抽取”“确实不适用”，不能因为本轮没抽取就写成不适用；
- 产品视图负责位置、阅读顺序、问题入口和下一跳，不复制规范事实；
- 当前实现、人工决定、目标设计、历史快照和开放问题可以互相连接，但不能混成一张“现状”。

在开始批量写页前检查：每个读者问题能落到一至三篇规范页或一个显式未知；每个候选页面都能说明服务哪个问题、属于哪一层、依赖哪些直接来源。发现上级全貌或关键事实源缺失时回到第 2 步，不用窄主题摘要填空。

完成标准：知识地图覆盖问题主线且没有孤立焦点、重复事实或无来源页面。

## 4. 从全貌到细节编织候选

所有相对路径都以 `workspaces/knowledge-ingestion/<case-id>/` 为根；候选只写入该根下的 `draft/knowledge/` 和 `draft/config/`，不能在仓库根或相邻目录另建 `draft/`。每页按读者理解顺序写：

1. 先给本页结论、解决的问题和适用边界；
2. 说明它在上级领域、流程或系统中的位置；
3. 用图与文字呈现全貌；
4. 再展开可以独立理解和更新的业务、数据、软件或算法块；
5. 最后区分现实形态、冲突、未知和直接来源。

不同内容的最低深度：

- 流程：起点、终点、角色、输入输出、并行、状态、异常、返工和下游去向；
- 模块：职责、上下游提供/消费什么、交接失败会怎样；
- 数据：核心对象、标识、关系、状态轴、统计口径、来源与新鲜度；
- 软件：真实业务动作、包/模块/类/数据职责、调用时序、数据转换、职责这样划分的理由、当前限制、一次具体修改路径、当前/目标差异和基于代码的设计判断；
- 规则/算法：用途、输入、输出、不变量、步骤、边界例子、容量/取整/失败行为和实际实现入口；
- 公共能力：唯一规范落点与本领域使用契约，不能把业务表字段语义吞进通用技术页。

层级、流程、模块协作、时序、数据关系或算法用图会更清楚时，提供 Mermaid 和完整文字备份。不堆设计模式名词，不使用无解释的内部黑话；名称不能替代结构、行为和理由。

同步建立领域位置视图和旅程/学习视图。视图首先回答“我在哪里、为什么先读这里、按什么问题下钻、哪些仍未知”，再链接规范页。

完成标准：零背景读者先看全貌即可定位，再下钻能看到足以支持学习或工作的真实细节；关键结论能回到直接来源，未知没有被完整叙事掩盖。

## 5. 先做内容消费，再做结构检查

从候选产品视图重新开始，假设自己没有读过原材料。在根 `reader-answers.md` 逐个回答 `brief.md` 的问题主线；每个有效问题必须恰好出现一次，答案要能独立理解，并且只依赖推荐视图和最多三篇规范页，精确核验时才进入来源记录。材料不足时写 `partial` 或 `unknown`，问题不能消失。

重点检查：

- 能否说清上级领域、主题全貌和焦点之间的关系；
- 能否画出主要流程、模块、对象或调用链；
- 能否从一个业务动作走到真实实现和结果；
- 能否区分当前、历史、目标、人工决定和未知；
- 能否找到算法细节、边界和来源，而不是只得到一句摘要。

回答不了时先补内容、调整知识地图或明确未知，不先围绕检查器修格式。如果 `partial` 来自已授权材料中本轮本应覆盖但尚未整理的内容，必须回到第 2—4 步；只有缺少外部事实时才保留责任人明确的未知。内容可用后再填写 `completion.yaml`：维度使用 `covered / unknown / not_applicable`；图表使用 `provided / not_applicable`；每项指向实际页面并说明边界。`not_applicable` 需要业务理由，不能表示“没有抽取”。这些仍是 Agent 的内容声明，人工审查前保持 `human_review_status: pending`。

完成标准：没有核心问题因为范围缺失、深度不足、错误事实源或导航断裂而不可回答；保留的未知明确由谁或什么系统补充。

## 6. 人工审查、发布与立即使用

在根 `review.md` 先链接 `reader-answers.md`，再展示推荐阅读路线、问题覆盖、核心内容差异和未知，并分为可以发布、需要选择、需要补充和建议忽略。最后运行结构检查：

```bash
python scripts/ingestion_workspace.py check <case-id>
```

它检查来源变化、工作台、Markdown、链接、视图、候选 Bundle 和正式知识零变化；`PASS` 只表示候选可交人工审查。正常摄入只使用 Skill、模板、命令帮助和错误输出，不读取检查器源码猜规则。

最终只链接根 `review.md`，说明候选已形成、内容等待人工审查、正式知识未修改。用户批准后才更新正式知识、来源记录、产品视图、索引、日志和领域地图，并运行：

```bash
python scripts/knowledge_check.py
```

展示 `git diff -- knowledge config`。发布后从 `knowledge/index.md` 完成一次真实浏览或问题消费；记录实际读取页面、引用来源、未知和误解。只有人工批准、发布、结构检查和真实消费都完成，才报告摄入完成。

## 模板

- 内容计划与问题主线：`assets/brief.md`
- 逐题消费结果：`assets/reader-answers.md`
- 来源与问题对应：`assets/inventory.md`
- 规范页与领域总览：`assets/knowledge-page.md`、`domain-overview.md`
- 产品视图：`assets/product-view.md`
- 内容与发布审查：`assets/review.md`
- 结构声明与来源记录：`assets/completion.yaml`、`source-record.md`
- 公共能力候选：`assets/shared-capability-review.md`
