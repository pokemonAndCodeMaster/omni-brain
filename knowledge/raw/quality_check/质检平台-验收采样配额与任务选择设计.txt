# 质检平台验收采样配额与任务选择设计

← 总入口：[[质检一站式平台人工质检模块整体架构]]。前端呈现：[[质检平台-人工质检验收中心前端设计]]。统计依据：[[质检平台-综合快照表设计]]。执行回查：[[质检平台-Delta调用与状态回查设计]]。现状来源：[[人工质检-⑧验收分配]]。

## ① 组件概述

验收采样配额与任务选择组件负责回答"今天这个组/这个人该抽多少 Good、多少 Bad、从哪些 task 抽"，位于质检平台整体架构的 **Service 层**，以 [[质检平台-综合快照表设计]] 聚合后的统计行为输入，输出 `SamplingQuota` 给 Repository 查询具体 task_ids，再由 `AssignmentService` 生成 preview 并通过 [[质检平台-Delta调用与状态回查设计]] 调用 DeltaClient。该组件遵循"算多少"与"取哪些"分离原则，使采样策略可纯数据测试。

### preview→execute 数据流时序图（Mermaid sequenceDiagram）

```mermaid
sequenceDiagram
    participant FE as 前端
    participant AS as AssignmentService
    participant SP as Sampler
    participant RP as Repository
    participant DC as DeltaClient

    FE->>AS: POST /preview (sampler_name, params)
    AS->>SP: compute(snapshot_rows, params)
    SP-->>AS: SamplingQuota(dim_key, good_count, bad_count)
    AS->>RP: query_task_ids(quota, waiting_review)
    RP-->>AS: task_ids[good], task_ids[bad]
    AS-->>FE: preview(配额, 分布, 缺口, 警告)

    FE->>AS: POST /execute (preview_id, task_ids)
    AS->>RP: recheck_status(task_ids)  %% 重查当前状态
    RP-->>AS: still_waiting_ids
    AS->>DC: batch_assign(still_waiting_ids)
    DC-->>AS: 即时成功/跳过/失败
    AS-->>FE: execute 即时结果（实际量由后续回查刷新）
```

时序图说明：preview 与 execute 分两步；execute 必须先重查 task 状态，只保留 `waiting_review`，复用 preview 的 task_ids 不重新选择；即时返回不等同最终成功量，最终量由 [[质检平台-Delta调用与状态回查设计]] 的状态回查刷新到 `acceptance_allocated`。

## ⑤ 详细设计展开

### 5.1 设计初衷

旧脚本把配额公式、任务查询、验收员轮询、平台调用和通知揉在一起，策略难以测试。新设计将"算多少"和"取哪些 task"拆开：

- Sampler 只根据快照计数计算配额；
- Repository 根据配额查询具体 task_ids；
- Service 生成 preview 并调用 DeltaClient。

拆分后既保留快照作为采样依据，也承认执行必须落到 clip/task 级。

> 📎 补充参考：[[人工质检-⑧验收分配]] 描述旧脚本中验收分配的现状实现，本卡是新平台设计，两者互补而非重复。

### 5.2 输入与输出

Sampler 输入为个人最小统计行：日期、scene、当日组、标注员、组员数、Good/Bad 可用量。

Sampler 输出 `SamplingQuota`：同样的维度键 + good_count + bad_count。它不包含数据库连接和 task 状态。

Repository 输入 quota，输出当前仍为 waiting_review 且满足分类条件的 task_ids。

### 5.3 三种策略

#### GroupSampler

来源规则：每组目标量 `min(组员数 × 90, 300)`，Good/Bad 各 50%，按 scene 比例覆盖。

步骤：

1. 按组汇总可用量和活跃标注员数。
2. 计算组总目标。
3. 将目标拆为 Good/Bad；奇数余量的归属需在实现前固定并测试。
4. 按各 scene 可用量比例分配配额。
5. 处理取整余数，确保总和等于目标且单桶不超过可用量。
6. 一侧不足时由另一侧补足。**旧版有补足逻辑**，来源：`data_check_debug/data_check/manual_label/batch_acceptance/assign_acceptance_task.py:500-510` 的 `in_group_simpling` 函数。

##### 采样常量值（旧版源码）

`assign_acceptance_task.py:36-39` 硬编码：

```python
ASSIGN_NUM_PER_SCREENER = 90  # 默认每名验收员的抽检数量
ASSIGN_NUM_PER_GROUP = 300    # 默认每组的抽检数量
GOOD_RATIO = 0.5              # good抽取比例
```

- `GOOD_RATIO = 0.5`：Good/Bad 各抽 50%
- `ASSIGN_NUM_PER_GROUP = 300`：每组最多抽 300
- `ASSIGN_NUM_PER_SCREENER = 90`：每人最多抽 90

##### 补足逻辑（旧版源码）

`assign_acceptance_task.py:500-510` 的补足规则：

1. 先计算 `good_need_num = math.ceil(total_assign_num * good_ratio)`，`bad_need_num = total_assign_num - good_need_num`
2. **判断哪侧少，先抽少的一侧，不足由多的一侧补足**：
   - 若 `good_total_num >= bad_total_num`（Good 多 Bad 少）：
     - 先抽 Bad：`bad_extract_num_actually = min(bad_total_num, bad_need_num)`
     - Good 补足：`good_need_num = total_assign_num - bad_extract_num_actually`，`good_extract_num_actually = min(good_total_num, good_need_num)`
   - 若 `good_total_num < bad_total_num`（Good 少 Bad 多）：
     - 先抽 Good：`good_extract_num_actually = min(good_total_num, good_need_num)`
     - Bad 补足：`bad_need_num = total_assign_num - good_extract_num_actually`，`bad_extract_num_actually = min(bad_total_num, bad_need_num)`
3. **补足方向**：少的一侧先抽到自身可用量上限，差额由多的一侧补足（而非简单 Good 不足由 Bad 补 or 反之，而是双向动态补足）。

> 本节事实来源见 [[质检平台-人工质检模块实施计划#待决疑问区]] 决策1/2。事实已填入，待人类决策（见计划卡决策1/2）。

#### PersonalSampler

每人目标 90，Good/Bad 各 45；一侧不足由另一侧补足。每个标注员独立计算，便于人员画像和公平覆盖。

#### RatioSampler

用户给最终目标数和 Good 比例，用于临时业务。必须校验总量非负、比例 0～1、筛选范围非空，并展示数据不足警告。

> 📎 2026-07-06 首版已落地（合并自源仓库 A6）：Good 可用量取 `option_annotation.GOOD - good_allocated`，Bad 取剩余未分配可用量，二者严格守恒；一类不足时由另一类补足并给出警告，总量不足返回 shortage。实现与预览闭环见 [[人工质检验收分配预览闭环设计]]。

### 5.4 比例分配与取整

比例分配不能逐桶 `round()` 后任由总数漂移。建议：

1. 计算每桶理论值；
2. 先取整数部分；
3. 按小数余数从大到小补足剩余名额；
4. 同余数时按稳定维度键排序，保证测试可重复；
5. 桶容量不足时把剩余名额继续分给有容量的桶。

这是实现建议，不改变原业务目标。

### 5.5 task 选择

Repository 查询条件至少包含 stat_date 对应范围、scene_name、annotator_id、Good/Bad 分类和 waiting_review 状态。

具体随机/稳定排序方式必须从旧脚本核实。无论采用何种方式，都只在 preview 时选择一次；execute 使用 preview 返回的原 task_ids，不重新选择。

### 5.6 供应商与人员约束

- 标注员与验收员不能来自同一供应商。
- 未进组标注员不能静默丢弃，preview 返回警告和数量。
- 非 ACTIVE 人员不参与新分配。
- 验收员池和 e2e/VPD 轮询关系来自现有配置，后续由人力表/配置替代硬编码。

### 5.7 注册表

`SAMPLER_REGISTRY` 是名称、描述和实现的唯一来源；不再维护 `SamplerName` Enum。前端 `/samplers` 直接读取注册表。

### 5.8 preview 与执行结果

preview 展示预期配额、具体 task 数、按组/scene/人员分布、缺口和警告。execute 返回即时结果；实际成功量以后续回查刷新为准。

### 5.9 测试矩阵

- 正常 Good/Bad 充足；一侧不足；总量不足。
- 多 scene 比例和取整余数。
- 0 人组、未进组、非活跃人员、供应商冲突。
- preview 后部分 task 状态变化。
- 重复 execute 跳过已处理 task。
