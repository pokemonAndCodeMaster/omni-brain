# 形成可审方案

把复杂诉求先变成用户能看懂、能纠正、能批准的需求和方案，再交给开发。核心产物只有一张
`workspaces/reviews/<task-id>/review.md`；不另建需求 YAML、方案账本或平行版本。

方案形成阶段的产品写入白名单只有这张 `review.md`。R2 获批前，不得创建或修改源码、测试、
配置、`.env`、`.env.example`、`.gitignore`、迁移文件、原型和运行数据；“不是源代码”不等于
“没有修改产品”。**方案获批前不修改产品代码或其他产品文件。** 可以只读查证配置和运行环境，
但不得为证明方案先把设计实现一部分。

## 1. 判断是否需要先形成方案

满足任一条件时使用本 Skill：

- 用户明确要求讨论需求、设计方案、比较技术选择或先不要开发；
- 用户描述了复杂目标，但业务口径、主要交互、公共能力边界或完成标准仍会改变实现方向；
- 改动跨前后端、数据、多个业务模块，或会建立以后复用的公共能力；
- 错误决定会造成大范围返工，且当前没有用户批准过的方案。

以下情况不触发：

- 文案、样式、局部 bug 等目标和验收都明确的低风险修改，直接执行；
- 已存在与当前请求对齐、且用户明确批准的 R1/R2，交给 `develop-with-knowledge`；
- 只审查已经发生的工作，交给 `review-work`；
- 关键事实缺失或冲突到无法讨论需求时，只做一次有界查证；仍无法回答就说明它会影响哪个决定、已经查过什么和需要谁补充什么，并停在相应审查阶段，不猜测也不另建平行工作区。

不要因“任务很大”自动拆成多个没有用户意义的小任务。是否分阶段只看每一阶段能否独立产生用户结果、降低真实风险或取得必要证据。

**完成标准：** 已说明为何需要方案、唯一审查文件在哪里、当前只推进 R1 还是 R2。

## 2. 先形成 R1：需求理解

第一次只使用用户原始请求、会话中明确补充的事实，以及项目根 `AGENTS.md` 和一份能确认产品位置的入口文档。不要先遍历目录、通读源码、加载已完成工作审查模板，也不要为了显得专业先设计技术方案。

把 R1 按人的理解顺序写清：

1. **背景与主要问题：** 谁在什么场景下遇到什么阻碍，最值得解决的矛盾是什么；
2. **目标与使用结果：** 用户最终怎样操作、看到什么、能完成什么；
3. **功能与业务规则：** 按用户旅程或同一层级的功能模块组织，不把不同粒度的点平铺；
4. **范围与保持不变的内容：** 本次必须覆盖什么、哪些现有行为不能被悄悄改变；
5. **完成标准：** 用可观察的操作、结果和关键边界说明怎样算完成；
6. **确实需要确认的问题：** 只问答案会改变产品行为、业务含义或方案责任的问题；能从用户原话或当前事实直接得到的内容不反问。

原始请求是事实，需求理解是分析，两者分开表达。使用普通业务语言；不要用“结构化需求理解、正差、契约、纵切”等内部词替代实际问题。复杂需求优先用一张表把“类别、目标、功能、规则、完成表现”放在同一层级；简单需求用几段话即可。

此时在 `review.md` 中只开放 `R1`。R1 后面的方案只标为“等待 R1 通过”，不得提前写成既定方案或读取大量实现来填满报告。

**完成标准：** 第一次接触任务的人能复述主要矛盾、用户结果、功能范围和完成标准；用户只需修订或批准 R1。

## 3. 接收 R1 反馈

用户反馈后更新同一张 `review.md`：

- 把用户纠正直接合入需求正文，同时保留简短的“本轮修订”说明；
- 重新检查目标、功能、规则、边界和完成标准是否受影响；
- 用户未回答且会改变方案的问题继续留在 R1，不靠模型偏好拍板；
- 用户明确说“R1 通过”后，将 R1 标记为已确认，才进入 R2。

不要创建 `review-v2.md`，也不要把历轮正文重复堆在文件末尾。

## 4. 为 R2 做最低充分查证

R1 通过后，先把方案需要回答的问题列成一个短清单，例如：功能位于哪里、现有 owner 是谁、哪些能力可复用、数据由谁提供、哪个未知会改变模块边界。每个问题只读取能直接回答它的来源。

按以下路线下钻：

1. 项目 `AGENTS.md`、当前接力页或组件地图；
2. 用户入口或页面 → 当前调用者 → 一个相近实现 → 数据/状态 owner → 对应验证入口；
3. 必要的 Schema、配置和运行结果；正式知识存在时，只读能回答 R1 中业务含义或架构边界的最少页面。

每次扩读前说明它可能改变哪个方案判断。连续两次读取没有改变系统位置、复用判断、模块责任或待决问题时停止扩读。不得递归通读源码，也不得把历史归档中的目标方案当作当前事实。

当前实现只证明“现在怎样做”，不自动证明它是需求、合理边界或应该保留的架构。源码中的临时
阈值、保护逻辑、目录、泛化服务、状态位和旧接口都先作为待解释的现状：只有用户决定、当前
工况证据或明确兼容责任支持时，才能升级为方案约束。

事实不足时分三类处理：

- 能通过一个直接来源或短运行探针确认：继续查证；
- 只是实现细节且不改变用户结果：在方案中给出有依据的默认选择；
- 会改变业务语义、公共接口、规模假设、不可逆副作用或模块责任：作为 R2 待决项，给出少量有实际差异的选项。

“存在多个技术选项”本身不构成人工待决。若选项不改变用户行为或业务语义，且可以通过当前
架构、真实工况和验证来裁决，Agent 必须给出一个有依据的方案和待验证假设，不能把实现责任
转交用户。只有人的偏好、权限或业务决定才能回答，或者决定会形成不可逆外部承诺时才提问。

**完成标准：** 每个会改变方案的判断都有当前来源、明确假设或人工待决项；没有为获得安全感而通读工程。

## 5. 形成 R2：可实施方案

复杂软件方案在写入前完整读取 [`references/software-solution.md`](references/software-solution.md)，按任务复杂度裁剪。R2 必须从用户和产品能理解的位置开始，再逐层进入工程实现：

1. **系统位置与现状：** 哪个产品、业务模块和用户入口发生变化，当前能力和阻碍是什么；
2. **总体方案：** 用一张简洁图呈现用户动作、前端、后端、数据和结果怎样连通，并标出继续复用与本次改变；
3. **模块方案：** 按同一粒度说明每个模块原职责、本次改变、改变后的作用和上下游；
4. **关键行为与数据：** 交互、状态、聚合/转换、完整性、复用和异常怎样处理；
5. **接口与代码组织：** 命名反映具体业务功能，责任归入对应领域模块；不要用 `analysis`、`manager`、`query` 等无边界名称承接所有能力；
6. **迁移与退出：** 新能力替代、吸收或重构旧职责时，说明保留什么、迁移什么、何时删除旧路径；不因“风险低”默认让新旧两套职责长期并存；
7. **验证方案：** 用真实用户路径、API/数据和关键边界证明需求完成；不拿大量低价值单元测试替代实际效果；
8. **仍需用户决定：** 只留下存在真实选择的内容，说明推荐项、差异和决定后的影响。

架构重构或平台化方案还要从 R1 中的日常工作反推结构。逐项覆盖用户主动操作、后台处理、数据
写入、后续读取和状态变化，确认每个过程都有入口、业务 owner、数据 owner、输出、失败处理和
真实验证；不能只画一条主流程，就遗漏浏览、编辑、导出、管理或其他已确认的日常动作。该覆盖
直接体现在现有流程、模块、接口和验证段中，不另建追踪文件。

若需求把“可扩展到多个真实对象”列为第一版结果，方案必须选择至少两个存在实质差异的真实
对象验证抽象，并说清差异落在哪个可替换责任；只定义 Protocol、基类、插件目录或“以后再增加”
不算形成可施工方案。若第一版并未承诺多个对象，则不要为了证明扩展性虚构第二个实现。

R2 是可施工方案，不是方向清单。每个计划中的接口或公共能力都要写出实际用例、责任 owner、
输入、输出、失败方式和消费者；不能用“例如某某查询”“必要时增加接口”代替设计。如果完整
数据、元数据、聚合计算或导出承担不同责任，就分别落到明确用例，不让万能端点或模糊候选
继续留给开发者猜。

接口表是方案的完整施工清单，不是示例摘要。写完后从总体图、模块表、关键流程和所有消费者
反向列出它们依赖的数据对象与动作，逐一确认接口表中有对应行；若复用既有接口，也要在该行
写清 owner、输入、成功输出、失败方式与消费者并标注“既有不变”。正文出现“指标定义单独
提供”“候选值独立查询”“完整明细另取”等承诺而接口表没有对应行，视为方案未完成，必须补齐
或删除承诺。接口表、模块表、图和验证中的业务用例名称应一致。

这里的施工清单也包含客户端聚合、指标计算、导出等不经过 HTTP 的本地用例。用“无新增后端
接口”标注它们，但仍写清 owner、输入、输出、失败方式与消费者；不能因为它是函数或 composable
就让核心算法从用例表消失。

兼容入口可以列入施工清单，但它的消费者只能是尚未迁移的旧调用方。若新页面、新工作台或新
公共能力出现在消费者列，就说明它仍是目标主链路，不能再标“既有不变/仅兼容”。此时必须把
所需责任迁入明确业务 owner、迁移新消费者，并在表中写目标 owner；不能用“后端不新增类”作为
继续依赖无边界模块的理由。若方案同时写“目标归业务模块”和“新消费者继续调用泛化 owner”，
视为责任冲突，R2 不可交接。

R2 不能悄悄削弱已经确认的 R1。形成方案后，逐项把 R1 的主要用户结果和业务规则对应到模块、
数据来源、接口/本地计算与真实验证；这项核对可以直接体现在现有模块表和验证段，不新增追踪
文件。特别检查“全部、任意、一次取用、共同复用、成功即完整”等范围词是否被方案改成了
“当前页、当前层、必要时、分批另查”。若确实需要改变已确认语义，必须回到用户说明原因和
影响，不能用实现便利或现状限制自行降级。

同一份数据被主表、详情、图表或导出共同消费时，必须说清它实际包含什么、谁保证完整、何时
失效或重新获取。某个输出若需要底层明细、一对多记录或指标定义，而当前数据只有聚合行，方案
必须补出这些数据的明确来源和取得时机；不能一边声称“无需新增查询/已有数据直接生成”，一边
在导出或详情中使用尚未取得的数据。

不要凭经验硬编码分页量、数据上限、异步任务、降级标志或备用结果。性能、完整性和规模策略应由当前工况、运行证据或用户决定支持；系统应先实现其承诺的正确结果，不用额外状态位掩盖不完整。

把用户语言翻译成状态时保持原语义：集合不自动变成有序列表，“任选”不自动变成固定顺序，
一次动作不自动变成长期配置。接口成功若承诺完整结果，就由提供方保证完整或整体失败；不要
把完整性责任泄漏给调用方，再用 `complete`、`loaded` 一类标志让调用方猜测结果能否使用。

导出、文件格式和第三方库从实际使用者、目标软件、字符集、数据类型、嵌套/变长结构和真实
规模反推。不要机械默认 CSV，也不要在没有证据时预建异步系统；需要引入库时先写清候选与
验证条件，而不是把第一个想到的包直接写成批准选型。

对结构化导出，稳定标量和固定嵌套字段展开为有类型的列；一对多或变长数据放入可关联的独立
明细表/工作表；另用说明区记录筛选范围、数据时间、导出时间和关键口径。只写“JSON 可读”或
“拆成行列”不算完成设计。

这里的“独立明细表/工作表”是与基础明细分开的关系表，不是把变长记录作为额外行混进同一张
基础明细表。方案必须写出关联键、每张表的粒度和字段类型，让目标软件可以直接筛选、透视和
关联，不依赖阅读序列化文本或猜测不同行的类型。

在 `review.md` 中开放 `R2`，R1 保留为已确认。方案获批前，产品写入仍严格限于这张审查页。

**完成标准：** 用户不读源码也能指出改的是哪里、全部已确认日常工作怎样流动、数据为何这样
存取、主要软件单元怎样协作、各模块为何这样分、扩展点由什么真实差异证明，以及哪些决定仍需要他确认。

## 6. 接收 R2 反馈并交接开发

收到反馈后只修改受影响的方案部分，并检查下游模块、接口、验证是否需要同步。用户明确说“R2 通过”后：

1. 在同一 `review.md` 标记 R2 已确认并记录批准范围；
2. 列出开发开始时必须保持的用户结果、业务规则、模块责任和验证目标；
3. 交给 `develop-with-knowledge` 从已确认 R1/R2 开始实施；该 Skill 不重新发明方案；
4. 实现与真实验证完成后，再由 `review-work` 在同一审查入口补充实现和验证阶段。

用户否定的设计必须从当前正文删除，不能只在文末追加一条相反结论。用户说明“其余内容合理”、
某问题不再阻塞或批准推荐项后，应关闭对应待决项；不要把已经收敛的选择换个说法再次提问。
最终交接前从头通读一次，清除重复章节、旧接口、旧状态、互相矛盾的图表和过期问题。

“其余内容合理”“其他方案基本合理”是对本轮反馈未点名部分的接受，不是继续保留旧待决项的
理由。处理这类反馈时先列出反馈前的全部待决项：被用户明确修订的按新意见落地，未被否定且
已有推荐方案的直接采用推荐项并关闭，只有用户明确保留或确实没有可负责默认值的业务决定才
继续开放。反馈要求“给出确认项”时，确认项是待用户一次批准的方案摘要，不得把已经有推荐且
被“其余合理”覆盖的旧问题重新包装成 D1、D2。

写完后做一次状态一致性检查：标题、导航、R1/R2 状态、正文中的待决表、结尾复选框和最终回复
必须表达同一状态；待决项数量必须相同。若尚待用户批准整份 R2，可以写“R2 待整体确认，当前
无开放决策”，不能为了维持互动而制造一个问题。检查正文中是否出现相邻重复行、重复表格行、
重复小节或同一结论的正反两种说法，发现后原位清理。

没有开放决策时，相关章节使用“确认摘要与尚未实施”之类准确标题，不再叫“仍需用户决定”。

最后从确认摘要反查正文原句，动作极性必须一致，尤其是“同步/异步、保留/删除、新增/复用、
完整/部分”。一句摘要若同时出现“不同步生成”和“不做异步”等冲突，必须回到当前方案统一。

关闭 R2 前逐项检查：每个需求都有模块、数据/接口和验证承接；每个待决项都能说明为何只能由
人回答；每个已被“其余内容合理”等反馈覆盖的推荐项已经写入当前方案而不是继续等待确认。

若用分阶段降低施工风险，必须明确这些阶段只是同一完整任务的实现顺序。除非某阶段本身交付
了用户认可的独立结果，否则不能把阶段完成冒充原需求完成。

如果用户只要求形成方案，到此停止。最终回复只给当前结论、可点击的 `review.md`、本轮批准状态和下一责任人，不复制整份报告。

**完成标准：** 开发者不依赖聊天历史即可按已批准方案实施；用户清楚接下来无需再做什么，或只需决定哪个具体问题。

## 护栏

- 一次任务只有一个 `review.md`，R1/R2 是同一条工作链的阶段，不是两份报告。
- 先抓主要矛盾，再补完整范围；不以字段齐全代替需求理解。
- 图用于说明关系和变化，表用于比较同粒度内容，正文用于解释原因和边界。
- 标题用稳定、简洁的名词短语；段落先说明目的或结论，只加粗关键短语，不整段加粗。
- 需求简单时压缩报告，不机械复制完整骨架。
- Skill 只规定形成方案的方法，不包含任何领域的固定接口、指标、目录、数值或参考答案。
