# 人工质检验收结论与通过/打回执行

## 先看结论

验收数据是样本统计，验收结论是规则基于统计得出的决定，执行才真正改变决定范围内的标注全集。结论可以是 PASS、REJECT，目标方案还引入 PENDING 表示数据不足；执行前要确认范围和当前数据，执行后要回查外部状态。

固定代码没有结论规则或执行能力。下面的阈值属于历史脚本，不是当前生产规则。

## 三个对象

```mermaid
flowchart LR
    M[验收指标\n完成度、Good/Bad/整体通过率] --> R[规则判断]
    R --> D[结论\nPASS/REJECT/PENDING]
    D --> C[人工确认\n范围、依据和影响数量]
    C --> E[外部执行\n作用于范围内标注全集]
    E --> V[状态回查\n确认实际结果]
```

## 历史规则快照

历史脚本材料记录：

1. **完成度前置**：总验收数至少达到应抽数量的 95%，或达到总提交数的 95%，否则不执行。
2. **Good/Bad 样本占比充足**：当 Good/Bad 验收数占总验收数至少 90% 时，Good 通过率严格 `> 0.9499`，Bad/脏数据通过率严格 `> 0.7999`。
3. **样本占比不足**：低于 90% 时用总通过率严格 `> 0.9499` 兜底。
4. **边界是严格大于**：恰好等于 `0.9499` 或 `0.7999` 不通过。
5. **历史打回链**：先处理待验收状态，等待 60 秒，再处理待审核/审核中状态，并写材料所称 DMP 打回记录。

这些细节被保留是为了不损失历史算法，但不代表当前生产继续使用 95%、90%、0.9499、0.7999 或两次回退；当前规则仍是未知。

## 目标规则输入和输出

目标规则接收明确的聚合指标，而不是数据库连接或任意字典：应抽数量、总提交、已完成验收、Good/Bad 已完成与通过数量、总通过数量和适用范围。

```text
decision: PASS | REJECT | PENDING
reason: 面向用户的中文原因
details:
  completion_rate
  good_pass_rate
  bad_pass_rate
  total_pass_rate
  thresholds
  rule_name
  scope
```

PENDING 不是质量失败，而是证据不足，不能执行通过或打回。用户已确认保留这个目标设计概念；当前代码和生产规则仍未证明使用它。

## 目标执行流程

1. 后端校验权限和请求范围。
2. 重新从当前数据聚合指标并计算结论。
3. 若当前结论与用户提交不同，停止并要求重新审视。
4. PENDING 直接拒绝执行。
5. Repository 按决定范围反查具体 task_ids，并检查当前外部状态。
6. PASS 或 REJECT 调用相应外部接口。
7. 返回请求、即时成功、跳过、失败和结果未知数量。
8. 后续回查外部状态，确认最终成功或返工状态，再更新页面统计。

执行范围可以按 Good/Bad、选项、任务、组或个人变化。无论粒度如何，打回对象是该范围对应的标注全集，不只是验收样本。

## 为什么请求成功仍不能结束

批量操作可能部分失败、超时或只表示外部系统已接收请求。需要分开记录：

| 结果 | 含义 |
|---|---|
| 请求量 | 本次提交给外部接口的 task 数 |
| 即时成功/失败 | 同步响应能够确认的结果 |
| 跳过 | 状态已经变化或已达到目标，不再重复操作 |
| 结果未知 | 超时或无法确认，需先回查 |
| 实际成功量 | 后续状态查询确认到达目标状态的数量 |

本页只解释业务正确性，不展开通用重试或可观察性方案。

## 当前实现缺口

固定提交不存在 `pass_rules.py`、`ExecutionService`、执行 API 或外部任务系统客户端。因此它不能计算正式结论、通过/打回、回查实际状态或跟踪返工。目标材料中后续 JSONB `exec_status` 状态机与早期列式方案也存在版本演进，未取得对应代码前不能选作当前 Schema。
