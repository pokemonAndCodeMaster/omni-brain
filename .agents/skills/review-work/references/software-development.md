# 软件开发工作审查

仅在审查软件开发、修复、重构或性能优化时读取。本文件规定要让人看懂什么，不是固定 Markdown 模板；按任务复杂度删减章节。

## 1. 完整工作全貌

开头用最短路径说明：

- 业务和系统背景；
- 原始任务及其来源；
- 最终采用的方案；
- 完成的功能；
- 修改的模块；
- 实际运行结果；
- 当前边界和批准状态。

全貌用于建立上下文，不提前替用户批准后续阶段。

## 2. 需求审查

先引用或链接原始问题，再按阅读直觉说明：

1. **要解决的问题：** 当前用户为什么不方便、错误或低效；
2. **希望达到的效果：** 用户完成操作时应该看到什么变化；
3. **需要增加或改变的功能：** 为得到该效果具体做什么；
4. **做到什么算完成：** 哪些用户操作和关键结果必须成立；
5. **必要范围：** 只保留确实影响判断的业务规则、兼容、非目标、风险和未知。

不要用抽象的“结构化需求理解”表把简单问题拆成十余项，也不要在需求阶段提前放置“需求—交付结果对应表”；实际完成情况属于验证。

## 3. 方案审查

### 3.1 先定位系统位置

从人能理解的位置开始，再下钻代码：

```text
产品
└─ 业务模块
   └─ 页面、接口或用户入口
      ├─ 前端相关模块
      ├─ 后端相关模块
      └─ 数据或外部系统
```

优先用上下文图标出本次主要修改节点和继续复用的节点。不能先罗列 Repository、Schema、Service、composable、类或函数，再让审查者猜它们属于哪一层。

### 3.2 说明从什么改成什么

用一张前后对比图或一段清晰流程说明：

- 原来怎样工作、问题卡在哪里；
- 修改后用户动作怎样经过各模块得到结果；
- 哪个模块新增、修改或保持不变。

随后用表格补充“所在位置、原来的情况、本次修改、修改后的作用”。如果图已经讲清，不重复建立“现状叠加”章节。

### 3.3 只展开真正重要的设计

数据模型、算法、交互、性能、兼容和公共能力只有会改变方案或审查结论时才展开。只有存在多个实质选项、风险或成本差异时才列取舍；“复用了现有能力”“没有新增无关模块”是正常设计结果，不自动成为关键决策章节。

## 4. 修改内容与实现审查

先给修改前后的仓库与提交，再提供完整 Diff 命令或链接。按模块和架构层次说明：

- 代码位置；
- 原职责；
- 本次实现；
- 相邻消费者和影响；
- 关键调用、状态或数据转换；
- 新增或改变的算法、边界与异常。

需要时使用组件图、时序图、类图或简短伪代码。不要搬运整段源码，也不要用 Diff 行数代替实现说明。

## 5. 运行演示与验证审查

把“修改后用户看到了什么”放在这里。按声明组织证据：

| 要证明什么 | 使用的真实输入和环境 | 实际观察 | 证据入口 | 未覆盖范围 |
|---|---|---|---|---|

优先展示真实页面、API、CLI、数据库或外部副作用，再列高价值回归。明确区分执行模型亲自观察、独立评测补跑和代码推断；测试数量不能替代用户结果，截图不能替代交互，实验环境不能冒充生产。

需求阶段若列出完成标准，可以在这里逐项核对，但不要复制第二套需求说明。

## 6. 审查点

通常使用：

- `R1`：任务和需求是否成立；
- `R2`：总体与模块方案是否合理；
- `R3`：实现是否符合方案；
- `R4`：真实证据是否支持声明；
- `R5`：成果的总体决定；
- `D1`：报告是否帮助完成审查。

简单任务可以合并审查点，复杂任务可以增加子问题，但始终保持前序失败阻断后序。`D1` 只评价报告，不与 `R5` 的成果决定混写。
