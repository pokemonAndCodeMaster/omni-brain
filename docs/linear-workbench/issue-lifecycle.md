# 从想法到成果：共同工作记录

你可以在 Linear 记一句想法，也可以直接对 Codex 或有 Linear 工具的 ChatGPT 说“我想做到……”。Agent 负责找回相关材料、澄清真正的问题、提出下一步，并把结果留在同一件事里。换会话后，依据线上当前记录继续。

本说明由 Omni-Brain 仓库维护，发布到 Linear 供各入口共同阅读。它是个人工作台的操作方法；每项工作的具体目标、最新进展和授权仍以当前用户请求及对应事项为准。

## 开始一件事

先判断是在随手记录、了解情况、讨论、执行还是检查结果。普通问答直接回答，不因为开了新会话就创建事项。需要跟踪时先找已有同一目标，有就继续；确实是新的工作再创建。

暂时只想保存的内容，用原话记到 Backlog，说明为什么值得以后再看。开始推进时再澄清，不要求先写完整需求。

需求澄清先回答：你在什么场景遇到什么问题，希望产生什么变化，有什么能说明成功或失败的真实例子，以及什么限制会改变选择。Agent 先整理已有信息，只问缺失的关键部分。你不用填表，也不用替 Agent 选择配置文件和技术步骤。

例如“我想找到全部文档”，要先分清是缺少完整目录，还是缺少阅读顺序。需要的使用结果明确后，才比较怎样做。

## 决定这次推进到哪里

一个清楚、可以整体检查的结果，用一条事项。几步顺手操作写在正文，不必各建一项。部分工作确实需要分别安排或交接时用子事项；多个成果共同形成一个阶段结果时用项目。

需求清楚不代表实施方法已知。关键问题还没有答案时，可以先跟踪探索或方案设计：写明需要回答什么，交什么证据或方案，得到答案后怎样继续。方案完成不代表功能实现完成。用户已允许自主取舍的范围由 Agent 负责选择，不因缺少固定审批用语再次索取授权。

共有目标、使用场景和重要取舍在父事项或项目说明中维护；具体事项引用这些背景并说明自己的结果。拆分后保留原始想法和承接关系，不能只剩一堆技术步骤。

## 事项里始终保存什么

读者不翻历史，也应能知道原任务、当前结果、还有什么没有做，以及下一步是谁的工作。按事情复杂程度组织这些内容，不要求每个小事项填写同样多的标题。

| 内容 | 保存方式 |
| --- | --- |
| 原问题、目标与成功例子 | 事项正文；复杂共有背景放项目说明或关联文档 |
| 当前决定与工作范围 | 合入当前正文。尚待验证的假设明确写出；保留重要取舍理由 |
| 实际进展与成果 | 链到可阅读的文档、可运行的代码或检查证据，并说明结果意味着什么 |
| 尚未完成与下一步 | 写具体缺口、准备采取的行动；确需用户时说明要补什么或判断什么 |
| 所需知识、代码、Agent 与技能 | 链到各自唯一原文，必要时记录本次使用的版本和影响范围 |

讨论可以发生在聊天或评论中。值得长期保留的决定应合回当前正文；不能让新旧意见并列、要求读者自己判断哪版有效。来源原文和真实验证记录保留原样，当前解释可以随证据修订。

一个合格的进度例子是：“新 Codex 会话已找到 YYH-12 并读到设计全文；线上回写还未由这次测试覆盖。”单说“已梳理、已沉淀、已核对”不能说明实际进展。

## 每次接续怎样做

给了编号就取得完整事项；没给编号时结合标题、目标和状态定位。读当前事项、必要的父目标或项目背景，以及本轮需要的文档全文。只在存在真实歧义时请用户区分。

需要恢复讨论、接受修改或核实争议时，取得相关评论的全部分页；有子事项时查清各项结果和依赖。全文材料的链接不是全文本身，列表摘要也不能代替正文。

按当前任务选用方法：澄清和方案形成、知识查询、知识整理、开发和交付检查各走对应能力。仓库中已有的技能用于这些工作；不让一次普通咨询跑完所有阶段。云端没有本地工具时，先完成能做的阅读与讨论，将需要本地执行的具体行动写回同一事项。

只有需要跨环境携带资料、审查或恢复时才生成上下文包。包内保存本次事项和必要材料全文、已取齐的评论和子事项、来源时间，以及所用文件和代码版本。它是阅读快照，不是第二份工作记录。新会话仍重新读取线上当前内容。

本地 `scripts/workbench_context.py` 会拒绝缺正文、未取齐分页、漏掉事项直接关联文档、错误父子关系等输入，并提供来源变化检查。它不会联网，也不能证明线上此刻没有更新。具体命令见仓库的 Linear 工作台 README，由 Agent 执行。

## 写回与结束

保存前重新读取当前正文，保留其他会话的有效修改；精确更新本轮负责内容，再回读确认。保存超时先查询是否成功，不盲目重复创建。写回失败时保留本地成果，清楚说明线上尚未更新。

Backlog 是尚未安排，Todo 是准备推进，In Progress 是正在处理。只有可判断的成果已经就绪且确实等待用户审阅，才用 In Review。资料不足、连接失败、会话结束都不自动意味着待审或完成。

Done 表示这条事项约定的结果达到，并具有相应验证；需要用户接受的工作不能由 Agent 虚构已接受。父目标要对照整体使用效果检查，不能用关闭子事项数量代替。重新发现未解决的问题可以重开原事项；目标已经转移则保留清楚的承接链接。

## 知识和代码怎样留下来

任务进展在 Linear，精确代码和配置在 Git，长期知识在所属领域的原文维护。知识和代码都有独立目录，可以不经过旧事项直接浏览；事项引用它们说明这次用了什么、改变了什么。

Git 管理的知识或操作说明先修改仓库原文，按发布清单检查线上差异后同步。Linear 开始的日常资料在原文档中维护；本地取得的是可重建快照。已有金铲铲原文继续维护版本、依据和未验证范围，不为导航整理另写一套攻略。

代码变更用真实使用过程验证，并记录相关提交、运行证据及知识需要复核的位置。旧实现、实验成功和正式已发布能力分别说明；缺少原始材料就记录缺口，不能用新生成的摘要冒充已经迁入。

## Agent 和技能怎样在工作中改进

真实事项暴露反复失败、缺失入口或稳定的有效办法时，先说明哪个行为需要改变。例如“在另一项目找不到工作台说明”，可在该事项中修改入口并验证，不必先新建一个庞大的技能项目。

改动前读取现有 Agent 入口与相关 Skill，定位最小改动：跨任务提醒留在 AGENTS，步骤留在 Skill，操作细节在引用文档，确定性检查由脚本负责。已有相同能力就合并，避免多个 Skill 争抢同一句请求。研究、开发、知识整理继续复用仓库已有方法。

每次有意义的更新保留：触发问题的事项、修改的版本、一个应正确触发的真实例子、一个不应触发的相邻例子，以及观察到的结果。脚本有相应测试；复杂能力还应由独立新会话检查。文件创建成功不能证明技能有效。

验证通过的改动合入唯一仓库，Codex 用户级入口引用同一份 Skill；线上操作说明同步后，ChatGPT 从稳定入口读最新版本。新会话检查实际加载；既有会话必要时显式要求重新读取，不能承诺所有环境热更新。失败时回退相应提交或恢复安装备份，并将未解决问题留在原事项。

Skill 版本变化只改变后续工作方法，不改写历史证据，也不扩大用户授权。Linear 内置 Agent 的技能设置与 Codex 本地 Skill 是不同配置；没有实际安装和验证时，不能声称已替 Linear Agent 配好。

## 随处接续的实际边界

当前电脑已接入的 Codex 新会话可以通过全局入口发现本工作台。ChatGPT 已由用户加入个人自定义指令，但该会话仍须有 Linear 工具及账号访问。没有工具的会话可以讨论用户提供的材料，也可以输出接续口令，不能编造线上读取或写回。

没有自动触发任务时，Agent 不在后台持续执行。你说“继续某事项”“看看今天做什么”“整理这次结果”即可触发相应工作；今天的推荐不等于自动执行全部待办。换机器、云端执行器或受限空间，需要配置当地的连接和入口后再验证。
