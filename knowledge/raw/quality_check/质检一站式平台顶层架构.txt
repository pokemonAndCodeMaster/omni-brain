## §0. 平台目标与全局共享能力（源仓库吸纳段）

### 0.1 平台目标重述

用统一前后端门面承载四类质检业务：人工质检、大模型质检、自动化质检、专题数据质量。统一的是工作台、交互语言与公共基础能力；各模块仍保持业务模型、表与流程边界。

### 0.2 模块架构入口表

| 模块 | 定位 | 成熟度 | 架构 Hub |
|---|---|---|---|
| 人工质检 | 数据集交付、标注、验收、返修与人力运营闭环 | 样板设计，部分实施中 | [[质检一站式平台人工质检模块整体架构]] |
| 大模型质检 | 生产任务与版本配置管理，衔接六通道生产状态 | 样板设计，正向设计中 | [[质检一站式平台大模型质检模块整体架构]] |
| 自动化质检 | 规则引擎与自动执行 | 仅冻结边界 | [[质检一站式平台自动化质检模块整体架构]] |
| 专题数据质量 | 专题监控、分析与报表 | 仅冻结边界 | [[质检一站式平台专题数据质量模块整体架构]] |

### 0.3 全局共享能力

只有被两个及以上模块复用、或必须全平台一致的设计才放在这里：

- **统一工作台壳层**：模块导航、用户与权限、全局搜索、帮助入口、环境与数据新鲜度提示。
- **共享交互组件**：筛选栏、保存视图、数据表、状态标签、详情抽屉、批量操作、二次确认、执行结果与错误反馈。
- **共享异步语义**：区分请求已提交、处理中、部分成功、失败、等待回查和最终状态；不能把同步响应当作最终事实。
- **共享危险操作范式**：高风险批量操作优先采用 `preview → confirm → execute → refresh`；普通 CRUD 不强套。
- **共享权限原则**：全员 OneTrack，不提供显式角色切换；登录权限裁剪路由、面板、按钮和数据范围。前端负责可见性与可用性，后端才是授权边界。
- **上下文下钻（ContextualDrilldown）**：总览数字、图表数据点、阶段轴、风险标签和任务摘要均可携带业务筛选跳转明细页。参数编码进 URL，明细页显示筛选 Chip 并真实过滤数据，保证可刷新、可分享与浏览器前进/后退。
- **共享前后端契约**：Vue 组件只调用 API 封装；请求/响应有 TypeScript 类型；FastAPI 用 Pydantic 校验；错误使用语义化 HTTP 状态。
- **共享工程边界**：Router 不拼 SQL，Repository 集中数据访问；跨模块调用经公开服务边界，不直接穿透 Repository。

### 0.5 上移与下沉规则

1. 两个模块出现相同问题时，先比较语义；确认可复用后上移平台层。
2. 平台层只定义公共契约和最小组件 API，不吞并模块业务规则。
3. 人工质检的采样、通过/打回、人力归属只留在人工模块。
4. 大模型质检的六通道状态、kill/clean、游标分页与版本冻结只留在大模型模块。
5. 未设计模块只记录边界和待确认问题，不从两个样板模块类推出不存在的业务。

## §1. 建设目标与全局约束

### 1.1 平台总目标

质检一站式平台是一站式质检能力平台，承载人工质检 / 大模型质检 / 自动化质检 / 专题数据质量四类质检业务，统一前后端门面与共享公共模块，但各子part 数据表层面各自隔离。

### 1.2 四子part 范围定义

| 子part | 业务范围（一句话） | 当前状态 |
|--------|------------------|---------|
| 人工质检 | 标注员标注→验收抽样→通过打回执行的全链路管理 | ✅ 部分实施中 |
| 大模型质检 | 大模型数据生产任务管理 + 版本配置 | 🟡 本次正向设计 |
| 自动化质检 | 自动化质检规则引擎与执行 | ⬜ 未来 |
| 专题数据质量 | 专题数据质量监控与报表 | ⬜ 未来 |

### 1.3 技术栈约束

- 后端：FastAPI + Python
- 前端：Vue3 + TypeScript
- 数据库：PostgreSQL / GaussDB-DWS
- 对象存储：OBS
- 配置中心：ConfigManager（单例）
- 连接层：PostgresConnector（基于 psycopg2，**禁 ORM**）

## §3. 全局目录划分规范（宪法层）

> 本段从人工质检"后端分层与组件边界设计"卡 + "质检前后端一体化理想架构设计"卡抽取上移。所有子part 目录结构必须沿用。

### 3.1 src/ 顶级目录标准

| 目录 | 职责 | 约束 |
|------|------|------|
| `src/api/` | FastAPI 统一后端门面 | 所有子part 共享；含 `app.py` / `routers/` / `schemas/` / `deps.py` |
| `src/frontend/` | Vue3 前端工程 | 所有子part 共享；含 `views/` / `components/` / `api/` / `utils/` / `router/` / `layouts/` |
| `src/{子part}/` | 各子part 的领域代码 | 每个子part 独立目录；含该 part 的 Service/Repository/Domain |
| `src/database/` | PostgreSQL 公共连接池 | 所有子part 共享；PostgresConnector |
| `src/config/` | 配置中心 | 所有子part 共享；ConfigManager 单例 |
| `src/obs/` | OBS 对象存储 | 所有子part 共享；ObsManager |

### 3.2 子part 目录命名规范

`src/{part_name}/`，part_name 使用 snake_case（如 `manual_qc`、`llm`）。

### 3.3 子part 内部目录结构（建议但不强制）

- `src/{part}/repository.py` 或 `src/{part}/repository/` — 数据库访问层
- `src/{part}/service.py` 或 `src/{part}/services/` — 应用服务层
- `src/{part}/models.py` 或 `src/{part}/schemas/` — 领域模型

具体组织方式由各子part 根据复杂度自定，但必须在子part 整体架构卡中显式声明。

### 3.4 前端目录规范

| 目录 | 职责 |
|------|------|
| `src/frontend/src/views/` | 页面级组件 |
| `src/frontend/src/components/` | 可复用组件 |
| `src/frontend/src/api/` | API 调用封装（按子part 分文件） |
| `src/frontend/src/utils/` | 工具函数 |
| `src/frontend/src/router/` | 路由配置 |
| `src/frontend/src/layouts/` | 布局组件 |

## §4. 前后端边界与组件边界（宪法层）

> 本段从人工质检"后端分层与组件边界设计"卡 + "领域模型层设计"卡 + "Repository 与数据库访问设计"卡抽取上移。所有子part 必须沿用四层架构红线。

### 4.1 四层架构定义

| 层 | 职责 | 允许操作 | 禁止操作 |
|----|------|---------|---------|
| Router | HTTP 端点定义、请求参数校验、调用 Application Service、返回响应 | Pydantic 校验、调用 Service | 禁止碰 SQL；禁止碰数据库连接；禁止含业务逻辑 |
| Application Service | 业务编排、事务边界、调用 Repository/Domain/外部客户端 | 编排多个 Repository、事务控制 | 禁止拼 SQL；禁止直接操作 HTTP 请求/响应对象 |
| Domain/Repository | 数据库访问、SQL 封装、领域模型定义 | SQL 执行、数据映射 | 禁止碰 HTTP；禁止碰框架对象；禁止含业务编排逻辑 |
| DB | PostgreSQL/GaussDB | — | — |

### 4.2 层间依赖红线

- 上层可依赖下层，下层禁止依赖上层。
- 同层之间禁止循环依赖。
- 跨子part 调用必须经 Application Service 层，禁止直接跨 part 调 Repository。

### 4.3 领域模型层原则

- **就近定义原则**：模型优先定义在使用处，复用后上移。
- **Pydantic 与内部模型隔离**：API 层用 Pydantic 模型，Repository 层用内部数据结构（dict/tuple/dataclass），两层模型禁止混用。
- **禁止 ORM 模型**：数据库模型不使用 ORM，Repository 用 PostgresConnector 直接执行 SQL。

### 4.4 Repository 原则

- **SQL 集中封装**：所有 SQL 必须集中在 Repository 层，Service/Router 禁止拼 SQL。
- **参数化 SQL**：禁止 f-string 拼 SQL，必须用 `%s` 占位符。
- **execute_query 禁止写操作**：`execute_query` 仅查询，写操作用 `execute` / `execute_values`。
- **禁止临时表**：禁止 `CREATE TEMP TABLE` 模式，用批量 UPSERT（`INSERT...ON CONFLICT...DO UPDATE`）。
- **连接层统一**：统一用 PostgresConnector（psycopg2），禁止引入其他连接器。
- **禁 ORM**：Repository 使用 PostgresConnector，禁止引入 ORM 框架。

> ⚠️ **Application Service 为可选层**：子part 可按业务复杂度决定是否需要。简单 CRUD 域可直接 `Router → Repository`，复杂业务编排域建议保留 AppService 层。各子part 在后端分层卡中显式声明是否采用 AppService 层。例如大模型质检part 采用三层架构（Router→Repository/Domain→DB），省略 AppService 层。

## §5. 前后端衔接方式（宪法层）

> 本段从人工质检"API 契约与前端交互设计"卡 + "SSO 鉴权接入方案"卡抽取上移。所有子part API 契约必须沿用。

### 5.1 API 契约规范

- **路由前缀**：每个子part 的路由前缀为 `/api/{part_name}`（如 `/api/tasks`、`/api/versions`、`/api/llm/tasks`）。
- **请求校验**：所有请求参数必须用 Pydantic 模型校验，禁止裸 dict。
- **统一响应格式**：成功返回数据体，失败返回 `{"detail": "错误描述"}` + HTTP 状态码。
- **错误码体系**：HTTP 状态码语义化（400 参数错误 / 404 不存在 / 409 冲突 / 500 服务器错误）。
- **分页范式**：游标分页（cursor-based）或 OFFSET 分页，由各子part 根据数据量选择，但必须在 API 契约卡中显式声明选择哪种。

### 5.2 前端调用规范

- **禁止 axios 直用**：组件必须通过 `src/frontend/src/api/*.ts` 间接调用。
- **API 函数命名**：动词开头（如 `getTaskList`、`createVersion`、`deleteTask`）。
- **TypeScript 接口**：所有 API 请求/响应必须定义 TypeScript 接口，禁止 `any`。

### 5.3 权限模型范式

- **模块权限等级**：按模块划分权限等级（如 `acceptance_access`、`personnel_access`），禁止每按钮一个 Boolean。
- **演进路径**：mock 鉴权 → SSO 接入，初期可 mock，但权限模型必须预留 SSO 接入口。

### 5.4 preview→execute 双步交互（如适用）

详见 §8 参考模式附录。非强制模式，子part 可根据业务需要选择是否采用。

## §6. 全局通用原则（宪法层）

> 本段从人工质检整体架构卡 §8 规范约束清单上移 6 张共享规范。所有子part 必须遵守，不可降低约束标准。

| 规范 ID | 规范名 | 一句话约束 | 影响范围 |
|---------|--------|-----------|---------|
| NORM-DDL-SYNC | DDL 变更同步规范 | 每张表必须同步交付：①迁移脚本 ②正式建表 SQL ③测试镜像 SQL | 所有涉及建表的子part |
| NORM-KB-SYNC | 知识库同步刷新规范 | 完成后必须重编译图索引、断链检查、双链焊死 | 所有子part |
| NORM-KM-001 | 知识库双链层级规范 | synthesis/concept 必须回链 Hub；枢纽出链子卡入链必含 Hub | 所有子part |
| NORM-GAUSSDB-DDL | GaussDB-DWS 建表 SQL 规范 | DDL 遵循 GaussDB 8.x 语法；DISTRIBUTE BY HASH；不支持 ADD COLUMN IF NOT EXISTS | 所有涉及 GaussDB 的子part |
| NORM-TRIGGER-UPDATED-AT | GaussDB TRIGGER 限制与 updated_at 处理规范 | updated_at 不用 TRIGGER，用应用层写入或 DEFAULT | 所有涉及 GaussDB 的子part |
| NORM-SOFT-DELETE | 软删除 is_deleted 设计规范 | 如含 is_deleted 字段按规范定义；业务查询默认 WHERE is_deleted=FALSE | 所有含软删除的子part |

**声明**：以上 6 张规范卡为全局强制规范，所有子part 必须遵守。各子part 可在自己的规范约束清单中引用，但不可降低约束标准。

## §9. 子part 上移机制 + Review 顺序

### 9.1 子part 上移机制

1. **触发条件**：子part 设计过程中，识别到某设计模式/原则/目录规范可被其他子part 复用。
2. **操作流程**：
   - ① 在子part 组件卡中标注"可上移"标记。
   - ② 将通用部分提取到顶层架构卡对应段落（宪法层或参考模式层）。
   - ③ 在子part 组件卡中改为"详见[[质检一站式平台顶层架构]] §X"。
   - ④ 通知其他子part 检查是否需同步引用。
3. **归属原则**：上移后的内容归属顶层架构卡，子part 仅保留 part 特有部分。

### 9.2 Review 顺序

1. 质检一站式平台顶层架构（本卡）
2. [[HUB-质检前后端一体化]]（共享枢纽）
3. 各子part 整体架构卡
4. 各子part 组件卡
