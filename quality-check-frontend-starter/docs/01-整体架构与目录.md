# 01. 整体架构与目录

## 一、先理解前端工程在整个系统中的位置

你的完整系统不是“前端直接查数据库”，而是：

```text
浏览器中的 Vue 页面
  ↓ HTTP
FastAPI Router
  ↓
Application Service
  ↓
Repository / DeltaClient
  ↓
PostgreSQL、GaussDB、Delta 平台
```

前端只认 **HTTP API 契约**，不认数据库表，也不应该在页面中拼 SQL。

## 二、这个工程为什么分四层

```text
src/
├── app/                         平台壳层
├── features/                    业务模块
├── shared/                      平台共享能力
└── styles/                      全局视觉变量和基础样式
```

### 1. `app/`：平台壳层

负责所有业务都会用到的应用入口：

- 路由；
- 左侧导航；
- 顶部标题；
- 页面容器；
- 平台级页面，如业务看板。

它不应该包含人工质检的采样算法，也不应该知道数据库字段。

### 2. `features/`：业务模块

每个 feature 是一块相对独立的业务，例如：

```text
features/
├── manual-qc/                   人工质检
├── llm-qc/                      大模型质检，后续新增
├── auto-qc/                     自动化质检，后续新增
└── data-quality/                专题数据质量，后续新增
```

人工质检内部再按：

```text
manual-qc/
├── api/                         调人工质检 HTTP API
├── mocks/                       本地 Mock 数据
├── pages/                       页面级组件
└── types/                       该业务的 TypeScript 类型
```

业务模块负责告诉共享组件：

- 数据是什么；
- 有哪些列；
- 哪些字段可编辑；
- 有哪些业务动作；
- 权限是什么。

### 3. `shared/`：平台共享能力

```text
shared/
├── api/                         Axios 公共实例
├── query/                       QuerySpec / Filter AST
├── data-workbench/              统一数据工作台
├── analysis/                    分析构建器和 ECharts
├── dashboard/                   卡片、GridStack、看板状态
└── persistence/                 localStorage 持久化
```

原则是：**至少两个业务模块会复用，或者全平台必须一致，才放到 shared。**

### 4. `styles/`：视觉底座

- `tokens.css`：颜色、圆角、阴影、间距等设计 Token；
- `base.css`：平台壳层、按钮、输入框、面板等全局样式。

以后换主题时，优先改 Token，而不是逐个页面搜颜色。

## 三、最重要的依赖方向

```text
app/pages
  ↓
features/manual-qc/pages
  ↓
shared/data-workbench、shared/analysis、shared/dashboard
  ↓
shared/api、shared/persistence、类型
```

允许：

```text
业务页面 → 共享组件
共享组件 → 共享基础工具
```

禁止：

```text
共享组件 → 人工质检业务页面
shared → features/manual-qc
```

本 Starter 中 `AnalysisBuilder` 暂时直接使用 `DeliveryRow`，这是为了让第一版容易读懂。正式平台化时，应该把它改成接收通用 `DataSourceSpec + MetricDefinition`，从而彻底去掉对人工质检类型的依赖。这一点已列入下一阶段清单。

## 四、运行时的数据流

### 表格加载

```text
DeliveryWorkbenchPage.vue
  → getDeliveries()
  → deliveries.ts 判断 VITE_USE_MOCK
      ├── true：读取 mocks/deliveries.ts
      └── false：通过 shared/api/http.ts 请求 FastAPI
  → rows
  → DataWorkbench.vue
```

### 单元格编辑

```text
用户修改负责人
  → DataWorkbench 发出 cellEdit
  → DeliveryWorkbenchPage 调 updateDeliveryCell
  → Mock 或 PATCH API
  → 成功后更新页面 rows
```

### 生成图表并加入看板

```text
当前筛选后的叶子行
  → AnalysisBuilder 聚合
  → 生成 ChartSpec
  → DashboardStore.addChartCard
  → localStorage 自动保存
  → DashboardGrid 渲染新卡片
```

### 卡片布局记忆

```text
GridStack change 事件
  → DashboardGrid emit layoutChange
  → DashboardStore.updateLayouts
  → Pinia cards 变化
  → watch 写 localStorage
```

## 五、为什么不把所有东西写进一个大组件

错误做法：

```text
MegaTable.vue
  同时请求 API
  同时处理人工质检规则
  同时生成 ECharts
  同时管理 GridStack
  同时写 localStorage
```

这样后续任何修改都会影响整个文件。

正确做法：

```text
业务页面：决定业务语义
DataWorkbench：决定表格交互
AnalysisBuilder：决定统计配置
Dashboard：决定卡片布局
API 文件：决定 HTTP 调用
Store：决定跨页面状态和持久化
```
