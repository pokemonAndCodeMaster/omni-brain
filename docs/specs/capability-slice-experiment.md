# 能力切片实验与证据分级协议

> **状态**：Provisional；由首个人工质检能力产物验证后再固化。  
> **目的**：区分一次路径跑通、可信闭环、可复用能力和跨场景泛化，避免用单个成功案例夸大 Blueprint 组件成熟度。  
> **关联**：[Blueprint](../blueprint.md)｜[质检场景](../scenarios/quality-domain-knowledge-workbench.md)｜[能力建设问题](../problems/2026-07-11-manual-quality-capability-construction-gap.md)

## 1. 四级证据

| 级别 | 要证明什么 | 最低证据 | 不能声称什么 |
|---|---|---|---|
| L1 路径跑通 | 从真实问题到能力产物的必要环节没有明显断裂 | 一个真实任务、完整过程记录、主要缺口和失败点 | 可重复、可维护、可泛化 |
| L2 可信最小闭环 | 同一能力在代表性条件下可重复、可核验、可变更 | 明确契约、权威来源、正常/边界/失败场景、回写与回滚、变更触发复核 | 已形成通用组件或跨场景能力 |
| L3 可复用能力 | 已有结构和组件可以迁移到邻近能力 | 第二个真实能力主要复用既有契约，只增加领域差异 | 跨领域普适性 |
| L4 跨场景泛化 | 核心机制在不同任务类型或领域仍成立 | 跨类型旅程、固定评测、失败边界和维护成本对比 | 无边界的通用平台能力 |

首个人工质检能力切片以 **L2 可信最小闭环** 为目标。L1 可以作为中间检查点，但不能作为 R1 完成依据；L3、L4 由后续切片验证。

## 2. 全局成熟度与切片证据分离

Blueprint 的 `0 Open → 5 Verified` 描述组件的全局成熟度。单个切片的成功只登记带范围的证据，例如：

```yaml
global_maturity: 2  # Provisional
slice_evidence:
  manual_acceptance_assignment_v1:
    level: 5        # Verified in this slice
    evidence: eval/reports/...
```

只有在第二个能力或跨场景反证后，才能据此提出全局成熟度升级。不得把 `Verified@某切片` 简写成组件整体 `Verified`。

## 3. 组件裁剪原则

首个切片不要求十个 Blueprint 组件全部产品化。每个组件必须明确归入一种状态：

- `required_tool`：闭环核心，必须有可执行实现；
- `required_manual`：能力必需，但首轮可人工执行；
- `thin_contract`：只实现当前范围的最小接口或引用；
- `deferred`：本轮不实现，并说明不会阻断什么；
- `not_applicable`：与本切片无关。

人工实现不是空缺豁免。每个人工步骤必须记录执行者、输入、输出、判断规则、耗时、失败方式和未来替代组件，不能用不可观察的人肉补偿掩盖组件缺失。

强模型或当前 Agent 自行检索、阅读、归纳和补写，只能作为人工基线或组件缺口证据。只有通过已声明的组件接口、状态契约和门禁完成的步骤，才能计入 Omni-Brain 的切片证据；同一记录应允许能力较弱的模型或另一执行者重放，观察失败发生在模型、来源、知识结构、组件还是工作流。

## 4. L2 最低完成门槛

- 使用真实问题、真实资料和可确认的事实源；
- 产出真实能力结果，而不是只生成文档或界面演示；
- 关键结论能回到来源，现状、目标、实现和待确认项分开；
- 上下文有范围、预算和纳入理由；
- 至少覆盖正常、边界、状态变化和失败场景；
- 所有人工步骤显式化并记录成本；
- 一项规则、来源或代码变化能触发正确的影响复核；
- 新知识通过受控流程回写，失败可以回滚；
- 任务投影与长期知识变更候选分开；稳定知识具有长期归属、关系和人类浏览入口，不因单任务摄入形成无归属碎片；
- 另一位执行者或 Agent 可以依据记录重放主要过程；
- 分别报告领域产物结果和 Omni-Brain 建设能力结果。

## 5. 首个切片的组件候选

针对“验收任务分配闭环”候选，初始裁剪如下，仍需实验修正：

| 组件 | 首轮候选状态 | 最小责任 |
|---|---|---|
| 事实源与来源注册 | required_manual | 登记关键资料、旧脚本、数据库、接口和代码的权威性、范围与新鲜度 |
| 规范知识底座 | required_manual | 建立本任务所需的最小对象、流程、规则、约束和证据，并为稳定新增知识确定长期归属与复用关系 |
| 公共能力与跨域契约 | thin_contract | 引用数据库、Delta、权限等能力，记录本任务使用契约 |
| 派生结构编译器 | deferred | 首轮允许人工定位代码/Schema，记录成本和替代契约 |
| 摄入与 Brownfield | required_manual | 完成来源冻结、冲突/粒度/归属检查和受控摄入，不要求完整自动化管线 |
| 检索与上下文组装 | required_tool 或可测人工基线 | 盘点存量、分类缺口并输出有范围、预算、纳入理由和遗漏记录的任务上下文包 |
| 产品视图与导航 | thin_contract | 用 Markdown/静态投影验证流程、方案和影响视图，并检查新增知识是否破坏长期浏览结构 |
| 任务知识准备、方案与能力建设工作区 | required_tool 或受控 Agent 流程 | 维护任务框架、问题/缺口图、知识准备状态和阶段门禁，再把合格上下文推进为方案、能力产物和验证证据 |
| 知识治理与演进 | required_manual | change set、影响清单、确认、回写和回滚 |
| 评测与可观测性 | required_tool | 固定输入、失败类型、领域验收、Omni-Brain 验收和基线 |

## 6. 待首个实验验证

- 验收任务分配的具体业务边界和真实执行范围；
- 零背景、模糊痛点和明确重构是否需要不同发现入口；
- 知识发现与需求明确如何迭代汇合；
- 如何同时验收当前决策充分性、长期知识归属、人类浏览体验和后续任务复用；
- 基础模型能否依靠组件契约重放主要步骤，以及哪些强模型能力仍在掩盖组件缺失；
- 哪些人工步骤成本最高，最应优先工具化；
- 第二个邻近能力应选择什么来验证 L3 复用。
