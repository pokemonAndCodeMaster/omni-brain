# AGENTS.md — Omni-Brain Harness 发布契约

本项目是可由 OpenCode 从根目录直接使用的 Omni-Brain 精简 Harness。只声明已经实现或取得证据的能力；设计仓库、历史聊天、已删除旧知识和 stub 不自动成为本项目能力。

## 启动顺序

1. 从用户请求按下方任务路由加载一个最低充分 Skill；
2. 只有问题涉及 Harness 成熟度、发布范围或项目当前计划时，才读 `harness.yaml` 或 `docs/now.md`；普通知识问答和局部执行不把项目状态文档当作固定前置；
3. 精确事实以源码、Schema、运行结果和直接人工确认为准。

## 任务路由

- 用户要求整理、导入、摄入或归并一批材料，建立或更新规范知识与产品视图：加载 `ingest-knowledge`。固定代码变化需要更新既有知识时，使用其中的 `writeback` 路径，不运行整仓完整摄入；该 Skill 自带工作台。
- 用户只要求浏览、学习、查询、判断已有/缺失/冲突，或在任务前取得已有知识上下文：加载 `answer-from-knowledge`，从正式或用户指定的候选知识根入口定向读取；不加载 `ingest-knowledge`，也不读取摄入工作台或原始材料。
- 用户要求先讨论、设计或评审软件方案，或者直接提出复杂开发诉求但关键业务语义、主要交互、公共能力边界或技术责任尚未确定：加载 `form-solution`。先形成并确认 R1 需求，再定向读取当前实现形成 R2 方案；方案批准前不修改产品代码。明确的局部低风险修改不触发，已有对齐且获批的方案也不重新形成。用户仅声称“方案已批准”不等于存在批准证据：只接受用户明确给出的路径，或当前 Harness 的 `workspaces/reviews/` 中与本任务对齐且标记已批准的审查入口；没有用户路径时只检查该目录一次，找不到就停止并索取，不得遍历产品树、Git 历史、运行产物、同级仓库、设计仓、评测目录、历史 Trial 或旧答案来补一份“批准方案”。
- 用户要求开发、修复或重构现有软件，且目标和方案已经明确，需要领域/架构知识、跨文件或跨层修改、真实数据库/API/页面验证，或代码变化会影响长期知识：加载 `develop-with-knowledge`。复杂任务若没有获批方案，先交给 `form-solution`；显而易见的单文件低风险修改仍直接执行。
- 用户明确要求审查、评审或复盘一项已经完成的软件开发工作，或跨文件/跨层代码变化需要人决定是否接受：加载 `review-work`，生成或更新唯一的本地 `review.md`。它审查已经发生的软件工作，不代替模糊需求的方案形成；知识摄入使用摄入工作台自己的审查页，设计与 Harness 审查尚未作为正式能力发布。
- 目标明确、局部、低风险、易回滚：直接读取事实源后执行。
- 问题明确但需要少量背景：定向读取，不创建持久工作区。
- 关键事实经过一次有界查证仍然缺失、冲突或过时时，明确它会影响哪个决定、已经查过什么和还需谁提供什么；停止猜测并请求来源或人工决定，不另建一套任务流程。

不要把所有任务机械升级为完整流程。

## 采用边界

能力是否存在、入口在哪里、验证到了哪个范围，只以 `harness.yaml` 为准；本文件不复制动态成熟度。不得把一个用例中的成功外推到任意领域、模型或规模，也不得把测试通过当作内容正确。本 Release 不预装质检知识；领域知识是 Harness 运行后的独立产物。

## 知识内容优先

知识摄入的首要结果是：不熟悉原始材料的人或模型能够从产品视图建立全貌、按问题下钻，并回到直接事实源继续工作。文件计数、覆盖账本、Schema 和结构检查只为这个结果服务，不能成为执行主线。

- 宽范围完整整理先建立全量材料地图，再逐个审阅可完整理解的材料单元；每项发现只表达一个可复用结论，并保留会改变理解或行动的必要细节、精确来源、现实形态和适用边界。材料单元不能替代长期知识结构，读后发现也不能用综合摘要压缩。
- 规范主题按长期维护边界组织，不按来源目录摘抄。每条发现只有一个规范正文维护者，完成主题前必须逐条确认核心结论和必要细节进入真实章节；产品视图引用规范正文，不复制第二套事实。
- 聚焦代码或问题整理仍以一个明确读者问题为最小交付单位，取得最低充分的直接来源并在需要时真实运行；不得为了统一形式强行执行完整材料盘点。
- 代码变化回写先判断来源与系统身份，再从受影响的业务/数据/规则、软件结构、产品视图和未知定向取源；新系统必须有独立来源和系统落点，不能并入名称相近的旧原型。
- 为不同结论选择匹配的直接事实源：当前代码行为查源码、Schema、配置和运行结果；业务语义查当前人工决定或业务原始资料；目标方案和历史做法必须分别标明。已有综合文档只能帮助定位，不能替代更直接的当前事实源。
- 材料涉及软件且知识将用于理解或开发时，至少沿一个真实业务动作，用代码地图、运行时序和必要的类/数据关系讲清入口、职责、转换、输出、组织理由、当前限制和一次修改路径；不能只复述“前端—API—Service—Repository”，也不机械凑图。
- 用户可见内容按“先结论和全貌、再分层细节、最后现实边界与来源”组织；层级、流程、时序、数据关系或算法适合图示时同时给图和文字说明。
- 在运行结构检查前，先从候选产品视图和最多三篇规范页回答原读者问题；多部分问题只有逐项成立才能标为可靠。公共能力出现两个消费者、明确公共 owner/契约或用户确认复用时即进入抽取审查；“相关但未知或尚未抽取”不能写成“不适用”。

## 知识摄入硬边界

- 只读取用户授权的来源并保持来源只读；当前事实必须回到匹配的直接事实源，不能用综合摘要代替。
- `ingest-knowledge` 初始化后，先用工作台 `next` 取得当前材料单元、主题或聚焦小批。只读取命令返回的精确路径；不得绕过它递归搜索、无界通读或另建平行清单。
- 候选只写入 `workspaces/knowledge-ingestion/<case-id>/`；用户批准前不得修改正式 `knowledge/` 或 `config/knowledge-domains.yaml`。
- 不确定、冲突、缺少当前证据的内容必须显式保留，不能为了叙事完整或通过检查而补写。
- 规范知识、领域位置视图和旅程/学习视图同步形成；视图引用规范内容，不复制另一套事实。
- 需要 API、SQL、页面或数值证明时，使用工作台 `run` 在临时 Git worktree 执行；不得在原来源代码目录写入调试文件，也不得把 Harness 测试当作来源项目运行证据。
- 按 Skill 完成当前单元或主题登记，人工审查前生成唯一的 `review.md`；完整整理的来源追溯页由工作台从已校验状态生成，不手抄。批准发布后运行正式知识检查。检查通过只代表结构和已声明关系成立，不代替内容判断。

详细步骤与模板只在 `ingest-knowledge` 中维护，本文件不复制。

## 来源边界

- 只读取本项目和用户明确指定的材料位置；不要自行搜索同级项目、历史聊天、旧答案或其他未声明材料。
- 用户指定的来源保持只读。需要扩展读取范围时，先说明哪个关键问题因此无法回答，并取得用户同意。
- 项目内没有业务参考答案。不得把测试、模板或工具实现当作待摄入主题的事实来源。

## 验证与沟通

- 代码改动运行 `python -m unittest discover -s tests`；
- 知识结构运行 `python scripts/knowledge_check.py`；
- 内容质量先于结构通过：用真实浏览路线和读者问题检查全貌、深度、事实保真与未知，再运行结构检查和用户确认。

优先使用中文。先给判断，再给证据与边界；结尾明确用户需要做什么、Agent 将做什么和下一产物。
