# 本地 AI 工作审查

让人审的是**实际工作**，不是模型写报告的能力。先核对任务对象，再按需求、方案、实现和验证的依赖顺序形成或更新一张本地审查单。

## 1. 判断是否需要审查单

- 用户明确要求审查、评审、复盘、生成本地 MR 说明或检查一项已完成工作时，使用本 Skill；
- 跨文件、跨层、公共契约、知识发布、长期设计或 Harness 变化需要人决定是否接受时，使用本 Skill；
- 简单问答、只读状态查看、显而易见的单文件低风险修改，继续使用简短交付，不创建持久审查单；
- 原始需求仍模糊、需要先形成方案时，交回项目的任务准备或方案形成路径；本 Skill 只能如实显示“方案尚未批准”，不能替它补做方案。

默认入口为 `workspaces/reviews/<task-id>/review.md`。同一任务已经存在审查单时更新原文件，不创建 `review-v2-final.md`。

**完成标准：** 已说明为什么需要或不需要审查单；需要时已确定唯一文件路径和本次审查对象。

## 2. 取得审查事实

事实读取分成两段，不能一开始就通读实现。先只取得**任务身份包**：用户原始请求、实际
交给执行者的任务、产物的一句话摘要、任务来源和批准状态。读完立即执行第 3 节；此时
不要读取 Git Diff、源码、运行记录，也不要加载任务类型参考。只有任务对象确认对齐，
或“是否对齐”明确依赖某个实现事实时，才继续取得下游审查事实：

1. 如果存在，实施前认可的需求和方案；不存在时明确写“没有找到已批准方案”；
2. 修改前后的仓库、版本、文件差异或知识候选；
3. 实际运行、页面、接口、数据和回归证据；
4. 已知问题、未验证路径、人工决定和当前状态。

复用现有 Prompt、Git Diff、验证记录、截图和运行日志，通过链接下钻；不要为了审查再复制一套 YAML、命令流水或事实副本。把用户原话、源码/运行事实、Agent 分析和人工决定分开，不用代码推断冒充实际观察。

**完成标准：** 先用任务身份包完成对齐判断；仅对齐任务的完成声明继续取得原始任务、
Diff 或运行证据，且任务来源和批准状态没有缺失。

### 阶段 A：任务对象工具边界

任务身份包存在时，第一次对齐判断必须只使用包内文件。判断完成前：

- **允许：** 读取原始请求、实际任务、执行交接中的产物一句话摘要与批准状态；
- **禁止：** 访问产品或知识产物目录，运行 Git，读取源码、Diff、验证记录、项目状态或
  任务类型参考，也不要用目录遍历“确认现场”；
- **输出：** 先明确写下“对齐 / 错位 / 仍无法确认”以及包内依据。

若结果为错位，阶段 A 就是终点：直接写短报告，只引用身份包中的产物摘要作为“已有声明”，
不得自行扩展文件数、实现细节或验证结论。若结果为对齐，才进入阶段 B 取得下游事实；若仍
无法确认，只能定向读取决定对齐结论所必需的一个实现事实，读完立即重新判断。

## 3. 先核对任务对象

在组织下游内容前，比较：

- 用户原始问题；
- 实际交给执行者的任务；
- 实际产物解决的问题。

明确三者是**对齐、错位或仍无法确认**。如果实际任务不是原始诉求的合法切片，或任务边界尚未得到必要批准：

1. 在报告开头直接说明错位；
2. 把已有实现和验证的身份、入口和已有声明保留为独立实验或历史事实；
3. 停止要求用户继续批准方案、实现和验证；
4. 指出应回到哪个需求或方案问题。

任务来源、实际任务和产物摘要已经足以证明错位时，立即停止继续读取 Diff、源码、运行历史和下游设计细节，也不再撰写完整方案或实现审查。只有“是否错位”仍取决于某个实现事实，或用户明确要求把该独立实验另行审查时，才定向下钻。任务对象错误时，更多实现细节不会提高当前审查结论的可信度。

错位报告只需包含：错位结论、三者摘要与依据、独立实验事实的身份/入口、应回到的问题和
一个待确认点。不得为让报告显得完整而补写实现模块、测试数字或运行细节。

下游实现再完整也不能弥补任务对象错误。

**完成标准：** 报告明确给出对齐判断及依据；错位时后续审查已停止。

## 4. 形成一张可顺序审查的报告

只有任务对象确认对齐后，软件开发工作才完整读取并执行
[`references/software-development.md`](references/software-development.md)，其中的报告骨架和逐阶段完成标准是该分支的交付契约。错位报告不加载该参考，也不套用完整软件报告骨架。
其他任务类型沿用本节共同顺序，只补充该任务真正需要的内容，不机械复制软件章节。

任务对象对齐时，不另建一节重复比较三者；在工作全貌中说明任务来源、覆盖范围和不能外推的更大诉求。报告先用短篇幅讲清完整故事：背景和原始任务 → 需求理解 → 采用的方案 → 实际变化 → 运行结果和边界。然后按依赖顺序展开：

1. **需求：** 主要问题、用户希望得到的效果、需要增加或改变的功能、完成标准和必要范围；
2. **方案：** 产品和业务位置、相关技术层、原来怎样、要改成怎样、各模块怎样变化；
3. **实现：** 修改的模块和文件、调用或数据流程、关键算法和完整 Diff 入口；
4. **验证：** 要证明的结果、真实环境与输入、实际观察、回归和不能外推的范围；
5. **决定：** 认可、修改后复审或驳回，以及不同决定会怎样处理当前成果。

每个审查点只问一个阶段，并写清：审查目的、当前待审内容、用户可以作什么决定、不同反馈会怎样处理，以及可直接填写的反馈区。使用稳定编号 `R1`、`R2`……；报告体验单独用 `D1`，不要与成果是否通过混为一个决定。只有会改变接受结论、后续修改或证据要求的问题才成为待决点；不要用次要措辞、测试偏好或代码风格淹没共享契约、业务语义、运行边界和知识/发布状态。

标题、图表和章节数量应随任务复杂度裁剪。简单问题用几段话讲清，不把它展开成字段齐全的规格书；适合图示的系统位置、模块变化、流程、时序和算法优先用图，表格只辅助解释。

**完成标准：** 第一次接触任务的人无需聊天历史即可复述“为什么做、做了什么、没做什么、怎样证明”，并能从 R1 开始逐阶段作决定。

## 5. 接收反馈并更新同一张审查单

用户可直接回复 `R2：……` 或 `D1：……`。收到反馈后：

1. 把不会改变业务含义的表达问题直接修到报告；
2. 把业务、方案或实现纠正保留在对应审查点，修订当前成果并重新检查所有下游阶段；
3. 前一阶段被驳回时，把后续状态改为等待，不要求用户继续审；
4. 分开记录“工作本身的决定”和“报告是否好用”；
5. 一次报告反馈只修当前报告和评测候选，不直接修改全局 AGENTS 或 Skill；跨第二类任务仍成立后再提出 Harness 修订。

**完成标准：** 用户反馈没有被改写成另一种意思；受影响阶段和下一动作已经明确；同一任务仍只有一个用户审查入口。

## 6. 交付

交付消息只说明：当前工作结论、审查单绝对路径或可点击入口、从哪个 `R` 开始、用户可以在第一个不通过点停止。只能邀请用户回答**当前第一个可审查点**；前序阶段未通过或未确认时，不得建议跳到 `R5` 或其他下游决定。若审查单尚未获批准，使用“候选、待审或等待复审”，不能写成已认证。

**完成标准：** 用户知道去哪里看、现在只需决定什么，以及反馈后谁会做什么。
