> - **表名**：`t_personnel` → `t_data_check_screeners`
> - **主键**：原复合主键 `(employee_id, join_date)` → 新复合主键 `(employee_id, id)`（id 为自增序列，employee_id 为 DWS 分布键最左列，满足 NORM-GAUSSDB-001 §3.1 分布键⊆主键约束）
> - **有效期字段**：`join_date DATE` / `leave_date DATE` → `start_time timestamp(6)` / `end_time timestamp(6)`；`leave_date IS NULL` → `end_time IS NULL`（判定当前有效行，语义不变）
> - **字段名/语义变更**：`name→user_name`、`role→work_type`（直接取值）、`supplier→company`、`current_group→team_leader`（**group_name 冗余来源改用 team_leader 字段**）
> - **类型变更**：`status VARCHAR(16) 'ACTIVE'/'INACTIVE'` → `status int2 DEFAULT 1`（1=在职, 0=离职）
> - **移除字段**：`level`、`unit_price`、`updated_by`（snapshot enriched 不再输出 level/unit_price）
> - **新增字段**：`created_at`、`team_leader_id`、`skills(json)`、`sub_project_name`
> - **SCD 封版逻辑**：旧记录 `UPDATE SET end_time=当天, status=0, updated_at=now() WHERE end_time IS NULL AND employee_id=%s`；新增记录 `INSERT (status=1, end_time=NULL, start_time=当天)`
> - **分布键**：`HASH(employee_id)` 不变
> - **op_log 表**：`t_personnel_op_log` 表**保留不变**（DDL 文件已物理删除，表本身由迁移历史保留，repository.py 中 op_log 方法保留，写入目标不变）

## ① 组件概述

**一句话职责**：定义人工质检模块的人力分类体系（标注员 / 验收员 / 内部抽检员 三轨）、3 张数据表（t_data_check_screeners SCD Type2 人员主表 + t_personnel_op_log 操作记录 + t_portal_permission 权限）、分组管理机制、统计指标体系、前端人力页签与 SSO 鉴权预留。

**在整体架构中的位置**：数据层 + 概念层。3 张表由 [[质检平台-Repository与数据库访问设计]] 的 `ScreenerRepository` 读写；`t_data_check_screeners.team_leader` 为 [[质检平台-综合快照表设计]] 的 `group_name` 冗余字段来源（查当前组须 `WHERE end_time IS NULL`）；`t_portal_permission` 为 [[质检平台SSO鉴权接入方案]] 的权限数据源；`t_data_check_screeners.employee_id` 被 `t_qc_daily_snapshot.employee_id` 逻辑引用（非物理 FK，复合主键无法被单列引用）。

### 三表关系图（Mermaid classDiagram）

```mermaid

        +employee_id VARCHAR(30) PK(复合,分布键)

        +work_type VARCHAR(10)
        +company VARCHAR(100)

```

**关系图说明**：
- `t_data_check_screeners` 采用 **SCD Type2 缓慢变更维度**，复合主键 `(employee_id, id)`（id 为自增序列，employee_id 为 DWS 分布键最左列，满足 NORM-GAUSSDB-001 §3.1 分布键⊆主键约束）。同一工号可有多行（每次变更产生新行）。`start_time` 为加入当前身份的时间，`end_time` 为结束当前身份的时间（NULL=当前有效）。
- `t_personnel_op_log.employee_id` 逻辑引用 `t_data_check_screeners.employee_id`，**非物理 FK**（复合主键无法被单列引用），由应用层保证一致性。记录人员变更动作（SCD Type2 变更的审计日志）。
- `t_portal_permission.employee_id` 与 `t_data_check_screeners.employee_id` 逻辑关联但**非外键**（权限表独立于人员表，SSO JWT sub 直接匹配 employee_id）。
- `t_qc_daily_snapshot.employee_id` 逻辑引用 `t_data_check_screeners.employee_id`（详见 [[质检平台-综合快照表设计]]）。

## ⑤ 详细设计展开

### 1. 人力分类体系

```
人工质检人力
├── 标注员 (ANNOTATOR, FP/计件制)
│   └── STANDARD / SENIOR（注：V20260714_01 移除 level 字段，等级不再入库）
└── 验收员 (ACCEPTOR, TM/固定工资)
    └── (附) INTERNAL_CHECKER 华为内部员工 — 用于抽检验收员质量，不在供应商体系
```

> ⚠️ **V20260714_01 变更**：原 `level VARCHAR(16)` 字段已移除，等级（STANDARD/SENIOR/N/A）不再入库；`role VARCHAR(20)` 改为 `work_type VARCHAR(10)` 直接取值。`unit_price` 字段已移除，计件单价不再入库。

#### 关键业务规则

| 规则 | 说明 | 执行位置 |
|------|------|---------|
| **供应商约束** | 同一任务的标注员和验收员不能来自同一供应商（company） | `AssignmentService.validate_supplier_conflict()` |
| **分组仅针对标注员** | 验收员不分组；INTERNAL_CHECKER 不分组 | DB 约束：`team_leader` 只对 ANNOTATOR 有意义 |
| **未进组预警** | 活跃标注员 `team_leader = ''` 的需要前端高亮 | `PersonnelService.get_ungrouped_annotators()` [待人类补充] |
| **一人单项目** | `project_name VARCHAR(100)`（原 VARCHAR(64)，NULL 性变为可空）；调项目时记录 PROJECT_CHANGE 日志 | DB 单值字段 + 普通索引 |

### 2. 数据库设计（3张表）

> ⚠️ **变更记录**：v1 设计为 7 张表，v2 简化为 3 张表，所有属性平铺到 t_personnel，历史变更靠 t_personnel_op_log 追踪。v3（V20260630_03）t_personnel 采用 SCD Type2，复合主键 (employee_id, join_date)。**v4（V20260714_01，当前）t_personnel 整体替换为 t_data_check_screeners**，复合主键 (employee_id, id)，start_time/end_time 有效期，字段映射见 §2.1。

#### 2.1 t_data_check_screeners — 人员主表（SCD Type2，复合主键 employee_id + id）

> 物理文件：[`data_schemas/postgresql_relational/t_data_check_screeners.sql`](../../../data_schemas/postgresql_relational/t_data_check_screeners.sql)（schema=`pnc_simulation`，测试镜像 schema=`data_common_4`，DISTRIBUTE BY HASH(employee_id)，显式 CREATE SEQUENCE `t_data_check_screeners_id_seq`）

**SCD Type2 设计说明**：
- **复合主键**：`(employee_id, id)`（employee_id 为 DWS 分布键最左列，满足 NORM-GAUSSDB-001 §3.1/§3.2；id 为自增序列 `nextval('t_data_check_screeners_id_seq'::regclass)`）。同一工号可有多行，每行代表该工号的一段身份有效期。
- **有效期字段**：`start_time timestamp(6)`（加入当前项目/组/身份的时间）、`end_time timestamp(6)`（结束当前项目/组/身份的时间，NULL=当前有效行）。
- **查询模式**：
  - 查现状（当前有效人员）：`WHERE end_time IS NULL`
  - 查历史（某日人员快照）：`WHERE start_time <= 查询日 AND (end_time IS NULL OR end_time > 查询日)`
- **变更操作（SCD 封版）**：人员信息变更（切换组/项目/角色/工号）时，**同事务内**执行：
  1. `UPDATE` 旧行 `SET end_time = 当前日期, status = 0, updated_at = now() WHERE end_time IS NULL AND employee_id = %s`（封版旧行）
  2. `INSERT` 新行（`start_time = 当前日期, status = 1, end_time = NULL`，新身份字段）
  3. `INSERT` t_personnel_op_log 记录变更动作
- **工号变更特殊处理**：工号变更视为"旧人离场 + 新人入场"（旧工号行设 end_time，新工号行 INSERT，op_log 记录工号映射关系）。

**ScreenerRepository.create_or_transition 封版 SQL 原文快照**（`src/manual_qc/personnel/repository.py`）：

### 3. 分组（team_leader）的作用

分组是标注员维度的核心管理手段，`t_data_check_screeners.team_leader` 是当前组长名（直接字段，非 FK）：

| 使用场景 | 说明 |
|---------|------|
| 验收采样 | `GroupSampler` 按组采样，每组 min(人数×90, 300) 条 |
| 批量通过/打回 | 以组为最小执行单位，一次操作覆盖一组所有人 |
| 标效监控 | 按组 GROUP BY 统计效率，与按人统计互补 |
| 快照聚合 | `t_qc_daily_snapshot.group_name` 冗余自 `t_data_check_screeners.team_leader`（**V20260714_01：来源字段由 current_group 改为 team_leader**） |

> ⚠️ 护栏：执行 GroupSampler 之前，必须先检查 `team_leader = ''` 的标注员数量，有未进组成员时应给前端提示，而不是直接 skip。

### 4. 统计指标体系

> 标注员和验收员的统计不在 `t_data_check_screeners` 表中存储，而是通过 `t_qc_daily_snapshot` 按不同维度聚合查询实现（详见 [[质检平台-综合快照表设计]]）。

#### 4.1 标注员指标

从 `t_qc_daily_snapshot` 按 `employee_id` 聚合：总提交量、标效（件/天）、整体通过率、Good 通过率、Bad 通过率、各选项分布、各选项通过率、任务内排名。

#### 4.2 验收员指标（抽检一致率体系）

验收员的质量代理指标 = **抽检一致率**（华为内部员工定期抽检验收结果）：一致率 = 抽检中"验收员判断与抽检员判断一致"的比例。

> 详见 [[质检平台SSO鉴权接入方案]]。真实公司 SSO 参数仍待提供，模块权限和 mock 接入方案已冻结。

简要流程：
1. 用户访问平台 → 跳转公司 SSO 登录页
2. 用户输入工号+密码 → SSO 颁发 JWT Token（含工号 sub 字段）
3. 前端存储 Token → 后续请求 Header: `Authorization: Bearer <token>`
4. 后端中间件验证 JWT 签名 → 提取工号 → 查 `t_portal_permission`
5. `is_admin=TRUE` → 直接放行；其他 → 按 `acceptance_access` / `personnel_access` 的模块等级判断权限
