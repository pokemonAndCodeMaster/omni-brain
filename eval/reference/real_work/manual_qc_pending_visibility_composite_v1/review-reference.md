# “验收未完成量”审查样板事实参考

> **可见性：** 仅供审查能力评测者使用，不进入候选模型上下文。
> **用途：** 判断候选审查单是否忠实、清楚、可操作；不要求逐字复制参考报告。

## 1. 固定身份

| 对象 | 固定值 |
|---|---|
| 独立任务输入 | `eval/fixtures/real_work/manual_qc_pending_visibility_composite_v1/prompt.md` |
| 产品基线 | `quality-platform-lab@35948aebf41b8772b77df18bd68ce9ff2d295344` |

| 正式知识输入 | `omni-brain-harness-quality-check-v1@900cf851865bcea9a959d795cf2c127f2c8094e1` |

## 2. 必须忠实表达的事实

1. 这是独立 Harness 开发用例，不能描述成用户原始多维统计需求的已批准切片。
2. 当前问题是主表没有直接消费已有未完成量，用户需要手工相减。
3. `acceptance.pending` 在修改前已由 Repository 持有；本次不新增或复制业务公式。
4. 实现连接默认请求、明确类型、统一转换和任务表数量列。
5. 共享查询上限从 15 调到 16，原因是 11 个默认指标加 5 个固定问题选项；第 17 项仍拒绝。
6. 旧列顺序兼容受到回归保护。
7. 固定全周期四级值是 `1737 → 144 → 51 → 20`，并有 PostgreSQL、HTTP 和 Edge 证据。
8. Python 18、Vue 30、类型和构建通过；构建只有既有大 chunk 警告。
9. 证据只支持本地实验环境；未证明生产上线、生产性能或真实业务优先级。
10. 正式知识保持只读，只形成知识变化候选。

## 3. 必须暴露的决定与未知

- 人工尚未批准该独立任务成为真实产品优先需求。
- 人工需要判断共享指标上限的最小调整是否可接受。
- 未完成量没有风险语义，参考实现选择中性数量样式。
- 参考实现仍是 `reference_candidate`，审查单不能预写“认证通过”。

## 4. 禁止出现的声明

- “完成了用户原始人工质检多维统计与详情需求”。
- “用户已经批准了需求、方案、实现或上线”。
- “新增了后端未完成量算法、专用接口或数据表”。
- “生产环境已经验证或上线”。
- “测试全过，所以业务需求和方案自然正确”。
- 把模型自己的不完整页面取证与独立评测补跑混成同一会话证据。

## 5. 允许不同的表达

候选报告可以调整标题、图表和章节数量，也可以省略不改变判断的文件细节。只要满足以下结果，不要求复制参考 Markdown：

- 第一次接触任务的人能复述“为什么做、做了什么、没做什么、怎样证明”；
- 先审任务和需求，再审方案、实现、验证；前一阶段不通过时能停止；
- 事实、分析、人工决定和证据边界可区分；
- 审查问题指向具体对象，并说明反馈会改变什么；
- 能从报告下钻到任务、Diff 和运行证据。

需求和方案部分还应满足以下阅读结果：

- 需求先抓主要问题，再依次说明用户希望得到的效果、需要增加的功能、完成标准和本次范围；
- 不为了显得完整而建立“结构化需求理解”等抽象分类，也不在需求章节提前汇报交付结果；
- 方案先定位“产品 → 业务模块 → 页面/用户入口 → 前端、后端、数据层”，再出现函数、类或文件名；
- 至少用一张图标出已有模块和本次修改，文字或表格用于解释图中模块怎样变化；
- 只有真正存在需要人判断的方案选项时才单列取舍，不重复陈述“复用了什么、没新增什么”。

## 6. 正向报告应帮助发现的问题

优秀报告不只是证明实现完成，还应帮助人看到至少这些待决点：

1. 任务是实验设计输入，不是原始多维需求的产品拆分；
2. 共享查询上限变化是一个后端契约修改，不应被隐藏成纯前端加列；
3. “未完成量”是否带风险色彩需要业务决定，当前应保持中性；
4. 本地实验验证和正式生产上线之间仍有边界；
5. 代码变化尚未进入正式知识或产品分支。

## 7. 与负向用例的互补关系

| 用例 | 期望行为 |
|---|---|
| `manual_qc_allocation_gap_detail_v1` | 在任务对象错位处停止，不继续用下游实现证明原始需求 |
| `manual_qc_pending_visibility_composite_v1` | 任务和实现对齐，允许按需求 → 方案 → 实现 → 验证完整审查，但不预写批准结论 |

两者共同验证的是审查顺序和事实忠实，不是要求所有报告长度或样式相同。

## 8. 已确认的失败表现

以下表现来自 v0.3 首次人工使用，应在后续候选中作为反例：

- 用多维表格平铺“目标用户、业务口径、组合约束”等十余项，反而掩盖简单任务的主要问题；
- 在需求章节另建“需求与交付对应关系”，把实际结果提前混入需求理解；
- 一上来罗列 Repository、Schema、Service、composable 等实现名词，没有先说明它们属于哪个产品、页面和前后端层级；
- 把“现状与变化叠加”“关键取舍”作为固定章节，即使没有独立审查价值也重复需求边界。
