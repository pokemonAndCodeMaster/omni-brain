# 人工质检验收的当前未知与冲突

## 先看结论

现有知识能够建立完整学习地图，但还不能作为当前生产系统说明书。生产接口、状态、字段、阈值、部署和部分业务口径没有直接证据；目标材料内部也存在版本演进。正确用法是明确缺口和补知责任，而不是选一份看起来最完整的文档当答案。

## 已确认的解释边界

| 决策 | 已确认处理 | 理由与边界 |
|---|---|---|
| D1 历史阈值怎样展示 | 保留具体数字但只标历史 | 能保留算法细节，又不会冒充生产规则 |
| D2 执行后数据回写和交付写多深 | 只说明去向，不展开 GT/交付实现 | 本轮聚焦验收，来源不足以形成生产真相 |
| D3 领域边界 | `质检 → 人工质检 → 人工质检验收` | 验收覆盖返工跟踪，但不展开完整标注、人员管理和最终交付 |
| D4 是否保留 PENDING | 作为目标方案的数据不足结论 | 当前代码和生产规则未证明使用它 |
| D5 质量通过率分母 | `完成/分配` 表示进度，`通过/完成` 表示质量 | 原始材料同时出现“通过/分配”与“通过/完成” |

这些边界由用户于 2026-07-20 全部按推荐项确认。D5 解决了本参考成果采用哪个口径，但没有抹除原始来源之间的冲突。

## 生产事实未知

- 当前外部任务状态系统（材料称 Delta）的接口、认证、批量上限、请求和返回结构是什么？
- waiting review、审核中、待验收、验收中、完成和打回后的真实状态字段与值是什么？
- 当前使用 Group、Personal 还是 Ratio，90/300/50% 等历史数值是否仍有效？
- Good、Bad 和整体通过率的当前阈值与等值边界是什么？
- 是否仍采用两次回退、DMP 记录、30 分钟刷新或其他历史调度？
- 当前原型是否部署，连接什么数据库和外部依赖？

## 数据与 Schema 冲突

- 固定代码查询 `acceptance_submitted`，较新目标设计改为 `acceptance_completed` 并新增 Good/Bad completed 字段。
- 目标材料先后出现列式结论/执行字段和 JSONB `exec_status` 状态机，不能静默合并成当前 Schema。
- 当前迁移没有创建 Repository 查询所需的 `t_qc_daily_snapshot`。
- 交付任务、`scene_name` 和外部 task/clip 的一对多映射与稳定主键尚未得到生产数据验证。
- 快照刷新周期、统计日期语义和数据延迟没有当前运行证据。

## 设计声明与代码冲突

- 目标 API 和产品页要求 preview 固定具体 task_ids；当前原型只保存数量计划和统计单元。
- Schema 声明 group、annotator、scene 叶子维度，Service 当前只接受 task/date。
- 材料声称 2026-07-09/14 的迁移、人员 Repository、DAG 和 141 项测试已经完成；固定提交不存在相应文件。
- 目标文档列出 Sampler/Rule 注册表、`DeltaClient` 和多个 Service；固定提交尚未实现。
- 固定代码 `src/obs/` 只有占位文件，无法证明 OBS 具体客户端或验收使用方式。

## 来源本身的限制

- 两份“人类纠正”文档 23/24 字节相同，只能算一份语义来源，且原始对话没有提供。
- ChatGPT 项目导出混合人工纠正、历史代码、目标方案和实施声明；文件头 `active` 不能证明今天仍然有效。
- 自动生成 Wiki 只可用于导航和发现冲突，不能独立确认关键事实。

## 谁需要补什么

| 责任方 | 需要提供的证据 |
|---|---|
| 业务负责人 | 当前阶段定义、采样规则、通过率口径、阈值、执行范围和交付完成条件 |
| 外部任务系统负责人 | 当前 OpenAPI/接口说明、状态映射、测试环境与回查结果 |
| 数据负责人 | 生产快照 DDL、血缘、刷新时间、字段口径和真实样例 |
| 原型维护者 | 部署状态、数据库初始化方式、端到端启动步骤和下一实现边界 |
| 资料或代码维护者 | ChatGPT 材料所称已完成实现对应的仓库和提交 |
