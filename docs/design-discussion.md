## 一、项目定位（已对齐）

**Omni-Brain** 是个人 AI 操作系统，目标是将工作、学习、开发、生活纳入认知闭环。
核心理念（已写入 AGENTS.md）：
- 知识即文件（OKF 兼容 Markdown + YAML Frontmatter）
- 索引可重建（BM25/图均为派生产物）
- 能力即技能（Agent Skills 开放标准）
- 记忆即知识（不单独设 memory 类别，直接形成卡片）

## 二、知识库架构（部分对齐，有争议）

### 2.1 已确定

- **存储格式**：OKF 兼容 Markdown + YAML Frontmatter，文件系统即知识库
- **索引策略**：`scripts/compile_index.py` 生成派生索引（SQLite FTS5），可从源文件重建
- **原始资料保护**：`knowledge/raw/` 不可修改，是摄入前的原始输入
- **规模预期**：1000+ 卡片，BM25 单独不够，需要向量检索
- **向量方案候选**：sqlite-vec（零外部依赖，嵌入同一 SQLite 文件）

### 2.2 已讨论但未最终确定

**知识架构分层（Middle-Out Ontology 方向）**：

```
Upper Ontology（总纲层）—— 不超过 10 个核心概念类型
    ↓ 具体化
Domain（领域层）—— taxonomy.yaml 中的 domain 枚举（~15 种）
    ↓ 实例化
卡片（叶子层）—— 无限扩展，但受约束
```

- **总纲层内容未定**：谁来定（用户 or AI 起草用户审）？具体是哪些类型？
- **叶子膨胀控制**：用 Faceted Classification（多维标注）代替深层树；`domain` 不允许超过一级子分类（`backend_dev.fastapi` 不合法，应是 `domain: backend_dev` + `tags: [fastapi]`）
- **taxonomy.yaml 升级方向**：从"枚举列表"升级为"Schema Packs"（每种 type 定义必填字段），尚未实施

### 2.3 争议点

**争议1：知识库规模与检索技术的取舍**

- 用户：想保持轻量，担心加向量数据库变重
- 调研结论：1000+ 卡片规模下 BM25 精度会明显下降，需要向量
- 当前倾向：sqlite-vec（本地嵌入向量，无需独立服务），但还未最终拍板

**争议2：代码和 MD 知识文件的配合方式**

- 痛点（用户明确指出）：代码相关 MD 卡片要么内容老旧导致不可信，要么需要读大量代码 token 爆炸，要么缺失细节
- 调研结论（2026 实践）：三层分工——WHY（ADR 卡）/ WHERE（符号地图）/ HOW（源文件）
- 用户追问：MD 里有了 WHY+WHERE，查阅时还是要读源代码，那 MD 的价值在哪？
- **未完成对齐**：MD 对代码的理解深度边界在哪里？查阅时哪些场景能省掉读源码，哪些不能？

## 三、知识摄入流程（有较多争议，核心问题未解）

### 3.1 已确定方向

- **REWRITE 优于 APPEND**：新内容摄入时，优先找到目标卡片并改写，而不是新建追加
  - 来源：obsidian-second-brain 的核心实践（5-15 张页面被改写 per source）
- **落点确认（选择题式半自动化）**：
  - 系统给出候选落点（A/B/C 或新建），用户选择，不是用户从零指定
  - 触发条件：BM25 相似度 > 0.7 时强制确认
- **原文出处锚定**：每个核心声明必须有 `> 📌 引自原文：`，以原文为质量保证，不依赖 AI 自评置信度

### 3.2 核心未解问题

**问题1：REWRITE 如何避免"追加一坨屎"**

普通流程：找到目标卡片 → 给 LLM "更新它" → LLM 追加内容 + 装模做样写更新日志

真正需要的是**内容关系决策树**，在执行前先判断新内容与目标卡片的关系类型：
- 替换现有声明（逐声明替换，不追加）
- 修正错误（高亮冲突，人工确认）
- 新增独立章节（在合适位置插入，而非尾部追加）
- 触发拆卡（卡片过大时一变多）
- 重定向到另一张卡（落点找错了）

这个决策树需要固化成 `ingest_pipeline.py` 的执行步骤，不能只靠提示词（提示词级别约束容易被模型忽略）。

**问题2：知识架构一致性如何在 REWRITE 过程中得到保证**

REWRITE 时不只是内容更新，还需要检查目标卡片的 type/domain 是否仍然合适，关系连接是否需要调整。"有条理地扩充知识"需要方法论牵引，现有开源项目均未在此下功夫。

**问题3：摄入评估 Agent 的设计**

- 需要：从"第二人称"角度交叉验证摄入结果（完整性、出处、结构合规、冲突检测）
- 约束：评估维度必须**可程序化验证**，不能依赖模型自评（置信度打分是虚的）
- 候选评估维度：
  - 完整性：原文关键实体 vs. 卡片覆盖率（覆盖 < 80% 触发人工）
  - 出处锚定：有声明但无 `📌` 锚点
  - 结构合规：frontmatter 必填字段完整性（schema check）
  - 冲突检测：BM25 找相似卡片，对比关键声明（相似度 > 0.7 且内容不一致）
  - 落点合理性：type/domain 是否在 taxonomy 枚举内

**问题4：部分内容过期，部分内容有效（已知无解）**

- 一张卡片里有 5 段内容，第 3 段过时——自动识别哪段过时目前无可靠方法
- 临时方案：CodeModule 卡靠 `code_hash` 触发过期；其他卡片靠健康检查人工 review
- 接受为已知局限，暂无优雅解法

## 四、检索系统（方向确定，技术选型未完成）

### 4.1 已确定

- **分层检索**（Hub 摘要快照机制）：
  - 检索默认先扫 Hub/Synthesis 层（摘要快照），命中后再展开叶卡
  - 类似 LinearRAG（ICLR 2026）Tri-Graph 层级，减少直接读全文的 token 消耗
- **BM25 + 向量混合**：BM25 处理词汇精确匹配，向量处理语义相似（双路 RRF 合并）
- **关系图过滤**：按 relation_type 权重过滤（`supports` > `depends_on` > `related`）
- **类型/领域过滤**：`--type Norm,Pitfall` 等查询参数，对应 taxonomy 枚举

### 4.2 未确定

- 向量模型选型（本地 embedding model 还是 API？）
- 向量维度和相似度阈值
- 关系图的存储格式（当前是 `graph.json`，是否足够）

## 五、健康检查体系（方向对齐，未实施）

健康检查只输出问题清单，不打质量分数（分数是虚的），不自动执行修复，周维度人工处理。

**评价维度（全部是确定性规则，不依赖 LLM 自评）**：

| 维度 | 检查规则 | 输出 |
|---|---|---|
| 完整性 | frontmatter 必填字段是否齐全 | 缺失字段列表 |
| 正确性（可验证部分）| 有 `📌` 的声明，raw/ 原文是否还存在 | 悬空引用列表 |
| 去冗余/重复度 | BM25 相似度 > 0.85 的卡片对 | 疑似重复对 |
| 一致性/自洽性 | 同实体在不同卡片有矛盾声明 | 矛盾对 |
| 孤岛检测 | 无 relations 且 index.md 未注册 | 孤岛卡片 |
| 过期检测 | CodeModule code_hash 变化 / 超 90 天未更新 | 疑似过期 |
| 叶子膨胀 | 某 domain+type 组合下卡片 < 2 张 | 过细分类预警 |
| 总纲覆盖 | type/domain 超出 taxonomy 枚举 | 超范围卡片 |

## 六、系统架构分工（最新讨论，尚未完整对齐）

### 6.1 四层分工框架（讨论共识，未最终拍板）

```
┌─────────────────────────────────────────────┐
│  AGENTS.md / system prompt（身份层）          │
│  WHO AM I + 核心原则 + 行为约束               │
│  永远在 context 里，不用检索                  │
├─────────────────────────────────────────────┤
│  Skills（技能层）                             │
│  HOW TO DO：工作流程、操作手册、思维框架        │
│  在任务开始时按 intent 注入，不是在执行中检索   │
├─────────────────────────────────────────────┤
│  Knowledge Base（知识层）                     │
│  WHAT：事实、规范、历史、具体上下文             │
│  在任务执行中按需检索（BM25 + 向量）            │
├─────────────────────────────────────────────┤
│  Code Tools（工具层）                         │
│  EXECUTION：确定性操作、IO、计算               │
│  模型调用，结果结构化返回                      │
└─────────────────────────────────────────────┘
```

### 6.2 各层分工原则

**靠 Code Tool（确定性，结构化返回）**：BM25/向量检索、AST 解析、文件读写、健康检查规则校验、Index 重编译

**靠 Skill（意图路由 → prompt 注入，不生成文字传回）**：知识摄入流程、知识检索流程、开发任务标准流程、任务反思、结构化思维框架

**靠异步 Sub-agent（后台，不阻塞主流程）**：批量摄入、夜间健康检查、评测集运行

**明确不用**：同步 sub-agent 生成长文本传回主 agent（15 token/s 下 1k token = 67s，不可接受）

### 6.3 关键未解问题：知识库优先是不是伪命题？

用户提出质疑：能否通过"构建优质知识库，模型在适当时机取用背景知识"来覆盖所有场景？

**当前判断（未完全对齐）**：
- 知识库擅长：WHAT（事实 + 项目特定信息），跨会话持久化，specificity（个人专属）
- 知识库不擅长：HOW TO THINK（程序性知识）、实时推理、创造性合成
- 触发时机问题是真实硬伤：知识库内容无法保证在恰当时机被检索，比 Skill 意图路由更难控制
- **结论**：知识库 ≠ 万能，需要与 Skills（HOW）和 AGENTS.md（WHO）共同构成完整体系

### 6.4 Harness 设计（刚开始，尚未展开）

用户明确需要一个覆盖各种工况的 Agent 体系（开发、学习、日常任务等），涉及：
- 什么靠 Skills，什么靠 Agent，中间步骤该多重或多轻
- 哪些靠代码解决，哪些靠模型解决
- 工具体系的整体设计

**这块讨论刚启动，是下一阶段重点**。

## 七、参考项目调研（已完成）

| 项目 | 核心价值 | 局限 |
|---|---|---|
| **gbrain**（garrytan）| Schema Packs + Dream Cycle（夜间批处理）+ pgvector 混合检索 | 依赖 Postgres，重基础设施 |
| **obsidian-second-brain**（eugeniughelbur）| REWRITE 原则 + 4个定时 agent + `/obsidian-architect`（codebase 扫描入 vault）| 依赖 Obsidian 生态，检索弱 |
| **LLM Wiki v2**（rohitg00）| Confidence decay + Consolidation tiers + Crystallization 理论 | 只有设计无实现，工程化极难 |
| **Yuxi**（xerrors）| LightRAG（向量+图双路）+ LangGraph 编排 + Neo4j | 企业级重量，个人用过度复杂 |
| **LinearRAG**（ICLR 2026）| Tri-Graph 层级（Passage/Sentence/Entity），零 token 构建图 | 学术论文，无直接开源实现 |
| **Graphiti**（getzep）| 时序感知图 + Entity Resolution（fuzzy+embedding+LLM 三层去重）| 生产可用，但依赖 Neo4j |
| **CocoIndex**| Tree-sitter AST + 增量索引 + MCP server | 代码工具，不涉及知识管理 |
| **HippoRAG 2**（ICML 2026）| 双节点表示（原文段落 + 短语节点），解决词汇失配 | 论文阶段 |

## 十一、讨论原则（用户明确要求）

- **不要直接开干**：需求未清晰前不能开始实现，宁可高频讨论
- **可实施性优先**：方案要考虑异常情况的鲁棒性，"设计时想得很美，一步偏轨就全崩"是不可接受的
- **半自动化确认**：人工介入以选择题形式，系统给候选，用户选择，不是用户从零指定
- **不依赖模型自评**：所有评估维度必须可程序化验证
- **不造假**：知识卡片极致精简，有具体证据，不虚构
- **外科手术式修改**：代码变更聚焦且可验证
- **中文优先**：面向用户的回复用中文
