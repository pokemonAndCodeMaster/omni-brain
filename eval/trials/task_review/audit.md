# 本地工作审查 Harness 弱模型审计

## 当前结论

`review-work` 已在认证参考约束下完成首个软件开发审查切片。最终候选由 OpenCode 的
`deepseek-v4-flash`（medium）盲测生成；模型看不到 `eval/reference/`、历史候选评分或
人工反馈答案。Agent 对照认证参考和隐藏事实独立评分，用户不需要再替 Harness 审查弱模型候选。

当前能力边界是：

- 对齐的已完成软件工作，生成一张可填写的本地审查单；
- 按需求、方案、实现、验证和总体决定的顺序审查，只开放第一个待审点；
- 原始诉求、实际任务和产物错位时，在需求阶段阻断下游批准；
- 简单只读状态问题不误触发审查能力。

这证明的是**软件开发本地审查**这一验证切片，不代表所有任务类型均已验证。

## 实际 Harness 组成

| 责任 | Harness 实体 | 实际作用 |
|---|---|---|
| 触发与排除 | `AGENTS.md` | 复杂成果或显式审查请求加载 `review-work`；简单问答和局部低风险工作不触发 |
| 共同工作流 | `.agents/skills/review-work/SKILL.md` | 固定事实、核对任务对象、按阶段审查、错位即停止、更新同一张审查单 |
| 软件开发分支 | `.agents/skills/review-work/references/software-development.md` | 规定软件审查的上下文、章节顺序、图表、R1—R5 和填写方式 |
| 人工入口 | `workspaces/reviews/<task-id>/review.md` | 用户最终只阅读这一张审查单，并按 R/D 编号回复 |

没有引入审查账本、YAML 交换协议、证据采集脚本或模型 API。事实仍来自任务原文、Git
Diff、源码和已有运行记录。

R1—R5 填写块、共享契约与边界说明均存在；没有参考泄漏、预写批准或低价值问题喧宾夺主。

## Harness 迭代带来的内容变化

上一轮正向 003 虽然事实基本正确，但报告结构不足：没有清晰的使用入口，把多个审查阶段
挤在同一节中，系统与实现图不足，R 点缺少稳定的“审什么、决定什么、反馈后改变什么”，
且注意力落在低价值的标签措辞和测试粒度上。

本轮没有写死本用例字段或数值，而是把可复用约束放到软件开发条件分支：

1. 顶部先给报告身份、使用方式和可点击导航；
2. 完整全貌先回答背景、来源、采用方案、完成结果和当前边界；
3. 需求、方案、实现、验证、总体决定分别成章；
4. 方案先画系统位置与改造通路，实现再给模块变化和关键流程；
5. 每个 R 点必须包含目的、当前内容、选项、影响和反馈块；
6. 优先暴露会改变决定的共享契约、业务语义、证据边界和发布状态。

共同触发、事实核验、错位阻断与阶段顺序仍保留在根 Skill；软件报告的详细结构只放在
条件引用中，避免把所有任务都强制成同一种长报告。

## 三类回归证据

| 工况 | 预期 | 当前证据 |
|---|---|---|
| 正向：任务与产物对齐 | 生成达到认证参考质量的完整审查单 | `TASK_REVIEW_POSITIVE_OPENCODE_DEEPSEEK_004/`，`17/18` |
| 负向：任务对象错位 | 身份包即可判定时不读产品实现，阻断下游审批 | `TASK_REVIEW_NEGATIVE_MISMATCH_OPENCODE_DEEPSEEK_006/`，通过 |
| 不触发：简单状态问题 | 只回答状态，不创建审查单 | `TASK_REVIEW_NO_TRIGGER_OPENCODE_DEEPSEEK_002/`，通过 |

负向回归还实际暴露并修掉了两类问题：第一版过读产品导致把中间 Harness 安装提交混入
业务改动，第二版虽不读实现却反复推演已被用户明确否决的切片。最终规则把任务对象判断变为
独立阶段 A：只读任务身份包，批准事实优先于 Agent 的“逻辑相关”推演；错位立即结束。
