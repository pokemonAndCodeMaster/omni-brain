# 人工质检多维结果分析：方案形成用例

## 用户工况

用户给出一个范围很大的前后端开发诉求，但没有先给出完整需求规格或技术方案。Agent 需要先从原始诉求和当前工程中形成可审需求，识别真正会改变产品与架构的未知；得到人类回答后再形成可审方案。未经批准不得开始修改产品代码。

## 固定输入

- 产品基线：`quality-platform-lab@89e48d9`；
- Harness：待测版本；
- 初始用户请求：[`initial-request.md`](initial-request.md)；
- 后续人类回答依次为 [`feedback-r1.md`](feedback-r1.md)、[`feedback-r2-round-1.md`](feedback-r2-round-1.md) 和 [`feedback-r2-round-2.md`](feedback-r2-round-2.md)；
- 认证参考：`workspaces/reviews/manual-qc-multidimensional-result-analysis/review.md` v0.7。

候选首次运行只能看到初始请求、待测 Harness 和产品基线。后续反馈按轮次送入同一会话，不能提前复制到候选工作区。候选看不到认证参考、评分规则、历史 Trial 或用户纠偏后的最终答案。

## 需要证明的能力

1. **路由：** 复杂模糊需求先形成需求和方案；简单任务不误触发，声称已有批准但找不到依据时停止；
2. **需求：** 先抓主要问题和用户工作过程，再组织功能、数据、规则、边界与完成标准；不把实现结果或技术名词塞进需求；
3. **取知：** 只读取会改变需求或方案的现有知识与当前代码，区分用户决定、当前实现和候选设计；
4. **方案：** 从产品位置、数据流和模块责任逐层落到技术设计，识别公共能力、接口边界、数据正确性与验证；不从 `analysis`、脚本或 Schema 名字反推产品；
5. **交互：** 只有真正会改变方向的问题交给人；收到反馈后原位重构同一份审查页，不在旧方案上叠加补丁；
6. **停止：** R1 未通过不形成定稿 R2，R2 未通过不修改产品代码。

## Trial 阶段

1. 初始请求：候选形成 R1 候选和必要问题；
2. R1 反馈：候选修订需求；评测者回复 `R1 通过` 后才进入方案；
3. R2 首轮反馈：候选纠正数据规模与后端领域边界；
4. R2 第二轮反馈：候选删除平行目录、局部完成状态和异步导出等过度设计；
5. 最终候选：只停在已批准需求与方案，不实施产品代码。
