## 1. 一页项目快照

### 终极目标

Omni-Brain 面向工作、开发和业务协作，目标是把分散在文档、代码、数据、流程、系统和人员经验中的信息，转化为一个：

- 人能够从全局逐层理解；
- AI 能够按任务可靠调用；
- 关键结论可追溯和核验；
- 能随业务与代码变化持续演进；
- 不因知识、关系和方案增加而失控膨胀的知识与决策系统。

### 近期产品目标

当用户需要理解、设计或建设一项业务/软件能力时，系统能够从可能不完整的目标出发，盘点已有知识，识别并补足关键缺口，在目标澄清与知识编织的迭代中形成**可核验、可下钻且不过载的任务上下文**；在受控范围内辅助形成方案和真实能力产物，以运行或任务证据验证结果。任务产生的稳定知识安全进入规范底座和可浏览视图，一次性选择与排序保留为任务投影，避免后续任务重复准备又不让知识库碎片化。

### 首个验证领域

质检业务，覆盖人工质检、自动化质检、大模型质检和专题数据质量。完整质检平台的能力建设闭环作为长期牵引，第一条深入旅程暂定为**一个人工质检具体能力产物的理解—设计—建设—验证—回写闭环**；“验收任务分配闭环”是候选，尚未最终确认。

### 当前焦点

正在验证以下架构假设：

1. 规范知识底座应怎样承载业务—系统—代码语义；
2. 小核心对象族、领域模式包和公共基建边界是否有效；
3. 产品视图能否按稳定用户任务模板化，而不是随领域无限增长；
4. 能否围绕一个可能模糊且知识不足的任务，迭代完成目标澄清、存量盘点、补知、编织、验证和决策准备度判断；
5. 任务驱动产生的新知识能否进入长期可维护的规范结构和人类浏览视图，而不是只形成一次性上下文或零散卡片；
6. 能否把可信上下文继续转化为一个可运行、可验证的能力产物，并将结果安全回收到知识体系；
7. 更换能力较弱的基础模型后，是否仍能依赖组件契约和阶段门禁重放主要过程，而不依赖强模型临场补偿。

### 当前真实状态

- 已形成产品基调、质检场景和候选信息架构；
- 已有 Markdown/YAML 知识目录、taxonomy、操作日志和手工摄入记录；
- `compile_index.py`、`search_engine.py`、`ingest_pipeline.py`、`health_checker.py` 均为 stub；
- 已有首个任务恢复 Capability Eval、冻结 fixture、参考响应、两次人工 Trial 基线和 Grader 校准；尚无自动 Runner、完整 Transcript 和质检领域 Suite；
- `.agents/skills/` 同时包含后续实验 Skill 与 Phase 0 能力草图；全量静态审计已完成，但高风险 Skill 尚未迁移；
- 尚无产品网站、视图引擎、任务上下文引擎或方案设计工作区实现。

### 下一里程碑

使用一个具体的人工质检能力产物，建立最小规范知识切片，生成并验证：

1. 领域/流程视图；
2. 方案设计上下文；
3. 实现与影响视图；
4. 一个受控范围内的真实能力产物及其运行/任务证据；
5. 同时评价领域结果和 Omni-Brain 建设能力的固定用例。

随后用自动化质检或数据产线公共基建反证，决定哪些结构可以固化。

## 2. 项目要解决的问题

### 2.1 不是“资料存在哪里”，而是“任务时如何获得可信上下文”

现有系统通常能保存或搜索大量资料，却难以回答：哪些内容是当前事实、哪些是目标方案、为什么与本任务有关、需要读到什么深度、代码做到哪里、还有什么未确认。

### 2.2 人类理解与 AI 使用必须同时成立

- 人需要总览、学习顺序、当前位置、上下游和逐层下钻；
- AI 需要稳定实体、语义关系、范围、状态、来源和检索边界；
- 两者应共享规范底座，但使用不同投影。

### 2.3 知识变化必须可控

业务事实、方案、代码和运行状态的更新速度不同。系统必须区分事实错误、关系问题、视图问题、检索问题和治理问题，并支持预览、影响分析、回归与回滚。

### 2.4 复杂领域不能被一棵目录树压平

质检实例同时存在数据交付、质检能力、生命周期、系统、数据资产和实现等多条轴。系统需要稳定坐标与显式关系，而不是无限深目录或全量复制。

## 3. 顶层架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 人与 AI 的产品体验                                           │
│ 浏览/学习｜精确问答｜任务上下文｜方案设计｜实现影响｜治理      │
└──────────────────────────────┬───────────────────────────────┘
                               │ 产品视图与任务投影
┌──────────────────────────────▼───────────────────────────────┐
│ 上下文与决策层                                                │
│ 意图/范围识别｜检索与有界扩图｜上下文组装｜方案引用与影响分析  │
└──────────────────────────────┬───────────────────────────────┘
                               │ 查询规范语义与派生结构
┌──────────────────────────────▼───────────────────────────────┐
│ 知识层                                                       │
│ 规范知识底座｜领域模式包｜来源与状态｜公共能力与使用契约       │
├──────────────────────────────────────────────────────────────┤
│ 派生结构                                                     │
│ 全文索引｜关系图｜代码符号图｜Schema 清单｜数据血缘｜新鲜度    │
└──────────────────────────────┬───────────────────────────────┘
                               │ 证据、抽取与实时读取
┌──────────────────────────────▼───────────────────────────────┐
│ 事实源                                                       │
│ 原始资料｜代码｜API/Schema｜数据库/数据资产｜运行系统｜人工确认 │
└──────────────────────────────────────────────────────────────┘

治理与评测控制面横切所有层：
Schema / taxonomy / provenance / view registry / change set /
health / eval / version / approval / rollback
```

### 核心分工

- **事实源**保存真实内容，不能被摘要副本取代；
- **规范知识底座**保存稳定语义、解释、关系、状态和证据；
- **派生结构**通过确定性工具从源码、Schema 和知识文件重建；
- **上下文与决策层**围绕当前任务选择必要知识，而非返回全部相关内容；
- **产品体验**提供面向不同用户任务的视图；
- **治理与评测控制面**决定系统如何安全变化并证明有效。

## 4. 组件地图与成熟度

成熟度统一使用：

```text
0 Open → 1 Hypothesis → 2 Provisional → 3 Approved → 4 Implemented → 5 Verified
```

`Implemented` 只表示存在实现，`Verified` 才表示真实用例证明有效。

组件的全局成熟度与特定切片证据分开记录。单个切片可以形成 `Verified@slice`，但不能据此把组件整体升级为 `Verified`；首个能力切片以 L2“可信最小闭环”为目标，L3 可复用和 L4 跨场景泛化由后续实例证明。详见 [能力切片实验协议](specs/capability-slice-experiment.md)。

| 组件 | 目标能力 | 关键设计思想 | 设计成熟度 | 当前实现 | 主要差距 |
|---|---|---|---:|---|---|
| 1. 事实源与来源注册 | 知道事实来自哪里、谁负责、何时有效 | 原料不可变；当前事实仍回到源码/系统；稳定 ID 与来源 | 2 | 有 `knowledge/raw/` 和来源字段，主要靠人工 | 缺来源注册表、权威矩阵、连接器、事实时间 |
| 2. 规范知识底座 | 唯一规范落点，连接业务—系统—代码 | 小核心对象族 + 领域模式包；当前/目标/历史分离 | 2 | 有 Markdown/YAML、taxonomy 和少量 draft 卡 | 类型与关系仍是旧骨架；缺质检最小实例和 Schema 校验 |
| 3. 公共能力与跨域契约 | 数据库、OBS、数据契约等只维护一份 | 按能力所有权维护；业务域只保存依赖或特有使用契约 | 1 | 只有讨论结论；外部 wiki 有零散模块卡 | 缺所有权边界、稳定标识和跨域映射实例 |
| 4. 派生结构编译器 | 自动生成检索、图、代码/数据结构 | 可重建；不手写每个函数、表字段和血缘 | 1 | `compile_index.py` 为 stub | FTS、关系编译、代码图、Schema/血缘适配均未实现 |
| 5. 摄入与 Brownfield 迁移 | 从新资料或混沌旧库建立受控、可复用知识 | 原料冻结、候选知识、冲突/粒度/归属门禁、分片迁移、可回滚 | 2 | `knowledge-ingest` 已按长期知识变更重写并通过契约测试；`ingest_pipeline.py` 为 stub | 尚缺独立模型路由/端到端 Trial、来源注册、自动归属/冲突检查和迁移工作区 |

| 7. 产品视图与导航 | 支持长期浏览、流程、学习、查询、影响和治理 | 视图按稳定用户任务模板化；任务新增知识不得破坏领域坐标和浏览层级 | 2 | 有候选视图清单，无引擎和 UI | 缺 view registry、知识晋升后的视图影响检查、页面原型和用户验证 |

## 5. 系统级设计原则

### P1. 任务价值优先

知识、关系、组件和视图都必须服务可复现的用户任务；“保存更多”和“连接更多”不是成功指标。

### P2. 一个规范落点，多种投影

核心定义和证据只维护一份。浏览页、学习路线、回答和方案上下文引用它，不复制成多套事实。

### P3. 事实源与解释层分工

代码、Schema、数据库和运行系统提供精确现状；知识底座提供边界、意义、因果、决策和定位。精确实现问题必须实时读取事实源。

### P4. 图谱有准入门和遍历预算

不是所有内容都建节点，不是所有关系都沿图扩展。节点/关系需要稳定身份和任务价值；查询受领域、关系、方向、跳数、状态和上下文预算限制。

### P5. 小核心、领域扩展

全局只保留稳定对象族；人工质检、自动化质检、大模型质检和数据平台通过领域模式包扩展，不把局部模型升级成全局本体。

### P6. 公共能力按所有权共建

数据库、OBS、数据契约和产线流程拥有唯一规范节点。消费者通过依赖、输入输出或使用契约连接；出现真实复用后再晋升共享能力。

### P7. 派生优于手工同步

代码符号、表字段、索引、血缘和新鲜度尽量由工具生成。人工维护稳定语义，不维护容易失效的结构镜像。

### P8. 变化必须可逆

结构和语义修改使用 change set，包含问题、影响、差异、验证和回滚。失败后回退整组变更，不在错误结果上继续打补丁。

### P9. 实例验证后再固化

讨论结论必须经历真实旅程和反例，才升级为 taxonomy、Schema、视图模板或代码机制。

### P10. 任务驱动发现，长期结构复利

具体任务负责暴露真实知识需求，但不决定规范知识的全部组织方式。每次知识准备同时区分短期任务投影与长期知识变更候选；稳定内容经来源、粒度、关系和视图门禁进入规范底座，确保后续任务可复用且人类仍能沿清晰的领域、流程、系统和学习视图浏览。

## 7. 当前聚焦切片

### 当前问题

以“一个人工质检具体能力产物”为入口，验证规范知识底座、任务上下文、方案/影响视图和公共基建引用能否共同工作，并继续走到受控建设、真实验证和知识回收。完整质检平台闭环负责长期牵引，不是当前一次性交付范围。

### 当前不做

- 不先迁移全部外部 wiki；
- 不先设计完整企业知识本体；
- 不先实现全功能网站；
- 不先引入图数据库或向量数据库；
- 不把质检一站式业务平台本身当作 Omni-Brain 的实现范围。

### 切片完成定义

1. 能指出相关业务对象、流程、规则、数据、系统、决策、代码和来源；
2. 能区分 `as_is`、`to_be`、`historical` 及知识状态；
3. 能生成三种投影：流程/领域视图、方案上下文、实现影响视图；
4. 每个纳入上下文的对象都有理由，整体受阅读/token 预算约束；
5. 能产出一个边界明确、可运行或可任务验证的领域能力产物；
6. 变更后能提出受影响知识与代码，不直接自动覆盖；
7. 有固定查询和旅程测试，同时比较领域结果与 Omni-Brain 自身能力。

## 8. 路线图

### R0：收束目标与架构（当前）

- 维护本 Blueprint；
- 明确文档职责、架构组件和成熟度；
- 选择第一条真实变更旅程。

完成条件：用户认可当前问题、架构边界和验证方式。

### R1：质检最小能力建设切片

- 从人工质检验收材料抽取最小规范对象和关系；
- 以验收任务为测试夹具，手工建立任务框架、问题/缺口图和知识准备度基线，区分模型临场能力与系统组件证据；
- 将补知结果拆分为任务投影与长期知识变更候选，验证稳定知识能进入可维护结构和人类浏览视图；
- 建立来源/状态/现实形态；
- 建立公共基建引用，不复制定义；
- 手工生成第一版三种视图和上下文包；
- 用该上下文辅助形成一个具体能力产物，记录设计、实现、验证和回写过程。

完成条件：达到 [能力切片实验协议](specs/capability-slice-experiment.md) 的 L2 可信最小闭环；不用通读全部卡片即可完成一次方案分析，并进一步产出经真实任务或运行证据验证的能力结果；领域产物和 Omni-Brain 建设过程均有可复核证据。该结果不自动证明 L3 可复用或 L4 跨场景泛化。

### R2：确定性编译与检索 MVP

- 实现 Frontmatter/Schema 校验；
- 实现 FTS、类型/状态过滤和有界关系扩展；
- 接入最小代码/Schema 索引；
- 将 R1 手工上下文过程变为可重复工具流程。

完成条件：固定质检评测稳定通过，输出规模和来源可解释。

### R3：产品视图与方案工作区 MVP

- 实现领域、流程、查询、方案和影响视图；
- 建立 view registry 与领域预设；
- 支持方案引用、缺口记录和安全回写候选。

完成条件：人可以通过网站完成一次理解—设计—下钻—回写旅程。

### R4：治理、Brownfield 与跨领域扩展

- 实现健康检查、change set、回归和回滚；
- 分片接入外部混沌知识库；
- 用自动化质检/大模型质检/数据平台反证模式；
- 稳定后再决定向量、图存储和更高自动化。

完成条件：新增领域不会复制公共知识，结构变化不会破坏既有关键旅程。

## 9. 关键决策与开放问题

### 当前暂定结论

- 一个规范知识底座、受维护产品视图和默认临时的任务投影；
- 事实源/规范语义/派生结构分工；
- 小核心对象族 + 领域模式包；
- 产品视图按用户任务模板化；
- 公共基建按能力所有权维护唯一规范落点；
- 完整质检平台能力建设闭环作为长期牵引，具体能力产物作为短期实验；
- 先手工验证“理解—设计—建设—验证—回写”切片，再实现通用工具。

以上均为 `provisional`，不是最终 Schema 或技术选型。

### 当前开放问题

1. 第一项人工质检具体能力产物是否选择“验收任务分配闭环”，边界到哪里；
2. 核心对象族和关系是否足以表达该变更；
3. 业务事实、目标方案、当前实现应采用卡级还是声明级状态；
4. 代码、数据库 Schema 和数据血缘的最小派生范围；
5. 产品视图定义需要怎样的最小 DSL/配置；
6. 外部质检 wiki 中哪些资料是权威事实、历史快照或待迁移候选；
7. 用什么用户结果证明上下文包真正改善方案设计；
8. 怎样区分领域能力产物的成功与 Omni-Brain 能力建设闭环的成功；
9. “能力建设与验证”应扩展现有方案工作区，还是在实例稳定后成为独立组件；
10. 零背景学习、模糊痛点和明确重构三种起点怎样汇合，任务框架、问题缺口和知识切片如何迭代推进；
11. 怎样判定知识已足够支持当前决策，同时确保新增稳定知识具有长期归属、可浏览、可复用且不过度碎片化；
12. 哪些步骤必须由组件和确定性门禁承担，才能让基础模型重放而不依赖强模型临场能力。

## 10. 文档职责与更新规则

| 文档 | 负责回答 | 不负责 |
|---|---|---|
| `docs/blueprint.md` | 当前目标、架构、组件、成熟度、焦点、差距和路线 | 展开全部讨论过程和实现细节 |
| `docs/product-direction-discussion.md` | 为什么形成这些判断、争议、备选和未决问题 | 冒充当前权威架构快照 |
| `docs/scenarios/*.md` | 在真实领域中怎样验证架构 | 定义全部跨领域系统规则 |
| 未来 `docs/specs/*.md` | 单组件或切片的实施契约 | 重复项目总目标和历史讨论 |
| `AGENTS.md` | Agent 如何工作、查事实、变更和验证 | 承载完整产品规格与路线图 |
| `knowledge/` | 可检索、可关联、带来源的稳定知识 | 代替项目 Blueprint 或堆积会话全文 |

发生以下变化时必须更新本 Blueprint：

- 项目目标、架构边界或原则被批准/推翻；
- 组件进入新成熟度或获得新验证证据；
- 当前焦点、完成定义或路线发生变化；
- 质检实例产生可推广或被反证的结论。

更新时优先改写对应章节和状态表，不在末尾追加重复总结；详细推理保留到 discussion，具体实现下沉到 scenario/spec。
