# 人工质检全流程能力长期依赖分散知识、手工跟踪与脚本

## 1. 场景与目标

人工质检从需求接纳开始，跨越数据准备、规则对齐、任务生产、标注、验收、通过/打回、返修、结果入库和最终交付。用户希望逐步建设一站式质检平台和可复用质检能力，最终具备规则资产复利、流程组合与 Agent 化条件。

本问题不是要求 Omni-Brain 当前直接运行整套质检业务，而是检验它能否成为能力建设基座：从真实问题和分散事实出发，帮助形成知识、流程、设计、软件或工具产物，完成验证并安全回收新知识。

## 2. 已确认的现实阻碍

- 需求管理依赖在线表格和人工同步，标准字段不等于流程真正被理解和执行；
- 信息散落在数据库、看板、脚本、表格和上下游系统中，且常以中间过程维度组织，难以还原单条需求状态；
- 新需求的输入、规则、界面和任务形态越来越定制化，既有质检方式难以及时适配；
- 标注/验收分配、统计、结论执行和返修跟踪大量依赖本地脚本、人工查询与人工判断；
- 人力被消耗在查数、拼接、同步和反复确认上，平台、知识、流程和原子能力均未形成稳定建设闭环。

## 3. 分诊与架构判断

| 层 | 判断 | 当前结论 | 成熟度 |
|---|---|---|---|
| 产品范围/假设（主层） | Omni-Brain 应怎样支撑庞大的质检建设目标 | 作为能力建设与演进基座，而非当前直接承载质检运行态 | provisional |
| 检索与上下文 | 建设一项能力前难以获得最小充分背景 | 现有 Blueprint 原则覆盖，但尚无真实上下文包和工具实现 | provisional |
| 工作流与治理 | 从方案到实现、验证、回写的建设过程未被显式建模 | 需要通过首个能力产物实验发现最小闭环 | hypothesis |
| 内容与实施细节 | 规则、流程、数据、代码和脚本事实分散 | 需按权威源、状态和任务范围逐步建立受控切片 | confirmed problem |

上一轮曾候选为 Omni-Brain 增加运行态业务上下文和动作控制层。经用户校正，当前不采用这一推断：这些能力可能属于被建设的质检平台或未来 Agent 基础设施，尚不能证明必须成为 Omni-Brain 当前顶层组件。

## 4. 双层目标

### 长期牵引

以“借助 Omni-Brain 逐步完成质检平台能力建设闭环”为北极星，持续检查知识、流程、方案、实现、验证和能力复用是否贯通。长期目标牵引方向，不等同于当前承诺建设完整质检平台。

### 短期实验

选择一个边界明确的人工质检能力产物，用 Omni-Brain 走完：

```text
理解真实问题 → 组装可信上下文 → 识别能力缺口 → 形成方案
→ 建设知识/流程/代码/工具产物 → 运行验证 → 影响分析与知识回收
```

首个候选是“验收任务分配闭环”，但尚未最终确认。

## 5. 双重验收

领域产物需要证明真实能力可运行、可解释、可验证，并降低对手工查询和脚本人员的依赖。

Omni-Brain 需要证明：

- 能从分散资料和事实源组装最小充分上下文；
- 能区分现状、目标、已实现和待确认；
- 能把方案推进到受控的能力产物及其验证；
- 能准确识别受影响知识并安全回收；
- 同一建设方法可以迁移到下一个能力，而不是一次性项目协助。

## 6. 下一步

1. 确认第一个具体能力产物及明确边界；
2. 建立长期质检能力地图的最小版本，只作为短期任务对齐坐标；
3. 为首个能力定义输入、上下文、产物、运行证据和双重验收表；
4. 完成一次手工闭环后，再决定 Blueprint 是否需要新增“能力建设与验证”组件或扩展方案工作区。
5. 用零背景学习、模糊痛点和明确重构三种入口，验证知识发现与需求明确的汇合方式。
