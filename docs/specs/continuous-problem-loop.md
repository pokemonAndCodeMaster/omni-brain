# 持续问题处理协议

> **状态**：Provisional；从真实日常困扰中验证后再固化。  
> **目的**：让工作中出现的困扰、难题和不友好体验成为可追溯、可判断、可验证的改进输入，而不是散落在会话里的抱怨或被过早写成产品需求。  
> **不替代**：项目总目标和路线以 [`../blueprint.md`](../blueprint.md) 为准；产品判断过程在 [`../product-direction-discussion.md`](../product-direction-discussion.md) 维护。

## 1. 最小闭环

```text
日常困扰
  → 原始语境（经明确同意才保存）
  → 结构化问题
  → 分诊与范围判断
  → 最小行动
  → 验证结果
  → 归档、关联或升级
```

记录的目的不是收集更多问题，而是回答：用户当时要完成什么、哪里受阻、该问题属于哪一层、现有方向能否解决、下一次怎样验证是否改善。

## 2. 处理步骤

### 2.1 捕获与澄清

先提炼下列最少信息；缺失项可以保留为空，不把猜测写成事实：

- 用户目标和具体场景；
- 当前做法、实际阻碍和造成的损失；
- 已尝试的替代方案及其不足；
- 可回到的原始材料、系统、代码或人工决定；
- 是否同意保存原始描述，以及敏感信息的处理范围。

### 2.2 分诊

每个问题先选择一个主层，必要时列出次层：

| 主层 | 典型表现 | 优先检查对象 |
|---|---|---|
| 内容事实 | 结论错误、过期或缺证据 | 来源、状态、规范知识 |
| 关系与粒度 | 内容正确但归属、边界或上下游不清 | 实体关系、Hub、重定向 |
| 阅读视图 | 找到内容却无法理解位置或下一步 | 视图、排序、展开和导航 |
| 检索与上下文 | 搜不到、噪声大、遗漏关键约束 | 索引、路由、过滤、上下文组装 |
| 工作流与治理 | 同类问题反复发生或改动难以控制 | Schema、流程、检查器、审批和评测 |
| 产品范围/假设 | 痛点不能被当前目标解释，或反证现有方向 | Blueprint、讨论稿、真实旅程 |

### 2.3 对照与行动

对照 Blueprint 后，明确归入下列一种行动，不能只给抽象建议：

| 判断 | 最小行动 | 需要的证据 |
|---|---|---|
| 信息不足或低频 | `待观察`，保留简短问题记录 | 后续复现或补充场景 |
| 已有目标覆盖但体验/实现不足 | 建立改进候选及验收条件 | 受影响路径和预期结果 |
| 可重复、可验收的核心任务阻碍 | 建立用户旅程或评测用例 | 输入、预期、失败表现、通过条件 |
| 架构假设的反例 | 写入讨论稿，提出候选调整 | 反例、替代解释、待验证方式 |
| 已验证改变目标、边界或路线 | 更新 Blueprint | 真实任务或评测证据 |
| 不属于当前范围 | `out_of_scope`，记录理由和重访条件 | 范围判断依据 |

涉及多文件知识、Schema 或核心视图的变更仍须遵循 `AGENTS.md` 的 change set 协议。

## 3. 问题记录的最小字段与生命周期

在流程未稳定前，问题记录采用轻量 Markdown，不预设新的 taxonomy 或目录结构。每条进入 `triaged` 的记录至少应有：

- 稳定 ID、标题、创建/最近复查时间和状态；
- 场景、用户目标、阻碍、影响与当前替代方案；
- 主问题层、根因假设及其置信度；
- 相关原始材料、知识、代码、旅程、讨论或 Blueprint 条目链接；
- 行动决定、负责人（若有）、验收方式和结果；
- 去重/替代关系。

状态流转：

```text
captured → clarifying → triaged → experimenting → resolved
                         ├→ out_of_scope
                         ├→ rejected
                         └→ superseded
```

`captured` 可以只有原始场景和日期；只有进入 `triaged` 才要求完整字段。`resolved` 必须附结果证据；`out_of_scope`、`rejected` 和 `superseded` 必须保留理由与替代链接，避免同一问题被反复提出。

## 4. 沉淀与升级边界

- 原始会话或资料：仅经用户明确同意后新增至 `knowledge/raw/`；原料不可修改。
- 具体问题与其处理过程：先作为任务/讨论资产维护；存放位置与 frontmatter 需在首批实例后再确定，避免过早创建新的知识类型。
- 反复且可验证的代表案例：进入 `eval/` 的用户旅程或固定评测用例。
- 稳定事实、经验或规范：按来源、冲突检查和人工门禁进入 `knowledge/`。
- 产品假设、争议和反例：进入产品讨论稿；只有验证后才更新 Blueprint。

不自动把一次问题保存为知识卡、产品视图或 Skill；这些都是升级后的资产，而不是默认输出。

## 5. 升级门槛与维护

满足任一条件，才建议把问题升级为正式旅程或评测：

1. 在不同场景中重复出现；
2. 阻断高价值任务；
3. 影响可信性、可追溯性或安全变更等核心承诺；
4. 为现有架构假设提供了明确反例；
5. 能写出可观察的验收条件。

定期检查相似问题、长期未动的 `captured`/`clarifying` 记录和已解决问题的回归情况。问题数量、重复率、升级率、解决后的复发率和人工维护成本是评估本协议是否有价值的信号；它们不是脱离真实任务的绩效指标。

## 6. 何时创建 Skill

只有在至少处理一批不同类型的真实问题后，且分诊类别、记录字段、升级规则和失败降级方式都稳定，才考虑创建 Skill。届时 Skill 只自动化捕获、结构化、去重提示、关联和候选输出；是否保存原始材料、改变知识/架构、升级 Blueprint 或发布变更，仍保留人工确认。
