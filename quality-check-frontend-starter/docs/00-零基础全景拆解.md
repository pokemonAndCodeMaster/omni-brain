# 00. 零基础全景拆解：这个前端项目到底在做什么

> 适合对象：第一次接触 Vue、Vite、TypeScript、前后端联调的人。
>
> 读法：不要试图第一次就记住所有名词。先读第 1～4 节，能画出全链路；再沿着第 5～10 节打开某一条用户操作；需要改代码时，按第 11 节定位文件。

## 0. 先给结论：它不是一个“完整生产系统”，而是一条可运行的样板链路

这个仓库是“质检一站式平台”的**前端 Starter（起步工程）**。它已经可以运行，并演示两条完整的前端用户路径：

1. 在“人工质检·交付中心”查看交付任务，搜索、筛选、排序、展开、选择、编辑单元格、保存自己的表格视图；
2. 用当前筛选结果生成图表，添加到“业务看板”，拖拽、缩放、复制或删除卡片，刷新浏览器后仍保留。

当前默认数据来自浏览器中的 Mock（模拟数据），不依赖后端。把环境变量切换后，页面会改为请求 FastAPI API。下面这些**还没有在当前代码中完成**：登录和权限、真实数据库、批量执行、审核预览、服务端分页、大数据虚拟列表、公共看板发布、审计日志。这些在 `06-下一阶段开发清单.md` 中是计划，不应误认为已有功能。

## 1. 先把业务说成人话

### 1.1 业务对象是什么

质检平台关注的是“交付任务”：例如“城区路口交互 July-W3”。每个任务有项目、场景、负责人、状态、优先级、目标量、完成量和 Good 比例（合格比例）。有些任务还按日期拆成子任务。

```text
交付任务（父行）
├── 2026-07-17（子行 / 叶子行）
└── 2026-07-18（子行 / 叶子行）
```

这里的“父行”是汇总任务，“叶子行”是没有下级的最细数据。统计分析只使用叶子行，避免父行汇总值和子行明细被重复计算。

### 1.2 两个用户入口和业务闭环

```text
用户
 │
 ├─ 交付中心：找到需要关注的任务
 │    ├─ 搜索 / 筛选
 │    ├─ 看表格、展开日期明细、选择行
 │    ├─ 修改低风险字段（负责人、状态、优先级、目标量）
 │    └─ 从当前结果生成图表
 │                         │
 └─ 业务看板 ◀─────────────┘
      ├─ 查看 KPI、图表、风险表、个人备注
      └─ 编辑布局：拖拽、缩放、复制、删除
```

这就是“业务全链路”：不是代码文件按顺序排列，而是用户完成一个目的时，数据和动作经过的完整路径。

## 2. 先认识整张技术地图

### 2.1 浏览器到数据库的边界

在真实系统里，浏览器不能直接读数据库，也不应该写 SQL。它只通过 HTTP 和后端沟通：

```text
浏览器中的 Vue 页面
  │ 用户点击、输入、查看
  ▼
前端业务 API 函数（features/manual-qc/api）
  │ GET / PATCH，发送 JSON 或查询参数
  ▼
Axios HTTP 客户端（shared/api/http.ts）
  │ 统一 API 基地址、超时、错误出口
  ▼
开发期：Vite 代理 ────────────────┐
生产期：Nginx / API 网关 ──────────┼──► FastAPI Router
                                   │       ▼
                                   │     Application Service（业务服务）
                                   │       ▼
                                   └──► Repository / 数据平台 / 数据库
```

**HTTP** 是浏览器和服务器约定的通信方式，可理解成“请求—响应”快递单：前端写明“我要哪些数据 / 我要改什么”，后端回“成功的数据 / 失败原因”。

**API 契约** 是这张快递单的固定格式，例如“`GET /manual-qc/deliveries` 返回交付任务数组”。契约稳定时，前后端可以分别开发。前端的 `DeliveryRow` 类型应对齐后端 API 返回的数据，不应该照搬数据库所有列。

### 2.2 当前开发时的实际全链路

默认 `.env.development` 中 `VITE_USE_MOCK=true`，因此链路在 API 层提前结束：

```text
DeliveryWorkbenchPage
  → getDeliveries()
  → useMock 为 true
  → mocks/deliveries.ts
  → 返回深拷贝后的模拟任务
  → rows 响应式状态
  → DataWorkbench 显示表格
```

它故意保留 `getDeliveries()` 这一层：页面不知道数据来自 Mock 还是真后端。未来接 API 时，只改 API 层和环境配置，页面不必大改。

### 2.3 前端内部的四层

```text
src/
├── app/       应用壳层：启动后所有业务共用的导航、路由和页面框架
├── features/  业务层：人工质检这块业务特有的数据、规则和页面
├── shared/    共享能力：表格、图表、看板、HTTP、本地保存等可复用积木
└── styles/    全局视觉底座：颜色、间距、按钮、页面壳样式
```

可以把它想成商场：`app` 是楼和导览；`features` 是一家具体店铺；`shared` 是全商场共用的电梯、收银系统；`styles` 是统一装修规范。

依赖应自上而下：

```text
app 页面 / feature 页面
          ↓ 可以使用
shared 共享组件、共享工具、共享类型
          ↓ 可以使用
浏览器能力、第三方库
```

反过来让 `shared` 引用 `features/manual-qc` 会造成“公共电梯认识某一家店”的耦合。当前 `AnalysisBuilder` 为了演示方便，暂时引用了 `DeliveryRow`，这是一个已知例外；未来应通过通用数据源/字段/指标定义解除它。

## 3. 三个最容易混淆的基础概念

### 3.1 Vue：负责把“数据变化”同步成页面变化

Vue 是浏览器中运行的 UI（用户界面）框架。你不必手动找 DOM、逐个改文字；而是声明“页面应长什么样”，把数据绑定进去。

```vue
<script setup lang="ts">
import { ref } from 'vue'

const count = ref(0)
</script>

<template>
  <button @click="count++">已点击 {{ count }} 次</button>
</template>
```

`ref(0)` 是 Vue 的“可观察盒子”。点击后 `count` 改变，Vue 自动更新 `{{ count }}` 对应的 DOM。当前项目使用 Vue 3 的 Composition API 和 `<script setup lang="ts">`：

- `<script setup>`：组件的 TypeScript 逻辑区；在这里定义数据、函数、导入组件；
- `<template>`：HTML 模板区；描述页面；
- `<style scoped>`：这个组件自己的样式；`scoped` 表示不会随意污染其他组件；
- `computed(...)`：由现有状态推导出的只读结果，例如 `filteredRows`；
- `watch(...)`：状态变化后做副作用，例如把配置写入 `localStorage`；
- `onMounted(...)`：组件第一次进入页面、DOM 已创建后运行；
- `onBeforeUnmount(...)`：组件离开页面前清理资源。

### 3.2 组件：可以嵌套和复用的 UI 积木

`.vue` 文件一般就是一个组件。页面本身也是组件，只是它负责把其他组件拼起来。

```text
App
└─ AppShell（导航和页面框架）
   └─ RouterView（当前路由匹配的页面插槽）
      ├─ DashboardPage
      │  └─ DashboardGrid → CardShell → BaseEChart
      └─ DeliveryWorkbenchPage
         ├─ DataWorkbench → BaseCheckbox
         └─ AnalysisBuilder → BaseEChart
```

父组件通过 **props（属性）向下传数据**，子组件通过 **emit（事件）向上传递用户动作**。例如：

```text
DeliveryWorkbenchPage
  -- rows / columns / editors（props，向下） --> DataWorkbench
  <-- cellEdit(payload)（emit，向上） ------- DataWorkbench
```

表格不知道如何请求“交付任务 API”，页面也不应知道 TanStack Table 如何计算排序；这就是组件边界。

### 3.3 Vite：开发和打包的“工程调度器”

**Vite 不是页面框架，也不是线上服务器。** Vue 负责 UI；Vite 负责把开发所需的工具串起来。

它处在这里：

```text
你编辑 .vue / .ts / .css 文件
       │
       ▼
Vite 开发服务器（npm run dev）
  ├─ 读取 index.html 作为入口
  ├─ 看到 /src/main.ts，按需转换 TypeScript、Vue 单文件组件
  ├─ 在浏览器中提供模块
  ├─ 文件改动后热更新（HMR）
  └─ 开发期可把 /api 请求代理到 FastAPI
       │
       ▼
浏览器 http://localhost:5173

准备上线时：npm run build
       │
       ▼
Vite 构建器把源码、依赖打包/压缩为 dist/ 中的静态 HTML、JS、CSS
       │
       ▼
Nginx / CDN 把 dist/ 文件发给访问者
```

**为什么不能双击 `index.html`？** 开发时它引用的是 `/src/main.ts`，浏览器本身不会理解 TypeScript、Vue 单文件组件和 `@/` 别名；Vite 正是负责这些转换和模块解析的程序。

本项目的 Vite 配置在 `vite.config.ts`：

- `vue()`：让 Vite 能理解 `.vue`；
- `@` 别名：`@/x` 等价于 `src/x`，避免长长的相对路径 `../../../x`；
- `server.port: 5173`：开发端口；`strictPort` 表示被占用时不偷偷换端口；
- `server.proxy`：只有设置 `VITE_API_PROXY_TARGET` 时，开发服务器将 `/api` 转发给后端；
- `preview.port: 4173`：`npm run preview` 验收生产构建时使用的端口。

## 4. 从“打开网页”开始，逐层跟一次启动过程

```text
浏览器请求 /
  ↓
index.html：只有 <div id="app"> 和 <script src="/src/main.ts">
  ↓
src/main.ts
  ├─ createApp(App)：创建 Vue 应用
  ├─ use(createPinia())：安装全局状态仓库能力
  ├─ use(router)：安装路由能力
  ├─ 引入全局 CSS、GridStack CSS
  └─ mount('#app')：把 Vue 渲染进 index.html 的 #app
  ↓
App.vue：只渲染 <AppShell />，不塞业务代码
  ↓
AppShell.vue：固定侧栏、顶部标题、<RouterView />
  ↓
RouterView：根据当前 URL 决定显示哪一个页面
```

### 4.1 路由是什么

URL 与页面组件的映射叫**路由**。表在 `src/app/router/index.ts`：

| URL | 页面组件 | 作用 |
| --- | --- | --- |
| `/` | 重定向 | 自动跳转到看板 |
| `/dashboard` | `DashboardPage.vue` | 看板 |
| `/manual-qc/deliveries` | `DeliveryWorkbenchPage.vue` | 交付中心 |

路由用 `component: () => import(...)`，这是**按路由懒加载**：第一次访问看板时不必下载交付中心代码，反之亦然。路由的 `meta.title` 会被 `AppShell` 显示在顶部，也会由 `afterEach` 写进浏览器标签标题。

### 4.2 Pinia 是什么

Pinia 是 Vue 的**全局状态管理库**。普通 `ref` 属于一个组件，组件销毁时它也会消失；Pinia Store 是应用中可被不同页面共同访问的一块状态和操作集合。

当前唯一 Store 在 `shared/dashboard/stores/dashboard.ts`：`useDashboardStore()`。它管理所有看板卡片。交付中心调用 `dashboard.addChartCard(chart)`，看板页读取 `dashboard.cards`，所以跨页面传图表不需要手写全局变量。

## 5. 交付中心：每个文件、每层数据、每个算法

### 5.1 文件地图

```text
features/manual-qc/
├─ types/delivery.ts              交付记录“长什么样”的 TypeScript 契约
├─ mocks/deliveries.ts            6 个顶层 Mock 任务及部分日期子任务
├─ api/deliveries.ts              对页面隐藏 Mock / HTTP 差异的 API 门面
└─ pages/DeliveryWorkbenchPage.vue 业务装配页面
```

`DeliveryRow` 是一条交付记录的类型定义。它不生成 JavaScript；它是 TypeScript 在开发和构建时的“检查清单”：如 `status` 只能是“待对齐、生产中、…、已完成”中的一个，`targetCount` 必须是数字。

### 5.2 加载数据：Mock 与真实 API 的分支

`api/deliveries.ts` 是“数据来源切换器”。

```text
getDeliveries()
  ├─ VITE_USE_MOCK !== 'false'
  │    └─ 等待 250ms 后返回 structuredClone(mockDeliveries)
  └─ 否则
       └─ axios.get('/manual-qc/deliveries')
            └─ http.ts 会补上 baseURL（默认 /api/v1）
```

`structuredClone` 是深拷贝：每次返回一份全新的对象树。若直接返回原始 Mock，用户编辑数据会意外改到模块中的“模板数据”，后续读取可能被污染。

真实 API 时，请求全地址通常是：

```text
浏览器请求：/api/v1/manual-qc/deliveries
Vite 代理目标：http://127.0.0.1:8000/api/v1/manual-qc/deliveries（仅开发期）
```

`shared/api/http.ts` 创建一个 Axios 实例并统一设置 20 秒超时。Axios 可以理解为浏览器 `fetch` 的常用封装；这里还统一记录 HTTP 错误。若以后需要登录 Token、401 自动跳登录、统一错误提示，优先加在这里，而不是散落在每个页面。

### 5.3 页面为什么叫“业务装配层”

`DeliveryWorkbenchPage.vue` 不自己实现表格引擎。它完成五件与人工质检有关的事：

1. 保存源数据 `rows`、筛选条件 `query`、加载/错误/提示等页面状态；
2. 声明表格有哪些业务列、每列如何显示；
3. 声明哪些列可编辑、用输入框还是下拉框；
4. 拉取、筛选、更新交付数据，保存/加载个人视图；
5. 把数据和规则传给共享表格，接收事件；把图表交给全局看板 Store。

它使用的 `columnHelper.accessor(...)` 来自 TanStack Table。每个 accessor 告诉表格“从每行哪个字段取值”。`progress` 列不是原始字段，而是函数计算：`completedCount / targetCount`，这就是**派生列**。

### 5.4 搜索和树形筛选算法

用户输入的 `query` 是最少的源状态。`filteredRows` 是 `computed` 推导结果，不另存一份，避免“改了筛选框却忘记同步数据”的 bug。

```text
rows（完整树） + query（关键词、项目、状态）
                   ↓
               filterTree
                   ↓
filteredRows（仍保留父子结构的命中树）
```

`rowMatches(row)` 先把任务名、项目、场景、负责人、状态拼成字符串，判断关键词是否包含；再判断项目和状态是否相等。

`filterTree(source)` 是**递归**：函数处理一行时，先用同一个函数处理它的 children。它保留三种情况：

```text
父行自己命中        → 保留父行及其完整子树
父行未命中、子行命中 → 保留父行，但只放命中的子行（保留上下文）
两者都不命中        → 丢弃该分支
```

这比简单 `array.filter` 更适合树表格，因为“某个 7 月 18 日子行命中”时，用户仍需要看到它属于哪个任务。

`flattenLeaves(filteredRows)` 同样递归：有 children 就继续深入；没有 children 就收集自己。得到的 `analysisRows` 是统计分析的输入。

### 5.5 编辑一个单元格到底发生了什么

```text
用户改下拉框/数字输入框
  ↓
DataWorkbench.editCell()
  ↓ emit cellEdit({ row, columnId, value })
DeliveryWorkbenchPage.handleCellEdit()
  ↓
updateDeliveryCell({ id, field, value })
  ├─ Mock：模拟延迟后成功
  └─ 真 API：PATCH /manual-qc/deliveries/{id}
  ↓
updateTree(rows, id, field, value) 生成新的树
  ↓
rows 被替换，Vue 更新表格
```

`updateTree` 不直接改旧对象，而是递归 `map` 出一棵新树。这种**不可变更新**使更新路径清楚、响应式更可预测：只有被编辑那条记录的字段和沿途父数组被换成新对象。

注意当前是“请求成功后才更新界面”，叫**保守更新**。下一阶段常见的“先让界面更新，失败后回滚”叫**乐观更新**，体验更快但实现要保存旧值、处理并发版本和失败提示，因此此样板暂未使用。

### 5.6 个人视图是什么，为什么要导出/应用状态

个人视图不是一份任务数据，而是“我怎么看这张表”的配方：

```text
搜索条件 + 项目/状态筛选
+ 排序规则 + 展开状态 + 列隐藏状态 + 列顺序 + 列宽
= SavedWorkbenchView
```

`DataWorkbench` 用 `defineExpose` 只向父页面开放三项受控能力：

- `exportState()`：读出表格的布局/交互状态；
- `applyState(state)`：恢复它；
- `selectedRows()`：取得当前选择的原始行。

父页面借组件 ref 调这两个“命令”，因为这是跨越普通 props/emit 的少数合理场景：保存和恢复的是子组件内部状态。`useWorkbenchViews()` 是一个**composable（组合式函数）**，它把读取、保存、删除视图的状态和逻辑封装起来；任何其他表格也能调用它。

## 6. 统一数据工作台：通用表格引擎如何工作

### 6.1 为什么要有它

`shared/data-workbench/components/DataWorkbench.vue` 是不认识“人工质检”具体业务的通用组件。它只要求每行有：

```ts
{ id: string, children?: TData[] }
```

`generic="TData extends ..."` 表示它是**泛型组件**：今天可以接 `DeliveryRow`，以后也可以接“模型验收记录”，只要满足 id/children 约定。业务页面传入 `rows`、`columns`、`editors`；它负责交互机制。

### 6.2 TanStack Table 在其中的位置

TanStack Table 不是替你画出 `<table>` 的黑盒组件，而是**无头表格（headless table）状态/计算引擎**：它计算行、列、排序、展开、选择的结果；本项目自己写模板决定视觉样式。这种分工让交互逻辑可复用，页面外观也完全可控。

```text
业务页面提供：数据、列定义、编辑规则
                         ↓
TanStack Table：把状态 + 数据计算成 row model
                         ↓
DataWorkbench template：循环 row model，渲染 HTML table
                         ↓
BaseCheckbox：显示普通/选中/半选复选框
```

### 6.3 表格的六份状态

组件中每份 `ref` 都是用户可改变的状态：

| 状态 | 含义 | 谁修改它 |
| --- | --- | --- |
| `sorting` | 按哪列升/降序 | 点击表头 |
| `expanded` | 哪些父行已展开 | 点击 + / − |
| `rowSelection` | 哪些行已勾选 | 复选框 |
| `columnVisibility` | 哪些业务列隐藏 | 列配置 |
| `columnOrder` | 业务列显示顺序 | 列配置左右移动 |
| `columnSizing` | 每列宽度 | 拖动列边界 |

`useVueTable()` 接收这些状态和对应的 `onXxxChange` 回调。第三方库既可能给“完整新状态”，也可能给“根据旧值算新值的函数”；`functionalUpdate(updater, oldValue)` 统一兼容两种写法，这就是 `updateRef` 的作用。

它依次启用三个 row model：

```text
原始 data
  → getCoreRowModel：把原始对象变成表格行对象
  → getSortedRowModel：按 sorting 排序
  → getExpandedRowModel：按 expanded 显示树的可见行
```

### 6.4 特殊列与普通列

组件在业务列前固定加了两列：

```text
__select：全选/行选择，宽 44px
__expand：父子展开，宽 48px
...props.columns：业务页面声明的任务名、项目、负责人等
```

双下划线只是内部约定，列配置时会过滤掉它们，防止用户把“选择”和“层级”列移乱。恢复个人视图时也会再次把两列放回最前面。

### 6.5 半选为什么需要 `BaseCheckbox`

父行的子行只选中一部分时，复选框不是“勾/不勾”两种，而是第三种**indeterminate（半选）**状态。这个状态不是 HTML 属性，而是 DOM 节点的 `input.indeterminate` 属性，所以 `BaseCheckbox`：

1. 收 `modelValue`、`indeterminate`、`disabled`、`label` 四个 props；
2. 挂载后和 `indeterminate` 改变时，把 DOM 属性同步过去；
3. 用户点击时 emit `update:modelValue` 给父组件。

它因此既可用于表头全选，也可用于每行选择和列显隐。

### 6.6 三条滚动条同步的实现

宽表格在顶部和底部都放横向滚动条，方便用户不必滚到表尾。三个 DOM ref 指向顶部、表体、底部的滚动容器：

```text
topScroll  ─┐
bodyScroll ─┼─ 任一滚动时读取 scrollLeft，写到另外两个
bottomScroll┘
```

`scrollLock` 防止“程序写入另一个滚动条 → 又触发 scroll → 无限互相同步”。`requestAnimationFrame` 在下一帧解锁。`ResizeObserver` 监听 table 宽度，重新测量 `scrollWidth`，让镜像滚动条的内部占位宽度始终等于表格真实宽度；组件卸载时断开 observer，避免内存泄漏。

## 7. 从筛选结果到图表：分析构建器

### 7.1 输入、输出与组件边界

`AnalysisBuilder.vue` 是右侧抽屉。输入是：

```text
props.rows：已筛选、已压平的叶子 DeliveryRow 数组
props.filtersSummary：给人看的筛选摘要
```

输出是事件：

```text
close：关闭抽屉
addToDashboard(chart)：交给父页面一份 ChartSpec
```

`ChartSpec` 是“可保存的一张图”的数据合同：标题、维度、指标、图形类型、聚合结果、筛选说明、创建时间。图表预览和看板卡片都能据此重建图。

### 7.2 分组聚合算法

选择“维度=项目、指标=完成数量合计”后，核心算法是：

```text
rows
  → 以 row.project 为 key 放入 Map<string, DeliveryRow[]>
  → 每个项目一桶 rows
  → 每桶 reduce 求完成量之和
  → 转成 [{ name: '城区', value: 2520 }, ...]
  → 由大到小排序
```

`Map` 可以看成“键 → 一组记录”的字典。`reduce` 是“从零开始逐条累加”的数组算法。四个指标的当前口径：

| 指标 | 当前浏览器算法 |
| --- | --- |
| `count` | 每桶行数 |
| `targetCount` | `targetCount` 求和 |
| `completedCount` | `completedCount` 求和 |
| `goodRate` | 排除 0 后，对每行 `goodRate` 做简单平均 |

最后一条很重要：简单平均只适合演示。若两行样本量不同，正确总通过率通常是 `所有 Good 数量之和 / 所有样本数量之和`，称为 **ratio of sums（分子分母分别求和再相除）**。本项目尚无 Good 数量字段和服务端指标注册表，所以文档的下一阶段明确要求把这一指标口径交给后端。

### 7.3 ECharts 怎样接入 Vue

`BaseEChart.vue` 是对 ECharts 生命周期的薄封装：

```text
父组件计算 chartOption（纯配置对象）
       ↓ prop
BaseEChart
  ├─ mounted：init(host) 创建图表实例，setOption(option)
  ├─ option 改变：再次 setOption
  ├─ 容器尺寸改变：ResizeObserver → chart.resize()
  └─ 卸载：dispose() 释放 Canvas / 事件资源
```

这里用 `echarts/core` 再 `use([BarChart, PieChart, ...])` 按需注册条形图、饼图及必要组件，而不是把整个 ECharts 功能都打进包。`chartOption` 则是 ECharts 认得的配置语言：x/y 轴、tooltip、series（数据系列）等。

## 8. 看板：全局状态、拖拽网格和不同卡片

### 8.1 一份卡片数据如何流动

```text
AnalysisBuilder.addToDashboard()
  → emit ChartSpec
  → DeliveryWorkbenchPage.addChart()
  → dashboard.addChartCard(chart)
  → Pinia cards 数组新增 DashboardCard
  → watch(cards, deep) 写入 localStorage
  → DashboardPage 读取同一 Store 的 cards
  → DashboardGrid 渲染卡片
```

`DashboardCard` 有统一外壳字段（`id/title/type/layout`），并根据 `type` 带不同内容：

- `kpi`：大数字、标签和辅助文字；
- `chart`：一个 `ChartSpec`；
- `text`：个人备注；
- `table`：小型风险表。

`system: true` 表示系统默认卡片。当前规则是不能删除它，但可以复制，副本自动变为个人卡片。

### 8.2 localStorage 是什么，保存了什么

`localStorage` 是浏览器为一个网站提供的小型键值存储，数据保留在用户的当前浏览器和当前域名中；它不是服务器数据库，也不会自动同步到同事电脑。

`shared/persistence/storage.ts` 不直接存数组，而包一层：

```json
{
  "schemaVersion": 1,
  "savedAt": "2026-...",
  "data": "真正的视图或卡片数组"
}
```

当未来数据结构变化，把 `schemaVersion` 升级后可选择迁移旧数据或安全回退，而不是盲目解析导致页面崩溃。当前 Key：

```text
quality-check.dashboard.cards
quality-check.delivery-workbench.views
```

在 Chrome/Edge 按 F12 → Application → Local Storage 可以查看或删除它们。删除只清浏览器个人配置，不会删除任何后端任务。

### 8.3 GridStack 在什么位置

GridStack 是“可拖拽、可缩放网格布局”第三方库。Vue 管理卡片数据和 DOM 渲染，GridStack 管理元素在 12 列网格中的位置；`DashboardGrid.vue` 是两者的适配层。

```text
DashboardCard.layout = { x, y, w, h }
  │ x/y 是左上角格子，w/h 是宽高格数
  ▼
模板写入 gs-x / gs-y / gs-w / gs-h 属性
  ▼
GridStack 让元素拖动/缩放
  ▼
change 事件给出 GridStackNode[]
  ▼
emit layoutChange([{ id, layout }])
  ▼
Store.updateLayouts() 回写 cards，再保存 localStorage
```

`makeNewWidgets()` 在 Vue 因新增卡片而更新 DOM 后（`nextTick`）把新增元素注册给 GridStack。`onBeforeUnmount` 调 `grid.destroy(false)`，避免离开页面后库继续持有 DOM。

`CardShell.vue` 是每张卡片的统一视觉外壳：标题、描述、编辑时的复制/删除按钮、内容区和图表筛选脚注。它根据 `card.type` 决定显示 KPI、`BaseEChart`、文本还是小表格。

## 9. 样式、类型、配置和依赖：它们不直接显示业务，但缺一不可

### 9.1 CSS 两层

| 文件 | 责任 | 修改时机 |
| --- | --- | --- |
| `styles/tokens.css` | CSS 变量：颜色、圆角、阴影、侧栏宽度、字体 | 改主题/全局视觉标准 |
| `styles/base.css` | 重置、页面壳、按钮、面板、响应式规则 | 改全局通用样式 |
| 每个 `.vue` 的 `<style scoped>` | 该组件局部布局 | 改单个页面/组件 |

例如 `--color-primary` 是设计 Token（设计变量）。改它会让所有使用 `var(--color-primary)` 的按钮、品牌标记一起更新；这是比逐文件搜索蓝色十六进制值更可靠的方式。

### 9.2 TypeScript 配置在保护什么

`tsconfig.app.json` 中：

- `strict: true`：更严格地检查可能为空、类型不匹配等问题；
- `noUncheckedIndexedAccess: true`：数组按下标取值也可能是 `undefined`，强迫处理边界；
- `noUnusedLocals / noUnusedParameters`：禁止积累没用的变量/参数；
- `paths`：使 TypeScript 也认识 `@/` 别名。

`env.d.ts` 是环境变量的类型声明；它告诉 TypeScript `import.meta.env.VITE_USE_MOCK` 等名字存在。**只有 `VITE_` 前缀的变量会被 Vite 暴露到浏览器，所以绝不能把密码、私钥放进去。**

### 9.3 `package.json` 是依赖和命令清单

| 依赖 | 在项目中的定位 |
| --- | --- |
| `vue` | UI 渲染和响应式 |
| `vue-router` | URL → 页面组件 |
| `pinia` | 跨页面看板状态 |
| `axios` | HTTP 请求封装 |
| `@tanstack/vue-table` | 无头表格状态/计算引擎 |
| `echarts` | 图表渲染 |
| `gridstack` | 看板拖拽/缩放网格 |
| `@tanstack/vue-virtual` | 已安装，未来大列表虚拟滚动使用；当前未接入 |
| `vite`、`@vitejs/plugin-vue` | 开发服务器与构建 |
| `typescript`、`vue-tsc` | 类型检查 |

`dependencies` 是浏览器运行产物需要的库；`devDependencies` 是开发/构建时需要的工具。`npm install` 按 `package-lock.json` 安装确定版本；`npm run build` 实际执行 `npm run type-check && vite build`。

## 10. 从源码到上线：构建、Nginx、Docker

### 10.1 开发、构建、预览三件不同的事

```text
npm run dev
  → Vite 开发服务器，源码按需转换，支持热更新，端口 5173

npm run type-check
  → vue-tsc 检查 .ts 和 .vue 中的类型；不生成上线文件

npm run build
  → 先 type-check，成功后 Vite 生成 dist/ 静态文件

npm run preview
  → 本地静态服务器预览 dist/，端口 4173；不等于完整生产环境
```

### 10.2 为什么线上需要 Nginx 的 `try_files`

项目使用 HTML5 History 路由。首次访问 `/manual-qc/deliveries` 时服务器看到的不是一个真实的 `manual-qc/deliveries` 文件夹；它必须回 `index.html`，由浏览器中的 Vue Router 再决定显示交付页。

```nginx
try_files $uri $uri/ /index.html;
```

这就是 `nginx.conf` 的关键行。没有它，直接刷新非首页常会得到 404。Nginx 还给带 hash 的静态资源设置 7 天缓存；构建时内容变化会产生新文件名，旧缓存不会误用。

### 10.3 Dockerfile 的两阶段构建

```text
阶段 1：node:24.11-alpine
  ├─ npm ci 安装锁定依赖
  └─ npm run build 生成 /app/dist

阶段 2：nginx:stable-alpine
  ├─ 只复制 nginx.conf
  └─ 只复制 dist 到 Nginx 静态目录
```

最终镜像不包含 Node 源码、`node_modules` 和构建工具，所以体积更小、攻击面更小。注意 Vite 的 `VITE_*` 环境变量是在 **build 时**写入 JS 的；Docker 运行 Nginx 后再改环境变量，不会让已生成的前端包自动变更。

| 你的目标 | 首先阅读/修改 | 还会影响 |
| --- | --- | --- |
| 改品牌色、圆角、侧栏宽度 | `styles/tokens.css` | 全局页面 |
| 改导航项或顶部结构 | `app/components/AppShell.vue` | `router/index.ts` |
| 新增一个页面 URL | `app/router/index.ts`，再新建页面组件 | `AppShell.vue` 导航 |
| 新增交付字段/表格列 | `types/delivery.ts`、后端契约、`DeliveryWorkbenchPage.vue` 的 `columns` | Mock/API、编辑规则、统计定义 |
| 让一个字段可编辑 | 页面中的 `editors`，再确认 `DeliveryUpdate` 和 API 支持 | `handleCellEdit` |
| 改搜索/筛选业务规则 | `DeliveryWorkbenchPage.vue` 的 `rowMatches/filterTree` | 大数据时应迁到后端 API |
| 改通用表格交互 | `DataWorkbench.vue` | 所有复用此组件的未来业务 |
| 改图表维度/指标 | `analysis/types/chart.ts` 与 `AnalysisBuilder.vue` | 正式环境还要改后端指标口径 |
| 改看板卡片类型/默认卡片 | `dashboard/types/dashboard.ts`、`stores/dashboard.ts`、`CardShell.vue` | Grid 布局与存储版本 |
| 接真实后端 | `.env.development`、`features/*/api`、`shared/api/http.ts` | 后端 API 契约 |
| 改开发端口、代理、别名 | `vite.config.ts` | 重启 `npm run dev` |

一个安全的新增业务模块模板：

```text
src/features/llm-qc/
├─ types/       本业务 API/页面数据类型
├─ api/         本业务的 HTTP 门面
├─ pages/       路由页面（装配层）
├─ components/  只属于本业务的 UI（需要时再建）
└─ composables/ 本业务可复用逻辑（需要时再建）
```

页面可以使用 `shared`，但 `shared` 不应导入这个新业务。若一个能力只服务于 LLM 质检，就先放在 feature 内；至少两个业务都会用且规则一致时，再抽到 `shared`。

## 12. 新手最常问的“为什么”和排查顺序

### “我改了代码，为什么页面没有变？”

先看终端的 Vite 是否还在运行；看浏览器是否打开 `http://localhost:5173`；检查 Console 是否有红色错误。普通 `.vue/.css` 改动应热更新。改 `.env.development` 或 `vite.config.ts` 必须停止并重新运行 `npm run dev`。

### “我把 `VITE_USE_MOCK=false` 了，为什么数据加载失败？”

检查顺序：

1. FastAPI 是否在运行、地址是否确为 `VITE_API_PROXY_TARGET`；
2. 浏览器 Network 中请求 URL 是否为 `/api/v1/manual-qc/deliveries`；
3. Vite 终端是否显示代理错误；
4. 后端状态码和响应 JSON 是否符合 `DeliveryRow[]`；
5. 改完环境变量后是否重启 Vite。

### “为什么不能把 API 调用写进 DataWorkbench？”

因为通用表格应能显示交付任务、模型列表、审核记录等不同数据。若它写死 `/manual-qc/deliveries`，就只能服务人工质检，失去共享价值；而且每个业务的权限、字段、编辑规则、错误提示都不同。

### “为什么保存的看板别的电脑看不到？”

当前存的是本机浏览器 `localStorage`，不经过服务器。要跨设备/团队共享，需要实现文档 04 中的 view-config/dashboard API、用户身份、权限和发布流程。

### “为什么文档说可扩展，不是已经都实现了吗？”

“可扩展”表示目录边界和数据流为后续功能留出了位置；它不是已完成的同义词。判断当前是否支持某功能，优先看对应源码、路由、API 调用和 `package.json` 脚本；`06-下一阶段开发清单.md` 是待办列表。

1. `README.md`：启动项目，在浏览器把两条用户路径亲自点一遍；
