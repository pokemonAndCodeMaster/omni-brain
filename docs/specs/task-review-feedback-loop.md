# 本地 AI 工作审查与反馈闭环

> **状态：** Verified@DeepSeek software-review positive/mismatch/no-trigger slice；v0.1 与 v0.2 作为失败参考保留，v0.3 已经用户多轮审视并成为认证参考，最薄 `review-work` 运行链完成三类弱模型验证。
> **目标：** 把 AI 完成的一项工作组织成类似 MR 的本地审查对象，让人先理解原始请求和实际变化，再审查需求理解、设计、实现、过程与证据，并把反馈用于修正结果和演进 Harness。
> **负向原型：** [人工质检验收分配缺口详情审查单](../../eval/reference/real_work/manual_qc_allocation_gap_detail_v1/review.md)。
> **正向样板候选：** [验收未完成量开发工作审查单](../../eval/reference/real_work/manual_qc_pending_visibility_composite_v1/review.md)。

## 1. 核心产品形态

本能力不是“任务结束后生成一份漂亮总结”，而是一个可持续更新的**本地工作审查单**：

```text
用户提出任务
  ↓
Agent 保留用户原话并用符合阅读直觉的顺序讲清主要问题、期望效果和任务范围
  ↓
按任务风险决定直接执行、简短设计或先审方案
  ↓
执行过程中持续留下版本、动作、变更与证据
  ↓
形成一张可本地阅读和填写的 review.md
  ↓
人按具体审查点评论、要求修改或批准
  ↓
Agent 修正同一项工作并更新审查单
  ↓
经确认的结果、知识、偏好和失败分别进入长期资产
```

它借鉴 MR 的认知模型，但首阶段不接 GitHub、GitLab 或其他平台：

- `review.md` 是本地主要审查入口；
- Git Diff、源码、截图和运行记录通过链接下钻；
- 内容稳定后可以直接复制到 MR 描述；
- 原始请求、源码和运行结果仍是事实源，审查单不复制成新的实现真相。

## 2. v0.1 暴露的根本问题

首版失败不是几个标题不够好，而是从评测者视角组织内容：

1. 还没展示完整任务和变化，就先让用户判断“报告能证明什么”；
2. 用 Agent 的问题分析替代了用户原始请求；
3. 把事实、Agent 推断和待审结论混写；
4. 没解释业务概念，就要求用户判断算法是否正确；
5. 大量“是否合理、是否完整”的问题没有说明审查目的和反馈后果；
6. 产品成果审查与 Agent 工作过程审查混在一起，用户尚未理解结果就被迫审 Trace。

v0.2 虽补齐了用户原话、概念、代码和证据，仍然失败：

```text
把后来构造的实验题误当成原始需求切片
→ 没有先讲清完整工作故事
→ 需求、外显变化、方案和实现顺序倒置
→ 用“用户想要什么 / Agent 认为要什么”割裂需求理解
→ 用决策表替代方案本身
→ 默认要求用户继续审空洞的 Agent 过程
```

v0.3 改为两层结构：先用一页内可读的全貌说明建立上下文，再从需求开始按阶段审查。全貌让人知道整件事发生了什么，但不绕过逐阶段批准；任一前序阶段被驳回，后续内容保留为已有事实或实验资产，不再要求用户继续审查。

## 3. 运行时怎样保证它会启动

共享设计文档本身不能触发能力。稳定版本必须形成以下运行链：

```text
AGENTS.md
  └─ 判断任务是否明确要求审查，或复杂成果是否需要人工验收

review-work Skill
  └─ 初始化、维护、交付审查单，接收和分流人工反馈

具体任务 Skill
  └─ 提供开发、知识摄入、方案或 Harness 修改的专属审查内容

直接事实源
  └─ 原始请求、Git Diff、源码与已有运行证据；当前不复制为新的中间账本
```

### 3.1 `AGENTS.md` 只保留触发规则

- 简单问答、状态查看和显而易见的局部低风险操作，不创建持久审查单；
- 用户明确要求审查、评审、复盘或生成类似 MR 的本地说明时，启动审查；
- 跨文件、跨层、公共契约、长期设计或 Harness 变化需要人决定是否接受时，启动审查；
- 原始需求仍模糊时回到任务准备或方案形成路径，审查能力只能显示“方案尚未批准”，不能替代方案形成；
- 未经人审的候选不能写成“已批准”。

详细字段、示例和任务专属内容不得复制到 `AGENTS.md`。

### 3.2 `review-work` 是共享生命周期 Skill

它需要由开发、摄入和任务准备等 Skill 共同到达，因此稳定后应作为模型可调用的共享 Skill。它负责：

1. 判断是否需要审查并确定唯一的本地审查入口；
2. 先用原始请求、实际任务、产物摘要和批准状态组成任务身份包；
3. 在访问产品、Diff 和源码前核对任务对象；错位时直接停止，对齐后才取得下游事实；
4. 对齐时先形成完整工作全貌，再按需求、方案、实现、演示与验证组织审查；
5. 接收人的评论、修改要求和批准，并持续更新同一张审查单；
6. 分开工作本身的决定与报告体验反馈，保留人的原意并提出资产分流建议。

共同信息结构和填写规则放在 Skill 的按需参考文件中；任务专属内容由对应任务 Skill 维护，避免一个巨型 Skill。

### 3.3 确定性工具不是首版前提

首版由模型直接读取原始任务、Git Diff、源码和已有运行证据，不新增 YAML 工作区、证据副本或报告生成脚本。只有弱模型重放证明以下机械步骤反复昂贵或易错时，才考虑最小工具：

- 固定完整用户请求、项目、模型、Harness、基线和候选版本；
- 记录文件变化、Git Diff、命令、退出结果和证据路径；
- 生成审查单骨架与本地链接；
- 检查标准或深度任务是否真的存在审查单；
- 保存人的反馈原文和审查状态。

工具即使后续出现，也不能判断用户意图、业务语义、架构品味或反馈是否应升级为全局规则。

### 3.4 当前实现状态

现在已有 v0.2 任务错位负例、v0.3 认证正向参考、隐藏事实参考和固定多维评价。实验 Harness 已实现 `AGENTS.md → review-work → develop-with-knowledge` 的最薄运行链；只包含共享 Skill、软件开发按需参考和唯一 `review.md`，没有新增脚本或 YAML 工作台。

OpenCode DeepSeek 三类结果为：正向候选对照认证参考独立评分 `17/18`；错位候选只读取任务身份包即阻断，没有访问产品实现；简单状态问题没有生成审查单。当前可标为软件开发本地审查切片内 verified。该结论不能外推到知识摄入、方案或 Harness 修改的专属审查，也不表示审查单可以替代尚未形成的需求和方案。

### 3.5 本地文件与归档

普通任务的默认入口暂定为：

```text
workspaces/reviews/<task-id>/review.md
```

一个任务默认只维护这一张用户可见文件。原始命令记录、Git Diff、源码、截图和运行日志留在宿主或原有事实位置，通过链接下钻，不复制成一组 YAML 和报告附件。

- 任务仍在修改时，持续更新同一张审查单；
- 用户要求修改时，保留反馈原话和修订摘要，不另建 `review-v2-final-final.md`；
- 普通任务完成后可以按项目保留策略清理或归档；
- 被提升为评测用例时，将冻结版审查单连同 Prompt、轨迹、结果和证据封存到对应 `eval/trials/<trial-id>/`；
- 认证参考的最终审查单可以进入对应 `eval/reference/<use-case>/`；
- 正式产品和知识仓不因为审查能力增加一套事实副本。

## 4. 轻量、标准和深度审查

| 深度 | 适用任务 | 形成时间 | 主要内容 |
|---|---|---|---|
| 轻量 | 目标明确、局部、低风险、容易回滚，但产生长期变更 | 完成时 | 工作概览、原始请求、修改内容、演示与验证、遗留问题 |
| 标准 | 跨文件或跨层，主要业务语义和现有模式明确 | 实质修改前初始化，完成后补齐 | 工作概览、需求主线、简短方案、修改与实现、演示与验证 |
| 深度 | 业务语义模糊、跨域、公共契约、长期架构或难回滚 | 实施前先审需求和方案，批准后继续同一审查单 | 完整需求、系统上下文、总体与模块方案、人工决定、实现、验证和演进；过程审计按需出现 |

任务执行中可以升降级。来源冲突、影响扩大、公共契约变化、连续失败或无法解释依据时升级；关键未知解决、范围收敛后不继续制造重流程。

## 5. 本地审查单的信息结构

### 5.1 第一层：完整工作全貌

报告开头先用最短路径讲清整件工作的来龙去脉，使第一次接触任务的人知道后文在审什么：

```text
业务与系统背景
→ 当前问题和原始需求
→ 问题、期望效果、功能和完成标准
→ 采用的总体方案和系统上下文
→ 完成的功能
→ 修改的模块与关键实现
→ 实际演示结果和验证结论
```

这一层是导航和摘要，不用几句空泛结论替代后文。它必须明确任务切片是谁提出、是否获批，以及最终产物究竟对应原始需求还是独立实验题。

### 5.2 第二层：按阶段审查

#### A. 需求审查

先保留用户原始请求作为事实，再用普通语言抓住这项任务的主要矛盾。简单任务通常按以下阅读顺序说明即可：

1. **要解决的问题：** 当前哪里不方便、错误或低效；
2. **希望达到的效果：** 用户完成任务时应该发生什么变化；
3. **需要增加或改变的功能：** 为得到该效果具体做什么；
4. **做到什么算完成：** 用户操作和关键结果怎样被确认；
5. **必要范围：** 只有确实影响理解和决定时才说明必须保持、不做、依赖或未知。

复杂任务可以增加业务规则、风险和待决项，但不能把简单问题机械展开成完整字段表，也不能用“结构化需求理解”之类抽象标签增加阅读门槛。实际交付结果属于后面的演示与验证，不在需求章节另建“需求—交付对应关系”。需求不成立、任务切片未经批准或验收无法定义时，停止方案、实现和验证审查。

#### B. 方案审查

方案必须在需求之后，并先用人能定位的层级说明功能在哪里：哪个产品、哪个业务模块、哪个页面或用户入口，以及涉及前端、后端和数据中的哪些层。函数、类、框架和文件名只能在这些位置说明清楚后再出现。

方案按“整体到局部”展开：

1. **系统位置：** 从产品到业务模块、页面/入口和相关技术层；
2. **总体方案：** 原来怎样工作，要改成怎样工作；
3. **模块变更：** 在现有模块上增加、修改或保持什么，以及模块怎样连接；
4. **必要下钻：** 只有真正影响判断时，才展开数据模型、算法、交互、性能、兼容或公共能力；
5. **真实待决：** 只有存在会改变方案、风险或成本的选项时才单列，不把复用和非目标重复包装成“关键取舍”。

优先用上下文图先定位系统层级，再用流程图、组件图、时序图或 UML 标出已有模块与本次修改。文字和表格用于补充图中看不出的职责、变化和边界，不能用一串抽象代码名词代替系统关系。方案未批准时不把既有实现写成合理方案的证明。

#### C. 修改内容与软件实现审查

不再使用容易与设计模式混淆的“责任链”，也不单列 Diff 行数。先按模块、架构层次和影响范围概括“改了哪些地方、各自实现什么”，再下钻：

- 变更模块、现有职责、新增或修改的行为及相邻影响；
- 关键调用流程、组件结构、状态变化或数据转换；
- 核心算法、规则、异常和边界；
- 重要代码入口和完整 Diff 下钻链接；
- 必要的兼容、迁移和公共消费者影响。

源码不整段搬入报告；能帮助理解关键结构和逻辑的流程图、时序图、组件图、类图或伪代码按需使用。

#### D. 运行演示与验证审查

“修改前后用户看到了什么”归入运行演示，不再放在方案之前。先展示代表性的真实操作、页面、接口或数据结果，再说明这些结果怎样被验证。

验证内容由对应的验证能力或项目验证流程产生，审查页只消费并组织证据：

- 要证明的用户结果或工程声明；
- 正常、边界、失败和回归路径；
- 使用的真实输入、环境和范围；
- 实际观察值及证据入口；
- 结论、未覆盖内容和不能外推的范围。

测试数量不能替代结果；演示截图不能替代验证；代码推断不能冒充运行证据。

#### E. 总体决定与后续变化

前序阶段均可接受后，再决定批准、修改后复审或驳回，并说明代码、文档、知识、项目规范、Harness 和 Eval 分别怎样处理。

### 5.3 按需过程审计

Agent 轨迹不再是每份用户审查页的默认正文。结果和证据能够充分判断工作质量时，普通审查者无需再逐步审 Agent 怎样完成。

只有以下情况才增加“过程异常与审计线索”，或由独立评测者下钻完整 Trace：

- 结果错误但无法从产物定位原因；
- Agent 越权、自行改变环境、跳过人工决定或作出超范围声明；
- 需要评价 Harness 的搜索、工具调用、恢复和执行效率；
- 同类结果问题反复出现，需要区分模型、Skill、工具或任务设计责任。

没有完整轨迹时不建立空章节，只在证据限制中说明无法还原。弱模型 Trial 对照属于 Eval 审计，不混入参考实现的普通成果审查。

### 5.4 反馈与演进

- 修正当前需求、方案或实现；
- 更新规范知识和产品视图；
- 形成有范围的项目偏好；
- 记录一次模型失误；
- 多用例复现后改进 Skill、工具或路由；
- 形成新的 Eval 或回归；
- 暂时只保留原始反馈，不晋升。

## 6. 审查交互规则

每个审查点只包含四部分：

```text
审查目的：为什么需要人判断
当前待审内容：需求候选、方案、实现或证据中的具体对象
请你决定：认可、要求修改、需要补充信息或需要他人确认
处理结果：不同反馈将修正哪里
```

审查点按依赖顺序出现。需求被驳回时，把方案及之后标记为“等待需求修订”；方案被驳回时，把实现及之后标记为“等待方案修订”。报告可以保留已经发生的代码和运行事实，但不得继续要求用户批准建立在无效前提上的下游结论。

本地 Markdown 使用 `R1`、`R2` 等稳定编号。用户不必编辑文件，可以直接在对话中回复：

```text
R2：这个业务规则不对，应该……
R4：方案认可。
```

不得在信息不足时询问“是否合理”“是否完整”；不得要求用户判断内部“输入、门禁、证据包”等未定义对象。

## 7. 事实、解释和决定必须分开

| 内容 | 表现方式 | 权威来源 |
|---|---|---|
| 用户说了什么 | “用户原始请求”并保留原文 | 用户消息或固定任务 |
| Harness 后来选了什么切片 | “任务切片”并说明与原始诉求的包含关系和批准状态 | 用例设计与人工决定 |
| 候选模型实际看到了什么 | “候选模型完整任务”并保留原文 | 固定 Prompt |
| 当前系统怎样运行 | “当前事实”并链接源码、Schema 或运行结果 | 直接事实源 |
| Agent 怎样理解 | “Agent 理解/提案” | 可被用户纠正的分析 |
| 人批准了什么 | “人工决定”并保留原话与时间 | 审查反馈 |
| 哪些结果通过 | “实际验证”并链接输入、命令和输出 | 新鲜运行证据 |
| 哪些不能确认 | “未知/证据边界” | 明确缺口，不以推断补齐 |

## 8. 不同任务补充什么

| 任务类型 | 专属内容 |
|---|---|
| 软件开发 | 主要问题、用户效果、功能与完成标准、系统位置、总体与模块变更方案、修改清单、关键结构/算法、交互、Diff 和运行结果 |
| 知识摄入 | 原始材料、覆盖与遗漏、内容保真、知识归属、父知识变化、产品视图和冲突 |
| 方案设计 | 现状、难点、知识与未知、候选方案、取舍、人工决定和验证方式 |
| Harness 修改 | 修改的 `AGENTS.md`、Skills、工具和流程，预期行为、泛化依据、过拟合风险和回归 |
| 能力验证 | 固定输入、宿主与模型、候选过程、实际结果、参考差异和失败归因 |

简单知识回答没有长期变化时不创建持久审查单；复杂分析或用户明确要求审查时可以采用轻量版本。

## 9. 人工反馈怎样成为资产

人的原话先保存在当前审查单，不因一句意见自动修改全局 Harness。

| 反馈类型 | 默认处理 | 晋升条件 |
|---|---|---|
| 当前需求或实现错误 | 修正当前候选 | 不自动晋升 |
| 已确认业务、数据或软件事实 | 知识更新候选 | 来源充分并经发布审查 |
| 本项目稳定偏好 | 项目规范候选 | 用户确认适用范围 |
| 单次模型失误 | 当前 Trial 记录 | 不直接改全局规则 |
| 跨用例重复失误 | Skill、工具或路由候选 | 有第二用例，并完成旧、新用例回归 |
| 本题特有做法 | 认证参考 | 不泄露到候选模型可见 Harness |
| 被否决方案 | 有范围的决策历史 | 写明原因和可能适用条件 |

## 10. 与 Eval 的关系

一项完整审查资产至少包含：

```text
候选模型可见的原始请求
+ 模型、Harness、项目基线和环境
+ 原始可观察轨迹
+ 实际产物与运行证据
+ 本地工作审查单
+ 人工反馈、修订和最终决定
+ 不向候选模型暴露的认证参考
```

测试“方案形成”时只给候选模型原始模糊需求；优秀需求理解和方案属于隐藏参考。测试“按方案开发”时，批准后的需求和方案才可以作为候选输入。
