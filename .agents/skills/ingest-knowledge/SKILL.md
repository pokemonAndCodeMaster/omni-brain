# 知识摄入

目标不是清点材料或通过检查，而是让不熟悉原料的读者建立正确心智模型并能继续工作。始终抓住三件事：用**问题主线**决定要学什么，用**逐层下钻**连接上级全貌与用户焦点，用**直接事实源**保住细节和现实状态。

来源是证据，`knowledge/` 是唯一发布面，`workspaces/knowledge-ingestion/<case-id>/` 是发布前工作台。工具只负责盘点、固定入口和结构约束；Agent 负责理解、取舍与编织；人负责关键语义和发布决定。

按下面六步顺序执行。**只在进入某一步时读取该步点名的模板**，不要在开始时预读整个 `assets/` 目录。

## 执行节奏

**一个读者问题就是一次最小交付。** 不要把“阅读材料”和“写知识”拆成前后两个大阶段：

1. 第一次运行 `source-select` 前，只把 `brief.md` 填到足以确定完整范围、初始三层地图、问题主线和第一个要回答的问题；不要试图先写完最终知识架构；
2. 一次只处理一份实质来源：选择 → 独立执行 `source-read` 直到完整 → 精确登记 → 立即把新增机制写入 `inventory.md` 和对应候选知识章节；
3. 只有当前来源改变的具体内容已经离开会话上下文、进入工作台和正文，才能选择下一份来源；
4. 通常用二至五份直接来源完成一个问题；工具会在开始第六份来源前检查前五份是否带来正文更新。未更新时先写可靠局部与明确未知，再继续补证据，不能堆上下文等待“一次写全”；
5. 不并行执行多份 `source-read`，不用循环、管道、重定向或隐藏输出批量处理来源，也不把正文阅读委派给子任务；
6. 每完成一个问题就留下可浏览、可追溯的最小结果，再决定下一个问题。会话中断时，已完成问题仍应可独立使用。

工作台服务于正文，不是另一份需要先填满的产品。计划、清单和状态只记录会改变阅读或写作的内容。

## 1. 定义读者结果并建立工作台

从请求中提取授权材料、目标读者、知识用途、用户要求覆盖的完整范围和本轮最深焦点。用户说“浏览、理解、学习、继续使用”且没有说明背景时，按零背景读者设计。

先读 `knowledge/index.md`、`config/knowledge-domains.yaml` 和直接相关入口，再初始化授权来源；初始化前不要自行递归枚举：

```bash
python scripts/ingestion_workspace.py init <case-id> \
  --goal '<用户读完后能够理解、判断或执行什么>' \
  --source <source-id>=<authorized-directory> [--source ...]
```

此时只读取并填写 `assets/brief.md` 对应的根 `brief.md`。先建立能启动第一个知识单元的内容计划，不按文件目录规划摘要：

1. 分开记录**用户请求的完整范围**和**材料中当前实现最完整的纵向切片**。后者可以成为重点证据，但不能悄悄取代前者；
2. 写出“上级定位 → 主题全貌 → 用户焦点”的逐层地图；
3. 用生命周期、角色、核心对象与状态、平台/业务模块、上下游与同级能力检查主题全貌；
4. 写出读者最终必须能回答的问题主线；只为当前问题细化所需深度、候选事实源、目标页面和完成标准，其余问题先保留为队列；
5. 用户焦点是业务环节时，规划从进入、计划/分配、实际作业、监控、分析/决定、结果执行到返工/结束的闭环；
6. 只有范围或关键语义必须由人选择时才追问，其余不确定项先保留为开放问题。

完成标准：用户原始范围没有被缩窄；初始地图能够防止局部焦点冒充整体；第一个问题、目标正文和候选直接来源已经明确。`brief.md` 此时可以不完整，后续随正文一起演进。

## 2. 先交付第一个可用知识单元

进入本步时读取 `assets/inventory.md`、`assets/questions.md` 和 `assets/knowledge-page.md`；只有当前问题需要领域概览或软件纵切时，再分别读取 `assets/domain-overview.md` 或 `assets/software-architecture.md`。不要预读视图和审查模板。

先读 `source-summary.md`。文件名不透明、同类材料较多或当前问题缺少直接入口时，先用机器提取的标题和章节建立**来源内容导航**，不要凭文件名猜主题：

```bash
python scripts/ingestion_workspace.py files <case-id> <source-id> \
  --status unreviewed [--glob '<pattern>'] --describe \
  [--heading-limit 12] [--limit 100]
```

`--describe` 只展示可重建的文件规模、标题和章节，用于路由，既不是全文阅读，也不能支持知识结论。先用默认章节上限定位主题；只有单个候选的深层章节可能改变选源时，才用精确 `--glob` 提高 `--heading-limit`。围绕当前问题在 `inventory.md` 记录“待回答部分 → 命中标题/章节 → 下一份候选”，形成足以启动精读的来源主题地图；不要在第一篇正文前给全部文件逐一分类。

围绕当前问题选择最小充分的直接事实源，不按目录从头读，也不能只读名字最像焦点的文件。先选择当前要处理的一份，不要一次绑定一长串随后才开始消化。其他层次、生命周期、规则或公共能力的候选来源只有会改变当前答案时才在本单元读取；其余留给后续问题。

把必要来源绑定到精确路径：

```bash
python scripts/ingestion_workspace.py source-select <case-id> <source-id> \
  --path '<exact-relative-path>' \
  --level <parent|subject|focus> \
  --reason '<它预计改变哪层理解>'
```

`source-select` 一次只允许保留一份尚未处理的已选来源；同一来源可以补充多个层次，但必须先形成 `read_full` 或带精确定位的 `read_targeted`。只有工具客观无法展示文件时才能登记 `unread_blocked`。工具只约束阅读节奏，不能证明已经理解；在选择下一份前，仍须把当前来源改变的机制和知识落点写入工作台。

最终每个适用层至少需要一份直接来源，但第一单元只负责当前问题。确无来源时，将该问题的对应部分标为 `unknown`，不能借焦点材料补位。

实质内容按单文件读取：

```bash
python scripts/ingestion_workspace.py source-read <case-id> <source-id> \
  --path '<exact-relative-path>'
```

`source-read` 必须作为独立命令直接执行。不要用管道、重定向、命令替换、Shell 变量、脚本或循环隐藏正文输出；重复执行返回的 `next` 命令直到 `displayed_complete=true`。该状态只表示脚本已分块输出全文，**不是理解证明，也不是内容完成证明**。

读完一份关键来源后，立即在 `inventory.md` 的“已读内容与知识落点”逐项写下：

- 会改变读者答案的机制、条件、边界、冲突或未知；
- 准备进入的规范页和章节，或只形成未知/排除的理由；
- 它属于当前实现、当前业务决定、目标设计、历史快照还是开放问题。

随后立即把这些内容写进目标知识页的对应章节；页面暂时不完整时明确标成局部与未知。完成清单和正文两处落地再选择下一份来源。不要先连续读完大量材料，最后凭记忆压成几段摘要；引用不能替代知识内化。

结论必须匹配事实源：

- 当前软件行为：源码、Schema、配置、测试和新鲜运行结果；
- 当前业务语义：明确人工决定、业务原始记录和当前数据口径；
- 目标方案：设计稿、计划和待实施契约；
- 历史做法：历史脚本、旧规范和带时间边界的快照；
- 生成综合或旧知识页：只用于定位和发现冲突。

新鲜运行结果只有在命令实际作用于已注册来源对应的项目、数据和测试时，才能证明该来源实现可运行。当前 Harness 仓库的测试不能被写成外部来源代码的测试结果；无法在来源环境执行时，只记录测试代码声明的覆盖范围，不声称已经跑通。

软件知识要支持运行、调试或开发时，在把命令和样例写成可执行指南前，先定向读取来源项目自己的运行契约：项目操作说明、环境声明、配置、启动脚本和真实入口。命令必须可以直接复制执行，不用 `...`、省略参数或假想路径代替尚未查清的步骤。具体请求、响应和数值必须标明证据类型：来自本轮新鲜运行、已有测试/夹具，或仅为明确标注的示意；不得把静态阅读推断写成已经运行的结果。用户要求真实例子时，最终至少沿一个例子完成同范围的输入、跨层转换、输出和验证；当前环境无法执行则保留为未验证步骤，并说明缺少什么，不以 UT 代替端到端事实。

材料涉及软件且知识将用于理解、开发或维护时，必须读取真实代码并至少追踪一个业务动作：

```text
用户目的与输入
→ 真实入口
→ 包、模块、类、函数与数据结构
→ 数据转换和状态变化
→ 数据库/外部系统
→ 返回结果与失败边界
→ 职责划分、当前限制和一次具体修改路径
```

覆盖账本只顺手记录阅读进展，不决定内容范围。首次登记前运行 `python scripts/ingestion_workspace.py mark --help`。只有 `source-read` 已完整输出且你确实理解全文，才可精确登记：

```bash
python scripts/ingestion_workspace.py mark <case-id> <source-id> \
  --status read_full --path '<exact-relative-path>' \
  --reason '<该文件支持什么问题>' --evidence '<exact-relative-path>#full-file'
```

尚未选择且经题名、类型或机器清单确认无需深读的材料，用已有 `screened / excluded / duplicate` 表达；不要把“暂缓、无关、重复或已经部分读取”写成 `unread_blocked`。选中后只需局部证据时，用 `read_targeted` 绑定精确标题、行号或符号。批量弱状态不会覆盖已选来源或 `read_full / read_targeted` 结论；不要为完成清单而把已读证据降级。

不能安全回答的事项统一写入 `questions.md`；“没有找到”不等于“不存在”。每个已选择来源必须在 `inventory.md` 有具体落点、开放问题或可复核排除理由。

正常摄入不得使用 `mark --all-unreviewed`，也不得用 Shell 循环或一个笼统理由批量结束剩余材料。只有身份、主题、现实形态和影响问题相同的小文件，才可在逐项确认身份后用精确 `--glob` 作为一组登记。总架构、Hub 或摘要只能帮助定位，不能证明其下的明细材料没有新机制；来源内容导航命中尚未回答的问题时，不得以“总卡已覆盖”为由批量 `screened`，至少定向读取最直接的一份候选后再判断。筛选理由必须对应该文件可见的身份、标题或章节，不能只引用另一份总览。

空目录、`.gitkeep`、stub、占位接口和只存在于设计稿中的路径也是**负面证据**。当读者问题涉及该能力时，记录“当前只能证明占位或目标，不能证明实现、契约或运行行为”；不能把它筛成无关材料，也不能据此写成能力不存在。

准备结束**当前问题**时，在 `inventory.md` 完成“当前问题缺口复核”：

1. 将当前复合问题拆回它实际要求的各部分，分别写清已有证据能回答什么、还不能回答什么；
2. 对仍缺部分用 `files --status unreviewed --describe` 反查来源内容导航。若存在可能回答它的业务流程、目标设计、历史做法、规则或责任材料，至少定向读取一份最直接的候选来源后再判断；
3. 当前代码纵切只能证明当前实现，不能据此排除完整生命周期、业务目标、规则、历史和责任材料；
4. 只有没有合理候选、来源不可访问或读后证据仍不足时，才登记为未知，并写明缺失事实、应由什么来源或责任人补充、对后续工作的影响和下一动作；
5. 复核结束后立即把结论、可靠局部和未知写进当前知识页，不等待全部问题复核完毕。

完成标准：至少一篇非 `index.md` 的实质知识页已经回答第一个问题；页面包含具体机制、现实状态、边界或未知以及可追溯来源；这个结果即使会话现在结束也能被人或下一模型使用。

## 3. 按问题逐个扩展知识

从 `brief.md` 选择下一个尚未充分回答的问题，重复“选择直接来源 → 完整阅读一份 → 更新清单 → 更新正文 → 复核当前问题”的小闭环。每个新增来源必须说明它准备补足哪个具体缺口；若不能改变答案、边界、风险或知识结构，就不要读取。

随着证据出现修订知识地图，而不是在阅读前一次定稿。用**独立变化**判断知识单元：不同事实源或现实形态、独立更新节奏、独立读者问题，或复杂到会淹没父页，任一成立就应建立独立规范页。

当同一页开始同时承担数据与口径、系统调用、界面交互、运行调试等多个会独立修改或被独立查询的任务时，停止继续向总页追加；先把已有内容按规范落点拆开，用总览和产品视图串联，再决定是否读取邻近源码。篇幅长本身不是拆分理由，但“一篇页必须从头读完才能完成不同任务”说明知识地图尚未形成。综合总页不能替代学习路线、开发路线或问题直达入口。

- 每个稳定主题只有一个规范落点；
- `domains/` 保存业务语义、流程、数据和领域规则；
- `capabilities/` 保存跨领域或跨模块复用的能力及使用契约；
- `systems/` 保存有独立实现与生命周期的系统或服务事实；
- `sources/` 保存来源记录，`views/` 保存产品视图；
- 领域目录 `index.md` 只导航，`overview.md` 才是领域规范正文；
- 当前实现、人工决定、目标设计、历史快照和开放问题不能混成一张“现状”。

公共能力出现共享实现、两个真实消费者、明确公共 owner/契约，或用户明确其为团队公共能力时，才读取 `assets/shared-capability-review.md`。正文若只证明主题依赖某公共能力，明确写“依赖点已知、公共契约未核实”；若要说明其接口、事务、重试、配置或复用边界，必须选择并读取公共实现的直接来源。只有占位或目标依赖时，可以形成知识缺口页，但不能虚构当前实现。

每完成一个问题，确认它能落到一至三篇规范页或一个显式未知；`inventory.md` 的每项不可丢失内容都已进入具体页面与章节；页面能说明为何独立、保留哪些机制和用什么来源证明。

选择下一个问题或扩读相邻模块前，先从当前候选正文回答刚完成的问题：能可靠回答时，先完成必要拆页、导航和视图；只能部分回答时，只读取能够补足明确缺口的直接来源；答案仍依赖未经核对的综合文档、假想命令或示例值时，当前问题尚未完成。不要用“继续读更多源码”推迟这次消费检查。

所有核心问题都有可用答案或明确未知后，对每个来源执行一次有界的 `files --status unreviewed --describe` 复核。剩余未审材料的标题和章节若仍命中尚缺部分，继续最小阅读闭环；否则读取 `assets/completion.yaml`，为 `parent / subject / focus` 分别填写主题、来源、正文主落点和层间关系。层次表达知识位置和下钻关系，不强制一层一文件：相邻层围绕同一稳定主题、会一起维护且页面章节边界清楚时可以共用主落点，并在 `rationale` 说明；不能为了少写内容让焦点页替代上级全貌。

- `covered`：计划范围已经完整落页；
- `partial`：已有可用内容，但计划范围仍缺一部分；`rationale` 必须同时说明已覆盖和缺失部分；
- `unknown`：授权材料不足以形成安全知识；
- `not_applicable`：该层或维度在业务上确实不适用。

不要为了显得完成把 `partial` 改成 `covered`，也不要让不同层静默共用一篇页面。

完成标准：每完成一个问题就有可使用的正文；最终知识地图覆盖用户完整范围与问题主线，每个适用层都有可到达主落点或诚实缺口。

## 4. 组装全貌与产品视图

候选始终只写入工作台的 `draft/knowledge/` 和 `draft/config/`。本步不是第一次写正文，而是把前面逐问题形成的页面按“全貌 → 焦点 → 细节”校准、补缝和导航。建立来源记录时才读取 `assets/source-record.md`，不要一次加载所有模板。

正文按读者需要信息的顺序组织，不按来源顺序拼接摘要。每页只选一个主意图：学习主题、完成任务、精确查询、理解机制或排查问题。

写作必须同时支持三种阅读深度：

- **快速定位**：标题、开头、章节名、短重点和关键图表足以说明本页回答什么；
- **理解主线**：对象、因果、流程或实现关系能够串成完整逻辑；
- **深入核验**：条件、机制、实现、例外、风险、未知和直接来源均可下钻。

标题表达知识逻辑，不用口语句、阅读指令或“背景/详细说明/其他”等空泛词。每个章节先说明其在父章节中的作用、范围或核心判断。实质段落用准确的加粗语义标签开头，并只加粗真正决定理解或行动的关键词、关系、限制或结论片段；不能整句、整段加粗。

按认知任务选择段落、列表、表格或图。图只回答一个主要问题；相邻内容补充图中难以表达但会影响使用的输入输出、触发条件、数据变化、异常去向、约束和边界，不复述箭头。改变结论的细节必须进入正文，不能缩成一两句再丢一个来源链接。

最低内容深度：

- 流程：起终点、角色、输入输出、并行、状态、异常、返工和下游；
- 模块：职责、上下游交接和交接失败；
- 数据：对象、标识、关系、状态、口径、来源和新鲜度；
- 软件：代码地图、运行时序、必要的类/数据关系、职责理由、限制和修改路径；
- 规则/算法：用途、输入输出、不变量、步骤、边界例子和实现入口；
- 公共能力：唯一规范落点与本领域使用契约。

每完成一篇正文，立即对照 `brief.md` 和 `inventory.md` 复核不可丢失内容，再写下一篇。只把父页的一段摘要搬成新文件不算形成知识。

正文形成后读取 `assets/product-view.md`，同步建立领域位置视图和旅程/学习视图。具名视图只写入 `draft/knowledge/views/by-domain/<slug>.md` 与 `draft/knowledge/views/by-journey/<slug>.md`；`index.md` 只导航，不另建 `draft/views/`。视图必须让读者按一个或一组问题找到**最小充分阅读路线**，不能把固定前三页当成所有问题的统一答案。

完成标准：零背景读者可以快速定位、沿主线理解并继续核验；用户完整范围中的已覆盖、部分覆盖与未知均清楚可见；材料细节已内化而不是被链接替代。

## 5. 先做内容消费，再做结构检查

进入本步时读取 `assets/reader-answers.md`，从候选旅程视图重新开始，假设自己没有读过原材料，逐个回答 `brief.md` 的问题主线。

每个问题必须恰好出现一次，答案可独立理解，并只依赖产品视图和最多三篇规范页。先判断事实可信度，再判断问题原始范围是否完整：

- `reliable`：题目主干和每个必要部分均有匹配的直接事实源；
- `partial`：有可靠局部，但必要部分仍缺失、未展开或只存在历史/目标材料；
- `unknown`：授权材料不足以安全作答；
- `not_applicable`：业务上确实不适用，并有理由。

不能用焦点局部的完整答案代替上级领域、主题全貌或完整生命周期。每个 `partial` 或 `unknown` 都要写清**缺失事实、责任来源、对后续工作的影响和下一动作**。若缺口来自本轮已授权但尚未整理的材料，回到第 2—4 步；若来自外部事实缺失，写入 `questions.md`。只要题目主干仍有缺口，就不能在消费结论中声称“没有未知”。

内容消费完成后再更新 `completion.yaml`：维度同样使用 `covered / partial / unknown / not_applicable`，每项指向实际页面；人工审查前保持 `human_review_status: pending`。

完成标准：原始问题范围没有被静默缩窄；可靠、部分可靠和未知的边界能够直接指导下一次学习或工作。

## 6. 人工审查、发布与立即使用

进入本步时读取 `assets/review.md`。`questions.md` 是开放问题的唯一状态源；`review.md` 的“需要补充”只引用问题 ID 和影响，不另写一套未知事实。

在 `review.md` 链接 `reader-answers.md`、两种产品视图和三层主落点，并把结果分为可以发布、需要选择、需要补充和建议忽略。然后运行：

```bash
python scripts/ingestion_workspace.py check <case-id>
```

`PASS` 只表示候选结构可交人工审查，不表示知识正确、完整或已被人理解。正常摄入不读取检查器源码猜规则。

检查若指出核心 `knowledge_path` 来源没有全文阅读，只有两条有效路径：继续用 `source-read` 读完并诚实登记 `read_full`；或保留 `read_targeted` 证据，把该来源移出“完整覆盖依据”并降低相应内容声明。不得把局部阅读改写成全文阅读。

最终只向用户链接根 `review.md`，说明候选内容、部分覆盖与开放问题，且正式知识尚未修改。用户批准后才更新正式知识、来源记录、产品视图、索引、日志和领域地图，并运行：

```bash
python scripts/knowledge_check.py
```

展示 `git diff -- knowledge config`。发布后从 `knowledge/index.md` 完成一次真实浏览或问题消费。只有人工批准、发布、结构检查和真实消费都完成，才报告摄入完成。
