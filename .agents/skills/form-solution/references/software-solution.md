# 复杂软件方案的审查结构

本参考只用于跨模块、跨层或公共能力的软件方案。目标是让审查者先理解需求，再理解系统中的变化；不是提前写实现报告。

## 顶部入口

标题下说明：

- **审查对象：** 这次要形成什么方案；
- **当前状态：** R1 待审、R1 已通过/R2 待审，或 R2 已通过；
- **怎样审查：** 从当前开放的 R 开始，回复编号和意见；前序不通过时后续暂停；
- **内容导航：** 背景、需求、方案和当前开放的审查点。

不要在顶部写模型、评分、门禁或实验术语。

## R1：需求

推荐顺序：

1. 背景与主要问题；
2. 目标与用户使用结果；
3. 日常使用流程；
4. 功能范围与业务规则；
5. 保持不变的行为和边界；
6. 完成标准；
7. 需要确认的问题；
8. R1 反馈区。

“日常使用流程”按用户动作组织；“功能范围与完成标准”可合成一张表，避免先平铺功能、后面再重复一次验收。复杂范围可按用户入口、公共组件、数据与后端能力分组，但同一张表中的行应保持同一粒度。

R1 反馈区包含：审查目的、当前待审内容、可选决定、不同决定如何处理、用户反馈占位。只开放 R1；不要提前让用户审方案。

## R2：方案

### 系统位置

先用普通名称说明产品、业务模块、页面/入口以及涉及的前端、后端和数据层。随后用 Mermaid 图表示关系，例如：

```mermaid
flowchart LR
    U[用户入口] --> F[页面与交互]
    F --> S[对应业务服务]
    S --> R[领域数据访问]
    R --> D[(当前数据源)]
```

图只保留理解本次方案所需节点。图后补充每个节点的职责、本次是否改变以及箭头承载的数据或动作；不要用文字重复图形外观。

### 总体方案

先用一段话说清“现状能力 → 本次改变 → 用户结果”。如变化跨层，再用前后对比图或主流程图标出新增、修改和继续复用的节点。

现状中的目录、接口、限制和保护逻辑不是天然正确的目标架构。方案应分别标明：继续复用、需要
增强、迁移后退出和有待实测的内容。新能力接管旧职责时写清调用方迁移、结果对账和删除旧路径
的条件，不把长期并存当成无需解释的安全选择。

重叠的用户页面或工作流也属于两套职责，不只是重复的组件、Service 或 Repository。除非用户
明确要两个独立入口且能说明各自不同的长期用户结果，否则优先在现有入口演进、吸收旧能力并
给出删除条件；不得用“新建独立页面、旧页保持不变”绕开迁移设计。

### 模块方案

使用同粒度表格：

| 所在位置 | 当前职责与现状 | 本次改变 | 改变后的作用 | 上下游 |
|---|---|---|---|---|

从产品入口到前端公共能力、领域前端、后端业务服务、数据访问与数据源逐层展开。只有大型模块内部确实存在多个独立责任时才再分一级。

模块边界从实际使用和变化方式推导：同一业务对象、同一段工作流中共同使用、共享事务或大概率
一起变化的职责优先放在同一业务模块内，再用文件或类区分技术角色。不要从 `config`、`service`、
`connector`、`content`、`analysis` 等泛化技术名词向下填目录，也不要把每个概念都升级成顶级模块。
列出目录后，沿每条主要工作流模拟一次调用；若一个内聚动作需要在多个没有独立业务含义的顶级
目录间来回跳转，重新审视边界。

### 从日常工作反推架构

先列出 R1 已确认的完整日常工作，而不是只挑最容易画的一条主链。根据任务选择适用过程，例如：

- 系统怎样启动、选择运行范围并取得默认结果；
- 外部信息怎样进入、校验、转换、保存以及逐条失败；
- 用户怎样浏览、筛选、查看详情、修改状态或执行领域动作；
- 已有数据怎样被导出、分析、推荐或提供给其他消费者；
- 配置、权限或人工接管怎样影响上述过程。

每个过程至少交代触发者、入口、主要协作者、读写数据、可观察结果和失败边界。用时序图说明跨层
协作，用状态图说明状态转换，用表格并列同粒度过程；图只选真正有助理解的类型。最后反查每个
过程依赖的模块、类、接口和表是否已在后文获得明确 owner。

### 关键流程与数据

选择真正会影响实现的内容说明：

- 默认使用路径与可调整路径；
- 筛选、聚合、展开、选择、下钻等交互怎样组合；
- 一份数据怎样被不同视图复用，何时才重新查询；
- 指标、状态或业务规则由谁计算；
- 完整结果、错误和大数据量怎样处理；
- 公共组件提供什么稳定能力，领域模块提供什么业务配置。

“一份数据共同复用”必须按实际数据范围说明：是顶部范围的完整事实、某一层聚合结果，还是仅
当前页；不能把“每次操作分别查询、各自复用结果”写成一次取数。若选择服务端聚合或懒加载，
需要明确它是否改变已经确认的用户要求，以及详情、图表、导出如何取得其所需的完整底层数据。

状态结构必须忠实表达用户动作。无序选择使用集合语义；有序步骤只有在先后顺序会改变结果时
才使用列表；一次展开、筛选或选择动作不要无依据持久化为全局配置。

若接口承诺完整结果，成功响应就必须可直接使用；无法取齐时整体失败并显式暴露原因。调用方
可以在新请求失败时保留上一次完整成功结果，但不能消费半份新结果，也不应靠完成标志判断
服务端是否兑现基本正确性。

适合时使用时序图、状态图或伪代码。不要为了齐全机械加入所有图。

### 接口与代码组织

接口按一个清晰业务动作命名并保持高内聚。目录先按领域和业务模块归属，再在模块内放路由、Schema、Service、Repository 或前端组件；这些技术角色不能替代业务边界。

先确认业务对象和责任 owner，再决定文件与技术角色。不要为一个页面需求新建“结果”“分析”
之类可以装下任何内容的平行领域；强相关的刷新、查询、统计和对外用例通常应在同一业务模块
内按文件职责分开。一个接口只服务一个可说清输入、输出和失败方式的用例，完整数据、元数据、
聚合计算和导出不能被含糊的万能端点包办。

把本轮确定会建设的接口列成表，而不是写“例如”或“必要时增加”：

| 用例 | owner | 输入 | 成功输出 | 失败方式 | 消费者 |
|---|---|---|---|---|---|

接口表必须覆盖方案中每个被消费的独立数据对象。完成后从图、模块表和消费者反查：完整事实、
指标定义/元数据、候选值、聚合结果、底层明细等凡是被使用，都必须有提供方；复用既有能力也
不能省略该行。不要在表外说“另有独立用例”，却让施工者自己寻找它的输入输出和失败方式。

只列本轮真实需要的用例。某能力直接消费客户端已有数据时，明确写“无新增后端接口”，避免
同一方案同时声称本地处理又候选新增 API。

若现有接口叫 `query`、`catalog`、`analysis` 等泛化名称，方案必须区分“当前兼容入口”和
“目标业务用例”：不能因为它已经存在就把模糊命名升级为目标设计。继续用于回归或迁移时写清
唯一消费者和退出条件；目标方案中的 owner、用例和新接口仍应表达具体业务对象。没有产品消费
者、只为对账保留的旧万能接口，不应继续成为新架构主链路。

目标链路的消费者不得继续把泛化兼容入口当作正式 owner。若目标能力需要其中的指标定义、统计
或数据访问，就在方案中把该责任迁入明确业务模块并迁移消费者；兼容入口只服务尚未迁移的旧
消费者，并有删除条件。不能一边写“不创建泛化 Service”，一边让新页面继续调用现有泛化
Service 来规避迁移。

方案只写职责、输入输出、复用关系和必要算法，不罗列尚不存在的文件清单冒充设计已经落地。

对架构重构，目录仍不足以证明软件设计成立。把具有长期状态、稳定不变量、替换策略或清晰协作
责任的主要类列出来，说明关键方法和调用关系；纯输入输出数据保持为数据对象，简单 Router 或
无状态转换可以是函数。既不能把业务实现散成无法定位 owner 的函数，也不能为了“面向对象”给
每个文件套一个没有状态和行为边界的空壳类。类图只画本次主链中的关键类，并由一条真实时序证明
这些类确实协作。

如果方案依赖可替换来源、认证、存储或算法，先描述两个真实变体的共同输入输出和实际差异，再
确定抽象边界。共同接口只容纳调用方真正需要的稳定语义；站点选择器、字段映射、验证码流程等
变体细节留在具体实现。只有一个现实变体且第一版不要求多个时，保留普通实现和明确的未来拆分点，
不要预建插件体系。

### 配置与秘密

需要配置时，分别说明非敏感业务配置、部署/本地覆盖、账号密钥、运行生成状态和业务数据的唯一
权威。业务代码只通过一个明确加载边界取得经过校验的配置，不在各模块散落 YAML、环境变量和
默认值读取。真实秘密可以位于受 Git 忽略的本地 `.env` 或部署环境变量；可提交的示例只保存变量
名和说明，日志、方案、测试夹具与版本库不得出现真实值。Cookie、令牌和缓存等运行生成状态放在
受控运行目录，不回写静态配置。

不要仅因存在配置就预建多层目录、配置数据库或管理页面。先按当前配置量使用最清晰的单一入口；
只有内容规模、不同维护者或运行时编辑需求真实出现时再拆分。

### 数据结构与访问方式

数据模型从使用过程反推，而不是从概念名词生成一张表。先枚举页面、后台任务和接口需要执行的
新增、更新、筛选、详情、关联、状态修改和分析，再设计业务对象、关系、字段、唯一约束和索引。
同时说明高频字段与低频扩展字段、正文与媒体、当前状态与历史事件分别怎样存，为什么符合当前
查询效率、空间成本和更新方式。

形成候选表以后逐表反证：它是否具有独立的一对多数量、查询/索引方式、安全边界、更新生命周期
或必须保留的历史。若只是主对象的一组当前状态、时间戳或少量同生命周期字段，就优先并入同一
状态记录；一个业务名词不自动获得一张表。反过来，需要独立筛选、去重、排序或多条并存的记录
不能为了少表塞进 JSON 或父表。表数量不是简洁或先进的指标，使用和维护边界才是。

一对多数据若需要独立筛选、排序、分组、去重或状态管理，优先正规化为有明确关联键的记录；低频
且不参与主要查询的网站特有元数据才适合留在扩展字段。前端需要完整业务快照不代表后端必须写一条
巨大 JOIN：可以用若干有界查询按业务标识组装，但必须说明查询数量、组装 owner、完整性和避免
笛卡尔膨胀的理由。

图片、附件、模型文件等大对象必须比较数据库、文件系统或对象存储在读取方式、事务一致性、备份
体积、删除清理和现有基础设施上的成本；不能因为旧实现使用 BYTEA/BLOB 就直接继承，也不能无据
改成另一种存储。数据库若只需要筛选和关联，通常保存元数据与受控位置；最终选择必须回到当前
工况和可验证的运维方式。

Repository 面向清晰业务对象和用例，不是“一表一目录”，也不是万能 `query()`。方案至少给出
主要写入、列表快照、详情和状态修改的具体方法或等价接口，并写清事务由谁控制、哪些相关记录必须
原子成功。表结构发生变化时，迁移方案说明旧数据映射、对账和退出；业务配置变化不能被误写成
数据库结构迁移。

### 验证方案

把每项重要用户结果对应到一个真实证据：页面操作、API 输入输出、数据库/固定数据对账、关键边界和必要回归。性能或规模结论必须有当前数据量与运行观察；没有证据时保留为待验证，不先定任意阈值。

“实测”“可行”“完整取得”和具体体积、耗时、负载只能来自本轮保存的命令或运行输出。由行数、
字段列表或经验推算的结果必须标为估算，并说明实施时怎样测量；不得把估算升级成方案事实或固定
验收数字。

文件导出要用目标软件真实打开，验证非 ASCII 文本、数值/日期类型、固定嵌套字段、变长明细和
代表性数据量。格式与库是方案的一部分：从消费者和数据结构反推，候选比较通过后再定；没有
规模证据时不预建队列、异步任务或备用格式。

对表格型导出，至少分别设计：用户当前看到的统计结果、可追溯的底层明细、一对多/变长数据
明细，以及包含筛选范围、数据时间、导出时间和口径的说明。它们可以是同一工作簿的不同工作表，
也可以是目标消费者能直接关联的等价结构；必须给出关联键和类型，不把大段序列化文本塞进格子。

一对多/变长明细应与基础明细分表或形成等价的独立关系表；“在基础明细中追加另一类行”不算
独立结构，因为会混合粒度和列语义。

### R2 反馈区

说明审查目的、待审方案、用户可批准/修订/驳回的内容、反馈将影响哪些模块，以及用户反馈占位。R2 通过前不得进入实施。

反馈合入后重写当前方案，不在文末堆叠相互矛盾的修订层。最终检查标题状态、图、模块表、
接口、验证、待决项和交接结论是否一致；已经被用户关闭的问题不得继续列为阻塞。

在列出任何待决项前先做责任判断：如果它只影响内部技术实现，Agent 应结合现状和验证选择；
如果它改变用户行为、业务规则、权限、安全或不可逆成本，才交给用户。用户说“其他内容合理”
并要求整理确认项时，未被否定的推荐方案进入当前确认范围，不再原样列为待决。

这类反馈处理完成后，R2 可以处于两种状态之一：用户已经明确批准时标为“已确认”；用户只是
认可内容并要求汇总时标为“待整体确认，当前无开放决策”。不要留下一个先前已有推荐答案的
问题来维持“待审”形式。状态文字、待决表和文末交接必须互相一致。

## 裁剪原则

- 单页面、单模块且无公共影响：系统位置、一段总体方案、模块表和验证即可；
- 跨前后端或共享能力：保留系统图、数据/交互流程和模块责任；
- 有真实技术选择时比较选项；没有选择时直接说明方案，不制造“关键取舍”；
- 需求尚未确认时只写 R1，不加载本参考来提前完成 R2。
