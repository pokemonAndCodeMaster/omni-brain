# 带知识开发

完成一条**最薄可运行纵切**：用户结果正确、既有组合不退化、真实环境有证据、长期知识有明确交接。不要把“查完所有背景”当作开始开发的前提。

本 Skill 负责开发和验证，不负责把模糊需求补成已批准方案。用户明确要求审查，或根 `AGENTS.md` 将本次复杂成果路由到本地审查时，在真实验证完成后调用 `review-work`，让它消费原始任务、Diff 和证据；不要在两个 Skill 中维护两套审查结构。

## 0. 核对实施依据

复杂任务若以“已有批准方案”为实施依据，第一次读源码或修改产品前先取得方案身份：任务对象、
唯一审查路径、批准状态和批准范围。可信入口只有两类：用户在当前请求中明确给出的路径；当前
Harness 工作区中能与原始请求直接对齐、并明确标记已批准的审查文件。

用户口头声称“已经批准”是查找线索，不是批准证据。没有用户路径时，只检查一次当前 Harness
的 `workspaces/reviews/`；目录不存在、为空或没有能直接对齐任务的已批准文件就立即停止并索取。
不得为找方案遍历产品树、Git 历史、运行产物、`/home/.../project`、同级仓库、设计仓、`eval/`、
历史 Trial、归档或旧答案，也不得自行新建方案后把它标为已批准。找到文件但任务对象、版本或
批准范围对不上时同样停止。

明确的局部低风险修改不需要伪造方案凭据，仍按根路由直接执行。

取得批准方案后，先提取其中明确的**施工约束**：指定依赖或实现方式、禁止的替代方案、
模块归属、接口职责、迁移/删除要求和任务关闭条件。只有方案明确留给实施实验的技术点才可
自行选择；“只能、不得、不保留、采用某成熟能力”等已经批准的取舍不能降级成建议。当前任务
说明与批准方案互相冲突时，在第一次修改前指出冲突并停止，不得通过手写协议、暗建备用路径或
缩小能力来同时假装满足两边。

**完成标准：** 已有可引用的批准入口且与当前任务对齐，或已明确停止并向用户索取；没有第三种
“从其他地方猜一个方案继续做”的路径。

## 实现前快照

在第一次修改文件前，先用一条简短进度消息公开以下内容；没有这条消息就不要开始编辑：

- **用户结果：** 入口、操作、正常/边界结果和通过证据；
- **实施依据：** 复杂任务所用批准方案的当前工作区路径、状态与范围；不需要方案的局部任务写“不适用”；
- **施工约束：** 本轮不可替代的技术取舍、禁止项和关闭条件；没有批准方案时写“不适用”；
- **知识入口：** 确定性路由返回的 `PRIMARY`、实际打开的候补及其仍需回答的问题；路由不可用时写明降级路径；
- **当前责任：** 直接事实源、现有 owner、最小修改链，以及正式知识与当前工程是否为同一来源身份；
- **组合总量：** 对本次影响的每个可增长集合，列出 `固定项 + 用户可追加项 + 隐式项 - 去重 = 最大合法总量`、各数字的代码/配置来源和当前限制路径；
- **用户动作闭环：** 对每项批准能力写清“用户怎样触发 → 改变哪一份状态或范围 → 哪些页面、弹窗、图表、导出或批量结果消费它 → 要观察什么变化”；同一能力出现在主页面和详情等多个入口时分别列出，不用组件名代替用户动作；
- **副作用基线：** 仅在写数据库、迁移数据或触发外部执行时，记录能识别当前环境的精确事实、字段所有权和恢复方法。事实至少要能暴露“行数相同但内容已经漂移”，例如来源版本、时间范围、关键样本或可复算指纹；
- **真实计划：** 先从全新页面、进程或会话运行无需预热的默认旅程，再运行最大合法组合、关键边界和其他用户旅程。

只有代码中确实没有可选列、批量项、插件、下钻、保存配置或其他可增长集合时，组合总量才能写“不适用”，并给出判断依据。这是会话内工作快照，不创建新的状态文件或审批文档。

## 1. 固定用户结果

先用普通语言明确：

- 谁在什么入口使用；
- 输入或操作是什么；
- 正常、边界和失败时分别看到什么；
- 哪项运行证据能证明有用。

不确定项若会改变业务语义、公共契约或副作用，停止实现并进入项目声明的完整知识准备/方案流程；不要用模型常识补全。

**完成标准：** 能用一段话描述用户怎样触发、看到什么、怎样判断通过。

## 2. 取得最低充分上下文

按以下顺序定向读取：

1. 当前项目的 `AGENTS.md`、当前接力页和组件地图；归档只在追溯特定理由时读取。
2. 项目声明了正式知识根时，先用**原始用户请求**调用知识入口路由；只读 `PRIMARY`，只有原始请求中的某一项仍未回答时才打开一个对应候补：

   ```bash
   python .agents/skills/answer-from-knowledge/scripts/knowledge_route.py \
     --root '<knowledge-root>/index.md' \
     --query '<原始用户请求>' \
     --limit 3
   ```

   路由器不可用、返回空结果或候补明显无关时，降级为从正式根入口或一个产品视图定向下钻，并记录失败原因。正式知识初始最多读取三篇会改变实现的页面；三篇是硬上限，不是阅读目标。知识未覆盖时直接说明缺口，不递归通读原料，也不因此转去通读原始材料。
3. 当前源码、Schema、配置和运行结果。精确实现以它们为准，知识用于业务意义、边界、设计理由和修改地图。

始终区分**来源身份**。若正式知识与当前工程属于不同仓库、提交或原型，不得合并成同一个“当前实现”；把知识当作业务/架构线索，再以本工程事实裁决行为。

源码使用一条 **tracer route** 定向下钻：用户动作入口 → 当前事件/调用者 → 一个同类纵切 → 数据或状态 owner → 对应验证入口。大文件先用符号或错误文本定位，只读能回答当前问题的连续片段；归档、整页和同目录其他文件只有在某个明确未知会改变方案时才打开。每次扩读前先指出它可能改变“业务语义、事实源、修改链、关键未知”中的哪一项；不能改变任何一项就停止读取并开始实现。连续两次读取没有改变这四项时，视为已经越过最低充分点，不再靠扩大搜索获得安全感。

在动代码前明确这四项并公开实现前快照。知识页只负责领域意义和已知边界；当前工程行为仍由源码、Schema 和运行结果裁决。

**完成标准：** 已知当前行为由谁拥有、可复用能力在哪里、最小修改链和关键未知；每项结论都有直接落点。

## 3. 沿现有纵切找最小改动

沿真实用户动作追踪输入、转换、输出和状态，不机械凑齐技术层。先寻找已存在的指标、算法、接口、公共组件、配置和验证入口；已有能力足够时只接入消费链。

实现前执行一次**组合审计**。组合审计不是口头检查清单；凡是请求字段、可选列、批量动作、插件或其他有数量上限的集合，都要完成以下动作：

1. 从真实消费端列出固定项、用户可追加项、框架隐式项和去重规则，写出最大合法状态的完整构成；不要用“本次只新增几项”代替总量计算。
2. 从当前目录、配置或真实数据取得可追加项，构造产品声称支持的最大合法状态，并实际发出完整请求或运行对应旅程。
3. 若命中上限，追踪 Schema、Service 和其他消费者中的全部限制声明；只调整当前工况所需的最低值，并尽量由一个公共定义维护。
4. 增加“最大合法状态通过、再多一项失败”的契约测试；测试必须调用真实校验边界，不能复制实现常量后自证。

随后检查旧保存配置、旧 Schema、默认值和迁移数据是否仍能加载；`null`、零、空集合、超过 100%、部分失败等既有边界是否保持语义；共享能力的其他消费者是否被公共修改影响。

只修改实现用户结果所需的层。调整公共契约时使用当前工况要求的最低充分范围，不预留没有证据的容量。

**完成标准：** 变更范围能解释为一条必要纵切；组合审计中的每一项已验证、明确不适用或保留为阻塞。

## 4. 实现并保持边界

- 延续项目已有分层、命名、类型和依赖方向；不为两三个同职责字段新造抽象。
- 将数据转换放在已有边界，不在模板、页面或调用点临时拼动态字段。
- 复用公共能力，不复制排序、筛选、保存、重试或错误处理的旁路实现。
- 方案指定成熟库、项目公共组件或既有协议实现时，使用该 owner；不能为了回避正式依赖变更而
  手写文件格式、压缩协议、客户端或另一套组件。确需改变批准取舍时回到方案审查，不在施工中
  静默替换。
- 复用视觉或状态样式也要匹配业务语义。只有正式规则或当前产品明确把某个状态定义为风险/异常时，才复用告警色、危险标签或短缺样式；否则先使用中性呈现，不能因为数值为正或名称相近就暗示风险。
- 不顺手重构无关代码，不把目标设计或历史原型覆盖为当前事实。

**完成标准：** Diff 只包含必要实现、必要契约保护和必须同步的当前工程说明。

## 5. 用真实路径验证

使用项目已经声明的环境和命令；不要为验证临时安装无关工具、切换解释器或重建用户数据。
批准方案要求的新产品依赖属于正式代码变更：写入项目依赖清单和锁文件，并在候选工作树安装、
审计、构建和运行验证。任务同时禁止安装而方案又要求新增依赖时按第 0 节报告冲突；不得用自研
协议实现绕过。

运行探针保持**单一目的、短超时、可停止**。启动服务前先检查项目声明的端口、进程或健康入口，已有可用实例就复用；长驻服务只使用宿主已经提供的会话/任务机制，不反复试验后台 shell 写法。相同启动或连接失败连续出现两次时，停止换命令碰运气，先定位进程、端口、工作目录、环境变量和日志中哪一项不成立。不要为了验证一项结果顺手安装图片库、浏览器库或其他依赖。

候选工作树需要独立端口或临时连接参数时，通过当前进程环境或启动参数注入，不修改受版本管理的
产品配置。记录自己启动的 PID/进程组并只停止这些进程；禁止用 `pkill -f`、模糊进程名或其他
可能终止同机工作树/用户服务的全局方式。

多个 Git worktree 共享可编辑安装时，验证前先确认实际加载的源码属于当前工作树。若导入路径指向其他工作树，使用项目已经提供的当前源码覆盖或隔离方式；不得把另一工作树的测试通过当成本候选证据，也不得为了修复路径自行重装共享环境。

按风险递增验证：

1. 从全新的真实入口运行默认旅程，不先手动刷新、预置会话状态或调用内部接口；这一步确认用户第一次进入就能取得承诺结果；
2. 在真实 API、CLI 或用户入口运行实现前快照中声明的最大合法组合；
3. 类型检查、编译和已有高价值回归；
4. 只为新增算法、边界或契约补聚焦测试；
5. 在项目真实数据库、API、CLI 或页面运行一个正常样例；
6. 运行至少一个会改变判断的边界/失败样例；
7. 涉及页面、持久化或外部副作用时，验证真实用户旅程，不用 jsdom、mock 或声明代替。

用户、fixture 或参考数据指定了日期、租户、项目、环境或其他 Scope 时，API、SQL 和页面必须显式设置为**同一个 Scope**再对账；页面默认范围不能冒充固定工况。要求下钻时，记录每个约定层级的对象和具体结果值，不能只证明“能够展开”或“列仍存在”。

页面交互按用户承诺逐项取证。对模态框、抽屉或弹窗，“键盘可用”至少拆成：入口能被 Tab 到达并用 Enter/Space 激活、打开后焦点进入浮层、Tab/Shift+Tab 不逃到背景、Escape/关闭动作生效、关闭后焦点回到触发点；只验证其中一部分就只声明该部分。视觉结果用真实截图或人工可读页面确认；模型不能读取截图时，明确保留视觉审查，不能用 DOM 数值或 canvas 存在替代。

每项交互必须验证它承诺的**业务后果**。出现控件、点击成功、标题变化或画布存在，只能证明这些
局部事实；筛选要观察结果范围变化，图表编辑要观察所改维度/数据范围/图形或坐标轴实际生效，
联动要观察下游状态和数值变化，导出要读取文件内容。没有观察业务后果的能力保持未验证。

逐项执行实现前的“用户动作闭环”，不能只验证其中一个入口或一个消费者。声称“每列可筛选”时，
要在承诺的列上看到匹配类型的控件并实际改变结果；声称详情继续支持某能力时，必须在详情内重新
执行该动作；声称筛选范围被复用时，要分别观察页面、详情、图表、未选择导出和批量动作中所有
承诺的消费者。缺少入口等于功能未实现，不得用底层公共组件“理论上支持”代替。

结构化产物不能只检查文件存在、大小、工作表/区块数量、返回 200 或包含某段文字。必须用正常
消费者或成熟解析库重新打开，至少核对标题/字段与实际列一一对应、代表行的单元格类型和数值、
可变长部分的关联键，以及一个重叠或空值样例。新增转换测试也必须断言这些结构和语义，不能只做
非空或 `contains` 检查。

目录、规则表或枚举聚合声称是统一语义时，从独立事实源挑一个最容易漏掉的合法状态做对账；
标签和描述必须与实际覆盖的全部枚举值一致。只对账默认数量/比例，不能证明状态、结论或其他目录
项正确。依赖审计命令非零时，依赖审计就是未通过；记录具体风险和决定，不能并入“回归全绿”。

验证完整组合，不只验证新字段孤立存在。例如可固定五个选项时，要验证基础请求与五个选项同时存在；支持保存时，要验证旧配置与新列共存。

环境本身不可用时，记录失败位置、已完成证据和用户仍无法确认的结果；不得把评测者事后补跑写成生产会话自行完成。

涉及写数据库、迁移数据或外部执行时，还必须完成一组**副作用验证**。产品功能声称只读不等于
验证过程无副作用；为性能实验创建的临时 Schema/表、运行配置、下载物和服务进程也纳入基线与
清理清单：

1. 第一次写入前保存实现前快照声明的精确基线和可逆恢复路径。取得基线的命令失败、输出不完整或无法复算时，先修复取证，不能继续写入。除非用户授权，且已证明能重建同一份数据，不运行 `seed`、`reset`、全量迁移或其他会改写测试夹具身份的命令；
2. 为每类不归本次功能拥有的状态设置有辨识度的冲突样本，同时覆盖非空值和 `null`。输入应主动与这些样本冲突，才能证明实现是在保护字段，而不是碰巧写入相同值；
3. 实际运行正常写入、部分或整批无效输入、预览后来源变化、重复执行等会改变安全判断的路径；幂等场景还要观察内容和更新时间是否保持不变；
4. 用精确快照、可验证的逆操作或项目声明的等价机制恢复环境，再用与写入前相同的事实或指纹比较。测试通过、行数相同或命令返回成功都不能单独证明已经恢复；
5. 新增解析、合并、预览令牌或事务算法时，补能长期保存这些边界的聚焦测试，而不是只依赖一次人工运行。

**完成标准：** 新鲜证据覆盖用户结果、关键组合和相关边界；不能完成的真实路径被准确标为未验证。

## 6. 形成知识变化候选

交付时单列“知识变化候选”，至少说明：

- **来源身份：** 哪个仓库、版本或运行环境产生新事实；
- **变化事实：** 新增、修改或被推翻了什么；
- **规范落点：** 明确到已有规范页或建议的新页面路径/稳定 owner，并说明原位更新、创建新实现页还是无需改知识；
- **保持边界：** 哪些业务规则、生产结论或目标设计没有因此改变；
- **证据：** 对应代码、Schema、命令或运行结果。

若正式知识尚未登记当前工程，优先提出独立来源记录和实现页，不把多个原型静默融合。除非用户明确授权发布，否则只提出候选，不直接修改正式知识。

来源身份至少精确到仓库和提交，运行事实还要说明环境或固定输入。稳定变化若会影响后续理解、查询或开发，规范落点不能只写当前工程的 handoff、组件图或验证报告；必须命名正式知识中的已有 owner，或给出建议的新稳定页面路径，并明确是原位更新、创建新系统/来源页还是无需更新。落点不清楚时，可用同一知识入口做一次有界定位，不得因此通读知识库。

**完成标准：** 每项稳定变化都有落点或明确的“不需更新”理由；未知和不同实现身份没有被抹平。

## 7. 交付

发出最终消息前，按“计划验证项 × 实际输出证据”逐条核对，每个声明只对应亲自观察到的最小事实：不能把“按钮可激活”扩写成“弹窗键盘完整可用”，也不能用页面出现替代页面操作、用代码推断替代运行输出。未观察项进入“未验证/阻塞”，不能用完成时态带过。

已有批准方案时，再按其每一条任务关闭条件核对“实现落点—真实业务后果—证据—剩余边界”。
任一必需项缺少实现、只验证控件外观、违反施工约束或依赖评测者补跑，都不能声明整项完成；
测试总数、文件数量和模型自述不能覆盖这个逐项核对。

关闭核对还必须主动审视**强范围声明**。凡是准备使用“全部、任意、每个、完整、公共、复用、
不再、已经迁移”等措辞，先把它改写成可反驳的检查项，并验证一个最可能失败的反例：非默认
分支、局部筛选后的下游产物、父子范围重叠、空值/失败路径或另一个既有消费者。只证明默认路径
不能支持全称结论。

- 筛选、选择、展开或范围切换会改变数据作用域时，把这个作用域沿每个承诺的下游消费者追到底；
  页面变化不能自动证明导出、弹窗、图表或批量动作使用了同一范围。
- 声称旧实现已退役或职责已迁移时，必须确认所有仍在运行的调用者已经切换，而且旧 owner 已经
  没有活跃消费者；“新页面不再调用旧实现”不等于全系统完成迁移。
- 删除旧代码或测试时，列出“旧行为 → 新 owner → 替代测试或真实证据”。测试总数减少后仍然
  全绿，只能证明剩余测试通过，不能证明被删除的行为继续受到保护。
- 施工中发现批准关闭条件无法完成、互相冲突或代价超出当前范围时，把它保留为未完成并回到
  对应方案决定；不能在实现后重新解释批准条件，再把缩小后的结果声明为完成。

最终只保留四部分：

1. **用户结果：** 现在能在什么入口完成什么；
2. **实现与证据：** 最小责任链、最大合法组合和实际运行结果；有副作用时同时给精确恢复证据；
3. **未验证与决定：** 环境阻塞、未执行路径和需要人类确认的语义；
4. **知识变化候选：** 来源身份、变化事实、规范落点、保持边界和证据。

四部分缺一时不声明任务完成。用户无需维护内部状态时明确说明。

如果本次还需使用 `review-work`，以上四部分进入本地审查单，最终消息只保留用户结果、审查入口、当前从哪个 `R` 开始以及第一个不通过点可以停止；不要再复制一份长交付说明。
