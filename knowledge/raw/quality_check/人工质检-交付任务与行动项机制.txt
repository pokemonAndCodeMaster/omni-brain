# 人工质检交付任务与行动项机制

← 总入口：[[质检一站式平台人工质检模块整体架构]]。前端落点：[[质检平台-人工质检交付中心前端设计]]。验收阶段：[[质检平台-人工质检验收中心前端设计]]。

## 1. 交付任务定义

人工质检以前端可管理的"一条交付任务"为主对象：**一个数据集就是一个批次的人工质检任务**。该对象从需求登记开始，持续到验收通过或打回返修完成，不以标注 task 创建成功作为交付完成。

交付任务既是管理者查看交付风险的单位，也是执行人员挂行动项、更新进度和进入各阶段操作的上下文。

## 2. 标准交付轨道

```text
需求登记与对齐
  → 需求接纳、排期与专题内优先级
  → 数据送检
  → 规则版本/新增修改/培训就绪
  → 视频与文本适配就绪
  → 人工质检任务创建与审批
  → 视频/文本任务生产
  → 标注任务分配
  → 实际标注
  → 验收任务分配
  → 实际验收
  → 通过/打回按日执行与状态回查
  → 可交付 Good 数量确认
  → 交付完成
```

标准轨道不是严格线性：

- 数据准备与规则对齐可并行推进。
- 沿用通用规则的任务可直接进入"规则就绪"。
- 新规则需要经历规范更新、标注员培训、试标、问题识别和规则再对齐，可能循环多轮。
- 验收打回后进入返修标注，再回到验收，不把 REJECT 当成流程终点。

因此前端同时记录"当前主阶段"和"当前轮次/子流程"，不能只用单一状态枚举描述全部进展。

## 3. 需求对齐机制

需求登记时常只有预估数据量和大致交付范围。每周两次需求对齐会继续确定或修改：

- 优先级；
- 期望交付时间；
- 预估数据量；
- 计划数据就绪时间；
- 负责人；
- 规则类型与待确认风险。

需求参与方必须区分：

- 需求方/数据专题 FO：提出并解释数据需求；
- 质检 FO：对接该专题的质检负责人，负责接纳、排期、规则、质检执行和交付推进。

数据真实到达后，再更新实际到数时间和实际数量。前端必须保留计划值与实际值的区别，不能用后一次编辑覆盖计划基线后失去偏差信息。

## 3.1 完整字段域

| 字段域 | 需要跟踪的信息 |
|---|---|
| 需求身份 | 数据集名称、所属专题、需求方/数据专题 FO、质检 FO、专题内优先级 |
| 需求目标 | 期望交付时间、期望交付数量 |
| 送检 | 待送检数量、是否已送来、预计送来时间、实际送来时间、实际数量 |
| 质检规范 | 应用规范版本、是否新增/修改、新规范归档版本、培训是否完成 |
| 任务适配 | 是否使用通用规范、视频适配进度/版本、文本适配进度/版本 |
| 建任务与审批 | 人工质检任务是否创建、创建时间、审批状态 |
| 任务生产 | 视频生产数量/进度、文本任务生产数量/进度 |
| 标注分配与执行 | 分配数量/比例、开始时间、预计完成时间、平均标效、日进度 |
| 标注质量 | Good/Bad 数量与占比、Bad 原因构成 |
| 验收分配与执行 | 分配数量/比例、开始时间、预计完成时间、日进度、按天/组/结果选项粒度 |
| 通过打回 | 通过/打回数量与比例、已执行日期、未执行日期、最终状态回查 |
| 可交付 | 验收通过中的 Good/Bad、最终可交付 Good 数量、与期望数量差额、完成归档 |

完整字段进入交付中心列视图和任务详情；总览只提取主要矛盾，见 [[人工质检总览信息架构]]。

## 4. 非标准行动项

不同交付任务会出现标准轨道之外的定制事项，例如：

- 摸排标效；
- 新规则对齐；
- 数据预筛；
- 规范文档更新；
- 标注员培训；
- 组织试标；
- 验证配置版本；
- 排查生产阻塞。

每个行动项至少表达：标题、所属交付任务、责任人、截止时间、状态、优先级、风险、闭环结论。行动项可以绑定某个交付阶段，也可以作为跨阶段事项存在。

交付中心需要主动暴露：

- 未来若干天到期的行动项；
- 今日到期与已逾期行动项；
- 无责任人、无截止时间或被阻塞的行动项；
- 行动项未闭环但交付任务准备进入下一阶段的冲突。

## 5. 重点批次跟踪

一批同时提出的本月或未来两周高优需求，需要被单独拎出持续跟踪。前端以"保存视图/关注集合"实现，不复制交付任务：

- 同一交付任务可出现在多个关注集合；
- 集合可按月份、交付窗口、专题、优先级或会议批次命名；
- 集合页沿用同一份任务数据和行动项，只保存筛选、排序、列配置和关注关系；
- 重点集合在交付中心提供固定入口和整体风险摘要。

## 6. 四类状态分离

| 维度 | 用途 | 示例 |
|---|---|---|
| 交付阶段 | 表示任务走到哪里 | 数据准备、生产中、标注中、验收中 |
| 健康状态 | 表示是否需要关注 | 正常、风险、阻塞、逾期 |
| 行动项状态 | 表示具体事项进展 | 待处理、进行中、已阻塞、已闭环 |
| 验收结论 | 表示质量判定 | PENDING、PASS、REJECT |

前端不得把四类语义合并成一个"状态"标签。用户需要同时知道任务处于哪个阶段、是否有风险、下一动作是什么以及验收结论是什么。

## 7. 交付时间判断

验收完成且结论通过才算交付。日常排期需要为验收保留时间；当前经验是标注完成后至少还需约 2 天完成验收。前端应并列展示：

- 目标交付时间；
- 预计标注完成时间；
- 预计验收完成时间；
- 当前验收预留时长；
- 预计交付相对目标的提前或延迟。

具体预测算法和口径尚未冻结，前端设计只要求展示这些语义，不在本卡虚构计算公式。

每个关键环节都需要倒排计划完成时间。任务风险不是单纯比较"预计交付"和"目标交付"，还要识别哪个环节已经偏离倒排计划，以及偏差是否会传导到最终交付。

## 8. 完成定义

人工质检完成不能只看验收流程结束。至少需要确认：

- 通过/打回执行及状态回查已完成；
- 验收通过中的 Good 数量能够形成最终交付量；
- 最终可交付 Good 数量与需求期望数量已对照；
- 使用的质检规范、视频/文本适配版本和关键记录已归档。

满足条件后任务"盖章完成"，默认退出活跃接纳、交付、标注和验收队列。留存率正式口径仍为 `[待人类补充]`。
