# 人工质检验收的当前未知与冲突

## 这套知识目前不能可靠回答什么

Batch 1 / K0 可以解释历史做法、目标设计和当前仓库原型；当前候选进一步补充了交付任务与行动项、人员权限、统一数据工作台的业务和目标设计边界，但不能作为生产操作手册。已有材料给出不同答案时，必须保留冲突并由相应负责人裁决；材料没有答案时，需要补充当前业务、Schema、接口或运行证据。

历史记录不会自动续期，目标方案不会自动变成实现，固定仓库实现也不等于生产部署。下面的问题正是当前候选仍需直接证据的边界。

## Batch 1 内部冲突

### 通过率分母

- 三阶段人工语义材料和快照设计要求以 `good_completed`、`bad_completed`、`acceptance_completed` 为分母，避免把未完成样本算成质量失败；
- 规则设计的“输入指标”段又写成“总通过数 / 总分配数”。

K0 不静默选一个。业务负责人需要确认“完成进度”和“质量通过率”分别采用什么分子分母；在确认前，任何页面数字都必须标明公式。

### 快照字段版本

- 当前 Repository 查询 `acceptance_submitted`、`good_passed`、`bad_passed`；
- 目标快照材料使用 `acceptance_completed`、`good_completed`、`bad_completed`，并描述另一套结论/执行字段；
- 固定迁移没有创建 `t_qc_daily_snapshot`。

因此，当前原型 SQL 依赖的真实表结构不在 Batch 1 中，不能声称端到端可运行。

### 历史规则与目标规则

历史材料保留 `> 0.9499`、`> 0.7999`、95% 完成度和两次回退调用；目标材料把它们整理为规则与执行组件，但仍把是否沿用列为待人决策。K0 只把具体数值标为历史细节。

## 当前生产事实未知

- 现网使用 Group、Personal、Ratio 还是其他采样策略？
- 当前阈值、等值边界、样本不足处理和执行粒度是什么？
- 外部任务系统的接口、认证、批量限制、返回和状态映射是什么？
- `waiting_review` 等历史状态值是否仍使用？
- 快照从哪里取数、多久刷新、如何判断新鲜度？
- 当前原型是否部署，连接哪个数据库，真实数据能否满足 SQL？

## 业务与产品的历史缺口及当前边界

Batch 1 / K0 曾不足以回答以下交付与运营问题；当前候选已补充它们的业务和目标设计边界，但以下现实口径与实现仍未被直接证实：

- 需求接纳、交付任务和行动项怎样形成一条可跟踪主线；
- 标注完成后以什么条件进入验收；
- 分配后怎样持续监控完成度、积压、人员和异常；
- 怎样分析低通过率究竟来自标注、验收、规则还是数据；
- 打回以后由谁跟踪剩余量、责任人、轮次和再次验收；
- 什么条件下可以判断最终可交付，以及预测口径如何计算。

当前候选还描述了人员/角色/权限和统一数据工作台的目标边界；它们仍不能证明对应页面、API、SSO、Schema 或端到端生产实现已经存在。

## 人员与公共能力的证据边界

- 当前候选的人员材料描述人员、组、供应商、角色、权限和历史有效期，但权威表、代码、SSO 与实际迁移是否部署仍未知；
- 数据库公共能力有当前代码，可以解释连接与事务；
- 当前候选定义统一数据工作台的交互和安全目标，但不能证明对应组件依赖、页面或部署已经存在；
- `src/obs/` 只有 `.gitkeep`，不能回答 OBS 客户端、路径、数据对象或维护责任。

## 补知责任与直接证据

| 责任方 | 需要的直接证据 |
|---|---|
| 业务负责人 | 当前阶段、质量公式、阈值、执行范围、返工和交付完成条件 |
| 验收运营负责人 | 当前分配、监控、分析和人员管理流程及真实案例 |
| 数据负责人 | 生产快照 DDL、样例、血缘、刷新时间和字段口径 |
| 外部系统负责人 | 当前接口、状态映射、测试环境和回查结果 |
| 原型维护者 | 部署状态、数据库初始化、端到端运行证据和后续实现边界 |
